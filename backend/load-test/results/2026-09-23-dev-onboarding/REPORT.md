## 0. 먼저 — 앞의 세 번은 옛 이미지에서 돌았다

테스트 준비로 Sentry 샘플링을 0으로 내리려고 `docker compose … up -d --no-build api` 를 쳤는데, **`API_IMAGE` 를 주지 않아 컨테이너가 서버에 남아 있던 2026-09-15 로컬 빌드 이미지(`ear-prod-api`)로 재생성됐다.** 에러가 없어 알아채지 못했고, 램프 A · A2 · "B" 는 그 옛 코드(클러스터 진입점·Sentry 없음) 위에서 돌았다. "B" 는 클러스터를 켰다고 믿었지만 단일 프로세스였다 — 파일을 `ramp-single-high-2` 로 바꿨다.

발견 뒤 `API_IMAGE=$(cat .api-image)` 로 현재 이미지(`85c41aa`, dev HEAD)를 띄워 **클러스터 2(B)** 와 **단일 프로세스(A3)** 를 다시 쟀다. 옛 이미지 결과는 버리지 않고 **코드 비교용**으로 남긴다 — 덕분에 현재 코드가 온보딩 경로에서 얼마나 무거워졌는지가 드러났다(3장). 재발 방지는 `docs/infra/runbook.md` 4장.

## 1. 한 줄 결론

**현재 코드 기준, 가입 몰림은 단일 프로세스에서 분당 약 600명, 클러스터 2에서 약 900명까지 지연 없이 받는다.** 그 위로는 응답이 길어질 뿐 **실패는 0 이다**(분당 1,600명까지 5xx·429 없음, 온보딩 완료 100%). 광고 규모(설치 수천 건/캠페인)와는 두 자릿수 차이라 **가입 경로는 캠페인의 병목이 아니다.**

다만 **온보딩 경로가 2026-09-15 빌드보다 약 1.7배 무거워졌다** — 같은 분당 600명에서 API CPU 50% → 70~93%. 어느 변경 때문인지는 프로파일링이 필요하다(3장, BE 티켓 감).

## 2-3. 원인 판정 — Sentry 계측이다 (같은 날 추가 실측)

3장 2번의 "프로파일링 대상"을 같은 날 갈라 냈다. 현재 이미지·단일 프로세스·**분당 600명 고정 2분**으로 Sentry 만 바꿔 가며 쟀다(`fixed600-*.json`).

| 구성 | API CPU | 전체 p95 | 완료 요청 p95 | 첫 드립 대기 p95 | 2분간 완료 가입 |
|---|---|---|---|---|---|
| **Sentry 없음**(`SENTRY_DSN` 비움) | **43~54%** | 51ms | 76ms | 1.09s | 1,349 |
| Sentry + `tracesSampleRate=0` (램프 A3 첫 구간) | 70~93% | 초 단위 | — | — | — |
| **Sentry + `tracesSampleRate=0.5`**(개발계 설정 그대로) | **100~140%** | 14.0s | 14.4s | 26.7s | 1,060 (드롭 289) |
| 2026-09-15 빌드(Sentry 이전, 램프 A2 첫 구간) | 49~54% | — | — | — | — |
| **수정 뒤(PR #666 배포, Sentry ON, 추적 env 삭제)** — 20:30 | **50~80%**(평균 약 60%) | 80ms | 130ms | 1.16s | 1,349 (드롭 0, 체크 12,141/12,141) |

- Sentry 를 빼면 **09-15 빌드와 같은 수치**로 돌아온다 — 코드 회귀가 아니라 계측 비용이다.
- 원인은 `instrument.ts` 가 `tracesSampleRate: Number(env ?? 0)` 으로 **0 을 SDK 에 넘긴 것.** Sentry Node SDK 는 값이 있기만 하면(`hasSpansEnabled`: `!= null`) 스팬을 켠 것으로 보고 express·nest·pg 성능 계측과 diagnostics-channel 주입을 전부 등록한다. 표본 0 이라 아무것도 보내지 않으면서 CPU 만 썼다. 0.5 면 거기에 트랜잭션 조립·전송이 더해져 한 코어를 넘긴다(GC·전송 스레드).
- **수정: PR #666(KAN-93)** — env 가 비었거나 0 이면 키를 빼서 계측을 등록하지 않는다. 운영은 성능 추적을 켜지 않는다(종전 계획 0.05~0.1 폐기). **dev 배포 뒤 재측정(20:30, 위 표 마지막 행): API CPU 100~140% → 50~80%, 완료 요청 p95 14.4s → 130ms, 첫 드립 대기 26.7s → 1.16s, 처리한 가입 1,060 → 1,349(= Sentry 없음과 같음).** "Sentry 없음"(43~54%) 대비 10~20%p 남는 것은 에러 수집용 http·nest 계측(요청 격리)의 몫이다 — 감수한다. 개발계 `.env.prod` 의 추적 줄은 지웠다(결정 2026-09-23 — 어드민 서버 상태 그래프는 Sentry 와 무관하게 남는다).
- 온보딩만 잰 것이지만 계측은 전 요청에 걸리므로 **청취 경로도 같은 만큼 무거워져 있었다**고 봐야 한다(2026-09-22 청취 램프는 Sentry 이전 이미지였다). 수정 뒤 청취 램프도 한 번 다시 잰다.

## 3. 그래서 무엇을 하는가

1. **광고 대비로는 충분하다.** 분당 600명(시간당 3.6만)은 캠페인 규모를 한참 넘는다. 순간 스파이크(인플루언서 게시 등)에서도 실패가 아니라 지연으로 무너지고, 첫 드립은 늦게라도 전부 완료된다.
2. ~~온보딩 경로 회귀를 BE 티켓으로 잰다.~~ → **같은 날 판정: Sentry `tracesSampleRate=0` 이 성능 계측을 전부 켠 것(2-3). PR #666·KAN-93 으로 수정.** dev 배포 뒤 재측정 + 청취 램프 재측정.
3. **운영 클러스터링 결정은 그대로다.** 온보딩에서도 1.3~1.4배. 켜기 전 `dev → main` 릴리즈(#586 레이트 리밋)가 먼저다(`scaling.md` 5.4).
4. **재생성 함정을 막았다.** `API_IMAGE` 없는 재생성이 옛 이미지로 빠지는 문제 — runbook 4장에 적었고 개발계의 옛 로컬 이미지는 지웠다(운영은 이날 image prune 으로 이미 없음).
