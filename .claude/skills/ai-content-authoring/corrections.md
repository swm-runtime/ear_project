# 교정쌍 — 어색한 문장과 실제로 하는 말

대본을 뽑은 뒤 **어색한 줄 3~5개**를 여기에 쌓는다. 이 스킬에서 사람 손이 필요한 곳은 여기 하나다.

## 왜 이 방식인가

"자연스럽게 쓰라"는 지시는 작동하지 않는다. 생성 쪽에 한국어 문장을 듣는 귀가 없어서, 문법에 맞는지는 판정해도 **한국인이 실제로 그렇게 말하는지는 판정하지 못한다.** 규칙을 산문으로 더 적어도 결과는 같은 자리로 돌아온다.

교정쌍은 그 판정을 밖에서 들여온다. **설명하지 말고 고쳐 쓴 문장을 보여주는 쪽이 훨씬 강하다.**

[`check.py`](scripts/check.py)와 역할이 갈린다.

| | 잡는 것 | 못 잡는 것 |
|---|---|---|
| `check.py` | 셀 수 있는 것 — 어미 비율, 완충어 빈도, 문장 길이 | 셀 수 없는 것 |
| 교정쌍 | 세지 못하는 어색함 — 어순, 호흡, 안 쓰는 표현 | 전수 검사 |

## 쓰는 법

- **고친 문장만 적는다.** 이유는 안 적어도 된다. 필요하면 한 줄 메모로 충분하다
- **원문을 그대로 옮긴다.** 다듬어서 적으면 무엇이 문제였는지 사라진다
- **완벽하지 않아도 넣는다.** 스무 개쯤 쌓이면 공통 패턴이 드러난다
- 20개를 넘기면 유형별로 묶는다

## 진행 상황

| 항목 | 값 |
|---|---|
| 누적 교정쌍 | 3건 (전부 **미검증**) |
| 목표 | 20건 — 이때 `writing-rules.md`에 반영한다 |
| 마지막 갱신 | 2026-08-14 |

> **아래 3건은 전부 생성 쪽이 혼자 만든 것이라 ✓가 맞는지 확인되지 않았다.** `check.py`가 잡아낸 지표에서 기계적으로 뒤집은 것이고, 실제 한국인이 그렇게 말하는지는 별개다. **검토해서 고치거나 지워야 시드로 쓸 수 있다.**

## 교정쌍

### 1. 정의를 문어체로 던진다 · 미검증

```
✗ 이 과정에 붙은 이름이 예측 부호화, 영어로는 predictive coding입니다.
✓ 이걸 뭐라고 부르냐면요, 예측 부호화라고 해요.
```

메모 — 명사구로 끊고 `입니다`로 닫는 건 발표 문체다. 말로는 앞에 도입을 깔고 간다.

### 2. 번역투 명사화 · 미검증

```
✗ 진짜 흥미로운 건 그 두 놀람이 서로 다른 종류의 반응이라는 것입니다.
✓ 근데 그 두 놀람이 좀 다른 반응이거든요. 그게 재밌어요.
```

메모 — `~라는 것입니다`는 영어 원문을 보면서 쓸 때 나온다. `check.py`가 잡는 표현이다.

### 3. 완충어를 전부 뺐다 · 미검증

```
✗ 다음 소리를 맞히기 쉬우면 앞소리를 금방 놓고 넘어갑니다.
✓ 다음 소리를 맞히기 쉬우면요, 앞소리를 그냥 좀 금방 놓고 넘어가요.
```

메모 — 측정상 완충어가 corpus의 1/13이었다. 다만 **낭독 대본에 구어 완충어를 어디까지 넣는 게 맞는지는 미정**이다. 실제 대화를 그대로 옮기면 TTS에서 지저분할 수 있다.

## 반영 경로

교정쌍은 여기 쌓이기만 하고 저절로 적용되지 않는다.

1. **10건** — 대본 쓸 때 이 파일을 같이 읽는다
2. **20건** — 반복되는 패턴을 [`reference/writing-rules.md`](reference/writing-rules.md)의 "대사 쓰기"에 규칙으로 올린다. 셀 수 있는 것으로 바뀌면 `check.py`에 넣는다
3. 규칙으로 올라간 교정쌍도 **지우지 않는다.** 예시가 규칙보다 강하다

`writing-rules.md`는 [`docs/ai/pipeline.md`](../../../docs/ai/pipeline.md)의 구현이다. **명세와 어긋나는 규칙을 여기서 만들지 않는다** — 명세를 고쳐야 하면 [`docs/changes/pending/`](../../../docs/changes/pending/)에 올린다.
