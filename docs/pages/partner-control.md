# 파트너 통제 · 리포팅 기능 명세서

> 연결 PRD: FR-32, FR-33, FR-34 / 비기능(저작권·파트너 계약 준수) / 리스크 8.3 / 사용자흐름 5.6

## 1. 목적 & 연결

파트너가 자기 콘텐츠를 통제할 수 있게 보장한다. **파트너십은 서비스 신뢰의 축**(PRD 1.3)이며, 회수 요청을 즉시 반영하지 못하면 계약 위반이 된다. 이 기능은 UX가 아니라 **계약 이행 수단**이다.

- FR-32 (P0) 파트너의 콘텐츠 단위 제외 지정·검수·회수 요청 지원. 회수는 **전 노출면(라이브러리·탐색·드립·저장분)에서 즉시 반영**
- FR-33 (P0) 협의된 범위·기간 내에서만 제공, 무단 재배포·다운로드 방지 접근 통제
- FR-34 (P1) 재생·완청·원문 유입 등 성과 데이터 집계 → 파트너 리포팅·정산 연동 검증
- PRD 8.3 리스크 — 콘텐츠 무단 복제, 원문 소비 감소

## 2. 진입 조건

| 트리거 | 경로 |
|---|---|
| 사전 제외 지정 | 파트너가 원문 목록에서 특정 콘텐츠를 오디오화 대상에서 제외 |
| 발행 전 검수 | 파트너가 발행 대기 콘텐츠의 대본·오디오를 확인하고 승인/반려 |
| 회수 요청 | 파트너가 이미 발행된 콘텐츠의 제공 중단을 요청 |
| 라이선스 만료 | 계약 기간 종료 시 자동 |
| 리포팅 조회 | 파트너가 성과 데이터를 조회 (FR-34) |

**MVP에서는 파트너 포털을 만들지 않고 운영자 대행으로 처리할 수 있다** — 단 회수 반영 로직 자체는 P0이므로 반드시 구현한다(미결 사항 참조).

## 3. 입력값

**제외 지정 / 회수 요청**

| 값 | 설명 | 필수 |
|---|---|---|
| partner_id | 요청 주체 | 필수 |
| target: content_id[] 또는 external_id[] | 대상 콘텐츠 | 필수 |
| action | exclude(사전 제외) / withdraw(회수) / restore(복구) | 필수 |
| reason | 사유(계약 범위 이탈, 저자 요청, 원문 삭제 등) | 선택 |
| effective_at | 적용 시점(기본 즉시) | 선택 |
| requested_by | 요청자(파트너 담당자 또는 대행 운영자) | 필수 |

**검수 결과**

| 값 | 설명 | 필수 |
|---|---|---|
| content_id | 검수 대상 | 필수 |
| result | approved / rejected | 필수 |
| reject_reason | 반려 사유 | 반려 시 필수 |

## 4. 처리 로직

### 4.1 사전 제외 지정

- 파트너가 원문 단위로 오디오화 제외를 지정하면 `content_control_requests(action = exclude)`로 기록한다
- **MVP에는 파이프라인이 없으므로**(`content-pipeline.md` 범위 상태) 제외 지정은 "이 원문은 제작 대상에서 뺀다"는 운영 지시로 처리한다. 제작 착수 전 목록에서 제거한다
- 이미 발행된 뒤라면 회수(4.3)와 동일하게 처리한다

### 4.2 발행 전 검수 — **MVP 범위 제외**

~~파트너 검수 대기 상태~~ → **폐기됐다.** 관리자 업로드 = 즉시 발행 구조(FR-37)이므로 `Content.status`에 `partner_review`가 없고 `PartnerReview` 테이블도 만들지 않는다(`domain.md` 14장).

- MVP에서 파트너 검수가 필요하면 **발행 전 단계, 즉 업로드 전에 운영자가 파트너와 오프라인으로 처리한다.** 시스템 상태로 관리하지 않는다.
- 파트너 계약상 검수가 필수로 확정되면 그때 `Content.status`에 검수 대기 상태와 `PartnerReview`를 함께 도입한다(PRD 4.2).

### 4.3 회수 (FR-32) — 이 명세의 핵심

회수는 **전 노출면에서 즉시 반영**되어야 한다. 노출면을 빠짐없이 열거한다.

| 노출면 | 반영 방법 | 시점 |
|---|---|---|
| 카탈로그 | `contents.status = withdrawn` + `withdrawn_at` | 즉시 |
| 탐색 피드·검색 | 조회 쿼리에서 `status = published`만 반환 | 즉시(다음 조회부터) |
| 드립 편성 후보 | 후보 필터에서 제외 | 즉시(다음 배치부터) |
| **이미 적립된 라이브러리** | 해당 `library_items` 제거 | 즉시(서버에서 삭제) |
| **재생 중인 세션** | 오디오 서명 URL 발급 차단. 진행 중 재생은 버퍼 소진 시 중단 | 즉시 |
| **오프라인 저장분** *(P1 — FR-26 이연)* | 회수 목록 동기화로 로컬 파일 삭제 | 기기가 온라인 될 때 |
| 푸시 발송 대기열 | 발송 직전 유효성 재확인으로 제외 | 즉시 |
| 스크립트 | 조회 차단 | 즉시 |

**처리 순서**

1. `contents.status = withdrawn`, `withdrawn_at` 기록
2. 오디오 서명 URL 발급을 즉시 차단 (신규 발급 중단 + 기존 발급분은 짧은 만료로 자연 소멸)
3. `library_items` 일괄 삭제 (해당 콘텐츠를 가진 전체 사용자)
4. 캐시(탐색 피드, 추천) 무효화
5. 오프라인 회수 목록에 추가 → 클라이언트가 앱 실행·포그라운드 복귀 시 동기화
6. 회수 처리 결과를 감사 로그에 기록

**클라이언트 노출**: 사용자에게는 "제공이 종료된 콘텐츠예요"로만 안내한다. 파트너·계약 사정을 노출하지 않는다.

**되돌리기**: `restore` 요청 시 `status = published`로 복구한다. 단 **삭제된 `library_items`는 복구하지 않는다**(사용자 라이브러리를 임의로 되살리지 않음). 담기로는 다시 들어올 수 있으나, 드립으로는 다시 오지 않는다 — 회수로 삭제된 시점에 `drip_excluded_contents`에 남기 때문이다.

**클라이언트 동기화**: 회수 목록은 별도 테이블 없이 `GET /contents/withdrawn?since=<timestamp>`로 `contents`에서 조회한다(`domain.md` 14장).

### 4.4 라이선스 범위·기간 통제 (FR-33)

- 라이선스 만료일은 `contents.license_expires_at`에 보관한다. `SourceDocument`는 폐기됐으므로 발행 시점에 콘텐츠 행에 직접 기록한다
- **발행 게이트**: 허용되지 않거나 기간 밖이면 업로드를 거부한다(관리자 업로드 검증 — `admin.md`)
- **만료 자동 처리**: 만료일이 지나면 배치가 `status = expired`로 전환하고 회수와 동일한 노출 제외를 수행한다
  - 단 만료는 회수와 달리 `LibraryItem`을 즉시 삭제할지 여부가 계약에 따라 다를 수 있다 → 미결 사항

### 4.5 재배포·다운로드 방지 (FR-33)

| 대상 | 통제 |
|---|---|
| 오디오 파일 | 스토리지 직접 접근 차단. **단기 만료 서명 URL로만 제공** |
| 서명 URL | 사용자·기기 단위 발급, 발급 이력 기록, 만료 시간 짧게 |
| 클라이언트 캐시 | 앱 전용 저장소, 외부 접근·백업 제외 |
| 오프라인 저장 | 암호화 저장소 한정, 파일 내보내기 금지 (`offline-download.md`) |
| 스크립트 | 텍스트 복사·선택 차단 |
| 공유 | 오디오 파일이 아니라 **스토어 링크만** 공유 (`explore.md` 4.6) |
| 이상 접근 탐지 | 단시간 대량 서명 URL 발급 등 비정상 패턴 탐지·차단 |

### 4.6 성과 리포팅 (FR-34, P1)

파트너에게 제공하는 집계 지표.

| 지표 | 원천 |
|---|---|
| 재생 수 | `content_stats.play_count` |
| 완청 수·완청률 | `complete_count` / `play_count` — **비율은 저장하지 않고 조회 시 계산한다**(비율은 합산이 불가능하므로) |
| 총 청취 시간 | `content_stats.total_listen_sec` ← `play_records.listened_sec` 합계. **도달 위치가 아니라 실제 재생된 시간**이다 |
| 담기 수 | `content_stats.save_count` |
| **원문 유입 수** | `content_stats.source_link_click_count` — PRD 8.3 "원문 소비 감소" 리스크 대응 지표 |
| 기간별 추이 | **주간·월간·전체** 3단위 (`period_type`) |

**집계 규칙**

- 갱신 주기: 주간은 매주 월요일 04:00, 월간은 매달 1일 04:00. 하루의 경계는 자정이 아니라 **04:00 KST**다(페이월 카운트와 같은 경계를 써야 숫자가 어긋나지 않는다).
- **직전 확정 구간의 값으로 리포팅한다.** 5월에는 4월 집계를 보여준다. 진행 중인 구간은 표본이 부족해 순위가 무너진다.
- 구간이 끝나면 `is_final = true`로 잠그고, **정산·리포팅은 확정된 행만 읽는다.** 돈이 나간 근거이므로 나중에 조회할 때 값이 달라지면 안 된다.
- `PartnerReport` 별도 테이블은 만들지 않는다. `content_stats` 집계 + `contents.partner_id` 필터로 산출한다 — 같은 숫자를 두 곳에서 집계하면 정산 분쟁이 된다.

- **개인 식별 정보를 절대 포함하지 않는다.** 집계값만 제공한다
- 정산 연동 검증(PRD 10 "재생·완청 데이터의 저자 정산 구조 정합 검증")을 위해 원천 로그와 집계값이 재현 가능해야 한다
- 파트너 정산은 **구독 매출 % 풀 방식**(PRD 7)이므로, 리포팅은 풀 배분 근거(재생 점유율)를 계산할 수 있는 형태여야 한다

## 5. 상태 전이 · 운영 노출

**콘텐츠 상태(파트너 통제 관점)**

```
qa_passed ──(검수 요구 파트너)──→ partner_review ──approved──→ published
                                        └──rejected──→ discarded / 재생성
qa_passed ──(무검수 파트너)────────────────────────────→ published

published ──withdraw──→ withdrawn ──restore──→ published
          ──라이선스 만료──→ expired
```

**파트너 포털(또는 운영자 대행 콘솔)**

| 화면 | 내용 |
|---|---|
| 콘텐츠 목록 | 파트너 소유 콘텐츠, 상태·발행일 필터, [제외] / [회수] |
| 검수 대기 | 대본·오디오 미리듣기, [승인] / [반려](사유 입력) |
| 회수 이력 | 요청 시각·처리 시각·대상 건수·처리 결과 |
| 리포팅 (P1) | 기간별 재생·완청·원문 유입 지표, CSV 내보내기 |

**사용자 앱에서의 표현**

| 상황 | 표현 |
|---|---|
| 라이브러리에 있던 콘텐츠가 회수됨 | 새로고침 시 조용히 사라짐. 별도 알림 없음 |
| 회수된 콘텐츠 재생 시도 | "제공이 종료된 콘텐츠예요" + 목록에서 제거 |
| 재생 중 회수됨 | 현재 재생은 버퍼 소진까지 유지, 이후 재생 불가 안내 |
| 오프라인 저장분 회수 | 온라인 동기화 시 조용히 삭제 |

## 6. 데이터 모델

> **스키마는 [`docs/backend/domain.md`](../backend/domain.md)가 유일한 기준이다.** 이 문서에 테이블·컬럼을 중복 기재하지 않는다 — 두 벌을 유지하면 반드시 어긋나고, 수정 비용이 두 배가 된다.
> 컬럼을 추가·변경해야 하면 `domain.md`를 먼저 고치고 이 문서에는 동작 규칙만 남긴다.

| 사용하는 것 | domain.md |
|---|---|
| `partners` — `status: active \| suspended \| terminated` | 10.1 |
| `content_control_requests` — 제외·회수·복구 요청 이력 | 10.2 |
| `audit_logs` | 10.3 |
| `contents` — `status = withdrawn` + `withdrawn_at`이 회수 상태의 원천 | 5.1 |
| `audio_access_logs` — 이상 접근 탐지 | 6.5 |
| `content_stats` — 성과 리포팅(P1) | 5.4 |

- `PartnerReview`는 **폐기됐다.** 업로드 즉시 발행 구조라 발행 전 검수 상태가 존재하지 않는다.
- `WithdrawnContent` 별도 테이블도 없다. `contents`에서 조회한다.
- `PartnerReport` 별도 테이블도 없다. `content_stats` 집계 + `contents.partner_id` 필터로 산출한다.

## 7. 예외 상황

- **회수 요청 시 대상 콘텐츠가 이미 회수됨**: 멱등 처리. 성공으로 응답한다.
- **회수 대상이 수천 명의 라이브러리에 있음**: `LibraryItem` 삭제를 비동기 배치로 처리하되, **노출 차단(카탈로그·서명 URL)은 동기로 즉시** 수행한다. 배치가 끝나기 전에도 재생은 불가능해야 한다.
- **회수 처리 중 일부 노출면 반영 실패**: `applied_surfaces`로 어디까지 됐는지 기록하고 실패분을 재시도한다. **부분 반영 상태를 성공으로 보고하지 않는다.**
- **오프라인 저장분을 가진 기기가 장기간 오프라인**: 즉시 삭제가 물리적으로 불가능하다. 오프라인 라이선스 유효 기간(30일 상한)으로 노출 상한을 관리하고, 이 한계를 **파트너 계약서에 명시**해야 한다.
- **재생 중인 사용자**: 진행 중 스트림을 강제 종료하면 UX가 나쁘다. 신규 서명 URL 발급만 차단하고 현재 버퍼까지는 재생을 허용한다. 이 정책도 계약상 허용 범위인지 확인이 필요하다.
- **검수 반려 후 재생성한 콘텐츠**: 다시 검수 대기 상태로 들어간다. 자동 발행하지 않는다.
- **검수 SLA(7일) 초과**: 자동 승인하지 않는다. 운영자가 파트너에게 확인한다.
- **파트너 계약 전체 종료**: 해당 파트너의 모든 발행 콘텐츠를 일괄 회수한다.
- **AI 생성 콘텐츠에 대한 회수 요청**: 파트너 콘텐츠가 아니므로 파트너 통제 대상이 아니다. 다만 소스 권리자의 이의 제기는 별도 프로세스로 처리한다(미결 사항).
- **복구(restore) 후 사용자 라이브러리**: 복구하지 않는다. 사용자에게는 새 콘텐츠처럼 보인다.
- **리포팅 집계와 원천 로그 불일치**: 정산 근거가 흔들리므로 재집계 가능해야 한다. 집계는 원천 로그를 지우지 않고 별도 저장한다.

## 8. 완료 조건

- Given 파트너가 특정 콘텐츠 회수를 요청한다 / When 요청이 처리된다 / Then 탐색·검색·드립 후보에서 즉시 제외된다
- Given 회수된 콘텐츠가 여러 사용자의 라이브러리에 있다 / When 회수가 처리된다 / Then 모든 사용자의 라이브러리에서 제거된다
- Given 회수된 콘텐츠 / When 사용자가 재생을 시도한다 / Then 서명 URL이 발급되지 않고 제공 종료 안내가 노출된다
- Given 회수된 콘텐츠를 오프라인 저장한 기기 / When 기기가 온라인 상태가 된다 / Then 로컬 저장 파일이 삭제된다
- Given 회수 요청이 접수된다 / When 라이브러리 삭제 배치가 아직 진행 중이다 / Then 그 시점에도 해당 콘텐츠는 재생할 수 없다
- Given 검수를 요구하는 파트너의 콘텐츠 / When QA를 통과한다 / Then 자동 발행되지 않고 검수 대기 상태가 된다
- Given 파트너가 검수에서 반려한다 / When 반려가 처리된다 / Then 콘텐츠가 발행되지 않고 반려 사유가 기록된다
- Given 라이선스 기간이 만료된다 / When 만료 배치가 실행된다 / Then 해당 콘텐츠가 모든 노출면에서 제외된다
- Given 오디오 파일의 스토리지 경로 / When 서명 없이 직접 접근을 시도한다 / Then 접근이 거부된다
- Given 파트너 콘텐츠가 100회 재생되고 60회 완청되었다 / When 리포팅을 조회한다 / Then 재생 100·완청 60·완청률 60%가 개인 식별 정보 없이 집계되어 표시된다
- Given 사용자가 플레이어에서 [원문 보기]를 탭했다 / When 리포팅을 조회한다 / Then 원문 유입 수에 집계된다
- Given 같은 회수 요청이 두 번 접수된다 / When 두 번째 요청이 처리된다 / Then 오류 없이 멱등하게 처리된다

## 미결 사항

- **파트너 포털 구축 여부** — MVP 2주 일정(PRD 8.1)에서 파트너용 웹 포털까지 만들 여력이 있는지. 대안은 운영자 대행 + 내부 콘솔. **회수 반영 로직 자체는 P0이므로 반드시 구현**
- 라이선스 만료 시 이미 적립된 `LibraryItem` 처리 — 회수와 동일하게 삭제할지, 만료 전까지 들은 것은 남길지 (계약 조건에 종속)
- 재생 중 회수 시 강제 중단 여부 — 계약상 허용 범위 확인 필요
- 오프라인 저장분의 회수 반영 지연(최대 30일)을 계약서에 어떻게 명시할지
- 리포팅 제공 주기·형식(대시보드 / 정기 CSV / API) 확정
- AI 생성 콘텐츠에 대한 제3자 권리 이의 제기 프로세스 — 현재 미정의
- FR-34는 P1 — MVP 제외 시에도 **원천 로그 수집은 시작해야 한다**(나중에 소급 집계가 불가능하므로)
