## 1. 범위

`career.md`가 정의한 동작을 HTTP 계약으로 옮긴 문서다. 다루는 것은 다음 셋이다.

- 커리어 현재 값 조회 — 직군·직무·연차 3필드
- 커리어 저장 — **3필드 전체 전송·전체 교체**, 빈 값(미입력) 저장 허용, last-write-wins
- 직군 선택지 목록 조회 — **서버 제공, 온보딩과 공용**(확정 2026-08-10 — `career.md` 미결 확정 표)

**이 문서는 동작 규칙을 새로 정하지 않는다.** 규칙이 충돌하면 `career.md`가 기준이며, 이 문서는 그것을 요청·응답으로 표현할 뿐이다. 스키마는 `domain.md`가 유일한 기준이다.

**다루지 않는 것** — 경계를 먼저 못 박는다.

| 대상 | 소유 문서 | 이 문서에서 하는 일 |
|---|---|---|
| [초기화] 버튼 | `career.md` 4.1 | **아무것도 하지 않는다.** 저장 전의 로컬 편집 조작이라 서버 계약이 아니다. 초기화 후 [저장]하면 4.2에 세 `null`이 실려 올 뿐이다 |
| 온보딩 2단계의 커리어 입력·건너뛰기 | `onboarding-api.md` 4.4 | 참조만 한다. 온보딩은 저장과 함께 `onboarding_step`을 전진시키는 별도 계약이다(3장 설계 메모) |
| 프로필·설정의 커리어 요약 표시 | `profile-api.md` 4.1 · `settings.md` 4.1 | 요약 조회를 정의하지 않는다. 저장 후 복귀 시 재조회는 각 화면 소관이다 |
| 추천 랭킹의 커리어 가점 계산 | `drip-scheduling.md` 4.2 | 저장이 즉시 반영되는 **보조 신호**라는 사실만 참조한다. 가점 방식을 정의하지 않는다 |
| 뒤로가기 확인 팝업·저장 토스트 문구 | `career.md` 5장 · uiux | 화면 상태·카피를 정의하지 않는다 |

## 2. 공통 규약

| 항목 | 값 |
|---|---|
| Base URL | `/api/v1` |
| 인증 헤더 | `Authorization: Bearer <access_token>` — 이 문서의 **모든 엔드포인트가 인증 필요** |
| 요청·응답 필드 | **snake_case** |
| 시각 | **ISO 8601 UTC 문자열** (epoch 정수 금지) |
| 추적 | 모든 응답에 `X-Trace-Id` |
| 멱등키 | **이 문서에는 `Idempotency-Key`가 필요한 엔드포인트가 없다**(3장 설계 메모) |

- 성공 응답에 `success: true` 같은 공통 봉투를 씌우지 않는다. **성공은 HTTP 상태로, 실패는 에러 규격으로 판단한다.**
- 에러 응답은 `architecture.md` 7.4 규격을 따른다.

```json
{
  "error_code": "VALIDATION_FAILED",
  "message": "입력값을 확인해주세요",
  "retryable": false,
  "retry_after_sec": null,
  "trace_id": "01H8X..."
}
```

**커리어 3필드 — 값 표현 규약**

온보딩 커리어 단계(`onboarding-api.md` 4.4)와 **같은 값 체계·같은 표현**을 쓴다. 두 화면이 같은 `users` 컬럼에 쓰기 때문이며, 표현이 다르면 같은 컬럼에 다른 값 체계가 쌓인다(`career.md` 3장).

| 필드 | 타입 | 표현 |
|---|---|---|
| `job_category` | string \| null | 직군. **4.3 목록의 `name` 값 중 하나.** 길이 상한 50자 |
| `job_title` | string \| null | 직무. **자유 입력**(확정 2026-08-09), 길이 상한 **100자** |
| `years_of_experience` | enum \| null | 구간 라벨 `"0-1"` / `"2-3"` / `"4-6"` / `"7+"`. **정수 연차를 주고받지 않는다** |

- **미입력은 `null`이다.** 세 값 모두 선택 입력이므로 어느 필드든 `null`일 수 있고, 셋 다 `null`이면 미입력 사용자다(`profile-api.md` 4.1과 같은 규약).
- **빈 문자열을 미입력 표현으로 쓰지 않는다.** 비움은 `null`로 보낸다. 빈 문자열·공백만인 값이 오면 서버가 `null`로 정규화해 저장한다 — 미입력 판정(프로필 카드의 "입력하면 추천이 정확해져요" 분기)이 `null` 하나로 수렴해야 하며, `""`과 `null` 두 표현이 공존하면 그 분기가 화면마다 갈라진다.
- `years_of_experience`는 구간 라벨로 주고받고, **서버가 `users.years_of_experience`(int)에 구간 하한값(`0` / `2` / `4` / `7`)으로 환산해 저장한다**(`onboarding-api.md` 4.4와 동일). 컬럼 타입과 구간 enum의 불일치는 `domain.md` 15.1 #4 **미결**이다 — 이 계약은 라벨을 확정값으로 쓰며, 저장 매핑이 어떻게 확정되든 전송 표현은 바뀌지 않는다(9장).

**서버가 받지 않는 값**

- **클라이언트가 보낸 `user_id`·티어를 신뢰하지 않는다.** 대상은 언제나 토큰의 사용자다(`architecture.md` 9.2).
- **"변경 있음" 여부를 요청에 싣지 않는다.** [저장] 활성 조건은 화면 규칙이고(`career.md` 4.1), 서버는 받은 3필드를 그대로 저장할 뿐이다. 변경 없는 본문이 와도 거부하지 않는다 — 결과가 같으므로 실패시킬 이유가 없다.

## 3. 엔드포인트 목록

| # | 메서드 | 경로 | 설명 | 인증 | 멱등키 |
|---|---|---|---|---|---|
| 1 | GET | `/users/me/career` | 커리어 현재 값 조회 | 필요 | |
| 2 | PUT | `/users/me/career` | 커리어 저장 — 3필드 전체 교체 | 필요 | |
| 3 | GET | `/job-categories` | 직군 선택지 목록 — **온보딩과 공용** | 필요 | |

**설계 메모**

- **온보딩의 `PATCH /onboarding/career`를 재사용하지 않는다.** 그 엔드포인트는 저장과 동시에 `onboarding_step`을 `pick`으로 전진시키는 **상태 전이**다(`onboarding-api.md` 3장 설계 메모). 완료 후의 커리어 수정에 그 부수 효과가 붙으면 수정할 때마다 재개 지점이 움직인다. 온보딩 쪽도 같은 이유로 완료 계정의 호출을 409로 거부한다 — 두 화면은 같은 컬럼을 쓰지만 계약은 분리한다.
- **저장이 PATCH가 아니라 PUT(전체 교체)인 이유**: 이 화면은 폼 전체를 그려놓고 [저장]에서 일괄 반영한다(`career.md` 4.1 — 시트 선택도 저장 전에는 반영되지 않는다). 화면이 보여주는 3필드가 곧 저장될 전부이므로 **화면 상태 = 요청 본문 = 저장 결과**가 되는 전체 교체가 맞다.
  - PATCH의 "본문에 없는 필드는 유지" 의미를 여기 쓰면, 여러 기기 동시 편집에서 필드 단위로 병합된 — **어느 기기의 화면에도 없던** — 결과가 만들어진다. `career.md` 7의 last-write-wins는 "마지막에 저장한 **화면**이 최종"이라는 뜻이고, 전체 교체가 그것을 그대로 구현한다.
  - [초기화] 후 저장(세 `null` 전송)도 별도 규칙 없이 같은 계약으로 표현된다.
- **`Idempotency-Key`를 쓰지 않는다.** PUT 전체 교체는 같은 본문을 두 번 보내도 결과가 같다(`PUT /onboarding/interests`와 같은 성질 — `onboarding-api.md` 3장). 따라서 타임아웃·5xx 시 `common-error-handling.md` 4.2의 자동 재시도 대상이다.
- **직군 목록(3)을 `/onboarding` 아래나 `/users/me` 아래에 두지 않는다.** 온보딩 2단계와 커리어 정보 화면이 **같은 목록**을 써야 하고(확정 2026-08-10 — 클라이언트 상수 금지), 사용자별로 다르지 않은 참조 데이터다. 온보딩 경로에 두면 온보딩 완료 계정의 접근이 어색해지고, `me` 아래에 두면 개인화된 값처럼 읽힌다.
  - `onboarding-api.md`에는 목록 엔드포인트가 없다(그 문서는 목록 원천 확정 전에 작성됐다). **공용 목록의 계약은 이 문서 4.3이 소유하며, 온보딩 2단계 화면도 이 엔드포인트를 호출한다.**
- **조회(1)에 프로필 요약(`GET /users/me/profile`)을 재사용하지 않는다.** 프로필 응답은 통계 3영역까지 실은 무거운 조회이고(`profile-api.md` 4.1), 설정 경로로 진입하면 프로필을 거치지도 않는다. 편집 화면은 3필드만 필요하다.

## 4. 엔드포인트 상세

### 4.1 `GET /users/me/career`

화면 진입 시 현재 값을 조회한다. `career.md` 5장의 로딩 → 정상(입력됨)/미입력 분기가 이 응답으로 결정된다.

**Response 200**

```json
{
  "job_category": "기획·PM",
  "job_title": "서비스 기획자",
  "years_of_experience": "4-6"
}
```

**Response 200 — 미입력 사용자**

```json
{
  "job_category": null,
  "job_title": null,
  "years_of_experience": null
}
```

- **미입력을 404로 응답하지 않는다.** 온보딩에서 건너뛴 사용자에게 미입력은 정상 상태이고, 클라이언트는 빈 폼 + 유도 문구를 그린다(`career.md` 5장). 자기 계정 행이 없는 상황은 조회 실패가 아니라 인증 실패다.
- **조회 실패는 화면 진입 차단형이다.** 전체 화면 에러 + [다시 시도]로 처리하고 캐시로 대체하지 않는다(`common-error-handling.md` 4.3) — 낡은 값을 폼에 채우면 그 위에서 편집한 저장이 다른 기기의 최신 값을 조용히 덮는다.

---

### 4.2 `PUT /users/me/career`

[저장] 탭 시점에 호출한다. **3필드를 전부 실어 보내고, 서버는 받은 그대로 전체 교체한다.**

**Request**

```json
{
  "job_category": "기획·PM",
  "job_title": "서비스 기획자",
  "years_of_experience": "4-6"
}
```

| 필드 | 타입 | 필수 | 비고 |
|---|---|---|---|
| `job_category` | string \| null | **키 필수** | 4.3 목록의 `name` 값 중 하나, 또는 `null`(선택 안 함). 길이 상한 50자 |
| `job_title` | string \| null | **키 필수** | 자유 입력. **길이 상한 100자 — 서버가 검증한다** |
| `years_of_experience` | enum \| null | **키 필수** | `"0-1"` / `"2-3"` / `"4-6"` / `"7+"` |

- **세 키가 모두 있어야 한다.** 키가 빠진 요청은 `VALIDATION_FAILED`로 거부한다. 전체 교체 계약에서 키 누락을 "유지"로 해석하기 시작하면 PATCH가 몰래 되살아나고, 3장 설계 메모의 병합 문제가 그대로 돌아온다. **비움은 키 생략이 아니라 `null`이다.**
- **[초기화] 후 저장은 세 `null`이다.** 별도 엔드포인트·별도 플래그가 없다 — 미입력 상태로 되돌리는 것도 저장의 한 경우다(`career.md` 4.2).
- **`job_category`는 4.3 목록에 있는 값만 허용한다**(또는 `null`). 목록을 서버 제공으로 확정한 이유가 두 화면의 값 체계 통일인데(`career.md` 미결 확정 표), 서버가 임의 문자열을 받아 저장하면 같은 컬럼에 목록 밖 값이 쌓여 확정이 무의미해진다. 위반 시 `CAREER_JOB_CATEGORY_UNAVAILABLE` — 클라이언트는 목록을 재조회하고 직군 필드를 선택 안 함으로 되돌린다.
- **`job_title`은 내용을 검증하지 않는다.** 자유 입력이므로 길이 상한(100자)과 빈 값 정규화(2장)만 적용한다. 100자는 클라이언트도 입력 단계에서 제한하지만(**uiux 소관**), 판정은 서버 검증이다 — 클라이언트 제한은 우회된다.
- **확인 팝업 없이 저장한다는 규칙은 계약에 아무 흔적을 남기지 않는다.** 확인 여부는 화면 규칙이고(`career.md` 4.2 — 잃는 것이 없어 확인할 내용이 없다), 서버는 요청이 오면 저장한다.
- **last-write-wins.** 여러 기기 동시 편집은 나중에 도착한 저장이 최종이다(`career.md` 7). 버전·타임스탬프 비교로 충돌을 거부하지 않는다 — 잃는 것이 추천 보조 신호뿐인 3필드 폼에 충돌 해소 UI를 붙일 근거가 없다.
- **트랜잭션 단위로 전부 반영 또는 전부 미반영이다**(`career.md` 7). 한 행의 3컬럼 UPDATE라 부분 반영이 만들어질 자리도 없다.
- **저장은 추천 랭킹의 보조 신호로 즉시 반영된다.** `users` 행이 바뀌는 즉시 다음 추천 계산이 새 값을 읽는다(`drip-scheduling.md` 4.2 — 커리어 적합도 소폭 가점). **드립 편성 대상과 기존 라이브러리에는 영향이 없다**(`career.md` 4.2) — 별도 반영 트리거·전파 엔드포인트가 없다.

**Response 200**

```json
{
  "job_category": "기획·PM",
  "job_title": "서비스 기획자",
  "years_of_experience": "4-6"
}
```

- 저장된 값을 그대로 반환한다(정규화 결과 포함 — 공백만 보낸 `job_title`은 `null`로 돌아온다). 클라이언트는 이 값으로 폼 상태를 갱신한 뒤 토스트를 띄우고 복귀한다. **토스트 문구("커리어 정보가 저장되었어요")는 화면 카피이며 응답 `message`가 아니다.**
- **복귀 후 프로필·설정 요약 갱신은 각 화면의 재조회가 담당한다**(`profile.md` 4.4). 이 응답을 다른 화면에 전파하는 메커니즘을 두지 않는다.

**오프라인·실패 처리**

- **오프라인 큐에 넣지 않는다.** 폼 제출은 큐 적재 대상이 아니다(`common-error-handling.md` 4.5 — "단일 값 토글은 큐 적재 대상이고, 폼 제출(관심사·커리어 저장)은 큐에 넣지 않는다"). 오프라인 저장 시도는 즉시 실패 처리하고 **인라인 에러 + [다시 시도], 편집 상태 유지**다(`career.md` 5·7).
  - 큐에 넣으면 사용자가 화면을 떠난 뒤 낡은 편집본이 뒤늦게 전송돼, 그 사이 다른 기기에서 저장한 최신 값을 덮는다. 토스트("저장되었어요")를 이미 봤다면 거짓 고지가 되고, 못 봤다면 언제 반영될지 모르는 저장이 된다.
- **타임아웃·5xx는 자동 재시도 대상이다**(최대 2회, `common-error-handling.md` 4.2) — PUT 전체 교체라 멱등이 보장된다. 소진 시 위와 같은 인라인 에러 + [다시 시도]다.

**에러**

| 코드 | HTTP | 상황 |
|---|---|---|
| `VALIDATION_FAILED` | 400 | 키 누락 · `job_title` 100자 초과 · `job_category` 50자 초과 · `years_of_experience` enum 위반 |
| `CAREER_JOB_CATEGORY_UNAVAILABLE` | 400 | `job_category`가 4.3 목록에 없는 값 |

- **온보딩 미완료 계정의 호출을 거부하지 않는다.** 화면 진입 자체가 온보딩 완료 사용자로 제한되지만(`career.md` 2장) 그것은 내비게이션 규칙이다. 이 엔드포인트는 `onboarding_step`을 건드리지 않아 미완료 계정이 호출해도 깨지는 불변식이 없고, 상태 검사를 추가하면 에러 코드만 하나 늘어난다. 온보딩 중의 커리어 저장이 단계를 전진시켜야 한다면 그것은 `PATCH /onboarding/career`를 썼어야 하는 클라이언트 버그다.

### 4.3 `GET /job-categories`

직군 선택 시트에 노출할 목록이다. **온보딩 2단계와 커리어 정보 화면이 같은 목록을 쓴다**(확정 2026-08-10 — 클라이언트 상수 금지).

**Response 200**

```json
{
  "items": [
    { "name": "개발" },
    { "name": "기획·PM" },
    { "name": "디자인" },
    { "name": "마케팅" },
    { "name": "데이터" }
  ]
}
```

| 필드 | 의미 |
|---|---|
| `items[].name` | 화면에 그대로 노출하고, **그 문자열 그대로 `job_category`로 전송·저장하는 값**이다. 배열 순서가 곧 노출 순서다 |

- **표시 문자열과 저장 값을 분리하지 않는다(단일 `name`).** `users.job_category`는 varchar이고 FK가 아니며(`domain.md` 3.1 · 15.1 #10), 프로필 카드는 이 컬럼 원값을 그대로 표시한다(`profile-api.md` 4.1). 코드·라벨을 분리하면 표시하는 모든 화면이 목록을 조인해야 하는데, 그 비용을 정당화할 요구(다국어·라벨 개명)가 아직 없다. 분리가 필요해지면 `items[]`에 필드를 추가한다 — 객체 배열로 둔 이유다(9장).
- **[선택 안 함]을 목록에 담지 않는다.** 비움은 값이 아니라 `null`이고(2장), 시트의 [선택 안 함] 행은 화면이 그린다(`wireframe/career.html` CR3). 서버 목록에 넣으면 "선택 안 함"이라는 문자열이 `job_category`에 저장될 수 있는 경로가 생긴다.
- **정렬 순서는 서버가 정한다.** 클라이언트는 받은 순서대로 그린다 — 순서 기준(가나다·사용 빈도·운영 지정)은 목록 저장 형태와 함께 미결이다(9장).
- **빈 목록(`items: []`)은 정상 상태가 아니다.** 직군 선택이 불가능해질 뿐 저장·온보딩 진행은 막히지 않지만(직군은 선택 입력), 서버는 운영 알림을 발생시킨다.
- 목록 저장 형태(서버 코드 상수 vs 관리 테이블)는 `domain.md` 15.1 #10 **미결**이다. **이 계약은 어느 쪽으로 확정돼도 바뀌지 않는다** — 클라이언트는 이 응답만 본다.

## 5. 에러 코드 표

**이 표는 `common-error-handling.md` 9장 중앙 표 형식을 따르는 커리어 발췌다** — 두 곳이 어긋나면 9장이 기준이다. 추가·변경 시 `architecture.md` 7.5에 따라 enum 한 곳에서 관리하고 **9장 표를 먼저 갱신한 뒤** 이 표를 맞춘다.

| error_code | HTTP | retryable | 클라이언트 동작 |
|---|---|---|---|
| `VALIDATION_FAILED` | 400 | false | 인라인 오류. 재시도를 권하지 않는다(`common-error-handling.md` 4.1). 편집 상태 유지 |
| `CAREER_JOB_CATEGORY_UNAVAILABLE` | 400 | false | 직군 목록 재조회 후 직군 필드를 선택 안 함으로 초기화 + 인라인 안내. 직무·연차 편집 값은 유지 |

- **`CAREER_JOB_CATEGORY_UNAVAILABLE`은 이 문서가 신설한 코드다.** `common-error-handling.md` 9.9 중앙 표에 등재됐고(협의 2026-08-10), enum 반영은 백엔드 구현 시 진행한다(`architecture.md` 7.5).
  - `VALIDATION_FAILED`로 합치지 않는 이유: 두 상황의 클라이언트 동작이 다르다. 형식 위반은 입력을 고치라는 뜻이지만, 목록 밖 직군은 **클라이언트가 든 목록이 낡았다**는 뜻이라 목록 재조회가 복구 경로다(`ONBOARDING_TOPIC_UNAVAILABLE`과 같은 구분 — `onboarding-api.md` 4.3).
- 401(토큰 갱신)·429·5xx의 처리는 `common-error-handling.md` 4.1~4.2의 공통 규칙을 따른다. 이 문서가 따로 정의하지 않는다.

## 6. 흐름

**화면 진입**

```
커리어 정보 화면 진입 (프로필 카드 · 설정 > 콘텐츠)
  ├─ GET /users/me/career    → 폼 현재 값 (미입력이면 세 null → 빈 폼 + 유도 문구)
  └─ GET /job-categories     → 직군 시트 선택지
        (병렬 호출 — 시트를 열 때 목록이 준비돼 있게 한다)
```

- 어느 한쪽 실패 시 전체 화면 에러 + [다시 시도]다(화면 진입 차단형). 절반만 그려진 폼에서 편집을 시작하게 하지 않는다.

**저장**

```
폼 편집 ([초기화] 포함 — 전부 로컬)
   ↓ [저장] (변경 있음일 때만 활성 — 화면 규칙)
PUT /users/me/career   ← 3필드 전체, 비움은 null
   ├─ 200                                → 토스트 후 복귀. 복귀 화면이 요약 재조회
   ├─ 400 VALIDATION_FAILED              → 인라인 오류, 편집 유지
   ├─ 400 CAREER_JOB_CATEGORY_UNAVAILABLE → 목록 재조회 + 직군 초기화, 편집 유지
   └─ 타임아웃·5xx                        → 자동 재시도(최대 2회) → 소진 시 인라인 에러 + [다시 시도]
        (오프라인이면 즉시 인라인 에러 + [다시 시도] — 큐에 넣지 않는다)
```

- **[저장] 연타·재시도로 같은 본문이 두 번 도착해도 결과가 같다**(전체 교체). 저장 중 조작 차단(`career.md` 5장)은 화면 규칙이고, 서버는 중복 도착을 거부하지 않는다.

## 7. 보안·검증 규칙

`architecture.md` 9장을 이 도메인에 적용한 결과다.

- **모든 조회·변경은 토큰에서 꺼낸 `user_id`로 스코프한다.** 경로에 `userId`를 받지 않고 `me`를 쓴다(IDOR 방지 — `architecture.md` 9.2).
- **길이 상한(직군 50자·직무 100자)과 `years_of_experience` enum은 서버가 검증한다.** 클라이언트 입력 제한은 우회된다.
- **`job_category`의 목록 소속 검증도 서버가 한다**(4.2). 시트 UI만 믿으면 임의 문자열이 컬럼에 쌓인다.
- 전역 `ValidationPipe`(`whitelist: true`, `forbidNonWhitelisted: true`) — DTO에 없는 필드는 잘라낸다. "변경 있음" 플래그 같은 로컬 상태가 실려 와도 서버에 도달하지 않는다.
- **직군 목록은 사용자별로 다르지 않다.** 개인화·티어 분기가 없으며, 응답에 다른 사용자의 정보가 섞일 자리가 없다.
- 커리어 값은 추천 보조 신호일 뿐 **권한·한도 판정에 쓰이지 않는다.** 위조해도 얻는 것이 추천 왜곡뿐이라 별도 방어를 두지 않는다.
