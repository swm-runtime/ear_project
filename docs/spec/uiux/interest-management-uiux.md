# 관심사 관리 UI/UX 명세서

> 기준 문서: [`docs/features/interest-management.md`](../../features/interest-management.md) (2026-08-10 개정 반영) · 로딩·오류 표현은 [`docs/features/common-error-handling.md`](../../features/common-error-handling.md)
> 와이어프레임: [`docs/wireframe/interest-management.html`](../../wireframe/interest-management.html) (화면 ID IM1–IM9 · 검증 항목 V1–V7 전부 해소)
> API: `interest-management-api.md` (작성 전 — 확정 전에는 `interest-management.md` 4.4·6장 + `backend/domain.md`로 추정하되 확정 계약으로 취급하지 않는다)

## 1. 범위

온보딩에서 고른 관심 주제를 언제든 바꾸는 일괄 편집 화면 — 주제 칩 그리드, "N/3 선택" 표기, 변경 배지, 해제 포함 저장의 확인 팝업, 0개 상태의 저장 게이트, 상한 초과 보유자 처리, 이탈 확인, 저장·조회 실패까지 `interest-management.md` 5장 화면 상태 표를 화면 단위로 풀어낸 문서다.

**이 문서는 동작 규칙을 새로 정하지 않는다.** 상한(최소 1·최대 3)·저장 분기·변경 반영 규칙은 `interest-management.md`가 소유한다. 여기서 정하는 것은 **무엇을 어떤 상태로 보여주고, 사용자 조작에 어떻게 반응하는가**다.

- **화면의 상한 처리는 안내이지 검증이 아니다.** 4번째 칩을 비활성으로 그려도 상한 판정은 서버가 저장 시점에 다시 한다(`interest-management.md` 3장). 화면 제한을 방어선으로 삼지 않는다.
- 주제 목록·상한·칩 동작은 **온보딩 1단계(O1–O3)와 같은 규칙**을 쓴다(`onboarding-uiux.md` 4.1). 다른 점은 저장 방식 하나 — 온보딩은 [다음]으로 전진하고, 여기는 **변경이 있을 때만 [저장]이 활성**된다.
- 편집은 일괄(batch)이다. 화면에서 켜고 끈 것은 로컬 상태일 뿐이고, [저장]을 눌러야 서버로 간다. **자동 확장 토글만 즉시 저장 예외인데, P1이라 MVP 화면에는 섹션 자체가 없다**(4.8).

## 3. 화면 흐름

```
프로필 [관심 주제 관리] 카드 ─┐
설정 > 콘텐츠 > 관심 주제 관리 ─┼─> IM9 로딩 ─┬─ 성공 ─┬─ 1~3개 보유 ──> IM1 (변경 없음)
드립 안내 배너 [관심 주제 추가하기] ─┘          │         └─ 4개 이상 보유 ─> IM6 (초과 보유자)
                                                └─ 실패 ──> IM9 조회 실패 ─[다시 시도]─> 재조회

IM1 ─[칩 편집]─> IM3 변경 있음 ─┬─[3개 채움]────> IM2 (미선택 칩 비활성)
                                 │                    └─[4번째 탭]─> 토스트 (선택 안 됨)
                                 ├─[전부 해제]──> IM5 (0/3 · [저장] 비활성 + 사유 문구)
                                 ├─[해제 후 같은 칩 재선택]─> 변경 없음으로 복귀 (IM1)
                                 └─[뒤로가기]───> IM7 팝업 ─┬─[계속 편집]·딤 탭─> 화면 유지
                                                             └─[나가기]─────────> 이전 화면 (편집 폐기)
IM1 ─[뒤로가기 · 변경 없음]─> 팝업 없이 이전 화면

IM3 ─[저장]─┬─ 추가만 있음 ──────────────> 저장 (팝업 없음)
             └─ 해제 포함 ──> IM4 확인 팝업 ─┬─[변경하기]─> 저장
                                              └─[취소]·딤 탭─> 편집 화면 유지 (저장 안 함)
저장 ─┬─ 성공 ─> 토스트 "관심사가 변경되었어요" ─> 이전 화면 복귀
       └─ 실패 ─> IM8 인라인 에러 + [다시 시도] (편집 상태 유지)
```

**진입 경로는 셋이지만 화면은 하나다.** 어느 경로로 들어와도 같은 화면·같은 규칙이고, 저장 성공·[나가기]의 복귀 지점은 **들어온 경로의 화면**이다.

- 경로마다 화면을 나누면 같은 편집 규칙이 세 벌이 되고, 드립 배너로 들어온 사용자만 다른 동작을 만나게 된다.

**확인 팝업(IM4)과 이탈 팝업(IM7)은 겹쳐 쌓이지 않는다.** IM4는 [저장]에서만, IM7은 뒤로가기에서만 뜬다 — 이탈 팝업에 [저장] 버튼을 두지 않은 이유가 이것이다(와이어프레임 V7 · 결정 2026-08-10).

## 4. 화면별 명세

### 4.1 IM1 정상 — 화면 골격

**구성** — 앱바(뒤로가기 + 타이틀 **"관심 주제 관리"**) / 헤드라인 **"어떤 이야기가 궁금하세요?"** / 개수 표기 **"N/3 선택"** / 주제 칩 그리드 / 하단 고정 독(dock)의 [저장]

- **헤드라인은 온보딩 1단계와 같은 문구다**(와이어프레임 V2 제안 → 이 문서에서 확정 2026-08-10). 목록·상한·칩 동작이 온보딩과 같은 규칙이므로 문구가 다르면 같은 화면 문법이 두 이름을 갖게 된다.
- 주제 목록은 온보딩과 동일하게 `is_visible = true`인 주제만, 같은 `display_order`로 노출한다(FR-03 · FR-38). **관리자가 숨긴 주제는 목록에서 사라지지만 선택 이력은 지워지지 않는다** — 화면은 보이는 것만 그린다.
- **개수 표기는 항상 "N/3 선택" 형태다.** 선택 직후부터 노출해 상한에 부딪히기 전에 남은 자리를 알린다(온보딩 4.1과 같은 이유 — 4개째에 처음 알리면 안내가 아니라 제약으로 읽힌다).
- **[저장]은 변경 사항이 있을 때만 활성이다.** 진입 직후·해제 후 같은 칩을 재선택해 원상태로 돌아온 경우 모두 비활성이다.
  - 변경이 없는데 [저장]이 활성이면 눌러도 아무 일도 없는 버튼이 되거나, 무의미한 저장 요청이 나간다. 비활성 자체가 "바꾼 것이 없다"는 상태 표시다.
- **[저장]은 스크롤 영역이 아니라 하단 고정 독에 둔다.** 주제 칩이 여러 줄로 늘어나 스크롤이 생겨도 저장 버튼이 목록에 묻히지 않는다.
- **선택 상태는 로컬에만 둔다.** 칩 탭마다 서버를 부르지 않고, [저장] 시점에 **델타가 아니라 최종 목록 전체**를 한 번 보낸다(`interest-management.md` 4.4 — 멱등, 다중 기기 last-write-wins).
- 이 화면에는 탭바를 그리지 않는다. 프로필·설정·라이브러리에서 푸시된 하위 화면이다.

### 4.2 IM2 3/3 선택 · 4번째 시도

| 상태 | 표시 |
|---|---|
| 3개 선택 완료 | **"3/3 선택"** + 미선택 칩 비활성 스타일 |
| 4번째 칩 탭 | 선택되지 않음 + 토스트 **"관심 주제는 3개까지 선택할 수 있어요"** |

- **비활성 칩도 탭은 받는다. 무반응으로 삼키지 않는다.** 반응이 없으면 사용자는 규칙이 아니라 버그로 읽는다(`interest-management.md` 4.1). 토스트 문구는 온보딩과 같은 문자열이다.
- 토스트는 3초, 같은 토스트가 쌓이지 않게 중복 노출을 억제한다(연타 시 교체·타이머 초기화).
- **비활성 대상은 미선택 칩뿐이다. 선택된 칩은 계속 누를 수 있다.** 주제를 바꾸는 유일한 경로가 기존 선택 해제인데 선택된 칩까지 잠그면 3개를 고른 순간 되돌릴 방법이 없어진다.
- 클라이언트 비활성은 안내다. 우회해 4개를 보내면 서버가 저장을 거부한다(`interest-management.md` 3장).

### 4.3 IM3 변경 있음 — "변경 사항 N개" 배지 · 저장 중

**구성** — IM1과 동일 + 개수 표기 옆 **"변경 사항 N개"** 배지 + [저장] 활성

- **배지 위치는 "N/3 선택" 라벨 옆이다**(위치 확정 2026-08-10 — 와이어프레임 V3). 화면 상단 별도 줄에 두지 않는다 — 개수와 변경은 같은 선택 상태의 두 측면이라 한 줄에서 함께 읽혀야 한다.
- **N 산정 규칙** — 서버에 저장된 현재 목록과 화면의 선택을 비교해, **추가 1개·해제 1개를 각각 1로 센 합계**다.
  - **해제했다가 같은 편집 안에서 다시 선택하면 0이다**(`interest-management.md` 7장 — 변경 없음 취급). 조작 횟수가 아니라 결과의 차이를 센다 — 조작을 세면 켰다 껐다만 해도 숫자가 늘어 "무엇이 바뀌었나"에 답하지 못한다.
  - 예: "생산성" 해제 + "돈·재테크" 추가 → **변경 사항 2개**.
- **변경이 0이 되면 배지를 제거하고 [저장]을 비활성으로 되돌린다.** 배지가 남은 채 [저장]만 꺼지면 두 표시가 서로 어긋난다.

**저장 중**

- [저장]이 **버튼 로딩** 상태가 되고, 인플라이트 동안 **칩 탭·뒤로가기를 포함한 화면 조작을 차단한다**(`interest-management.md` 5장).
  - 저장 중에 칩을 바꾸면 방금 보낸 목록과 화면이 어긋나고, 성공 토스트가 어느 상태에 대한 것인지 알 수 없게 된다.
- 별도 전체 화면 로딩·딤을 두지 않는다. 저장은 요청 한 건이라 버튼 로딩으로 충분하고, 0.3초 미만이면 로딩 표시 자체를 생략한다(`common-error-handling.md` 5장).

### 4.4 IM4 해제 포함 저장 — 변경 확인 팝업

**노출 조건은 `interest-management.md` 4.2가 소유한다** — 해제가 포함된 저장에만 뜬다. 추가만 있으면 팝업 없이 바로 저장된다.

**구성** — 본문 **"선택이 해제된 주제의 새 콘텐츠가 더 이상 라이브러리에 도착하지 않아요. 이미 받은 콘텐츠는 그대로 남아 있어요."** / [취소] · [변경하기]

- **주제명을 명시하지 않는 단일 문구다**(확정 2026-08-10 — 와이어프레임 V4, 나열 제안 기각). 해제 개수(1개·복수)와 무관하게 같은 문구를 쓴다. 별도 제목 없이 본문만 두는 한 문단 팝업이다.
- **저장당 1회다.** 해제 항목 수만큼 반복하지 않는다 — 편집이 일괄(전체 목록 전송)이라 확인 단위도 저장 단위와 같다. 항목별로 띄우면 중간 [취소]의 의미(부분 적용?)가 성립하지 않는다.
- 버튼은 [취소] 좌, [변경하기] 우이며 [변경하기]가 주 액션 스타일이다.
- **[취소]·딤 탭은 저장하지 않고 편집 화면으로 돌아간다.** 편집 상태는 그대로 유지된다 — 저장이 일어나지 않았을 뿐 사용자가 고른 것을 버리지 않는다.
- **문구에 잃는 것과 남는 것을 함께 담는다.** "신규 도착 중단"만 말하면 이미 받은 것도 사라지는 줄 알고 해제를 겁내게 된다. 이 두 문장이 이 기능의 핵심 규칙(FR-05) 그 자체이므로 요약·의역하지 않고 그대로 쓴다.
- [변경하기] → 저장 → 성공 시 토스트 **"관심사가 변경되었어요"** → 이전 화면(진입 경로) 복귀. 오늘 이미 편성 확정된 콘텐츠가 그대로 적립되는 것은 별도로 안내하지 않는다(`interest-management.md` 7장 — 자연스러운 지연으로 보인다).

### 4.5 IM5 전부 해제 — 0개 상태 · IM6 상한 초과 보유자

**IM5 — 0개 상태**

**구성** — **"0/3 선택"** / 전 칩 미선택 / 하단 독에 사유 문구 **"관심 주제를 1개 이상 선택해주세요"** + [저장] 비활성

- **마지막 1개도 해제할 수 있다 — 편집 중 0개 상태를 허용한다**(개정 2026-08-09). 현재 선택을 전부 갈아엎고 새로 고르는 동선을 막지 않기 위해서다. **막는 것은 탭이 아니라 저장이다.**
- 사유 문구는 **[저장] 버튼 위에 상시 노출한다.** 토스트로 대체하지 않는다 — 사라지는 안내로는 [저장]이 왜 눌리지 않는지 화면에 남는 단서가 없다. 온보딩 O1(미선택 시 [다음] 비활성 + 같은 문구)과 같은 패턴·같은 문자열이다.
- 0개 상태에서 뒤로가기를 누르면 변경이 있으므로 IM7 이탈 팝업이 뜬다. [나가기]를 고르면 편집이 폐기되고 서버의 기존 선택이 그대로 남는다.

**IM6 — 상한 초과 보유자(상한 도입 이전 가입자 · 자동 확장으로 초과)**

**구성** — **"N/3 선택"**(예: "5/3 선택") / 안내 배너 **"관심 주제는 3개까지예요. N개를 해제하면 다시 추가할 수 있어요"** / 보유 칩 전부 선택 상태 + 미선택 칩 비활성

- **강제로 줄이게 하지 않는다.** 현재 목록을 그대로 노출하고 **추가만 막는다.** 해제·저장은 자유이며, 3개 이하로 내려간 뒤부터 상한이 정상 적용된다(`interest-management.md` 7장 — 상한은 앞으로의 선택을 제한하는 규칙이지 기존 상태를 되돌리는 규칙이 아니다).
- 안내의 `N`은 **3을 초과한 개수**다(5개 보유 → "2개를 해제하면"). 배너는 초과 상태인 동안 상시 노출하고, 해제로 3개 이하가 되면 제거한다.
- **개수 표기를 "3/3"으로 거짓 클램프하지 않는다.** "5/3 선택"이 어색해 보여도 사실이 우선이다 — 3/3으로 그리면 안내 배너의 "N개를 해제하면"과 화면 숫자가 어긋난다.
- 초과 상태의 비활성 칩 탭도 IM2와 같이 토스트로 반응한다. 무반응 금지는 상태와 무관한 공통 규칙이다.
- 초과 상태 그대로의 재저장(해제 없이 다른 변경만 저장)도 서버가 허용하므로("기존 개수보다 늘어나지 않으면 통과"), 화면도 이를 막지 않는다.

### 4.6 IM7 뒤로가기 — 이탈 확인 팝업

**구성** — **"변경 사항을 저장하지 않고 나갈까요?"** / [계속 편집] · [나가기]

- **변경이 있는 상태의 뒤로가기·스와이프 제스처에만 뜬다.** 변경이 없으면 팝업 없이 바로 나간다 — 잃을 것이 없는데 묻는 팝업은 모든 이탈에 세금을 매기는 것이다.
  - **스와이프 제스처는 팝업 대신 비활성화로 처리한다**(구현 제약 기록 2026-08-11). React Navigation native-stack에서는 스와이프 백이 네이티브에서 확정된 뒤에야 JS에 통지돼 `beforeRemove`로 막을 수 없다 — 변경·저장 중에는 `gestureEnabled: false`로 제스처 자체가 동작하지 않고(변경 없으면 정상 dismiss), 팝업은 뒤로가기 버튼·Android 하드웨어 백에서 뜬다. 동작 규칙의 목적("잃을 것이 있는 이탈은 확인 없이 일어나지 않는다")은 유지된다.
- 버튼은 **[계속 편집] / [나가기] 현행 유지다**(확정 2026-08-10 — 와이어프레임 V7, [저장]/[나가기] 안 기각). 이탈 팝업에 [저장]을 두면 해제 포함 편집에서 팝업 위에 확인 팝업(IM4)이 쌓인다.
- [나가기]는 편집을 버리고 이전 화면으로 복귀한다. [계속 편집]·딤 탭은 팝업만 닫고 편집 화면을 유지한다.
- **[나가기]를 위험색으로 강조하지 않는다.** 버려지는 것은 저장 전 로컬 편집뿐이고 서버 상태는 그대로다 — 파괴적 조작처럼 그리면 나가기를 겁내게 된다.

### 4.7 IM8 저장 실패 · IM9 로딩 · 조회 실패

**IM8 — 저장 실패**

- 인라인 에러 **"저장하지 못했어요. 다시 시도해주세요"** + [다시 시도]. **편집 상태를 버리지 않는다**(`interest-management.md` 5장).
  - 전체 화면 에러로 전환하지 않는다 — 실패한 것은 저장 한 건이지 화면이 아니다. 칩 선택·변경 배지가 그대로 남아 있어야 [다시 시도]가 같은 내용을 다시 보낼 수 있다.
- **오프라인 저장 시도도 같은 처리다.** 폼 제출은 오프라인 큐 대상이 아니다(`common-error-handling.md` 4.5 — 즉시 실패 + [다시 시도], 편집 상태 유지).
- 해제 포함 편집이라면 [다시 시도] 성공 경로에서 **확인 팝업(IM4)을 다시 띄우지 않는다.** 사용자는 이미 [변경하기]로 확인을 마쳤다 — 실패 후 재시도는 같은 저장의 반복이지 새 저장이 아니다.
- [다시 시도] 연타는 인플라이트 요청이 있으면 무시한다(`common-error-handling.md` 7장).

**IM9 — 로딩 · 조회 실패**

- 로딩은 **칩 모양 스켈레톤**이다(개수 표기 자리 포함). 스피너를 중앙에 띄우지 않는다. 앱바 타이틀·헤드라인은 서버 응답과 무관하므로 먼저 그린다. **0.3초 미만이면 표시하지 않는다**(`common-error-handling.md` 5장).
- 조회 실패는 에러 안내 **"주제 목록을 불러올 수 없어요"** + [다시 시도]다.
- **로딩·실패 중 [저장]은 비활성이다.** 현재 선택을 모르는 상태에서는 저장이 성립하지 않는다.
- 목록이 빈 배열로 오는 경우의 처리(온보딩은 기본 주제 세트 폴백 — `onboarding.md` 7장)는 features에 이 화면 기준 규칙이 없다 → 9장 미결.

### 4.8 자동 확장 섹션 (P1 — MVP 미노출)

- FR-06(토글)·FR-18(자동 확장)은 P1이다. **MVP에서는 섹션 자체를 노출하지 않는다**(`interest-management.md` 5장). "준비 중" 표시·빈 자리도 두지 않는다.
- P1 도입 시 구성(참조용 — 도입 시점에 확정): 칩 그리드 아래 토글 + 설명 "관심 주제와 가까운 주제도 자동으로 찾아드려요" + 자동 추가 주제의 "자동 추가됨" 배지 칩. **토글은 일괄 저장 예외로 즉시 저장**이다(`interest-management.md` 3장).
- 자동 추가분도 3개 상한에 포함해 세므로, 도입 시 이 화면의 개수 표기·비활성 규칙이 그대로 적용된다.

## 5. 공통 컴포넌트 규칙

| 컴포넌트 | 용도 | 규칙 |
|---|---|---|
| **주제 칩** | 다중 선택 | 온보딩 1단계와 같은 컴포넌트·같은 목록·같은 순서. 선택 = 색 + 체크 아이콘, 비활성 = 스타일만 낮추고 **탭은 받는다** |
| **개수 표기 + 변경 배지** | 선택 상태 요약 | "N/3 선택" 상시 + "변경 사항 N개"는 변경 있을 때만, 라벨 옆 |
| **하단 고정 독** | 주 액션 | [저장] 하나. 0개 상태에서는 사유 문구를 버튼 위에 함께 |
| **다이얼로그** | 진행 전 확인 | IM4(해제 확인) · IM7(이탈 확인). 주 액션이 오른쪽. **겹쳐 쌓지 않는다** |
| **토스트** | 되돌릴 필요 없는 결과 통지 | 상한 안내 · 저장 성공. 3초, 중복 노출 억제 |
| **인라인 에러** | 사용자 액션 실패 | 저장 실패·조회 실패. [다시 시도] 포함, 편집 상태 유지 |
| **스켈레톤** | 최초 조회 | 칩 모양. 0.3초 미만이면 미표시 |
| **버튼 로딩** | 중복 탭 차단 | [저장] · [변경하기] · [다시 시도]. 인플라이트 동안 비활성 |

- **모든 제출 버튼은 인플라이트 동안 비활성화한다.** 저장은 상태를 바꾸는 요청이라 중복 실행이 실제 부작용을 만든다.
- **저장 성공 토스트는 화면 복귀와 함께 띄운다.** 이전 화면 위에 얹혀도 3초 뒤 사라지는 통지이므로 복귀를 지연시키지 않는다.

## 6. 카피 원칙

- **해요체**로 통일한다.
- **확정 카피 전수** — 이 화면의 사용자 노출 문구는 아래가 전부다.

| 위치 | 문구 |
|---|---|
| 앱바 타이틀 | "관심 주제 관리" |
| 헤드라인 | "어떤 이야기가 궁금하세요?" (온보딩 1단계와 동일 — 확정 2026-08-10) |
| 개수 표기 | "N/3 선택" |
| 변경 배지 | "변경 사항 N개" |
| 상한 토스트 | "관심 주제는 3개까지 선택할 수 있어요" (온보딩과 동일 문자열) |
| 0개 사유 문구 | "관심 주제를 1개 이상 선택해주세요" (온보딩 O1과 동일 문자열) |
| 초과 보유자 안내 | "관심 주제는 3개까지예요. N개를 해제하면 다시 추가할 수 있어요" |
| 해제 확인 팝업 | "선택이 해제된 주제의 새 콘텐츠가 더 이상 라이브러리에 도착하지 않아요. 이미 받은 콘텐츠는 그대로 남아 있어요." + [취소] · [변경하기] |
| 이탈 팝업 | "변경 사항을 저장하지 않고 나갈까요?" + [계속 편집] · [나가기] |
| 저장 성공 토스트 | "관심사가 변경되었어요" |
| 저장 실패 | "저장하지 못했어요. 다시 시도해주세요" + [다시 시도] |
| 조회 실패 | "주제 목록을 불러올 수 없어요" + [다시 시도] |

- **온보딩과 공유하는 문구는 문자열까지 동일하게 쓴다**(헤드라인 · 상한 토스트 · 0개 사유). 같은 규칙을 두 화면이 다른 말로 하면 어느 쪽이 맞는지 사용자가 판단하게 된다.
- **해제 확인 팝업은 사실 두 문장이 전부다** — 잃는 것(신규 도착 중단)과 남는 것(받은 콘텐츠 유지). 사과·경고 톤·주제명 나열을 붙이지 않는다.
- **내부 용어를 화면에 노출하지 않는다** — "드립", "적립", "편성", "자동 확장 배치". 확인 팝업도 "라이브러리에 도착"이라는 사용자 언어를 쓴다.
- 사용자를 탓하지 않는다: "3개를 초과했습니다" (×) / "관심 주제는 3개까지 선택할 수 있어요" (○).
- **남은 단계·저장 재촉 문구를 두지 않는다.** "저장을 잊지 마세요" 류는 이탈 팝업(IM7)이 이미 대신한다.

## 7. 접근성

- **터치 타깃 최소 44×44pt.** 주제 칩은 글자 수에 따라 폭이 달라지므로 **최소 높이를 고정**한다(온보딩 7장과 동일).
- **주제 칩은 `role="checkbox"` + `aria-checked`로 노출한다.** 선택 상태가 색·체크 아이콘과 함께 낭독으로도 전달돼야 한다.
  - 3개를 채운 뒤의 미선택 칩은 `aria-disabled="true"` + **"관심 주제는 3개까지 선택할 수 있어요"** 를 이유로 함께 읽히게 한다. 비활성 사실만 읽히면 이유를 알 수 없다.
  - IM6의 비활성 칩도 같은 방식이되, 이유는 초과 안내 문구를 쓴다.
- **"N/3 선택"은 화면 문자열 그대로 읽히면 안 된다.** "이 슬래시 삼"으로 읽힌다 — 라벨을 **"3개 중 N개 선택"** 형태로 따로 붙인다.
- **개수 표기와 변경 배지는 하나의 라이브 리전(`aria-live="polite"`)으로 묶는다** — "3개 중 3개 선택, 변경 사항 2개"처럼 한 문장으로 읽는다. 값이 실제로 바뀔 때만 알리고, 두 요소를 따로 리전으로 두면 칩 하나에 두 번 끼어든다.
- **색만으로 선택을 구분하지 않는다.** 선택 칩은 색 변화 + **체크 아이콘**을 함께 쓴다(온보딩과 동일). 비활성은 흐림 처리에 `aria-disabled`가 동반되므로 색이 유일한 단서가 아니다.
- **[저장] 비활성의 이유를 화면 텍스트로 밝힌다.** 0개 상태는 사유 문구가 상시 노출되므로 충족된다. 변경 없음 상태의 비활성은 "바꾼 것이 없다"는 상태 그 자체이므로 별도 문구를 두지 않는다.
- **다이얼로그(IM4·IM7)는 포커스를 가두고, 닫으면 열기 전 요소로 포커스를 되돌린다.** 열릴 때 본문을 먼저 읽힌 뒤 주 액션이 아니라 **안전한 쪽([취소]·[계속 편집])에 초기 포커스를 둔다** — 해제 확정과 편집 폐기는 실수로 눌렀을 때 비용이 큰 쪽이다.
- **토스트는 `aria-live="polite"`.** 4번째 선택 시도는 오류가 아니라 안내이므로 `assertive`로 끼어들지 않는다. 저장 성공 토스트는 화면 복귀 직후 읽히게 한다.
- 초과 보유자 안내 배너는 진입 시 한 번 polite로 읽히게 하고, 매 조작마다 반복하지 않는다.
- **동적 텍스트 최대 200%에서 잘리지 않아야 한다.** 칩 그리드는 줄바꿈으로, 하단 독은 사유 문구·버튼의 세로 확장으로, 팝업 버튼 줄은 세로 쌓기로 대응한다. 고정 높이를 쓰지 않는다.

## 8. 금지 사항

`interest-management.md`가 명시적으로 금지했거나 검토(2026-08-09·10)에서 기각된 것들이다. **UI 구현 시 되살아나기 쉬우므로 여기 모아 둔다.**

**선택·상한**

- 4번째 칩 탭을 **무반응으로 삼키는 것** — 규칙이 버그로 읽힌다
- 3개를 채운 뒤 **선택된 칩까지 비활성화**하는 것 — 되돌릴 방법이 사라진다
- **마지막 1개 칩의 해제를 탭 시점에 막는 것** — 판정 지점은 저장이다(개정 2026-08-09). 0개 상태를 금지 상태로 그리지 않는다
- 클라이언트 비활성 처리를 **상한 검증으로 취급**하는 것(서버 재검증 생략)
- 초과 보유자에게 **강제 축소를 요구**하는 것("N개를 지워야 저장할 수 있습니다")
- 초과 보유자의 개수 표기를 **"3/3"으로 클램프**하는 것

**저장·팝업**

- 칩 탭마다 **즉시 저장**하는 것 — 편집은 일괄이고 반영 단위는 [저장]이다
- 추가만 있는 저장에 **확인 팝업을 띄우는 것**
- 확인 팝업을 **해제 항목마다 반복**하거나 **주제명을 나열**하는 것 — 저장당 1회·단일 문구 확정(2026-08-10)
- 0개 상태의 [저장]을 **활성으로 두는 것**, 사유 문구를 **토스트로 대체**하는 것
- 해제 후 같은 칩 재선택을 **변경으로 세는 것** — 변경 없음이다
- 이탈 팝업에 **[저장] 버튼을 두는 것** — 팝업 위에 확인 팝업이 쌓인다([계속 편집]/[나가기] 확정 2026-08-10)
- 변경이 없는데 **이탈 팝업을 띄우는 것**
- 저장 실패 시 **편집 상태를 폐기**하는 것, 저장 요청을 **오프라인 큐에 적재**하는 것
- 실패 후 [다시 시도] 성공 경로에서 **확인 팝업을 다시 띄우는 것**

**화면·카피**

- 해제 확인 팝업에 **경고 톤·데이터 삭제 뉘앙스**를 얹는 것 — 받은 콘텐츠는 남는다는 것이 핵심 규칙이다

## 9. 미결 사항

- **주제 목록이 빈 배열로 오는 경우의 처리** — 온보딩은 기본 주제 세트(하드코딩 폴백)로 그리지만(`onboarding.md` 7장), 이 화면은 features에 규칙이 없다. 선택지: (a) 온보딩과 같은 폴백 세트로 그린다 (b) 조회 실패(IM9)와 동일 처리한다. 기존 선택이 이미 있는 화면이라 폴백 세트와 사용자의 실제 선택이 어긋날 수 있어 (b)가 안전해 보이나, **동작 규칙이므로 features가 정해야 한다.**
- **조회 실패 문구의 온보딩과의 통일** — 이 문서는 와이어프레임 IM9의 "주제 목록을 불러올 수 없어요"를 썼고, 온보딩 O6은 "주제를 불러오지 못했어요"다. 같은 실패(주제 목록 조회)에 두 문구가 존재한다. 선택지: (a) 이 화면을 온보딩 문구로 맞춘다 (b) 각자 유지한다(화면 맥락이 달라 사용자가 비교할 일은 없다). 통일한다면 어느 쪽 문자열로 할지 결정 필요.
- ~~저장 성공 토스트의 표기 계열~~ → **해소(2026-08-10): 현행 유지.** 저장 성공 토스트는 **"관심사가 변경되었어요"** 로 확정한다(features 4.4 확정 문구 그대로). 화면의 다른 문구("관심 주제" 계열)도 그대로다 — 혼용을 수용한다.
- **저장 중 조작 차단의 시각 표현** — features는 "화면 조작 차단"만 규정한다. 이 문서는 버튼 로딩 + 조작 무시(별도 딤 없음)로 풀었는데, 차단을 시각적으로 보여줄지(칩 흐림 등)는 시안 검증에서 정한다.
- **P1 자동 확장 도입 시 화면 확정** — 토글·"자동 추가됨" 배지·설명 문구는 4.8의 참조용 구성이다. 도입 시점에 상한 3개와의 충돌 재확인(features 미결)과 함께 이 문서를 개정한다.
- **다크 모드 대응 범위** — 와이어프레임은 단일 테마 기준이다. 비활성 칩의 흐림 처리와 선택 강조색의 대비를 다크 모드에서 다시 확인해야 한다.
