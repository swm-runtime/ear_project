# 프로필 기능 명세서

> 연결 PRD: FR-02, FR-04, FR-05, FR-28 / 사용자흐름 5.5

## 1. 목적 & 연결

사용자가 **자기 계정에 관한 것**을 한 화면에서 확인하고 바꾸는 곳이다. 담기는 것은 다섯 가지다 — **관심사 설정 · 커리어 설정 · 이메일 인증 · 현재 플랜 표시 · 청취 통계.**

- PRD FR-05 (P0) 관심 주제 일괄 편집 → 편집 화면은 `interest-management.md`
- PRD FR-04 (P0) 커리어 정보 이후 수정 → **별도 커리어 정보 화면**(합의 2026-08-06 — 관심사 관리에서 분리, `career.md`)
- PRD FR-02 (P0) 계정 — 이메일 등록·인증은 `auth.md` 4.4~4.5
- PRD FR-28/31 (P0) 구독 티어 — 현재 플랜 **표시**. 변경·해지는 `subscription.md`
- 청취 통계 — 누적 3지표 · 주간 그래프 · 주제 분포. PRD FR에는 없던 **추가 결정(2026-08-06)** 이다. 판정·집계 규칙은 이 문서 4.5~4.7이 소유한다

**설정과 무엇이 다른가**

`settings.md`는 앱 동작(배속·알림·버전·문의)까지 포함한 전체 허브고, 프로필은 **사용자 자신에 관한 값만** 모은다.

**이 화면은 편집 로직을 갖지 않는다**

관심사·커리어·이메일·구독은 **모두 다른 명세가 이미 소유한 기능이다.** 프로필은 현재 값을 요약해 보여주고 각 소유 화면으로 보낼 뿐, 저장 규칙을 새로 정의하지 않는다.

- 이유: 같은 데이터를 두 화면이 각자 저장하면 규칙이 갈라진다. 실제로 관심사는 "최소 1개" · "해제 시 확인 팝업" 같은 규칙이 붙어 있어(`interest-management.md` 4.2) 프로필에서 따로 편집하면 그 규칙을 두 벌 유지해야 한다.
- 청취 통계도 마찬가지다. **모든 수치는 서버가 계산해 내려주고 클라이언트는 그리기만 한다** — 서비스 날짜(04시 경계)·주 경계 판정이 필요한 값이라 기기에서 계산하면 공통 원칙(클라이언트 판정 금지)에 어긋난다.
- 예외는 없다. **프로필에서 직접 서버에 쓰는 값은 하나도 없다.**

## 2. 진입 조건

- **하단 탭 [프로필]** — 라이브러리 / 탐색 / 프로필 3개 탭 중 하나다(`library.md` 2)
- 온보딩을 완료한 로그인 사용자만 접근할 수 있다

**설정은 이 화면 안에 있다**

- 하단 탭에 설정을 따로 두지 않는다. **프로필 우상단의 설정 아이콘**으로 들어간다(`settings.md`).
- 진입 방향이 프로필 → 설정이므로, 설정 화면에는 프로필로 되돌아가는 계정 카드를 두지 않는다.

## 3. 입력값

화면 자체는 입력 폼이 아니라 **요약 조회**다. 서버에서 아래를 받는다.

| 값 | 설명 | 출처 |
|---|---|---|
| user.nickname, user.provider | 헤더 표시 | `users` |
| user.email | 없으면 "등록되지 않음" | `users` |
| interest_summary | 선택한 주제 개수 + 대표 주제명 | `user_interests` |
| career_summary | 직군·직무·연차 (없으면 미입력) | `users` |
| tier, plan_name | 현재 플랜명 | `subscriptions` → `plans` |
| next_billing_at / expires_at | 다음 결제일 또는 만료일 | `subscriptions` |
| cancel_scheduled | 해지 예약 여부 | `subscriptions` |
| stats_summary | 누적 청취 콘텐츠 수 · 누적 청취 시간 · 연속 청취 일수 | `play_records` 집계 |
| weekly_listening | 한 주(월~일)의 요일별 청취 시간 | `play_records` 집계 |
| topic_distribution | 주제별 청취 비율(상위 + 기타) | `play_records` + `content_topics` 집계 |

- **한 번의 요청으로 받는다.** 항목마다 API를 따로 호출하면 카드가 제각각 늦게 채워져 화면이 계속 흔들린다.
  - 통계도 같은 요청에 포함한다 — 요약 3지표, **이번 주** 그래프, 주제 분포까지. **이전 주차 그래프만** 화살표 탐색 시점에 주 단위로 추가 조회한다(4.6).
- 사용자 입력은 각 항목 탭(내비게이션)과 주간 그래프의 주 이동 화살표뿐이다.

## 4. 처리 로직

### 4.1 화면 구성

```
[헤더]        닉네임 · 로그인 제공자(카카오/네이버/구글 아이콘)    [⚙ 설정]
──────────────────────────────
[현재 플랜]   티어명 + 다음 결제일 / 만료일        → 구독 관리
[이메일]      등록된 주소 또는 "등록되지 않음"      → 이메일 인증
──────────────────────────────
[관심 주제 관리]  선택한 주제 N개 · 대표 주제 3개 표시  → 관심사 관리 화면
[커리어 정보]     직군 · 직무 · 연차 (또는 "미입력")    → 커리어 정보 화면
──────────────────────────────
[통계 요약]   누적 청취 N편 · 누적 N시간 · 연속 N일  (가로 3분할)
[주간 그래프] ◀  이번 주 요일별 청취 시간 막대  ▶
[주제 분포]   주로 듣는 주제 원형 그래프 (상위 + 기타)
```

- 네 항목의 순서는 **바꾸지 않는다.** 위 두 개는 계정·결제, 아래 두 개는 추천에 쓰이는 값이라 성격이 다르다.
- 관심 주제와 커리어는 **별도 카드 · 별도 화면**이다(합의 2026-08-06). [관심 주제 관리]는 관심사 관리 화면으로, [커리어 정보]는 커리어 정보 화면으로 이동한다 — 두 편집을 한 화면에 합치지 않는다.
- 청취 통계 세 영역은 **카드 아래에 이 순서로** 둔다(4.5~4.7). 모두 표시 전용이며 탭 이동이 없다 — 주간 그래프의 주 이동 화살표만 예외다.
- **우상단 설정 아이콘**이 설정 화면의 유일한 진입점이다(`settings.md`). 목록 항목이 아니라 헤더 아이콘으로 두는 이유는, 설정이 프로필의 하위 항목이 아니라 별개의 화면이기 때문이다.
- 닉네임과 로그인 제공자는 **표시만 한다.** 닉네임은 소셜 제공자에서 받은 값이고, 제공자 변경·계정 통합은 MVP 비범위다(`auth.md` 4.1).

### 4.2 현재 플랜 표시

| 상태 | 표시 | 진입점 |
|---|---|---|
| 라이트(무료) | "무료 이용 중 · 하루 2편" (편수는 `plans.daily_play_limit` 서버 값 — 2 하드코딩 금지) | [구독 알아보기] → `subscription.md` |
| 데일리 / 프로 | 플랜명 + "다음 결제일 N월 N일" | [구독 관리] → `subscription.md` |
| 해지 예약 | 플랜명 + "N월 N일까지 이용 가능" | [구독 관리] |
| 결제 실패·유예 | 플랜명 + "결제에 문제가 있어요" 경고 | [구독 관리] |

- **표시 전용이다.** 요금제 변경·해지·구매 복원은 전부 구독 관리 화면에서 한다(`subscription.md`). 프로필에 해지 버튼을 두지 않는다 — 결제 관련 조작은 진입점을 하나로 모아야 스토어 상태와 어긋나지 않는다.
- 티어의 진실의 원천은 `subscriptions`다. `users.tier`는 캐시이므로 **표시에 그대로 쓰되, 값이 어긋나면 `subscriptions` 기준으로 갱신한다**(`domain.md` 3.1).
- 무료 티어에 "하루 2편"을 함께 적는다. 플랜명만으로는 무엇이 제한되는지 알 수 없다. **편수 숫자는 `plans.daily_play_limit` 서버 값으로 채운다 — 2를 하드코딩하지 않는다**(`paywall.md` 5장의 `M`과 같은 원칙).

### 4.3 이메일 인증

**세 가지 상태를 구분해 표시한다** — `users.email`과 `users.is_email_verified`의 조합이다(`domain.md` 3.1).

| 상태 | 표시 | 버튼 |
|---|---|---|
| `email = null` | "등록되지 않음" | [등록] |
| `email` 있음 + `is_email_verified = false` | 주소 + **"인증되지 않음"** 배지 | [인증하기] · [변경] |
| `email` 있음 + `is_email_verified = true` | 주소 | [변경] |

- **"저장된 주소"와 "인증된 주소"를 같은 것으로 보여주지 않는다.** 카카오가 준 미인증 주소를 그냥 표시하면, 사용자는 결제 직전에 인증 화면을 만나고 나서야 인증되지 않았다는 것을 알게 된다(`auth.md` 4.1).
- 탭하면 **`auth.md` 4.4의 이메일 등록·인증 화면**으로 이동한다. 설정 경로·결제 경로와 **같은 화면, 같은 코드 규칙**을 쓴다.
  - 인증 방식은 **이메일 코드 인증**이며, 코드 유효 시간 **3분**, 재발송 쿨다운 **30초**, 발송 가능 횟수 **이메일 주소당 5회**, 소진 후 **1시간** 뒤 초기화다(`auth.md` 4.5).
  - 발송 횟수는 **`(계정, 주소)` 단위로 센다.** 같은 주소라면 프로필에서 3회 보냈을 때 설정·결제 경로에 2회만 남지만, **다른 주소를 입력하면 그 주소의 5회가 새로 시작된다.**
  - 코드 입력 화면에는 **[메일 다시 입력]** 이 있어 오타를 낸 주소에서 빠져나올 수 있다(`auth.md` 4.5).
- [인증하기]는 저장된 주소로 바로 코드를 보내고, [변경]은 새 주소를 입력받는다. **두 경로 모두 같은 인증 화면을 쓴다.**
- 인증에 성공하면 **직전 화면(프로필)으로 복귀**하고 이메일 항목이 새 값·인증 상태로 갱신된다.
- **검증 성공 전에는 값이 바뀌지 않는다.** 코드 입력 중 이탈하면 기존 이메일과 인증 상태가 그대로 남는다.
- 이메일이 없거나 미인증인 사용자에게 **여기서 인증을 강요하지 않는다.** 강제 지점은 첫 결제 하나뿐이다(`auth.md` 4.4). 다만 "결제하려면 인증된 이메일이 필요해요" 정도의 보조 문구는 노출한다.

### 4.4 관심 주제 관리 · 커리어 정보

- **두 카드는 서로 다른 화면으로 이동한다**(합의 2026-08-06 — 편집 화면 분리). [관심 주제 관리]는 관심사 관리 화면(`interest-management.md`)으로, [커리어 정보]는 **커리어 정보 화면(`career.md`)** 으로 간다.
- 프로필에는 **요약만** 둔다.
  - 관심 주제: "N개 선택 · 커리어, 자기계발, 경제 …" — 대표 3개까지, 나머지는 `+N`(상한이 3개이므로 `+N`은 상한 도입 이전 초과 보유자에게만 나타난다 — `interest-management.md` 7장). **대표 3개는 별도 선정 기준 없이 서버 응답 순서의 앞 3개다**(합의 2026-08-06).
  - 커리어: "기획 · 서비스 기획 · 4-6년" / 미입력이면 "입력하면 추천이 정확해져요"
- 편집 화면에서 저장하고 돌아오면 **요약을 다시 조회한다.** 캐시된 값을 그대로 두면 방금 한 변경이 반영되지 않은 것처럼 보인다.
- 저장 규칙은 각 편집 화면이 판정하고 프로필은 관여하지 않는다. **관심 주제는 편집 화면에서도 최소 1개 선택을 강제하므로**(합의 2026-08-06) 관심 주제 0개인 요약 상태는 생기지 않는다.

### 4.5 통계 요약 — 누적 3지표

카드 아래 첫 통계 영역. **세 지표를 가로 한 줄에 나란히** 둔다.

| 지표 | 정의 |
|---|---|
| 누적 청취 콘텐츠 수 | **완청한 고유 콘텐츠 수**(합의 2026-08-06 — 완청한 콘텐츠만 반영). 완청 판정 값은 `player.md`가 소유한다. 같은 콘텐츠를 여러 번 완청해도 1편이다 |
| 누적 청취 시간 | `play_records.listened_sec` 총합. 배속·반복과 무관하게 **실제 들은 시간**이다(`domain.md` 6.3) |
| 연속 청취 일수 | 서비스 날짜(04시 경계) 기준으로 재생 기록이 이어진 연속 일수 |

- **세 값 모두 서버가 계산해 내려준다.** 특히 연속 일수는 04시 경계 판정이 필요하므로 기기 시각으로 계산하지 않는다(공통 원칙).
- 연속 청취 일수 규칙:
  - 그 서비스 날짜에 `play_records`가 1건 이상이면 그날은 "들은 날"이다(합의 2026-08-06 확정 — 최소 청취 시간 조건을 두지 않는다).
  - **오늘 아직 듣지 않았어도 어제까지 이어진 연속 기록을 그대로 표시한다.** 오늘 들으면 +1 된다. 어제도 오늘도 듣지 않았으면 0일이다.
- 수치 표기 형식(단위·반올림)은 `spec/uiux/profile-uiux.md`에서 확정한다.

### 4.6 주간 청취 그래프

- **한 주의 요일별 청취 시간**을 막대 그래프로 보여준다. 막대는 아래에서 위로 차오르는 세로 막대, 가로축은 월~일 7개다.
- 주 경계는 **월요일 04:00 ~ 다음 월요일 03:59**다 — `content_stats` 주간 집계와 같은 경계를 재사용한다(`domain.md` 2). 클라이언트가 기기 시각으로 주를 나누지 않는다.
- 기본 표시는 **이번 주(진행 중인 주)** 다. 좌우 화살표로 주를 이동한다:
  - [◀ 이전 주] — **가입 주까지** 거슬러 갈 수 있다. 그보다 이전은 비활성.
  - [다음 주 ▶] — 이번 주에서는 비활성이다. 미래 주는 없다.
- 이전 주차 데이터는 **화살표를 눌렀을 때 주 단위로 추가 조회**한다. 한 번 받은 주는 화면을 벗어나기 전까지 다시 조회하지 않는다.
- 기록이 없는 요일은 0 막대(자리 유지), 한 주 전체가 0이면 그래프 자리에 빈 상태 문구를 보여준다. 막대 스케일 등 시각 표현은 uiux 문서가 정한다.

### 4.7 주제 분포 — 원형 그래프

- **어떤 주제의 콘텐츠를 주로 듣는지** 누적 청취 시간 기준 비율을 원형 그래프로 보여준다.
- **집계 기간은 가입 후 전체이며, 절대값(시간)은 표시하지 않고 비율만 보여준다**(합의 2026-08-06).
- **비율은 서버가 계산해 내려준다.** 집계 규칙:
  - 원천은 `play_records.listened_sec` × `content_topics`다.
  - 여러 주제에 속한 콘텐츠는 **각 주제에 청취 시간을 그대로 더한 뒤** 전체 합 대비 비율로 정규화한다(합 100%). 분할 배분하면 다주제 콘텐츠의 비중이 실제 청취보다 축소된다.
  - **상위 5개 주제 + 나머지는 "기타"** 로 묶어 내려준다.
- 숨겨진 주제(`topics.is_visible = false`)도 청취 기록이 있으면 집계에 포함한다 — 주제 분포는 관심사가 아니라 청취 이력의 집계라, 숨김 주제를 관심사에서 제거하는 결정(2026-08-11, `interest-management.md` 7장)의 대상이 아니다. 이미 들은 시간이 주제가 숨겨졌다고 사라지면 합계가 왜곡된다.
- 청취 기록이 없으면 그래프 대신 빈 상태 문구를 보여준다.

### 4.8 조회 실패 처리

- 프로필 조회가 실패해도 **화면 자체는 연다.** 각 카드에 "정보를 불러올 수 없어요" + [다시 시도]를 표시하고, 하위 화면으로 가는 내비게이션은 그대로 동작시킨다.
  - 이유: 요약을 못 받았다고 관심사 편집까지 막을 이유가 없다. 하위 화면은 자기 데이터를 직접 조회한다.
- **통계 조회만 실패하면** 통계 영역만 에러로 두고 카드는 정상 노출한다. 반대의 경우도 같다 — 부분 실패가 화면 전체를 덮지 않는다.
- 세션이 만료되면 공통 처리에 따라 시작 화면으로 이동한다(`common-error-handling.md`).

## 6. 데이터 모델

> **스키마는 [`docs/backend/domain.md`](../backend/domain.md)가 유일한 기준이다.** 이 문서에 테이블·컬럼을 중복 기재하지 않는다 — 두 벌을 유지하면 반드시 어긋나고, 수정 비용이 두 배가 된다.
> 컬럼을 추가·변경해야 하면 `domain.md`를 먼저 고치고 이 문서에는 동작 규칙만 남긴다.

|---|---|
| `users` — 닉네임·제공자·`email`·`is_email_verified`·커리어 3필드 | [3.1](../backend/domain.md#31-users) |
| `user_interests` — 선택 주제 요약(`is_active = true`) | 4.2 |
| `topics` — 주제명 표시 | 4.1 |
| `subscriptions` — 현재 플랜·다음 결제일·해지 예약 | 8.2 |
| `plans` — 플랜명·무료 티어 한도 | 8.1 |
| `email_verifications` — 이메일 인증 진행 상태 | 3.7 |
| `play_records` — 청취 통계의 원천(`listened_sec` · `play_date`) | 6.3 |

- **프로필 전용 테이블은 만들지 않는다.** 이 화면이 쓰는 값은 전부 기존 테이블에 있다.
- `content_stats`는 **콘텐츠 단위** 집계라 사용자 통계에 쓰지 않는다. 사용자 축 통계는 `play_records`에서 계산한다(파생값 — `domain.md` 1.5·6.3에 원천 명시, 2026-08-06). 사용자 단위 집계 캐시 테이블 신설 여부는 `domain.md` 15.1 결정 항목 #9로 등록됨(집계 비용 실측 후 판단).
- 커리어는 `users`에 병합돼 있다. `user_careers` 테이블은 없다(`domain.md` 3.1).

## 7. 예외 상황

- **이메일이 없는 사용자**: "등록되지 않음"을 표시할 뿐 진입을 막거나 강제하지 않는다. 강제 수집은 첫 결제에서만 한다.
- **카카오 미인증 이메일을 가진 사용자**: 주소와 함께 "인증되지 않음" 배지를 노출한다. 인증을 강제하지 않되, 결제 시점에 인증이 필요하다는 보조 문구를 함께 보여준다(`auth.md` 4.1).
- **이메일 변경 중 이탈**: 기존 이메일과 인증 상태가 유지된다. 프로필 값은 변하지 않는다(`auth.md` 4.4).
- **한 주소로 발송 5회를 소진한 상태에서 [변경] 탭**: 인증 화면은 열리며, **그 주소로의** 발송만 잠긴다. [메일 다시 입력]으로 다른 주소를 넣으면 정상 발송된다(`auth.md` 4.5).
- **관심 주제를 편집하고 돌아옴**: 요약을 재조회해 갱신한다. 편집 화면에서 [취소]로 나온 경우는 재조회하지 않는다.
- **다른 기기에서 구독을 해지한 상태**: 프로필 진입 시 구독 상태를 재동기화해 최신 값을 표시한다. `users.tier` 캐시가 어긋나 있으면 `subscriptions` 기준으로 갱신한다.
- **구독 조회만 실패**: 플랜 카드만 에러로 두고 나머지 항목은 정상 노출한다. 화면 전체를 에러로 덮지 않는다.
- **청취 기록이 전혀 없는 신규 사용자**: 통계 요약은 0으로, 그래프 두 개는 빈 상태 문구로 표시한다. 영역 자체를 숨기지 않는다 — 숨기면 무엇이 채워질 자리인지 알 수 없다.
- **통계 조회만 실패**: 통계 영역만 에러 + [다시 시도]로 두고 카드·내비게이션은 정상 동작한다.
- **04시 경계 부근 진입**: 오늘·이번 주의 경계는 서버가 내려준 값을 그대로 쓴다. 기기 시각과 어긋나 보여도 클라이언트가 보정하지 않는다.
- **오프라인 상태로 진입**: 마지막으로 받은 요약을 표시하고 상단에 오프라인 배너를 노출한다. 이메일 인증은 **온라인에서만** 가능하므로 탭 시 안내한다.
- **관심 주제가 관리자에 의해 숨겨진 경우**(`is_visible = false`): **요약 개수·대표 주제에서 제외한다**(결정 2026-08-11 — 숨김 주제는 모든 사용자에게서 제거된다). 편집 화면의 N/3과 같은 기준이라 프로필 카드와 편집 화면의 숫자가 어긋나지 않는다(`interest-management.md` 7장).
- **탈퇴 처리 직후 프로필 진입**: 토큰 갱신이 실패해 시작 화면으로 이동한다.

## 8. 완료 조건

- Given 로그인한 사용자 / When 하단 탭에서 [프로필]을 선택한다 / Then 플랜·이메일·관심 주제·커리어 네 항목과 우상단 설정 아이콘이 노출된다
- Given 프로필 화면 / When 우상단 설정 아이콘을 탭한다 / Then 설정 화면으로 이동한다
- Given 무료(라이트) 사용자 / When 프로필에 진입한다 / Then "무료 이용 중 · 하루 2편"과 구독 안내 진입점이 노출된다
- Given 프로 구독 중인 사용자 / When 프로필에 진입한다 / Then 플랜명과 다음 결제일이 표시되고, 해지 버튼은 프로필에 없다
- Given 해지를 예약한 사용자 / When 프로필에 진입한다 / Then "N월 N일까지 이용 가능"이 표시된다
- Given 이메일이 없는 사용자 / When 프로필에 진입한다 / Then "등록되지 않음"과 [등록]이 노출되고, 등록을 강제하는 팝업은 뜨지 않는다
- Given 이메일이 없는 사용자 / When [등록]을 탭하고 코드 인증을 완료한다 / Then 이메일이 저장되고 프로필로 복귀해 주소가 표시된다
- Given 카카오 미인증 이메일을 가진 사용자 / When 프로필에 진입한다 / Then 주소와 함께 **"인증되지 않음" 배지**, [인증하기]·[변경]이 노출된다
- Given 미인증 이메일을 가진 사용자 / When [인증하기]를 탭해 코드 인증을 완료한다 / Then 배지가 사라지고 주소만 표시된다
- Given 이메일 인증 화면에서 코드를 입력하지 않고 뒤로 나간다 / When 프로필을 확인한다 / Then 기존 상태가 그대로 유지된다
- Given 프로필에서 **같은 주소로** 인증 코드를 3회 발송했다 / When 설정 경로에서 그 주소로 코드를 발송한다 / Then 남은 횟수는 2회로 합산 적용된다
- Given 프로필에서 한 주소로 5회를 발송해 잠겼다 / When [메일 다시 입력]으로 다른 주소를 넣고 발송한다 / Then 정상적으로 발송된다
- Given 프로필 화면 / When [관심 주제 관리] 카드를 탭한다 / Then 관심사 관리 편집 화면으로 이동한다
- Given 프로필 화면 / When [커리어 정보] 카드를 탭한다 / Then 커리어 정보 화면으로 이동한다(관심사 관리 화면이 아니다)
- Given 관심 주제를 편집하고 저장한 뒤 뒤로 온다 / When 프로필을 본다 / Then 변경된 주제 개수와 대표 주제가 갱신되어 있다
- Given 커리어를 입력하지 않은 사용자 / When 프로필에 진입한다 / Then 커리어 항목에 입력 유도 문구와 [입력하기]가 노출된다
- Given 구독 정보 조회만 실패한다 / When 프로필에 진입한다 / Then 플랜 카드만 에러로 표시되고 나머지 항목과 내비게이션은 정상 동작한다
- Given 청취 기록이 있는 사용자 / When 프로필에 진입한다 / Then 카드 아래에 누적 청취 콘텐츠 수·누적 청취 시간·연속 청취 일수가 가로 한 줄로 노출된다
- Given 프로필 화면 / When 주간 그래프를 확인한다 / Then 이번 주(월~일)의 요일별 막대가 기본 표시되고 [다음 주 ▶]는 비활성이다
- Given 주간 그래프에서 이번 주를 보는 중 / When [◀ 이전 주]를 탭한다 / Then 지난주의 요일별 막대가 표시된다
- Given 가입 주의 그래프를 보는 중 / When 이전 주로 이동하려 한다 / Then [◀]가 비활성이라 이동하지 않는다
- Given 어제까지 5일 연속 청취했고 오늘은 아직 듣지 않은 사용자 / When 프로필에 진입한다 / Then 연속 청취 일수가 5일로 표시된다
- Given 청취 기록이 없는 신규 사용자 / When 프로필에 진입한다 / Then 통계 요약은 0으로, 그래프 자리는 빈 상태 문구로 표시되고 영역은 유지된다
- Given 여러 주제의 콘텐츠를 들어온 사용자 / When 주제 분포를 확인한다 / Then 서버가 계산한 비율이 상위 5개 주제 + "기타"의 원형 그래프로 표시된다
- Given 통계 조회만 실패한다 / When 프로필에 진입한다 / Then 통계 영역만 에러로 표시되고 카드 4개와 내비게이션은 정상 동작한다

## 미결 사항

- **닉네임 편집 허용 여부** — 현재는 소셜 제공자 값을 표시만 한다. 편집을 허용하면 금칙어 필터·길이 제한·중복 정책을 정해야 한다. 서비스에 타인에게 닉네임이 노출되는 지점이 없어 **MVP는 표시만으로 둔다.**
- **프로필 이미지** — 도입하지 않는다. 노출 지점이 없고 스토리지·중재 비용만 생긴다. 커뮤니티 기능이 생기면 재검토.
- **관심사·커리어를 프로필에서 인라인 편집할지** — 현재는 각 편집 화면으로 이동한다. 인라인으로 바꾸면 저장 규칙이 두 벌이 되므로 권장하지 않으나, 이동 단계가 길다는 피드백이 나오면 재검토.
