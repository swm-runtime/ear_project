# 소셜 로그인 · 계정 기능 명세서

> 연결 PRD: FR-01, FR-02 / 사용자흐름 5.1

## 1. 목적 & 연결

네이버·카카오·구글·애플 소셜 로그인만으로 가입과 인증을 처리한다. 자체 아이디/비밀번호는 만들지 않는다. 로그아웃·회원 탈퇴도 이 기능에 포함된다.

**애플은 iOS 심사 요건이다.** App Store 심사 가이드라인 4.8에 따라 다른 소셜 로그인을 제공하는 iOS 앱은 Sign in with Apple을 함께 제공해야 한다. 넣고 빼는 선택지가 아니다.

**이메일은 제공자에게서 받아 저장하는 것이 기본이다.** 다만 **저장과 인증은 별개다.** 제공자가 준 주소는 저장하되, 그 주소가 제공자 쪽에서 인증된 것인지를 `users.is_email_verified`에 함께 기록한다. 인증되지 않은 주소는 첫 결제 직전에 우리 코드 인증을 거쳐야 한다(4.4). 제공자가 주지 않았거나 발송이 불가능한 주소(마스킹)면 `users.email = null`로 둔다.

**이메일은 가입 조건이 아니다.** 제공자가 이메일을 주지 않아도 가입은 그대로 진행된다. 사용자가 먼저 등록하고 싶으면 **설정 또는 프로필 화면**에서 언제든 등록·변경할 수 있다.

**이메일 인증은 코드 인증 방식이다.** 입력한 주소로 인증 코드를 보내고, 사용자가 그 코드를 입력해야 저장한다. 상세 규칙은 4.5.

- PRD FR-01 (P0) 소셜 로그인으로 가입·인증 — 네이버·카카오·구글·애플
- PRD FR-02 (P0) 로그아웃·회원 탈퇴, 탈퇴 시 사용자 데이터 처리
- PRD 7 비기능 (소셜 로그인 기반 인증, 개인정보보호법 준수)

## 2. 진입 조건

- **로그인**: 시작 화면(서비스 소개)에서 [시작하기] 또는 제공자 버튼을 탭할 때
- **재인증**: 토큰 갱신 실패로 세션이 끊겨 시작 화면으로 돌아온 때
- **로그아웃**: 설정 > 계정 > 로그아웃
- **탈퇴**: 설정 > 계정 > 회원 탈퇴
- **이메일 등록(강제)**: 이메일이 없는 사용자가 구독 결제를 시도할 때 (4.4)
- **이메일 등록·변경(자발)**: 설정 > 계정 > 이메일, 또는 프로필 > 이메일 (`profile.md` 4.3)

## 3. 입력값

**로그인**

| 값 | 설명 | 필수 |
|---|---|---|
| provider | kakao / naver / google | 필수 |
| provider_token | 제공자 SDK가 반환한 인증 코드 또는 액세스 토큰 | 필수 |
| device_id | 기기 식별자(푸시 토큰 매핑용) | 필수 |

- **로그인 요청에 동의 값을 싣지 않는다.** 동의는 로그인 성공 이후 별도 화면에서 받는다(4.1).

**약관 동의** — 신규 가입 시 별도 화면

| 값 | 설명 | 필수 |
|---|---|---|
| agreed_terms | 이용약관 동의 + 약관 버전 | 필수 |
| agreed_privacy | 개인정보 처리방침 동의 + 방침 버전 | 필수 |
| agreed_marketing | 마케팅 수신 동의 | 선택 |

- 동의 3종은 **개정 시점이 서로 다르므로 각각 별개로 기록한다**(`consents.consent_type`). 마케팅 동의만 껐다고 약관 동의 이력이 함께 갱신되면 안 된다.
- **마케팅 동의는 동의일로부터 2년마다 재확인한다**(정보통신망법 제50조 제8항, PRD 7장 — 합의 2026-08-06). 재확인 알림·기록은 **서버가 처리한다** — 저장 구조 확정(2026-08-06, `domain.md` 3.2): 동의·철회·재동의 모두 `consents` 행 추가로 기록하고 최신 동의 행의 `agreed_at`이 2년 기산점이다(별도 컬럼 없음). 재확인 통지 발송 기록은 `notification_logs`. 철회 경로는 설정 알림 섹션의 토글이다(`settings.md` 4.1).

**이메일 등록·인증** — 첫 결제 직전 또는 설정·프로필(4.4)

| 값 | 설명 | 필수 |
|---|---|---|
| email | 사용자가 직접 입력 | 필수 |
| verification_code | 메일로 받은 6자리 숫자 코드 | 필수 |

- 두 값은 **한 번에 보내지 않는다.** `email`로 코드 발송을 요청하고(1단계), 발송 성공으로 만들어진 인증 건에 `verification_code`를 검증한다(2단계).
- 클라이언트는 "인증 완료" 상태를 서버에 보내지 않는다. 코드 검증에 성공한 **서버가** `users.email`을 저장한다.

**탈퇴**

| 값 | 설명 | 필수 |
|---|---|---|
| reason_code | 탈퇴 사유(선택형) | 선택 |
| reason_text | 자유 입력 | 선택 |
| confirm | 안내 확인 체크 | 필수 |

## 4. 처리 로직

### 4.1 로그인·가입

1. 사용자가 제공자 버튼 탭 → 해당 SDK 인증 플로우 실행(앱 전환 또는 웹뷰)
2. 제공자 인증 성공 → `provider_token`을 서버로 전달
3. 서버가 제공자에게 토큰 검증 및 프로필(고유 ID, 이메일, 닉네임) 조회
4. `provider + provider_user_id` 조합으로 기존 계정 조회
   - **기존 계정 있음** → 로그인 처리. `onboarding_completed`에 따라 라이브러리 또는 온보딩으로 분기
   - **기존 계정 없음** → **약관 동의 화면**(별도 페이지)으로 이동 → 동의 완료 시 계정 생성 → **온보딩 첫 단계**로 이동
5. 서버는 access_token(단기) + refresh_token(장기)을 발급, 클라이언트는 보안 저장소에 저장
6. **동일 이메일 다른 제공자**: 별개 계정으로 처리한다(계정 통합·연동은 MVP 비범위). 단 로그인 화면에서 "이전에 OO로 가입한 이력이 있어요" 안내는 표시하지 않는다 — 개인정보 노출 우려.

**약관 동의는 별도 화면에서만 받는다**

- 시작 화면에는 **"계속하면 약관에 동의한 것으로 봅니다" 같은 묵시적 동의 문구를 두지 않는다.** 약관·개인정보 처리방침 **링크만** 제공하고, 동의 의미는 부여하지 않는다.
  - 이유: 시작 화면에서 묵시적으로 동의시키면 별도 화면의 명시적 동의와 이중이 되고, 어느 시점의 동의를 기록해야 하는지가 모호해진다.
- 동의 화면은 **로그인 성공 이후**에만 노출된다. 제공자 인증조차 하지 않은 사용자에게는 띄우지 않는다.
- 필수 2종을 모두 체크해야 [동의하고 시작하기]가 활성화된다. **이 버튼을 누른 시점에 계정이 생성된다.**

**제공자 이메일은 인증 여부를 함께 판정해 저장한다**

- 4.1-3의 프로필 조회에서 이메일이 오면 **주소와 인증 여부를 함께 판정해** `users.email` · `users.is_email_verified`에 저장한다.
- **카카오는 응답의 두 플래그를 모두 확인한다** — `kakao_account.is_email_valid`(주소가 유효한지)와 `kakao_account.is_email_verified`(카카오가 소유를 확인한 주소인지). **둘 다 `true`일 때만 인증된 이메일로 취급한다.**

| `is_email_valid` | `is_email_verified` | 저장 | 결제 시점 |
|---|---|---|---|
| true | true | `email` = 받은 주소, `is_email_verified = true` | 인증 화면 없이 바로 결제 |
| true | false | `email` = 받은 주소, `is_email_verified = false` | **인증 화면으로 보낸다** (4.4) |
| false | — | **`email = null`** (마스킹 주소) | 이메일 입력부터 (4.4) |

- **`is_email_valid = false`면 카카오가 주소를 마스킹해서 내려준다**(`ka***@kakao.com`). 발송도 불가능하고 거래 주체 식별에도 쓸 수 없으므로 **저장하지 않고 `null`로 둔다.** 마스킹 여부를 문자열 패턴(`***`)으로 추측하지 않고 **`is_email_valid` 플래그로 판정한다** — 패턴 매칭은 제공자가 마스킹 형식을 바꾸면 그대로 뚫린다.
- **`is_email_verified = false`인 주소는 값은 온전하지만 카카오가 소유를 확인하지 않은 주소다.** 저장은 하되 인증된 것으로 취급하지 않는다. 메일이 도달하지 않을 수 있어 거래기록 보존 목적(4.4)을 담보하지 못하기 때문이다.
- **구글·네이버는 인증된 주소만 내려준다고 보고 `is_email_verified = true`로 저장한다.** 두 제공자는 카카오의 두 플래그에 대응하는 값을 별도로 주지 않는다. 다만 구글이 `email_verified` 클레임을 내려주면 그 값을 그대로 쓴다. (연동 스펙의 인증 플래그 제공 여부 확인 필요 — 미결 사항 "구글·네이버의 이메일 인증 여부 판정" 참조. FR-39는 "판정해 저장"을 요구한다.)
- **애플은 두 가지가 다르다.** ① 이메일·이름은 **최초 인가 때 한 번만** 내려온다. 재로그인 시에는 오지 않으므로 **첫 응답에서 반드시 저장한다** — 놓치면 사용자가 애플 설정에서 앱 연동을 해제하기 전까지 다시 받을 수 없다. ② 사용자가 "이메일 가리기"를 고르면 릴레이 주소(`...@privaterelay.appleid.com`)가 온다. **값이 온전하고 발송도 되므로 저장하고 `is_email_verified = true`로 둔다** — 카카오의 마스킹 주소(발송 불가)와 다르다. 다만 사용자가 언제든 전달을 끊을 수 있어 도달을 영구히 보장하지는 않는다.
- **인증된 주소에는 우리 코드 인증을 다시 요구하지 않는다.** 제공자가 이미 소유를 확인한 주소를 다시 확인하는 것은 같은 검증을 두 번 하는 것이고, 가입 직후 인증 단계를 끼워 넣으면 이탈만 늘어난다. 따라서 **인증된 소셜 이메일로 가입한 사용자는 결제 시점에 인증 화면을 보지 않는다**(4.4).

**이메일 없이도 가입할 수 있다**

- 제공자가 이메일을 주지 않으면 `users.email = null`로 저장하고 **가입을 그대로 진행한다.** 이메일을 가입 조건으로 두지 않는다.
  - 카카오는 이메일이 없는 계정(휴대폰 번호로만 가입)이 존재하며, 동의항목을 필수로 설정해도 값이 오지 않을 수 있다.
  - 카카오 동의항목의 `카카오계정(이메일)`은 **선택 동의로 설정한다.** 필수 동의는 개인정보보호법 제16조의 최소수집 원칙과 충돌할 소지가 있다 — 로그인·식별에는 `provider + provider_user_id`로 충분하기 때문이다.
- 계정 식별은 항상 `provider + provider_user_id`로 한다. **이메일을 식별자로 쓰지 않는다.**

### 4.2 로그아웃

1. 확인 팝업 노출
2. 서버에 refresh_token 폐기 요청 → 실패해도 진행
3. 로컬 토큰·캐시(라이브러리 캐시, 재생 위치, (오프라인 저장분 — P1 도입 시)) 삭제
4. 푸시 토큰 등록 해제
5. 시작 화면으로 이동(스택 전체 초기화)

### 4.3 회원 탈퇴

1. 탈퇴 안내 화면 — **삭제되는 데이터와 보존되는 데이터를 모두** 명시하고, 구독 상태·재가입 제한을 안내한다
   - **결제 이력 유무에 따라 고지 문구가 갈린다.** 어느 쪽인지는 **서버가 판정해 내려준다** — 클라이언트가 로컬 구독 상태로 추측하지 않는다
     - **결제 이력 있음**: "결제·구독 이력과 이메일 주소는 관련 법령에 따라 **5년간 보관**됩니다"를 삭제 항목과 나란히 노출한다
     - **결제 이력 없음**: 보존 항목이 없으므로 "**모든 데이터가 즉시 삭제됩니다**"만 노출한다. 5년 보관 문구를 띄우지 않는다
   - 이유: 실제로는 보존되는데 삭제 항목만 보여주면 사용자가 "전부 지워진다"고 이해한 채 탈퇴하게 된다. 반대로 **보존할 것이 없는데 5년 보관을 고지하면 사실과 다른 안내**가 되어 같은 문제를 반대 방향으로 만든다
   - 보존 근거는 전자상거래법 시행령 제6조(거래기록 5년)이며, **거래가 없으면 그 근거 자체가 성립하지 않는다**(4단계)
2. **구독 활성 상태 확인**
   - 활성 구독이 있으면 "스토어에서 구독 해지를 먼저 진행해야 결제가 중단된다"는 안내를 노출한다(스토어 구독은 앱 탈퇴로 자동 해지되지 않음)
   - **안내는 텍스트로만 한다.** 스토어 구독 관리 화면으로 보내는 버튼·딥링크를 탈퇴 화면에 두지 않는다
     - 이유: 탈퇴 도중 외부 앱으로 이탈시키면 돌아오지 못하고 흐름이 끊긴다. 해지 진입점은 설정 > 구독 관리에 이미 있다(`subscription.md` 4.5)
   - **구독 만료에 동의해야만 탈퇴를 진행할 수 있다.** 동의 체크 없이는 [탈퇴하기]를 활성화하지 않는다
3. 사유 입력(선택) → 최종 확인 체크 → [탈퇴하기]
4. 서버 처리 — **결제 이력 유무로 갈린다.** 이관과 파기는 **하나의 트랜잭션**에서 수행한다 (상세: `domain.md` 12.3)
   - **판정 기준은 `subscriptions` 행의 존재 여부다.** 무료(`light`) 사용자는 구독 행이 생기지 않으므로(`domain.md` 1.3), 행이 하나라도 있으면 결제 이력이 있는 것으로 본다. 환불(`refunded`)·만료(`expired`) 건도 거래기록이므로 포함한다
   - **결제 이력이 있는 사용자**
     - **즉시 파기**: 라이브러리·관심사·커리어·재생 위치·재생 기록·소비 신호·설정·기기 토큰·세션·알림 로그·드립 제외 목록·이메일 인증 기록
     - **아카이브 후 파기(5년)**: 계정 정보 → `archived_users`, 동의 이력 → `archived_consents`, 구독 이력 → `archived_subscriptions`
       - 보존 범위는 **거래 주체 식별에 필요한 최소치**다 — 전자우편주소·제공자 계정 ID·구독 이력. 닉네임·커리어·관심사는 보존하지 않는다
       - 운영 테이블과 **물리적으로 분리된 스키마**에 저장한다(개인정보보호법 제21조 제3항, 전자상거래법 시행령 제6조의 별도 보존 의무)
   - **결제 이력이 없는 사용자 — 아카이브하지 않고 전량 즉시 파기한다**
     - `archived_users` · `archived_consents` · `archived_subscriptions` 어디에도 행을 만들지 않는다
     - 근거: **개인정보보호법 제21조 제1항의 원칙은 파기이고, 보존은 다른 법령에 근거가 있을 때만 허용되는 예외다.** 거래가 없으면 전자상거래법 시행령 제6조가 보존을 허용하는 대상(거래기록, 그리고 그와 관련된 거래 주체 식별 정보)이 애초에 존재하지 않는다. 근거 없이 5년을 보관하는 것은 그 자체가 제21조 제1항 위반이다
   - `withdrawal_logs`는 두 경우 모두 남긴다. 식별자 없는 해시라 개인정보가 아니다(`domain.md` 3.4)
   - `users` 행은 두 경우 모두 **삭제한다.** `status = withdrawn`으로 남겨두지 않는다
5. 로컬 데이터 전량 삭제 → 시작 화면으로 이동
6. 동일 소셜 계정으로 재가입은 즉시 허용하되, 신규 계정으로 취급한다(이전 데이터 복구 불가)

### 4.4 이메일 등록 — 진입 경로

가입 시점이 아니라 **이메일이 실제로 필요해지는 시점**에 받는다. 다만 사용자가 먼저 등록하겠다면 막지 않는다.

| 경로 | 성격 | 진입점 |
|---|---|---|
| **첫 결제 직전** | 강제 — 이 단계를 통과해야 결제가 시작된다 | 결제 시도 시 자동 |
| **설정 > 계정 > 이메일** | 자발 — 등록·변경 모두 가능 | `settings.md` 4.1 |
| **프로필 > 이메일** | 자발 — 등록·변경 모두 가능 | `profile.md` 4.3 |

- 세 경로는 **같은 인증 화면과 같은 코드 규칙(4.5)을 쓴다.** 화면을 따로 만들지 않는다 — 규칙이 갈라지면 발송 횟수 제한이 경로별로 새는 구멍이 된다.
- 다른 점은 **인증 성공 후 어디로 돌아가는가** 하나뿐이다. 결제 경로는 원래 결제 플로우로, 설정·프로필 경로는 직전 화면으로 복귀한다.
- 결제 경로만 이탈 시 결제를 중단한다. 설정·프로필 경로에서 이탈하면 기존 이메일 값이 그대로 유지될 뿐 다른 영향이 없다.

**왜 결제 시점인가** (강제 수집 근거)

- 로그인·식별·알림에는 이메일이 필요 없다. 필요한 곳은 **탈퇴 후 거래기록 보존** 하나뿐이고, 그건 결제한 사용자에게만 발생한다.
- 개인정보보호법 제16조는 "목적에 필요한 **최소한**"만 수집하도록 하고, **최소한이라는 입증책임을 사업자에게** 지운다. 무료 사용자 전원에게 가입 단계에서 강제하면 이 기준을 충족하기 어렵다.
- 반면 결제 사용자에게는 근거가 분명하다 — 전자상거래법 시행령 제6조의 거래기록 보존, 그리고 `archived_users`의 거래 주체 식별(`domain.md` 11.3).

**처리 순서 — 결제 경로**

```
결제 시도
   ↓
users.email · users.is_email_verified 확인
   ├─ 값 있음 + 인증됨   → 결제 플로우 진행 (subscription.md 4.2)
   │
   ├─ 값 있음 + 미인증   → 인증 선택 화면
   │                        ├─ [이 주소로 인증] → 그 주소로 코드 발송
   │                        └─ [다른 메일 입력] → 이메일 입력 화면
   │
   └─ null              → 이메일 입력 화면
                              ↓
                          이메일 입력 → 인증 코드 발송 → 코드 입력 → 검증 성공
                              ↓
                          users.email 저장 + is_email_verified = true
                              ↓
                          원래 시도했던 결제 플로우로 복귀
```

- **인증이 끝나기 전에는 결제를 시작하지 않는다.** 결제만 되고 이메일이 없는 상태를 만들지 않기 위해서다.
- **`email`에 값이 있어도 `is_email_verified = false`면 결제를 막는다.** 주소가 저장돼 있다는 것과 그 주소로 메일이 도달한다는 것은 다르다. 거래기록 보존 목적은 도달하는 주소여야 달성된다.
- **미인증 사용자에게는 두 갈래를 준다** — 저장된 주소를 그대로 인증하거나, 다른 주소로 바꿔서 인증하거나. 카카오가 준 주소를 사용자가 더는 쓰지 않는 경우가 있으므로 그대로 인증하도록 강요하지 않는다.
  - 인증 선택 화면은 **어느 주소를 쓸지만 고르는 화면이다.** 두 갈래 모두 이후에는 4.5의 같은 코드 규칙을 따른다.
  - [이 주소로 인증]을 고르면 이메일 입력 화면을 건너뛰고 바로 코드가 발송된다.
- 인증 화면에서 이탈하면 **`is_email_verified`를 바꾸지 않고** 결제도 진행하지 않는다. 다음 결제 시도 시 같은 화면부터 다시 시작한다.
- 이미 인증된 이메일이 있는 사용자는 이 단계를 **건너뛴다.** 재확인·재인증을 요구하지 않는다.
- **코드 인증(4.5)을 거치는 대상은 두 가지다** — 사용자가 직접 입력한 주소, 그리고 제공자가 줬지만 인증되지 않은 주소. 제공자가 준 **인증된** 주소는 이 화면에 들어오지 않는다(4.1).
- **마스킹 주소**(`ka***@kakao.com`)는 가입 시 `null`로 뒀으므로 이메일 입력부터 시작한다.

**처리 순서 — 설정·프로필 경로**

```
설정 > 계정 > 이메일  또는  프로필 > 이메일
   ↓
현재 이메일 표시(없으면 "등록되지 않음")
   ↓
새 이메일 입력 → 인증 코드 발송 → 코드 입력 → 검증 성공
   ↓
users.email 저장(변경이면 기존 값 덮어씀)
   ↓
직전 화면으로 복귀 + 토스트 "이메일이 등록되었어요"
```

- **변경도 신규 등록과 같은 절차를 거친다.** 새 주소로 코드를 보내 검증해야 바뀐다.
- **검증 성공 시점에만 값이 바뀐다.** 새 주소를 입력하고 코드 발송까지 했더라도, 검증 전에 이탈하면 **기존 이메일이 그대로 남는다.** 중간 상태를 `users.email`에 쓰지 않는다.
- 기존 이메일과 동일한 주소를 입력하면 코드를 보내지 않고 "이미 등록된 이메일이에요"로 막는다. 발송 횟수를 소모시키지 않는다.

### 4.5 이메일 인증 코드 규칙

**코드 규칙**

| 항목 | 값 |
|---|---|
| 인증 방식 | 이메일로 발송한 인증 코드 입력 |
| 코드 형식 | **6자리 숫자** |
| 코드 유효 시간 | **3분** |
| 동시 유효 코드 | **1개** — 재발송 시 이전 코드는 즉시 무효 |
| 코드당 검증 시도 | **5회** — 소진 시 코드 무효, 재발송 필요 |
| 발송 가능 횟수 | **이메일 주소당 5회** |
| 발송 횟수 초기화 | 그 주소의 5회 소진 시점으로부터 **1시간 후** |
| 재발송 쿨다운 | 직전 발송으로부터 **30초** |
| 계정 단위 발송 상한 | **1시간 20회 / 하루 50회** — 백스톱. **클라이언트 비노출**(아래) |

- 코드는 **원문을 저장하지 않고 해시로 저장한다.** `sessions.refresh_token_hash`와 같은 규칙이다(`domain.md` 3.3).
- 유효 시간 3분은 **발송 시각 기준**이다. 화면에는 남은 시간을 `mm:ss`로 카운트다운한다.
- 만료된 코드를 입력하면 "인증 시간이 지났어요. 코드를 다시 받아주세요"로 안내하고 **재발송을 유도한다.** 만료 여부는 서버가 판정한다 — 클라이언트 타이머는 표시용이다.
- 코드 검증 실패 응답에 **"코드가 틀림"과 "코드가 만료됨"을 구분해서 내려준다.** 둘을 뭉뚱그리면 사용자가 재발송해야 하는지 다시 입력해야 하는지 알 수 없다.
- 존재 여부·검증 결과에 관계없이 **응답 시간을 일정하게** 유지한다(타이밍 공격 방지).

**발송 횟수 5회 제한 — 이메일 주소 단위**

- **`(계정, 이메일 주소)` 조합을 카운트 키로 쓴다.** 계정 단위로 세지 않는다.
  - 이유: 오타로 잘못된 주소를 넣으면 그 주소로는 메일이 영영 도착하지 않는데, 계정 단위로 세면 **틀린 주소가 맞는 주소의 기회까지 소진한다.** 사용자는 잘못한 것 없이 1시간을 기다리게 된다.
  - 잘못 입력했다면 코드 입력 화면의 **[메일 다시 입력]** 으로 돌아가 다른 주소를 넣는다. 새 주소는 자기 몫의 5회를 새로 갖는다.
- 실제로 **발송에 성공한 건만** 카운트한다. 메일 발송 자체가 실패하면 횟수를 차감하지 않는다.
- 한 주소로 5회를 모두 쓰면 **그 5회째 발송 시각 + 1시간** 동안 **그 주소로의 발송만** 잠긴다. 그 시점이 지나면 해당 주소의 카운트가 0으로 초기화되고 다시 5회를 쓸 수 있다.
  - 잠긴 동안에도 **이미 받은 코드의 입력은 막지 않는다.** 유효 시간(3분)이 남아 있으면 그 코드로 인증을 끝낼 수 있다. 잠기는 것은 발송이지 검증이 아니다.
  - 잠금 안내에는 **남은 시간을 분 단위로 표시한다.** "잠시 후 다시 시도해주세요"만으로는 언제 풀리는지 알 수 없어 CS 문의가 된다.
  - **한 주소가 잠겨도 다른 주소로는 발송할 수 있다.** [메일 다시 입력]으로 주소를 바꾸면 된다.
- 이 제한은 **3개 진입 경로(결제·설정·프로필)에 합산 적용된다.** 같은 주소라면 경로를 옮겨 다녀도 카운트를 공유한다.
- 발송 잠금 중에 결제를 시도하면 **그 주소로는 결제를 진행시키지 않는다.** 이메일 인증 없이 결제를 통과시키지 않는다(4.4). 다만 다른 주소로 인증을 끝내면 결제는 진행된다.

**계정 단위 발송 상한 — 백스톱** (확정 2026-08-10)

- 주소 단위 5회 위에 **계정 단위 상한을 얹는다: 최근 1시간 20회 / 최근 24시간 50회**(주소 무관 합산, 3개 진입 경로 공통). [메일 다시 입력]으로 주소를 계속 갈아 끼워도 한 계정이 보낼 수 있는 총량이 잡힌다 — 서비스가 제3자에게 메일을 보내는 발송기로 악용되는 것과 발신 도메인 평판 훼손을 막는 백스톱이다.
- **클라이언트에 노출하지 않는다.** 남은 횟수·전용 잠금 화면·안내 문구를 두지 않는다 — 정상 사용자는 주소당 5회와 쿨다운 30초에 먼저 걸려 이 상한에 도달할 수 없고, 노출하면 우회 힌트만 준다. 초과 시 발송 요청은 공통 에러 계약의 일반 오류로 처리된다(`common-error-handling.md`).
- 판정·집계는 **서버 소유**다 — 발송 이력(`email_verifications`, `domain.md` 3.7)으로 계산한다. 클라이언트 대응 작업은 없다.

**[메일 다시 입력]**

- 코드 입력 화면에 **항상 노출한다.** 오타를 냈든 다른 주소를 쓰기로 마음을 바꿨든, 사용자가 스스로 빠져나올 수 있어야 한다. 이 버튼이 없으면 잘못 입력한 사용자에게 남는 선택지는 이탈뿐이다.
- 누르면 **이메일 입력 화면으로 돌아가고, 직전에 입력한 주소가 채워진 상태로 시작한다.** 오타는 대개 한두 글자이므로 처음부터 다시 치게 하지 않는다.
- **돌아가는 순간 직전 코드는 무효가 된다.** 유효한 코드는 항상 마지막 1개다.
- **같은 주소로 다시 보내는 것은 [재전송]과 동일하다.** 30초 쿨다운과 그 주소의 5회 제한이 그대로 적용된다 — [메일 다시 입력]을 경유해 쿨다운을 회피할 수 없다.

**서버가 판정한다**

- 유효 시간·발송 횟수·시도 횟수는 **전부 서버에서 판정한다.** 클라이언트의 카운트다운과 버튼 비활성화는 UX 보조일 뿐이며, 앱을 재설치하거나 다른 기기에서 시도해도 제한이 그대로 적용돼야 한다.
- 재발송 쿨다운(30초)도 서버가 함께 검사한다. 클라이언트 타이머만으로 막으면 우회된다.
- **주소별 카운트는 서버가 `email_verifications`(`domain.md` 3.7)로 관리한다.** 클라이언트는 남은 횟수·잠금 해제 시각을 서버 응답으로만 알 수 있다.

| 제공자 인증 중 | 외부 앱·웹뷰 전환. 복귀까지 로딩 오버레이 |
| 사용자가 인증 취소 | 시작 화면으로 복귀, 별도 에러 문구 없음 |
| 인증 실패 | 토스트 "로그인에 실패했어요. 다시 시도해주세요" |
| 신규 가입 | **별도 약관 동의 화면**. 전체 동의 / 필수 2종 / 선택 1종. 필수 전체 체크 시 [동의하고 시작하기] 활성 |
| 인증 선택 (결제 전, 미인증 이메일 보유) | 저장된 주소 표시 + [이 주소로 인증] + [다른 메일 입력]. "이 주소로 메일이 도착하는지 확인이 필요해요" 안내 |
| 이메일 입력 (결제 전) | 이메일 입력 필드 + [인증 코드 받기]. 진입 사유 안내 문구 노출 |
| 이메일 입력 (설정·프로필) | 현재 이메일 표시 + 새 이메일 입력 필드 + [인증 코드 받기]. 진입 사유 문구 없음 |
| 형식 오류 | [인증 코드 받기] 비활성 + 인라인 "이메일 형식을 확인해주세요" |
| 코드 발송 중 | 버튼 로딩, 중복 탭 차단 |
| 인증 코드 확인 | 발송한 주소 표시 + 6자리 코드 입력 + **남은 시간 `mm:ss` 카운트다운(3분)** + [재전송](30초 쿨다운, `N초 후 재전송`) + **[메일 다시 입력]** |
| 메일 다시 입력 | 이메일 입력 화면으로 복귀, **직전 주소가 채워진 상태.** 직전 코드는 무효 |
| 코드 불일치 | 인라인 "인증 코드가 올바르지 않아요 (남은 시도 N회)". 입력값 유지. [메일 다시 입력] 계속 노출 |
| 코드 만료 (3분 경과) | 카운트다운 `00:00` + 입력 비활성 + "인증 시간이 지났어요. 코드를 다시 받아주세요" + [재전송] 활성 |
| 시도 5회 소진 | 코드 무효화 + "코드를 다시 받아주세요" + [재전송] 활성 |
| 발송 5회 소진 (해당 주소) | [재전송] 비활성 + "이 주소로 보낼 수 있는 횟수를 모두 사용했어요. **약 N분 후** 다시 시도해주세요" + **[메일 다시 입력] 활성** (다른 주소는 발송 가능) |
| 인증 성공 (결제 경로) | 원래 결제 흐름으로 복귀 |
| 인증 성공 (설정·프로필) | 직전 화면 복귀 + 토스트 "이메일이 등록되었어요" |
| 메일 발송 실패 | 토스트 "인증 메일을 보내지 못했어요. 다시 시도해주세요" + 발송 횟수 미차감 |
| 서버 처리 중 | 버튼 로딩 상태, 중복 탭 차단 |
| 로그인 성공 | 온보딩 또는 라이브러리로 전환 |
| 탈퇴 안내 (결제 이력 있음) | **삭제 항목 + 5년 보존 항목** 리스트 + 구독 안내(활성 시, **텍스트만**) + 구독 만료 동의 체크 + 사유 선택 + 확인 체크박스 |
| 탈퇴 안내 (결제 이력 없음) | **삭제 항목 리스트 + "모든 데이터가 즉시 삭제됩니다"** + 사유 선택 + 확인 체크박스. **5년 보존 안내·구독 만료 동의 없음** |
| 탈퇴 처리 중 | 전체 화면 로딩(취소 불가) |
| 탈퇴 완료 | "탈퇴가 완료되었습니다" 토스트 후 시작 화면 |

## 6. 데이터 모델

> **스키마는 [`docs/backend/domain.md`](../backend/domain.md)가 유일한 기준이다.** 이 문서에 테이블·컬럼을 중복 기재하지 않는다 — 두 벌을 유지하면 반드시 어긋나고, 수정 비용이 두 배가 된다.
> 컬럼을 추가·변경해야 하면 `domain.md`를 먼저 고치고 이 문서에는 동작 규칙만 남긴다.

| 사용하는 것 | domain.md |
|---|---|
| `users` — 계정·역할·티어 캐시, `email` · `is_email_verified` | [3.1](../backend/domain.md#31-users) |
| `consents` — 동의 이력(append-only) | 3.2 |
| `sessions` | 3.3 |
| `withdrawal_logs` | 3.4 |
| `email_verifications` — 코드 해시·만료·검증 시도·주소별 발송 순번 | 3.7 |
| `archived_users` · `archived_consents` · `archived_subscriptions` — 탈퇴 후 보존 | 11장 |
| 탈퇴 시 파기·보존 정책과 법적 근거 | 12장 |

- **`users.is_email_verified`가 인증 여부의 유일한 기준이다.** 제공자 응답(카카오의 `is_email_valid`·`is_email_verified`)은 가입 시점에 이 컬럼으로 환산해 저장하고, 이후 판정에 원본 플래그를 다시 조회하지 않는다 — 제공자 응답은 재로그인 때마다 달라질 수 있고, 우리 코드 인증으로 확인한 주소는 제공자와 무관하기 때문이다.
- 발송 횟수는 컬럼이 아니라 **`email_verifications`의 행으로 센다.** `(user_id, email)`당 5행이 한 창이다(`domain.md` 3.7).
- 인증 완료 건은 오래 보존하지 않는다. 만료·완료된 행은 배치로 정리한다(개인정보 최소보유).

## 7. 예외 상황

- **제공자 인증 후 서버 통신 실패**: 제공자 로그인은 성공했지만 서버 등록이 실패한 상태. 재시도 버튼 제공, 재시도 시 같은 `provider_token`이 만료됐을 수 있으므로 제공자 인증부터 다시 수행한다.
- **약관 동의 화면에서 이탈**: 계정을 생성하지 않는다(동의 완료 시점에 생성). 다시 로그인하면 약관 동의부터 재시작.
- **약관이 개정된 뒤 기존 사용자가 접속**: 재동의 판정은 서버가 `consents`의 최신 버전과 현행 버전을 비교해서 한다. 클라이언트가 보낸 버전을 신뢰하지 않는다 — 앱 삭제·기기 변경 시 로컬 값이 사라지기 때문이다.
- **제공자 앱 미설치**: 웹 로그인으로 폴백한다.
- **제공자가 이메일을 제공하지 않는 경우**: `users.email = null`로 저장하고 가입을 그대로 진행한다. 이메일을 가입 조건으로 두지 않는다(4.1).
  - 카카오는 선택 동의 거부뿐 아니라 **계정 자체에 이메일이 없는 경우**(휴대폰 번호로만 가입)에도 값이 오지 않는다. 동의항목을 필수로 설정해도 마찬가지다.
- **카카오가 `is_email_valid = false`인 이메일을 준 경우**: 주소가 마스킹되어(`ka***@kakao.com`) 내려오므로 발송도 식별도 불가능하다. **저장하지 않고 `null`로 둔다.** 결제 시점에 4.4로 직접 받는다.
- **카카오가 `is_email_valid = true` · `is_email_verified = false`인 이메일을 준 경우**: 주소는 온전하므로 **저장하되 `is_email_verified = false`로 둔다.** 결제 시점에 인증 선택 화면으로 보내 그 주소를 인증하거나 다른 주소로 바꾸게 한다(4.4).
- **미인증 이메일을 가진 사용자가 설정·프로필에 들어온 경우**: 현재 주소를 "인증되지 않음" 상태로 표시하고, 결제를 기다리지 않고 지금 인증할 수 있게 한다. 인증 절차는 4.5로 동일하다.
- **이메일 인증 화면에서 이탈(결제 경로)**: 이메일을 저장하지 않고 결제도 진행하지 않는다. 다음 결제 시도 시 같은 화면부터 재시작한다.
- **이메일 변경 중 이탈(설정·프로필 경로)**: **기존 이메일이 그대로 유지된다.** 검증 성공 전에는 `users.email`을 건드리지 않기 때문이다.
- **인증 코드 입력 중 앱 종료**: 코드는 서버에 유효 시간과 함께 남아 있으므로 재진입 시 재발송 없이 이어서 입력할 수 있다. 남은 시간은 **서버가 준 만료 시각으로 다시 계산한다** — 클라이언트 타이머를 복원하지 않는다. 3분이 지났으면 재발송부터.
- **코드를 3분 안에 못 넣은 경우**: 만료로 처리하고 재발송을 유도한다. 만료된 코드는 이후 정답이어도 통과시키지 않는다.
- **재발송을 눌러 새 코드를 받은 뒤 이전 코드를 입력**: 실패로 처리한다. 유효한 코드는 항상 마지막 1개다(4.5).
- **이메일을 잘못 입력해 코드가 오지 않는 경우**: [메일 다시 입력]으로 입력 화면에 돌아간다. **직전 주소가 채워진 상태로 시작하며, 틀린 주소가 소모한 횟수는 새 주소에 영향을 주지 않는다**(4.5).
- **[메일 다시 입력]으로 돌아간 뒤 주소를 바꾸지 않고 그대로 발송**: [재전송]과 동일하게 처리한다. 30초 쿨다운과 그 주소의 5회 제한이 그대로 걸린다.
- **한 주소의 발송 5회를 소진한 상태에서 결제 시도**: 그 주소로는 잠금 해제까지 남은 시간을 안내하되, **[메일 다시 입력]으로 다른 주소를 쓰는 길은 열어둔다.** 인증을 마치기 전에는 결제를 통과시키지 않는다.
- **발송 잠금 중이지만 유효한 코드가 남아 있는 경우**: 그 코드로 인증을 완료할 수 있다. 잠기는 것은 발송이며 검증이 아니다.
- **잠금 1시간이 지나기 전 앱 재설치·기기 변경**: 제한이 `(계정, 주소)` 단위로 서버에 남아 있으므로 그대로 적용된다.
- **결제 화면과 설정 화면을 오가며 같은 주소로 코드를 반복 요청**: 발송 횟수는 경로와 무관하게 주소 기준으로 합산되므로 5회에서 함께 막힌다.
- **이미 등록된 것과 같은 이메일로 변경 시도**: 코드를 보내지 않고 "이미 등록된 이메일이에요"로 안내한다. 발송 횟수를 소모하지 않는다.
- **메일이 스팸함으로 가거나 도착하지 않는 경우**: 재발송 안내와 함께 스팸함 확인 문구를 노출한다. 발송 성공 응답을 받은 건은 도착 여부와 무관하게 횟수에 포함된다.
- **메일 발송 API 자체가 실패**: 발송 횟수를 차감하지 않고 재시도를 안내한다. 인프라 장애로 사용자의 5회를 소진시키지 않기 위해서다.
- **인증된 이메일을 이미 가진 사용자가 결제**: 4.4를 건너뛰고 바로 결제 플로우로 간다. 재인증을 요구하지 않는다.
- **결제 이력이 없는 사용자의 탈퇴**: 아카이브하지 않고 전량 즉시 파기한다. 보존을 허용하는 법령 근거(전자상거래법 시행령 제6조)가 성립하지 않으므로, 5년 보관은 개인정보보호법 제21조 제1항 위반이 된다(4.3).
- **무료로만 쓰다 탈퇴한 뒤 재가입**: 아카이브에 아무 행도 없으므로 복원할 것도 없다. 완전한 신규 계정으로 시작한다.
- **결제했다가 전액 환불받은 사용자의 탈퇴**: 환불도 거래기록이므로 **결제 이력이 있는 것으로 본다.** `subscriptions` 행이 남아 있으면 `status`와 무관하게 아카이브 대상이다.
- **다른 계정이 이미 쓰는 이메일을 입력**: 허용한다. 이메일은 식별자가 아니라 거래 주체 확인용 연락처이며, 계정 식별은 `provider + provider_user_id`가 한다.
- **탈퇴 처리 중 앱 종료**: 서버 트랜잭션은 완료되므로 재실행 시 토큰 갱신이 실패해 시작 화면으로 간다.
- **탈퇴 직후 같은 계정으로 즉시 재로그인**: 신규 계정으로 온보딩부터 시작한다.
- **여러 기기에서 로그인**: 동시 로그인 허용. 로그아웃은 해당 기기 세션만 폐기한다.
- **활성 구독이 있는 상태로 탈퇴 후 재가입**: 스토어 구독이 살아 있으면 영수증 검증으로 새 계정에 티어를 복원한다(구독 명세의 복원 로직 참조).

## 8. 완료 조건

- Given 처음 앱을 쓰는 사용자 / When 카카오 로그인을 완료한다 / Then **별도 약관 동의 화면**이 노출되고, 동의를 완료해야 계정이 생성되며 온보딩 첫 단계로 이동한다
- Given 시작 화면 / When 제공자 버튼을 누르지 않고 약관 링크만 연다 / Then 약관 본문이 열릴 뿐 동의로 기록되지 않는다
- Given 네이버·구글 등 제공자가 이메일을 내려주는 계정 / When 로그인해 약관에 동의한다 / Then 받아온 이메일이 `users.email`에 **그대로 저장되고**, 별도 인증 단계 없이 온보딩으로 진행된다
- Given 소셜 이메일이 저장된 사용자 / When 구독 결제를 시도한다 / Then 이메일 인증 화면 없이 바로 결제가 진행된다
- Given 이메일이 없는 카카오 계정 / When 로그인해 약관에 동의한다 / Then `email`이 비어 있는 상태로 가입이 완료되고 온보딩으로 진행된다
- Given 카카오가 `is_email_valid = false`인 계정(마스킹 주소 `ka***@kakao.com`) / When 가입이 완료된다 / Then 그 값을 저장하지 않고 `email`은 비어 있으며, 결제 시점에 코드 인증으로 받는다
- Given 카카오가 `is_email_valid = true` · `is_email_verified = false`인 주소를 내려준다 / When 가입이 완료된다 / Then 주소는 저장되지만 `is_email_verified = false`이며, 결제 시점에 인증 선택 화면으로 이동한다
- Given `is_email_verified = false`인 사용자가 결제를 시도해 인증 선택 화면에 있다 / When [이 주소로 인증]을 누른다 / Then 저장된 주소로 코드가 발송되고, 검증에 성공하면 `is_email_verified = true`가 되어 결제로 복귀한다
- Given `is_email_verified = false`인 사용자가 인증 선택 화면에 있다 / When [다른 메일 입력]을 누른다 / Then 이메일 입력 화면으로 이동하고, 새 주소로 인증을 마치면 기존 주소가 교체된다

## 미결 사항

**확정된 것**

| 항목 | 결정 |
|---|---|
| 약관 동의 위치 | **로그인 이후 별도 화면.** 시작 화면의 묵시적 동의 문구는 두지 않고 링크만 제공한다 |
| 탈퇴 시 보존 고지 | **결제 이력이 있을 때만 고지한다.** 있으면 5년 보관 안내, 없으면 "모든 데이터 즉시 삭제"만 노출 (4.3) |
| 탈퇴 시 보존 대상 | **결제 이력이 있는 사용자만 아카이브한다.** 결제 이력이 없으면 보존 근거가 없으므로 전량 즉시 파기 — 개인정보보호법 제21조 제1항 (4.3) |
| 스토어 해지 안내 | **텍스트만.** 탈퇴 화면에 스토어 이동 버튼·딥링크를 두지 않는다 |
| 이메일 없는 가입 | **허용.** `users.email = null`로 저장하고 가입을 진행한다 |
| 제공자 이메일 취급 | **주소와 인증 여부를 함께 판정해 저장한다.** 인증된 주소는 재인증 없이 그대로 쓰고, 미인증 주소는 저장하되 결제 시점에 인증한다 (4.1) |
| 마스킹 주소 판정 | **카카오 `is_email_valid` 플래그로 판정한다.** `false`면 마스킹 주소이므로 `null`로 둔다. 문자열 패턴(`***`) 매칭을 쓰지 않는다 (4.1) |
| 이메일 수집 시점 | **인증된 제공자 이메일이 없는 사용자에 한해 첫 결제 직전.** 인증까지 끝나야 결제가 시작된다 |
| 이메일 인증 방식 | **이메일 코드 인증.** 6자리 숫자 코드를 메일로 보내고 사용자가 입력한다 (4.5) |
| 코드 유효 시간 | **3분.** 만료 후에는 재발송해야 한다 |
| 발송 가능 횟수 | **이메일 주소당 5회.** 소진 시점으로부터 **1시간 후** 초기화. `(계정, 주소)` 단위로 세고 3개 경로에 합산 적용 |
| 계정 단위 발송 상한 | **1시간 20회 / 하루 50회 백스톱(4.5 — 확정 2026-08-10).** 클라이언트 비노출 — 화면·문구 없음, 서버 판정 |
| 재발송 쿨다운 | **30초.** 서버가 함께 검사한다 |
| 잘못 입력한 주소 복구 | **[메일 다시 입력].** 코드 입력 화면에서 직전 주소가 채워진 입력 화면으로 돌아간다 (4.5) |
| 이메일 등록·변경 경로 | **결제 전 강제 수집 + 설정 + 프로필.** 세 경로가 같은 인증 규칙을 쓴다 |

**남은 것**

- **메일 발송 인프라** — SES·SendGrid 등 제공자와 발신 도메인(SPF·DKIM·DMARC) 설정. 인증 메일이 스팸으로 분류되면 4.5의 5회 제한이 그대로 이탈로 이어진다. 인증 방식·수치는 확정됐으므로 남은 것은 인프라 선택뿐이다.
- ~~계정 단위 발송 상한(백스톱) 필요 여부 — P0~~ → **확정(2026-08-10): 1시간 20회 / 하루 50회를 얹는다(4.5).** 클라이언트에 노출하지 않는다 — 화면·문구·클라이언트 대응 작업 없음. 서버 판정(`domain.md` 3.7 발송 이력 집계) — 백엔드 구현 필요.
- **코드당 검증 시도 횟수(5회)** — 별도 지시가 없어 기본값으로 정했다. 6자리 숫자 코드의 무차별 대입을 막는 최소치이며, 운영 중 CS 문의를 보고 조정한다.
- **구글·네이버의 이메일 인증 여부 판정** — 카카오와 달리 대응하는 플래그가 없어 **인증된 것으로 간주**하기로 했다(4.1). 구글 ID 토큰의 `email_verified` 클레임을 실제로 쓸지, 네이버는 무엇을 근거로 신뢰할지 연동 시점에 확인이 필요하다.
- **카카오 동의항목 설정** — `카카오계정(이메일)`을 선택 동의로 두기로 했다. 비즈 앱 전환·검수가 필요한 다른 항목이 있는지 개발자 콘솔에서 확인 필요.
- **`archived_users`의 보존 범위** — 전자우편주소·제공자 계정 ID만 보존한다. 전자상거래법상 "계약에 관한 기록"에 그 이상이 필요한지는 **법무 확인이 필요하다**(`domain.md` 15.1). 다만 4.4로 결제 사용자는 전원 인증된 이메일을 갖게 되므로 식별 수단이 없는 경우는 사라진다.
- **결제 이력 없는 사용자의 동의 이력 파기 — 법무 확인** — 4.3에서 `archived_consents`도 함께 파기하기로 했다. 동의 획득의 입증 책임은 사업자에게 있으므로, 탈퇴자가 나중에 "동의를 받은 적 없다"고 다투면 반박 근거가 남지 않는다. **입증 책임과 제21조 제1항 중 어느 쪽이 우선하는지 법무 확인이 필요하다.** 보존이 필요하다는 판단이 나오면 동의 이력만 별도 근거로 남기는 예외를 두어야 한다.
- 계정 연동(같은 이메일 다른 제공자 통합) 도입 여부 — 현재 비범위로 두었으나 CS 부담 발생 시 재검토
- 재가입 쿨다운(어뷰징 방지) 필요 여부 — 무료 티어 하루 2편 제한을 탈퇴·재가입으로 우회할 수 있음
