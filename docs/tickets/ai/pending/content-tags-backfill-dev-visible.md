## 왜 따로 떼는가

KAN-163으로 앱은 탐색 카드·상세에 태그를 그릴 준비가 끝났다(개발계 OTA 반영). 그런데 **개발계 실기기에서는 태그가 하나도 안 보인다** — 콘텐츠 대부분이 `tags: []`다. `ai/content-tagging.md`(KAN-139)의 "남은 것" 중 **소급**을 확인 가능한 완료 조건으로 떼어 낸 티켓이다. KAN-139는 2026-10-09 완료 처리했다(소급은 이 티켓으로 이관).

## 개발계에서만 채우면 안 되는 이유

개발계 콘텐츠는 **운영 콘텐츠 표의 복사본**이다. 운영이 발행할 때마다(그리고 매일 04:30 안전망) `sync-content-import.sh`가 운영 덤프를 받아 `contents`를 **열 전체 upsert**한다. 운영에 `tags`가 없으면 개발계 `tags`는 다음 복사 때 비워진다.

- 그래서 **운영에 태그가 들어가야 개발계에 남는다**. 콘솔의 개발계 채널(`ear-dev`)로 개발계 서버에만 반영하는 건 다음 운영 발행 때 사라지는 임시 확인용이다.
- 운영 서버는 KAN-162 배포 전까지 형식 3 파일을 **파일째 거부**한다(admin-api 4.6). 스위치를 먼저 켜면 그사이 운영 발행분의 추천 메타 전체가 빠진다 — 반드시 운영 배포 뒤에 켠다.

## 무엇을 한다

1. **운영 배포 확인** — dev → main 릴리즈로 KAN-162(#1304)가 운영에 나갔는지 본다(운영 태그 `v<앱 버전>+N`, 콘솔 목록의 서버 최신 형식).
2. **스위치 켜기** — 워커 `ENRICH_TAGS=1`, 콘솔 `ENRICHMENT_SCHEMA_VERSION_FALLBACK`을 3으로 올린다. 발행분이 "구형 v2"로 잡힌다(소급 대상 표시 — 의도된 동작).
3. **소급** — 서비스 중 편을 [다시 뽑기 → 반영]으로 운영에 보낸다. 메타 단독 전송이라 콘텐츠 버전·재생 위치는 그대로다. 규칙 밖 태그는 그 태그만 빠지고 2개 미만이면 키가 빠진다 — 그런 편 수를 처리 기록에 남긴다.
4. **개발계 복사 확인** — 운영 발행 알림으로 바로, 늦어도 다음 04:30에 개발계로 넘어온다. 넘어오지 않았으면 개발계에서 `bash deploy/sync-content-import.sh`를 수동으로 돌린다(BE·인프라).
5. 끝나면 이 티켓 처리 기록에 결과를 적는다(KAN-139는 2026-10-09 완료 — `ai/archive/content-tagging.md`).

## 완료 조건

- Given 운영에 KAN-162가 배포됐다 / When 워커 스위치와 콘솔 기준을 확인한다 / Then `ENRICH_TAGS=1`, `ENRICHMENT_SCHEMA_VERSION_FALLBACK = 3`이다
- Given 서비스 중(published) 콘텐츠 / When 운영 관리자 목록을 본다 / Then 구형(v2 이하)으로 남은 편이 없다 — 남은 편은 사유와 함께 처리 기록에 적혀 있다
- Given 다음 운영 → 개발계 콘텐츠 복사가 끝났다 / When 개발계 API `GET /contents/:id`(상세)와 탐색 피드를 부른다 / Then 소급한 편의 `tags`가 2~4개 문자열로 온다
- Given 개발계 앱(OTA `01a11c4a` 이후) 실기기 / When 탐색 탭과 콘텐츠 상세를 연다 / Then 카드 메타 줄과 상세 머리에 `#태그`가 보인다
