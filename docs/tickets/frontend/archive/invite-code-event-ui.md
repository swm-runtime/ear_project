## 배경

PoC용으로 요금제를 무상 지급하는 **이벤트(초대) 코드**가 서버에 있다(`subscription.md` 4.9). 코드마다 이름(예: "산군 PoC")·지급 요금제(Daily 또는 Pro)·지급 기간·사용 한도·입력 기간이 있고, 관리자 API로 만든다.

- 입력 API: `POST /users/me/subscription/invite-codes` `{ "code": "..." }` → **200이면 구독 조회(4.2)와 같은 본문**, `plan.grant`에 지급 내용이 실린다(앱이 4.2를 다시 부르지 않는다).
- 지급 상태: `plan.grant = { name, tier, plan_name, ends_at, last_date }` 또는 `null`. 구독 조회·프로필·설정의 `plan`에 **같은 모양**으로 들어간다(서버 조립 함수 하나).
- `plan.status`는 지급과 무관하게 구독 상태 그대로다. 지급 요금제가 구독보다 높으면 `plan.tier`·`plan_name`·`daily_play_limit`·`entitlements`가 지급 요금제 값이 된다(재생 한도는 서버가 이미 푼다).

**앱에는 코드를 입력할 곳도, 지급 상태를 보여 주는 곳도 없다.** 이 티켓이 그 둘과 결제 흐름의 팝업을 붙인다.

## 요청 내용

### 1. 설정 화면에 **[이벤트 코드 입력]** 항목을 추가한다 (진입 위치 확정)

- **위치: 설정 화면**(섹션은 FE가 정한다 — 계정 또는 콘텐츠 섹션 권장). 행을 누르면 코드 입력 화면(또는 시트)으로 간다. 입력 필드 하나 + [확인] 버튼.
- **결제 UI 플래그(`IS_SUBSCRIPTION_UI_ENABLED`)와 묶지 않는다.** 결제 화면이 꺼진 빌드(운영은 아직 off)에서도 이 항목은 **항상 보이고 동작**해야 한다. 지급은 구독이 아니라 스토어 결제 없이 서버가 풀어 주는 것이다.
- **결제 화면에도 진입점을 둘지는 FE 개발자가 정한다** — 페이월 시트·요금제 관리 아래에 "프로모션 코드가 있나요?" 같은 링크를 두고 같은 입력 화면으로 보내는 방식(2026-10-14 요청자 제안). 두면 결제 UI가 켜진 빌드에서만 보이는 **보조** 진입점이고, 설정 항목이 주 진입점이다(결제 UI가 꺼진 빌드에서도 코드를 넣을 수 있어야 하므로).
- 요청 본문 `{ "code": "..." }`. 대소문자·앞뒤 공백은 서버가 정규화하므로 앱은 손대지 않는다(빈 값·64자 초과만 서버가 400).
- 성공(200): 응답 본문으로 구독 상태 캐시를 갱신하고(`subscription`·프로필·설정 플랜 요약 invalidate), "**{코드 이름} 이벤트가 시작됐어요 · {요금제} · N월 N일까지**" 류 확인 안내 뒤 돌아간다. 확정 카피는 FE가 정해 `spec/uiux/settings-uiux.md`에 등재.
- 에러는 `subscription-api.md` 5장 문구 그대로, 화면 상태는 유지(입력값 남김):

| `error_code` | HTTP | 문구 |
|---|---|---|
| `INVITE_CODE_NOT_FOUND` | 404 | "사용할 수 없는 코드예요" |
| `INVITE_CODE_EXPIRED` | 409 | "사용 기간이 지난 코드예요" |
| `INVITE_CODE_EXHAUSTED` | 409 | "선착순이 마감된 코드예요" |
| `INVITE_CODE_ALREADY_USED` | 409 | "이미 사용한 코드예요" |
| `INVITE_GRANT_ALREADY_ACTIVE` | 409 | "다른 코드의 혜택이 아직 남아 있어요" |
| `VALIDATION_FAILED` | 400 | 빈 값·64자 초과 — 입력 전 앱이 막아도 된다 |

- 레이트 리밋 사용자 단위 **분당 10회**. 429는 공통 규칙(`common-error-handling.md` — `Retry-After` 대기, 안내).
- **같은 코드 재전송**은 지급 중이면 200(중복 지급 없음)이라 [확인] 연타·재시도가 안전하다.

### 2. "이벤트 이용 중" 표시 — **세 곳 모두**, 코드 이름을 넣는다

- **요금제 관리**(이용 중 카드 안 또는 목록 위 안내), **프로필**(플랜 카드), **설정**(플랜 요약) 세 곳에 지급 중임을 표시한다. `plan.grant`가 `null`이면 아무것도 그리지 않는다(이벤트 종료 뒤 앱을 다시 열면 표시가 사라진다).
- **문구에 코드 이름을 쓴다**(2026-10-14 결정 — 어떤 PoC인지 사용자가 알아야 한다). 예시: **"{grant.name} 이벤트 이용 중 · {grant.plan_name} · N월 N일까지"** → "산군 PoC 이벤트 이용 중 · Pro · 11월 8일까지". 세 곳 **같은 문자열**(프로필·설정 요약은 원래 같은 문자열을 쓰는 규칙 — `settings-uiux.md` 245행). 확정 카피는 `spec/uiux/` profile·settings·subscription에 등재.
- 날짜는 **`grant.last_date`(`YYYY-MM-DD`) 그대로** "N월 N일까지". `ends_at`으로 계산하거나 05시 경계 보정을 **하지 않는다**(판정은 서버 — 루트 `CLAUDE.md`).
- 지급 요금제가 구독보다 낮거나 같으면(예: Pro 구독자가 Daily 코드 입력) 서버는 구독 표시를 그대로 두고 `grant`만 싣는다 — 이때도 이벤트 줄은 보인다(혜택은 구독이 더 크다는 뜻). 티어 비교를 앱이 하지 않는다 — 서버가 준 `plan.tier`·`plan_name`을 그리고 `grant`는 덧붙이는 줄이다.
- 요금제 목록의 `action`은 구독만 보고 정해진다(지급 중이어도 무료가 `current`일 수 있다). 카드 판정을 바꾸지 않고 **안내 줄만** 더한다.

### 3. 이벤트 중 결제 팝업

- 코드를 입력할 때 **구독이 없던** 계정이 지급 기간 중 결제하면 서버가 지급을 끝내고 응답의 `plan.grant`는 `null`이 된다. 미리 알리는 것은 앱 몫이고, 분기는 `plan.grant.tier`와 **고른 요금제**로 FE가 판단한다(서버 판정 아님 — 안내용).
  - **Daily 이벤트 중 Pro 결제**: 결제 시트 전에 확인 팝업 — "지금 이벤트 혜택은 끝나고 Pro 구독으로 바뀌어요" 류. 문구는 FE가 정한다.
  - **Pro 이벤트 중 Daily 결제**: 막을지("이벤트가 끝나기 전에는 바꿀 수 없어요") 확인 팝업으로 보낼지 **FE가 정한다**. 결정을 `subscription-uiux.md`에 적는다.
  - 결제 뒤 응답(`grant: null`)으로 세 곳 표시가 사라지고 구독 표시로 바뀐다.
- **입력 전부터 구독 중이던** 계정은 그 구독을 갱신·변경해도 지급이 끝나지 않는다 → 팝업 불필요. 구분은 "입력 시점에 구독이 있었나"인데 앱은 그 이력을 모르므로, **지급 중 + 현재 `plan.status`가 `free`** 일 때만 팝업을 띄우면 된다(구독이 있는데 지급 중이면 입력 전부터 구독자였거나 지급이 더 큰 경우라 끝나지 않는다).

### 4. 결제 UI 플래그와 분리

- 1·2는 `IS_SUBSCRIPTION_UI_ENABLED`와 **무관하게** 항상 노출. 3은 결제 흐름 안의 팝업이라 결제 UI가 켜진 빌드에서만 의미가 있다.
- 결제 화면이 꺼진 운영 빌드에서도 **코드 입력 → 세 곳 표시 → 재생 한도 풀림**이 끝까지 동작해야 한다(PoC는 결제 오픈 전에 시작할 수 있다).

### 5. **왜 새 스토어 빌드인가** (OTA로 끝내지 않는다 — 2026-10-14 결정)

- 코드 입력·표시·팝업은 전부 JS라 **기술적으로는 OTA로도 간다**(네이티브 모듈 없음). 그러나 **심사 때문에 새 빌드로 낸다.**
- "앱 밖에서 받은 코드로 유료 기능 해제"는 Apple 가이드라인 **3.1.1**(인앱 결제 우회)로 읽힐 수 있는 항목이다. 심사를 거치지 않은 OTA로만 넣으면 ① 뒤에 다른 이유로 심사받을 때 한꺼번에 지적되고 ② 심사 없이 결제 관련 동작을 바꾼 것이 OTA 가이드라인 위반으로 읽힐 소지가 있다. 새 빌드로 한 번 통과시키면 이후 수정은 OTA로 안전하다.
- 따라서 이 티켓의 완료에는 **runtimeVersion을 올린 스토어 빌드 제출**이 포함된다(`frontend/architecture.md` 2.1 이력 표에 행 추가). iOS는 TestFlight로 개발계 확인 뒤 심사 제출, Android는 내부 테스트 트랙 → 운영.
- **심사에서 3.1.1로 반려되면** 앱 안 코드 입력 대신 **회사 메일 인증 자동 지급** 같은 다른 지급 경로로 바꾼다(서버 티켓 별도). 반려 사유를 이 티켓 처리 기록에 적는다.

### 일정 (PoC 역산)

코드 작업 → 개발계 확인(TestFlight·내부 테스트) → 스토어 제출 → 심사(iOS 1~3일, 재심사 시 더) → PoC 시작. 심사 기간이 통제 밖이라 **코드와 빌드 제출은 이번 주 안에** 끝나야 PoC 일정이 지켜진다. PoC 코드 자체는 심사와 무관하게 백엔드가 관리자 API로 미리 만들어 둔다.

## 완료 조건

- Given 구독 없는 사용자 / When 설정 > [이벤트 코드 입력]에서 유효한 Pro 코드를 넣는다 / Then 200 응답으로 화면이 갱신되고 요금제 관리·프로필·설정 세 곳에 **"{코드 이름} 이벤트 이용 중 · Pro · N월 N일까지"** 가 보이며, 재생 한도가 Pro로 풀린다(서버 판정)
- Given 지급 중인 사용자 / When 프로필·설정·요금제 관리를 연다 / Then 세 곳에 같은 문자열의 이벤트 줄이 보이고, 날짜는 `grant.last_date` 그대로다
- Given 없는 코드·기간 지난 코드·마감 코드·이미 쓴 코드·다른 지급 중 / When 입력한다 / Then 각 `error_code`의 문구가 보이고 화면 상태는 그대로다
- Given 지급 중인 사용자 / When 같은 코드를 다시 보낸다 / Then 200이고 표시가 그대로다(중복 지급 없음)
- Given Daily 이벤트 중(`plan.status = free`) / When Pro [구독하기] / Then 결제 시트 전에 확인 팝업이 뜨고, 결제 뒤 이벤트 줄이 사라지고 Pro 구독으로 보인다
- Given Pro 이벤트 중 / When Daily [구독하기] / Then FE가 정한 대로(막음 또는 팝업) 동작하고 그 결정이 `subscription-uiux.md`에 적혀 있다
- Given `EXPO_PUBLIC_SUBSCRIPTION_UI`가 꺼진 빌드 / When 설정을 연다 / Then [이벤트 코드 입력] 항목이 보이고 입력·표시가 끝까지 동작한다
- Given 지급이 끝난 뒤 / When 앱을 다시 연다 / Then 세 곳 이벤트 줄이 사라진다
- Given 이 기능이 든 빌드 / When 스토어에 제출한다 / Then runtimeVersion이 올라간 새 빌드이고 `frontend/architecture.md` 2.1 이력에 행이 있다. 심사 결과(통과/3.1.1 반려)가 처리 기록에 적혀 있다
