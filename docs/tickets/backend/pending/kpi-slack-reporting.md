## 요청 — 2단계로 나눈다

### 1단계 — 가입 건별 Slack 알림 (2026-09-29 추가)

GA4 `sign_up` 이벤트를 받아 Slack 에 게시한다. "하루 한 번"으로 줄이기 전에 **우선 들어올 때마다** 보고 싶다는 PM 요청이다.

- 메시지는 **`가입 · 카카오 · 시각`** 수준으로 짧게.
- **이메일·닉네임 등 신원 값은 넣지 않는다**(`backend/convention.md` 8.4 — 로그에 신원 값 금지). 제공자(`method`)와 시각만으로 충분하다.
- 빈도가 부담스러워지면 같은 경로로 일일 집계로 바꾼다 — 그것이 2단계다.

### 2단계 — DAU·완청률·리텐션 일일 보고 (원래 요청)

지표를 집계해 Slack 에 정기 보고한다 — 지표 정의(서비스 날짜 04시 경계, 완청 판정 기준)를 문서에 맞추고 일일 자동 게시. **게시 시각은 17:00 KST**(PM 2026-09-29).

**착수 전에 정해야 할 것 — 지표의 출처.** `features/analytics.md` 1장이 **"퍼널·리텐션·화면 체류처럼 제품 결정에 쓰는 지표는 이 문서(GA4)가 소유한다"** 고, **"`user_signals` 로 퍼널을 보지 않는다"** 고 못박고 있다. 리텐션을 서버 데이터로 만들면 그 경계와 충돌한다 — 규칙이 틀렸다면 **코드가 아니라 문서를 먼저 고쳐야 한다**(루트 CLAUDE.md).

| 지표 | 문서상 소유 | 서버가 낼 수 있나 |
|---|---|---|
| 완청률 | **서버** — 완청은 서버 판정이다(`player.md` 4.4: `max_reached_sec` ≥ 길이의 90% → `status = completed`) | 그대로 가능 |
| DAU | 명시 없음 — 성격상 GA4 쪽 | 재생·요청 기록으로 가능 |
| 리텐션(D1/D7/D30 — PRD 296행) | **GA4** | 가입일 + 활동 기록으로 가능 |

**다만 지금 GA4 로 내면 숫자가 틀린다.** GA4 는 2026-09-23(runtime 7)에 들어갔는데 스토어 빌드는 **1.0.0**(runtime 4 이전)이라 **대부분의 실사용자가 GA4 에 잡히지 않는다.** 반면 서버는 앱 버전과 무관하게 전부 본다(1단계 가입 알림이 그 이유로 서버 경로를 택했다).

선택지는 둘이다.

* **(A) 서버로 만들고 `analytics.md` 의 경계를 고친다** — 숫자가 정확하고 오늘 바로 된다. 문서 수정은 `changes/pending/` 에 올려 판단받는다
* (B) GA4 Data API 로 가져온다 — 문서와 정합하지만 서비스 계정이 필요하고, **새 스토어 빌드가 퍼지기 전까지 수치가 실제의 일부만 보여준다**

기술적 준비물은 이미 있다 — `@nestjs/schedule` 의 `@Cron(..., { timeZone: 'Asia/Seoul' })` 과 `isSchedulerProcess()` 게이팅(클러스터에서 한 번만 돈다), 서비스 날짜 04시 경계(`common/utils/service-date.util.ts`). **17:00 KST 는 `@Cron('0 17 * * *', { timeZone: 'Asia/Seoul' })` 한 줄이다.**

## 1단계 — 구현 방식을 서버 직접 발송으로 바꿨다 (2026-09-29)

처음에는 GA4 `sign_up` 이벤트를 받아 오는 쪽으로 잡았다가 **서버에서 직접 보내는 쪽으로 되돌렸다.**

**GA4 에는 이벤트 웹훅이 없다.** "이벤트가 들어오면 URL 호출" 기능이 아예 없어서, 알림을 받으려면 Data API 를 5분마다 폴링하거나(집계 수치만 나온다) BigQuery 스트리밍 내보내기를 붙여야 한다(GCP 결제 필요). 게다가 GA4 는 **1.1.0 스토어 게시** 이후에야 이벤트가 들어온다 — 지금 스토어 빌드는 1.0.0 이고 GA4 는 2026-09-23(runtime 7)에 들어갔다.

서버는 그 모든 것과 무관하다. 가입은 `auth.service.ts` 의 `signUp()` 을 반드시 거치고, 그 시점이 **가입의 진실**이다. 스토어 게시를 기다릴 필요도, 앱 버전을 가릴 필요도, 새 인프라도 없다.

앱에서 직접 Slack 을 부르는 안은 **쓰지 않는다** — 웹훅 URL 이 앱 번들에 박혀 누구나 뜯어 채널에 도배할 수 있다.

### 무엇을 넣었나

| | |
|---|---|
| `auth/services/signup-alert.service.ts` | 새 파일. 문구 조립(`formatSignupText`)과 발송을 나눠 문구는 순수 함수로 검증한다 |
| `auth/services/auth.service.ts` | `signUp()` 에서 **계정이 실제로 생겼을 때만** 호출. `await` 하지 않는다 |
| `config/env.validation.ts` | `SLACK_SIGNUP_WEBHOOK_URL`(선택). 비우면 꺼진다 |

- **가입을 방해하지 않는다.** 호출부가 `await` 하지 않고, 실패는 `logger.warn` 으로만 끝난다. Slack 이 죽어도 가입 응답이 밀리지 않는다(타임아웃 3초).
- **같은 signup token 재호출에는 알리지 않는다.** `signUp()` 은 멱등이라 기존 계정을 찾으면 계정을 만들지 않는다 — 그때는 가입이 아니다.
- **신원 값을 보내지 않는다**(`convention.md` 8.4). 문구는 `:wave: 가입 · 카카오 · 09-29 14:03` 이고 시각은 서버가 UTC 여도 KST 로 적는다.
- **기존 알림 채널을 그대로 쓴다**(`SLACK_ERROR_WEBHOOK_URL`). 채널을 새로 만들지 않으려는 결정이다(2026-09-29 PM) — 덕분에 **서버 env 를 건드리지 않고 배포만으로 켜진다.** 가입 알림만 따로 빼고 싶어지면 `SLACK_SIGNUP_WEBHOOK_URL` 을 넣으면 되고 **코드는 안 고친다**.
- **운영·개발계가 섞이지 않는다.** 운영이 아니면 문구 앞에 `[development]` 처럼 환경을 붙인다. 기준은 `SENTRY_ENVIRONMENT` 다 — `NODE_ENV` 는 양쪽 다 `production` 이라 쓸 수 없다(개발계도 배포된 서버라 운영과 같은 코드 경로를 타야 한다).

### 설정 — 끝났다. 남은 것은 배포뿐이다 (2026-09-29)

전용 웹훅을 만들지 않고 기존 알림 채널(`SLACK_ERROR_WEBHOOK_URL`)로 보낸다. Secrets Manager 를 확인한 결과:

| | `SLACK_ERROR_WEBHOOK_URL` | 조치 |
|---|---|---|
| `ear/prod/api` | 값 있음 | 없음 |
| `ear/dev/api` | **키는 있는데 값이 비어 있었다** | **운영과 같은 값으로 채웠다**(버전 `79742dd3`) |

키 개수는 10 → 10 으로 그대로다 — **`apply-secrets.py` 함정에 걸리지 않는다**(있는 키의 값만 바꿨다). 값은 읽어서 출력하지 않고 해시(`5ea99249`)로만 대조했다.

**`dev`·`main` 에 배포되면 그때부터 양쪽 다 알림이 온다.** 그 전에는 서버 `.env.prod` 가 옛 값(빈 문자열)이라 개발계는 조용하다.

### 곁딸린 변경 — 자원 경보에도 환경 표시를 붙였다

개발계 웹훅을 채우면 **가입 알림만이 아니라 `resource-alert.service.ts` 의 자원 경보도 같이 켜진다.** 그런데 그 문구에는 환경 표시가 없었다:

```
:rotating_light: *API 서버 CPU 85%* — 임계 70% 3분 이상 초과
```

운영·개발계가 같은 채널을 쓰는데 이러면 **개발계 경보를 운영 장애로 오해한다.** 가입 알림과 같은 규칙(`SENTRY_ENVIRONMENT` 기준 접두)을 자원 경보에도 넣었다. 운영에는 표시가 없고 개발계만 `[development]` 가 붙는다.

개발계 자원 경보가 시끄러우면 `ear/dev/api` 의 `SLACK_ERROR_WEBHOOK_URL` 을 다시 비우면 된다 — 그러면 **가입 알림도 함께 꺼진다.** 가입 알림만 남기고 싶으면 그때 `SLACK_SIGNUP_WEBHOOK_URL` 을 쓴다(단, 새 키라서 서버 `.env.prod` 에 줄을 먼저 넣어야 한다 — 아래 함정).

> ⚠️ **키를 새로 넣을 때만 해당.** `deploy/apply-secrets.py` 는 Secrets Manager 에 있는 키가 `.env.prod` 에 **없으면 배포를 중단시킨다**(`tickets/backend/archive/deploy-path-reads-secrets-manager.md`). 서버 파일이 먼저다. 중단 시점이 컨테이너를 건드리기 전이라 돌던 API 는 살아 있다.

- 실패해도 던지지 않는다(던지면 스케줄러가 멈춰 다음 날도 안 온다). 부하: 하루 1회, 워커 1개, 우리 DB 접근 없음

### 자격·검증 (2026-09-29 오후) — 실제 GA4 로 끝까지 확인했다

- **서비스 계정은 별도 GCP 프로젝트에 만들었다.** Firebase 프로젝트 `ear-push`(번호 800761431485)가 GCP 콘솔에서 잡히지 않아(계정·선택기 문제로 시간을 많이 썼다) 팀이 보는 GCP 프로젝트에 **읽기 전용 `ga4-reader`** 서비스 계정을 만들고 GA4 속성 `555336596` 에 뷰어로 붙였다. GA4 는 서비스 계정의 소속 프로젝트를 따지지 않는다 — 속성 뷰어인지와 그 프로젝트에 Data API 가 켜졌는지만 본다. 덤으로 푸시 권한까지 든 firebase-adminsdk 키를 서버에 두지 않게 됐다(그 키는 지워도 된다).
- **실제 API 로 세 요청 다 확인** — 총계·`sign_up` 이벤트 필터·코호트(+스트림 필터). 최근 7일 활성 20명·신규 9명, 8일치 `sign_up` 4건.
- **스트림이 셋이다**: `ear prod iOS`(15824238718 · 14일 활성 9) · `ear preview iOS` · `ear preview`(Android). **운영 스트림만 보도록** 세 요청 모두에 `streamName BEGINS_WITH "ear prod"` 필터를 걸었다(`analytics.md` 1장 "대시보드는 운영 스트림만 본다"). 이름 접두라 안드로이드 운영 스트림이 생겨도 코드를 안 고친다.
- **파서 결함을 실데이터로 잡았다**: GA4 는 값이 0 인 행을 주지 않아 1명 코호트에서 아무도 안 돌아온 날은 N일차 행이 없다 → "모른다(—)"로 가려지던 것을 **0%** 로 고쳤다. 분모는 0일차 행. 빈 코호트만 `—`.
- **Slack 에 같은 코드로 미리보기를 보냈다**(운영 스트림, 09-28): 활성 1 · 신규 1 · 가입 0 · D1 — · D7 —. 운영 스토어가 아직 1.0.0(GA4 없음)이라 수치가 작다 — 새 빌드가 퍼지면 오른다.
- `.env.prod` 는 SSH 로 넣지 않는다 — **이 PC 에서 AWS 로 가는 22번이 전부 타임아웃**(SG 를 열어도)이라 배포 스크립트(`push.sh`)가 GA4 키 두 줄을 빈 값으로 스스로 선언하게 했다. `apply-secrets.py` 의 "모르는 키는 막는다" 판단은 그대로다.

### 남은 것 — 운영 Secrets 한 번 + 배포

개발계는 **필요 없다**(운영 기준 하루 1회). 순서가 중요하다:

1. **`ear/prod/api` 에 `GA4_PROPERTY_ID`·`GA4_SERVICE_ACCOUNT_BASE64` 추가** — 반드시 **새 `push.sh` 가 main 에 들어가는 그 릴리스 직전**에. 그 전에 다른 운영 배포가 나가면 옛 `push.sh` 가 `.env.prod` 에 없는 키를 만나 배포가 중단된다(돌던 API 는 산다).
2. #957 → dev 머지 → `dev → main` 릴리스 → 배포. 새 `push.sh` 가 두 줄을 선언하고 Secrets 가 값을 채운다.
3. `POST /admin/reports/daily-metrics` 로 한 번 쏴서 확인 → 다음 날 17:00 자동 발송 확인 → archive.

### GA4 는 어떻게 되나

버리지 않는다. 퍼널·리텐션·코호트는 GA4 가 훨씬 낫고, 1.1.0 이 게시되면 `sign_up` 이벤트가 GA4 에도 그대로 쌓인다. **알림만 서버에서 보내는 것**이다.
