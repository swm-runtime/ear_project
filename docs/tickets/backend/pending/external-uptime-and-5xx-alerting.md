| 항목 | 값 |

| 대상 | 감시 주체(제품 서버 밖) · `all-exceptions.filter.ts`(5xx 알림) · `docs/infra/inventory.md` 4장(SNS 구독) |
| 요청 파트 | 백엔드 (인프라 포함) |
| 요청자 | 박준현 |
| 발행 날짜 | 2026-09-12 |

## 문제

**제품 API가 죽었을 때 사람에게 닿는 경로가 하나도 없다.**

### 1. 감시가 감시 대상 안에서 돈다

`SLACK_ERROR_WEBHOOK_URL`을 쓰는 코드는 `admin/services/resource-alert.service.ts` **하나뿐**이고, 그것도 **API 프로세스 안에서 도는** CPU 70%·메모리 80% 감시다. **프로세스가 죽으면 감시도 같이 죽는다.**

`features/backend-monitoring.md` 미결에 이미 적혀 있다 — *"인스턴스 자체가 죽으면 이 경로도 죽는다"*.

### 2. 5xx 알림이 없다

`common/filters/all-exceptions.filter.ts`는 로그만 남기고 webhook을 부르지 않는다. **500이 쏟아져도 신호가 없다.** 사용자가 말해주기 전까지 모른다.

### 3. 외부 헬스체크가 0건

`GET /api/v1/health`는 있는데 **바깥에서 주기적으로 찌르는 것이 없다.** 저장소·인프라 문서 어디에도 uptime 감시 기록이 없다.

### 4. 유일한 외부 알람도 살아 있는지 모른다

CloudWatch 알람 `ear-prod-ec2-status-check`(인스턴스 상태 검사) 하나가 있는데, `inventory.md` 4장에 **SNS 토픽 `ear-prod-alerts`의 메일 구독이 "⏳ 확인 대기"** 로 적혀 있다. Confirm을 안 눌렀으면 **그 알람마저 아무 데도 가지 않는다.**

## 왜 지금 발행하나

같은 날 **DB 백업이 2026-08-31부터 열하루 동안 매일 실패했는데 아무도 몰랐다**(`fix(deploy): make the db backup actually run` — PR #333). 실패 자체보다 **11일간 신호가 없었다는 것**이 문제였다.

이 티켓은 같은 구조의 다음 사고를 막는 것이다. **지금은 API가 죽어도 똑같이 조용하다.**

## 요청 내용

**① 외부에서 `/health`를 주기적으로 찌르고, 실패하면 Slack으로 알린다.**

- 감시 주체는 **제품 서버 밖**이어야 한다. 후보: **AI 서버 EC2**(이미 있고, 추가 비용 0, 파이프라인 워커가 이미 Slack webhook을 쓴다 — `log-watch.ts`) 또는 외부 uptime 서비스 무료 티어.
- AI 서버에서 감시하면 **서로 감시**가 된다. 다만 **두 서버가 같은 리전·같은 계정**이라 AWS 전체 장애는 함께 놓친다 — 그 한계를 알고 택하는 것이면 괜찮다.
- 연속 N회 실패에만 알린다(1회 실패로 깨우지 않는다). 복구되면 복구 알림도 보낸다 — 알림이 끊긴 것인지 장애가 끝난 것인지 구분돼야 한다.

**② 5xx 급증을 알린다.**

- `all-exceptions.filter.ts`가 `INTERNAL_ERROR`를 만들 때 webhook을 태운다. **건마다 보내면 안 된다** — 한 번 터지면 채널이 마비된다. 창(예: 5분) 단위로 묶어 개수와 대표 `trace_id` 하나만 보낸다.
- 토큰·이메일·요청 바디는 실어 보내지 않는다(`backend/CLAUDE.md` 8장).

**③ SNS 메일 구독 Confirm 확인.** `inventory.md` 4장의 "⏳ 확인 대기"를 확정 상태로 갱신한다. 안 돼 있으면 구독을 다시 걸고 Confirm까지 한다.

## 판단이 필요한 것

1. **감시 주체를 AI 서버로 할 것인가, 외부 서비스로 할 것인가.** AI 서버는 공짜지만 같은 계정·리전이다. 외부 서비스는 독립적이지만 계정이 하나 늘고 무료 티어 한도가 있다.
2. **알림 채널을 나눌 것인가.** 지금은 자원 경고·백업 실패·파이프라인 ERROR가 모두 같은 webhook으로 간다. "API 다운"이 그 사이에 묻히면 소용이 없다.
3. **누가 받는가.** 채널에 던지는 것과 사람을 깨우는 것은 다르다. 새벽 3시 장애를 누가 보는지 정하지 않으면 알림을 붙여도 결과가 같다.

## 완료 조건

- Given 제품 API 프로세스를 정지시킨다 / When 감시 주기가 지난다 / Then **Slack에 다운 알림이 도착한다**
- Given 그 상태에서 API를 되살린다 / When 감시 주기가 지난다 / Then **복구 알림이 도착한다**
- Given 5xx가 짧은 시간에 여러 건 발생한다 / When 알림을 본다 / Then 건별이 아니라 **창 단위로 묶여 오고** 개수와 대표 `trace_id`가 있다
- Given 그 알림 / When 본문을 본다 / Then 토큰·이메일·요청 바디가 들어 있지 않다
- Given `inventory.md` 4장 / When SNS 구독 항목을 본다 / Then "확인 대기"가 아니라 확정 상태로 적혀 있다

## 참고

- `features/backend-monitoring.md` — 로그·자원 콘솔, Slack 알림 규칙의 소유 문서. 이 티켓의 구현은 그 규칙 안에 들어가야 한다
- `pipeline/apps/worker/src/log-watch.ts` — 이미 CloudWatch 로그를 읽어 Slack으로 보내는 코드가 AI 서버에 있다. 감시 주체를 AI 서버로 정하면 이 옆에 붙이는 것이 자연스럽다
- `backend/deploy/backup.sh` — 같은 날 붙인 실패 알림. 크론에서 `curl`로 직접 Slack에 쏘는 가장 단순한 형태이며, 그 경로가 동작하는 것을 실측 확인했다(HTTP 200)
