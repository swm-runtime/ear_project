## 문제 — 실측 쿼리 수

사용자 1명당 순차 실행되는 쿼리(orchestrator 코드 대조 2026-09-09):

| 구간 | 쿼리 | 비고 |
|---|---|---|
| 관심사·재고·플랜 | 4 | `PlanService`는 티어별 결과가 같은데 사용자마다 2회 재조회 |
| 취향 재계산 | 5~6 | 신호·콘텐츠·주제·임베딩 |
| **정규 풀** | 300행 조회 + 통계·주제·임베딩 3회 | **풀은 사용자 무관인데 매번 재조회.** 임베딩은 1536차원×최대 300개 ≈ 수 MB |
| **탐험 풀** | 300행 재조회 + 3회 | 같음 |
| 적재·제외·노출 | 4~5 | |

= **사용자당 20~24 쿼리, 그중 300행 풀 조회 2회 + 수 MB 임베딩 2회.** 전부 사용자 루프 안에서 순차.
5,000명이면 약 10~12만 쿼리 — 쿼리당 10ms면 20~30분(일 1회 배치로 치명적이진 않지만 선형 증가).

## 이번에 한 것 (값싼 선행 개선 — 2026-09-09 별도 PR)

- `PlanService` 티어별 결과를 run 단위로 메모이즈 → 사용자 수만큼의 중복 2N 쿼리 제거.
- run 소요시간은 `drip_batch_runs`(claim/finish 시각)에 이미 기록되므로 **추가 계측 없이 관측 가능**하다.

## 요청 내용 (착수 시)

1. **run 단위 공유 적재** — 발행 콘텐츠 풀·`content_stats` 전체구간·임베딩을 배치 시작 시 1회 메모리에
   적재하고 사용자별로는 **제외 필터만** 적용한다. 주의: 현재 `findCandidates`는 `excludeSeenByUserId`가
   SQL(NOT EXISTS) 안에 사용자별로 박혀 있어 **"슈퍼셋 조회 + 앱단 사용자별 필터"** 로 구조를 바꿔야 한다.
   관심 주제 교집합은 앱단에서 `topicIdsByContentId`로 거른다.
2. **제한 동시성** — 사용자 처리를 `p-limit`(5~10)로 병렬화. 적립은 사용자 단위 트랜잭션이라 병렬 안전.
3. 메모리 상한 검토 — 풀 전체 임베딩(콘텐츠 수천 편 × 1536 float ≈ 수십 MB)이 컨테이너 메모리에 들어가는지.
   넘으면 관심 주제 조합별 부분 적재로.

## 완료 조건

- Given 사용자 N명 / When 배치가 돈다 / Then 풀·통계·임베딩 조회가 사용자 수와 무관하게 상수 회수다
- Given 같은 입력 / When 개선 전후를 비교한다 / Then 각 사용자의 편성 결과(선정 콘텐츠)가 동일하다(회귀 없음 — 순수 성능 개선)
- Given 5,000명 시뮬레이션 / When 배치가 돈다 / Then 소요시간이 개선 전의 1/5 이하다
