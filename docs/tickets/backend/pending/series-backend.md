## 배경

시리즈 콘텐츠의 서버 쪽 구현이다(PRD FR-13 "분할된 편은 시리즈로 묶어 순서를 유지한다"). 처음 발행할 때 이 티켓의 범위는 "편성(다음 화)·조회 API·탐색 필터"였다. 2026-10-09에 코드를 확인해 보니 편성은 이미 구현돼 있고, 비어 있는 것은 **시리즈라는 대상 자체**다. 그래서 현황과 결정 사항을 정리하고 설계를 제안했고(2026-10-09), **2026-10-17 박수헌이 아래 설계로 확정했다 — 이대로 구현한다.** 구현 중 바꿔야 할 점이 생기면 착수 전에 AI(박수헌)와 맞춘다. 파이프라인(KAN-136)이 이 계약에 맞춰 만든다.

## 현재 상황 (2026-10-09 코드·문서 확인)

- **스키마**: `contents`에 `series_id`(uuid)·`episode_no`·`total_episodes`가 있다. `series_id`가 가리키는 테이블은 없다 — 같은 값을 공유한다는 뜻뿐이라 시리즈 이름·소개가 없다. 총 편수는 편마다 따로 들고 있어 같은 시리즈의 편끼리 값이 달라도 막지 못한다.
- **업로드**(`admin-api.md` 4.6): 시리즈 필드를 받는다. 검사는 uuid 형식과 "편 번호 ≤ 총 편수"뿐이다 — 같은 시리즈의 `(series_id, episode_no)` 중복은 막지 않는다. 업로드 뒤에는 시리즈 필드를 바꿀 수 없다(4.10 — "회수 후 새로 올린다").
- **드립**: 순서 필터(1편을 듣지 않은 사용자에게 3편을 적립하지 않는다)와 연속 편 우선 선정이 **구현돼 있다**(`drip-scoring.service.ts`, `drip-scheduling.md` 4.2-3·7). 원래 범위의 "편성(다음 화)"은 대부분 끝났다.
  - 단 필터가 "직전 편(k-1)을 완청했는가"를 정확히 맞춰 본다. **중간 화가 회수되면 그 뒤 편은 아무에게도 편성되지 않는다.**
- **탐색·검색**: 시리즈를 모른다 — 편마다 한 줄이다. 시리즈가 생기면 16편짜리 시리즈 하나가 인기·피드 목록을 덮을 수 있다.
- **라이브러리·재생 위치·완청·통계·페이월 차감**: 전부 편(콘텐츠) 단위다. 연속 재생은 없다(FR-24).
- **상세 화면**: "N부작 중 M화" 표시 규칙이 있다(`content-detail.md` 4.3-1). 상세는 별도 엔드포인트 없이 카드·라이브러리 항목 데이터로 열린다.
- **콘텐츠**: 시리즈로 발행된 콘텐츠는 아직 없다. "키워드로 빠르게 배우는 CS 지식" 16편이 단일 콘텐츠로 올라가 있고, 시리즈 도입 때 묶는다.
- **제작(AI)**: 기획 시리즈 제작 설계가 끝났다(`ai/spec/11-series.md`, KAN-136). 시리즈 시스템이 도입되면 구현한다. 그 전에는 시리즈 필드를 실어 발행하지 않는다.

## 결정 사항 (2026-10-09, 박수헌 전달)

- **탐색에서 시리즈는 하나의 요소다.** 누르면 그 시리즈의 편 목록이 쭉 나온다.
- **"다음 화 듣기"(완청 뒤 다음 편 유도)는 보류한다.**
- **시리즈 표지는 1화 썸네일이다.**
- 시리즈는 처음부터 N편으로 기획한 것만이다. 군집 분할로 나눈 편은 독립 편이다(KAN-136).
- **발행(파이프라인, `ai/spec/11-series.md` 7장)**: 전 편이 준비된 뒤 한꺼번에 발행한다 — 서버에 시리즈를 만들고(발행 시점) 1화부터 순서대로 올린다. 발행된 시리즈 편은 한 편만 회수하지 않고 고쳐서 재발행한다. 회수는 시리즈 전 편을 한꺼번에 한다.
- **콘텐츠 제목에 시리즈 이름을 그대로 둔다** — 예: 시리즈 "키워드로 빠르게 배우는 CS 지식", 콘텐츠 "키워드로 빠르게 배우는 CS 지식 N - {주제}". 시리즈 이름을 따로 보여 줘도 제목은 바꾸지 않는다.

## 결정 사항 (2026-10-17, 박수헌)

- **편수 상한은 없다.** 시리즈 기획(편수·편 구성)은 관리자가 직접 한다.
- **기존 콘텐츠의 시리즈 지정 API는 만들지 않는다.** 대상이 CS 키워드 시리즈 16편뿐이라 일회성 데이터 마이그레이션으로 바꾼다(아래 7번). `admin-api.md` 4.10(업로드 뒤 시리즈 필드는 바꾸지 않는다)은 그대로다.
- AI가 시리즈 주제를 제안하는 기능은 보류한다(파이프라인 쪽, 서버 영향 없음).

## 확정 설계 (2026-10-17)

**원칙**: 시리즈를 별도 대상으로 둔다. 담기·재생 위치·완청·통계·페이월 차감은 지금처럼 편 단위로 둔다 — 이 테이블들이 시리즈를 알게 하면 손댈 곳이 지나치게 넓어진다.

1. **`series` 테이블 신설** — 시리즈의 주인
   - `id uuid PK`(`contents.series_id`의 FK 대상) · `title` · `description` · `total_episodes`(계획 편수) · `status`(`ongoing` · `completed`) · `created_at` · `updated_at`
   - **표지 칸은 두지 않는다** — 1화 썸네일을 쓴다(결정 사항).
   - 총 편수의 기준은 `series.total_episodes`다. **편수 상한은 없다.** `contents.total_episodes`는 업로드 계약 호환을 위해 남기되, 업로드 때 `series.total_episodes`와 같아야 하고 다르면 400이다. 응답의 총 편수는 `series` 값을 쓴다.
   - 부분 유니크 `(series_id, episode_no) WHERE status = 'published'` — 같은 시리즈에 같은 번호가 둘 발행되지 않게 한다.
   - 진행 중 시리즈는 총 편수를 늘릴 수 있다. 이미 발행된 가장 큰 편 번호보다 작게 줄일 수는 없다.
2. **관리자 API**
   - `POST /admin/series` · `PATCH /admin/series/:id` · `GET /admin/series`(목록·편 현황) — 시리즈를 먼저 만들고, 업로드(4.6)는 **존재하는 시리즈의 `series_id`와 `episode_no`만** 보낸다.
   - **기존 콘텐츠 시리즈 지정 API는 두지 않는다**(2026-10-17) — 4.10은 개정하지 않는다. CS 16편은 7번으로 바꾼다.
3. **사용자 응답**
   - 카드·라이브러리 항목(상세 화면이 이 데이터로 열린다)·플레이어 응답에 같은 모양의 객체를 싣는다:
     `series: { id, title, episode_no, total_episodes } | null` — 평평한 세 칸 대신 객체 하나로, FE가 어디서든 같은 방식으로 그린다.
   - **`GET /series/:id`** — 탐색에서 시리즈를 눌렀을 때 화면의 데이터. 시리즈 정보 · 표지(1화 썸네일) · 발행된 편 목록(`episode_no` 순) · 편마다 내 상태(담음 · 완청 · 재생 위치).
4. **탐색 — 시리즈를 한 요소로 접는다**
   - 피드·주제별·인기·검색(`explore-api.md` 4.1·4.2·4.2-1·4.5)에서 같은 시리즈의 편들을 **시리즈 카드 하나**로 낸다. 카드: 시리즈 제목 · 표지(1화 썸네일) · 편수 · 주제.
   - 카드의 순위는 시리즈의 대표값으로 정한다(예: 편 점수의 최댓값 — BE 판단). 검색은 편 제목이나 시리즈 제목이 맞으면 시리즈 카드로 낸다.
   - 응답은 단일 콘텐츠 행과 시리즈 카드가 섞인 목록이다 — 항목 종류(`type: "content" | "series"`)를 두는 형태를 제안한다.
5. **드립 순서 필터 보정**
   - 다음 편을 "**마지막으로 완청한 편보다 번호가 큰, 발행 중인 편 중 가장 앞 편**"으로 본다. 중간 화가 회수됐거나 탐색에서 앞 편을 건너뛴 경우가 함께 풀린다.
6. **문서**: `domain.md`(`series` 테이블·`contents` FK) · `admin-api.md`(시리즈 API, 4.6 업로드의 `series_id` 존재·총 편수 일치 검사) · `explore-api.md`(시리즈 카드·`GET /series/:id`) · `library-api.md`(`series` 객체).
7. **CS 키워드 시리즈 16편 전환 — 일회성 데이터 마이그레이션**
   - `series` 행 하나: `title` "키워드로 빠르게 배우는 CS 지식" · `description` "소프트웨어 개발부터 데이터베이스·운영체제·네트워크·보안까지, CS 핵심 키워드를 16편에 나눠 정리한 시리즈" · `total_episodes` 16 · `status` `completed`.
   - 아래 16개 콘텐츠의 `series_id`(위 행)·`episode_no`(표의 번호)·`total_episodes`(16)를 채운다. **`content_id`·`content_version`·제목·오디오는 바꾸지 않는다** — 담기·재생 위치·완청·별점·통계가 그대로 남는다. 제목은 이미 `키워드로 빠르게 배우는 CS 지식 N - {주제}` 꼴이다.
   - 운영 콘텐츠 ID 기준이다. 개발계에 없는 ID는 건너뛴다. 다시 돌려도 결과가 같게(멱등) 짠다.

### 두지 않는 것

- 라이브러리의 "시리즈 항목" 종류 — 묶어 보여 주기는 FE가 `series` 객체로 한다.
- 시리즈 구독(새 편이 나오면 자동 담기) — 드립의 연속 편 우선 선정이 그 역할을 한다.
- `next_episode` 같은 "다음 화" 필드 — 다음 화 듣기 보류(결정 사항).
- 시리즈 표지 칸 — 1화 썸네일(결정 사항).

### 확정한 세부 (2026-10-17 — 종전 "확인 요청")

- `contents.total_episodes`: **유지한다.** 업로드 때 `series.total_episodes`와 같아야 한다(1번).
- 탐색 시리즈 카드의 순위: **그 시리즈 편 점수의 최댓값**으로 정한다.
- 진행 중 시리즈(일부 편만 발행): **노출한다.** 파이프라인 시리즈는 전 편을 한꺼번에 올리므로 보통 생기지 않는다.
- 시리즈 카드 탭 = 목록 진입은 `explore.md` 4.4 "행 탭 = 즉시 재생"의 예외다 — `features/` 개정은 화면 쪽(FE·PM) 몫이다.

## 완료 조건

- Given 발행된 시리즈 3편 / When 탐색 피드·인기·검색을 본다 / Then 시리즈가 카드 하나로 나오고 편 3개가 따로 나오지 않는다
- Given 시리즈 카드 / When `GET /series/:id`를 부른다 / Then 1화 썸네일 표지·시리즈 정보·편 목록(번호순)·편마다 내 상태가 온다
- Given CS 16편 / When 일회성 마이그레이션을 돌린다 / Then 16편이 같은 `series_id`·`episode_no` 1~16·총 16편이 되고, `content_id`·`content_version`·담기·재생 위치가 그대로이며 응답에 `series` 객체가 실린다. 다시 돌려도 결과가 같다
- Given `series.total_episodes = 3`인 시리즈 / When `total_episodes = 4`로 업로드한다 / Then 400으로 거부된다
- Given 없는 `series_id` / When 업로드한다 / Then 400으로 거부된다
- Given 같은 시리즈에 이미 발행된 2화 / When 같은 번호로 업로드한다 / Then 400으로 거부된다
