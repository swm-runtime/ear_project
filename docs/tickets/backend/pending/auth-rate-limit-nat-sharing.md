## 문제

레이트 리밋의 키는 **유효한 액세스 토큰이 있으면 사용자 ID, 없으면 IP** 다(`getTracker`). 그래서 다음 세 경로가 IP 로 세어진다.

| 경로 | 왜 IP 인가 | 분당 한도 |
|---|---|---|
| `POST /auth/social-login` | 로그인 전이라 사용자를 알 수 없다 | 20 |
| `POST /auth/sign-up` | 같음 | 20 |
| `POST /auth/token/refresh` | **액세스 토큰이 만료돼서 부르는 것**이라 검증에 실패하고 IP 로 내려간다 | 20 |

**같은 공유기(NAT) 뒤의 사용자들이 하나의 IP 로 합산된다.** 회사·학교·대형 건물처럼 수백 명이 한 공인 IP 를 공유하는 환경에서, 서로의 한도를 깎아 정상 사용자가 429 를 받을 수 있다.

앞의 둘은 **의도된 설계다** — 로그인 전에는 사용자를 특정할 수 없고, 크리덴셜 스터핑 방어는 IP 단위가 맞다. 문제는 **세 번째**다. 토큰 갱신은 **이미 로그인한 사용자**의 동작이라 크리덴셜 스터핑 방어 대상이 아닌데, 같은 한도를 나눠 쓰고 있다.

## 언제 고칠 것인가 — 사용자 수 기준

**액세스 토큰 수명이 30분**이라(`auth.constant.ts` `ACCESS_TOKEN_TTL_SEC`) 사용자 한 명이 시간당 2회, 분당 **0.033회** 갱신한다. 한도 20회에 닿으려면:

```
20회/분 ÷ 0.033회/분/명  ≈  동시 활성 사용자 600명 (한 IP 뒤에)
```

| 한 IP 뒤 동시 활성 | 분당 갱신 | 판정 |
|---|---|---|
| 수 명 (가정·카페) | 0.2 미만 | 여유 |
| 수십 명 (회사·학교) | 1~2 | 여유 |
| 200명 | 약 7 | 여유 |
| **600명** | **약 20** | **한도 도달** |

여기에 로그인·가입 호출이 더해지므로 실제로는 그보다 조금 일찍 온다. 또한 **동시 만료가 겹치면** 평균보다 나빠질 수 있다 — 캠퍼스 홍보처럼 여러 사람이 같은 시각에 로그인하면 30분 뒤 갱신이 한꺼번에 몰린다.

**그래서 고칠 시점은 이렇다.**

- **전체 사용자 수천 명** 수준까지는 손대지 않아도 된다. 한 IP 뒤에 동시 활성 600명이 모이려면 그 조직 하나에서만 수백 명이 쓰고 있어야 한다.
- **전체 사용자 1만 명을 넘고, 특정 조직·캠퍼스 단위 사용이 보이기 시작하면** 그때 고친다.
- 그 전이라도 **429 가 인증 경로에서 실제로 관측되면** 즉시 올린다(`ear_rate_limited` · 어드민 에러 모아보기).

막히더라도 **1분 뒤 자동으로 풀린다.** 영구 차단이 아니라 서비스가 멈추는 종류의 문제는 아니다.

## 요청 내용 (제안)

**토큰 갱신을 IP 한도에서 떼어낸다.** 그러면 IP 한도는 순수하게 로그인·가입만 맡게 되어 NAT 합산 문제가 사실상 사라진다.

1. `POST /auth/token/refresh` 의 레이트 리밋 키를 **리프레시 토큰 단위**로 바꾼다(토큰 원문이 아니라 해시). 한 세션이 분당 몇 번까지 갱신할 수 있는가는 세션 단위로 세는 것이 의미상 맞다.
2. 갱신용 한도를 별도 상수로 둔다. 정상 동작이 30분에 1회이므로 분당 5회면 넉넉하다.
3. 로그인·가입은 **종전대로 IP 20회**를 유지한다 — 크리덴셜 스터핑 방어는 IP 가 맞다.

**대안**으로 IP + 기기 식별자 조합을 키로 쓰는 방법도 있으나, 기기 식별자는 클라이언트가 보내는 값이라 위조 가능해 방어력이 떨어진다. 한도를 올리는 방법은 방어를 그만큼 약화시킨다.

## 범위 밖

- 여러 **인스턴스**로 늘릴 때의 정확한 한도 — 인메모리 저장이라 나누기로도 안 되고 Redis 스토리지가 필요하다(`infra/scaling.md` 5장). 이 티켓과 별개다.
- 클러스터(워커 N개)에서의 한도 취급 — 2026-09-22 에 정리했다(`rate-limit.constant.ts` 주석 + `rate-limit.constant.spec.ts`).

## 완료 조건

- Given 같은 IP 뒤에서 사용자 600명이 동시에 토큰을 갱신한다 / When 갱신을 요청한다 / Then 서로의 한도를 깎지 않고 전부 통과한다
- Given 한 사용자가 같은 리프레시 토큰으로 분당 한도를 넘겨 갱신을 시도한다 / When 초과분을 요청한다 / Then 429 로 막힌다
- Given 같은 IP 에서 로그인을 분당 20회 넘게 시도한다 / When 21회째를 요청한다 / Then 종전과 같이 429 다(로그인 방어는 그대로)
- Given `architecture.md` 9.6 / When 읽는다 / Then 갱신 한도가 별도 행으로 있고 키가 세션이라고 적혀 있다
