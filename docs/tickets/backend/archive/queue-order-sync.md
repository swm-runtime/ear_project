## 배경

플레이어의 재생 목록은 **필터 없는 라이브러리 첫 페이지**를 그대로 쓴다(새 엔드포인트 없음 — 2026-09-17 결정). 2026-09-18 에 FE 가 행 오른쪽 손잡이로 **순서를 바꾸는 기능**을 넣었는데, 서버에 순서를 둘 자리가 없어 **기기 로컬**(`player.queue_order` — `library_items.id` 의 나열)에만 저장한다.

그 결과:

- 다른 기기·재설치·로그아웃 후 재로그인에서 순서가 사라진다.
- 같은 계정의 두 기기가 서로 다른 순서를 본다.
- 나중에 **연속 재생**(현재 비범위 — `player.md` 8장 미결)이 들어오면 "다음에 재생할 편"을 이 순서로 정해야 하는데, 그 판정을 서버가 할 수 없다("판정은 서버가 한다" 원칙과 부딪힌다).

## 요청

사용자가 정한 재생 목록 순서를 **계정 단위로 저장하고 돌려주는 계약**. 모양은 BE 가 정한다 — 아래는 FE 가 필요한 것과 제안이다.

### FE 가 필요한 것

1. **순서 저장** — 사용자가 한 번 옮길 때마다 호출한다(끌기 1회 = 호출 1회). 실패해도 재생에는 영향이 없어야 한다 — FE 는 조용히 로컬 순서를 유지하고 다음 저장 때 다시 보낸다.
2. **순서 조회** — 재생 목록을 열 때 순서가 입혀진 목록 또는 순서 자체를 받는다.
3. **순서에 없는 항목의 자리 규칙** — 새로 담긴 항목은 **맨 위**(라이브러리 최신순과 같은 감각). FE 의 현재 규칙이고(`frontend/src/features/player/services/queue-order.ts` `applyQueueOrder`), 서버가 같은 규칙을 가지면 기기마다 결과가 같다.
4. 삭제·회수된 항목은 순서에서 빠진다.

### 제안(택일 — BE 판단)

- **A. 순서 목록을 통째로 저장**: `PUT /library/queue-order` `{ "itemIds": ["…", "…"] }` + `GET /library/queue-order`. FE 의 현재 로컬 구조와 같아 이관이 가장 단순하다. 목록 상한(예: 200)이 필요하다.
- **B. `library_items` 에 정렬 키 컬럼**: `queue_position`(실수 또는 문자열 분수 인덱스). 한 항목 이동 = 한 행 갱신. 라이브러리 조회에 `sort=queue` 를 더한다. 페이지네이션과 자연스럽게 맞는다.

B 가 장기적으로 낫다고 본다(첫 페이지 밖의 항목까지 일관되게 정렬되고, 연속 재생의 "다음 편" 판정이 쿼리 한 번이다). 다만 스키마 변경이라 `domain.md` 갱신이 먼저다.

### 범위 밖

- 연속 재생 자체(FR-24 자동 재생 금지·재생 한도 차감과 얽힌 정책 결정이 먼저다 — PM 결정 대기).
- 라이브러리 **화면**의 정렬 변경 — 이 순서는 재생 목록 패널에만 쓴다.

## FE 후속

계약이 확정되면 FE 는 `useQueueOrder` 의 저장소를 로컬 → API 로 바꾸고, 로컬에 남은 순서를 첫 호출 때 한 번 올려 이관한다. 별도 FE 티켓으로 발행한다.

## 완료 조건

- Given 기기 A 에서 재생 목록 순서를 바꿨다 / When 같은 계정으로 기기 B 에서 재생 목록을 연다 / Then 같은 순서다
- Given 순서를 저장한 뒤 새 콘텐츠가 담겼다 / When 재생 목록을 조회한다 / Then 새 항목이 맨 위에 있고 나머지는 저장한 순서다
- Given 순서에 있던 항목이 라이브러리에서 삭제·회수됐다 / When 조회한다 / Then 그 항목 없이 나머지 순서가 유지된다
- Given 순서 저장 호출이 실패한다 / When 사용자가 계속 재생한다 / Then 재생·라이브러리 조회에는 영향이 없다
- Given `domain.md`·api 문서 / When 읽는다 / Then 순서의 저장 위치·상한·새 항목 자리 규칙이 적혀 있다

## 처리 기록 (2026-09-19 — B 채택·구현, PR `feat(be)/queue-order-sync`)

- **B(`library_items.queue_position` 정렬 키)를 택했다.** 사유: 첫 페이지 밖 항목까지 한 정렬로 일관되고, 연속 재생이 들어오면 "다음 편" 판정이 쿼리 한 번이다. A는 목록 밖 항목의 자리를 표현할 수 없다.
- 계약: `GET /users/me/library-items?sort=queue`(`queue_position ASC NULLS FIRST, added_at DESC, id DESC` — 새로 담긴 항목 맨 위·최신순, 그 아래 저장한 순서) + `PUT /users/me/library-items/queue-order` `{ item_ids: uuid[1..200] }` → 204. `library-api.md` 3장·4.1·4.8·8장, `domain.md` 6.1 반영.
- 저장 규칙: 보낸 목록을 1..n으로, 이번 목록에 없는 기존 순서 항목은 n+1부터 저장한 순서대로 이어 붙인다. 남의 항목·삭제된 항목은 조용히 뺀다(끌기마다 오는 호출을 실패시키지 않는다 — 요구 1). 삭제해도 값은 남겨 복구 시 자리가 돌아온다(완료 조건 3). 한 트랜잭션·한 UPDATE 문장.
- 커서: `sort=queue`는 세 키 keyset이라 커서에 `queue_position`(`p`, null 허용)을 더했고 다른 정렬 커서와 섞이지 않는다.
- 마이그레이션 `1787600000000-AddLibraryItemQueuePosition`(컬럼 + NULLS FIRST 인덱스).
- **FE 후속 티켓 발행**: `tickets/frontend/pending/queue-order-api-migration.md` · Jira KAN-74(이주호, Low) — `useQueueOrder` 저장소를 로컬 → API로, 로컬 순서는 첫 호출 때 한 번 올려 이관. 서버 규칙이 `applyQueueOrder`와 같아 결과가 바뀌지 않는다.
