# [BE] 탐색 피드가 선호도 캐시를 읽지 않고 매 요청 신호를 재집계한다

| 요청 파트 | 백엔드 |
| 발행 날짜 | 2026-09-08 |
| 발견 시점 | 2026-09-08 백엔드 코드 전수 점검 — 성능 항목으로 잡았으나 **추천 결과가 바뀌는 제품 결정**이라 분리했다 |

| 상태 | 대기 — **결정이 먼저다**(아래) |

## 문제

`domain.md` 7.2가 이렇게 정한다.

> **실시간 재계산은 하지 않는다.** 탐색 피드 랭킹(조회 시점 계산)도 **이 캐시를 읽는다** — 랭킹마다 재집계하지 않는다.

`drip-scheduling.md` 2도 "추천(탐색 피드 랭킹)은 … **같은 신호·같은 스코어링을 공유한다**"로 적는다.

그런데 탐색은 **피드를 열 때마다** `user_signals` 최근 200건과 그 콘텐츠들의 주제를 읽어 자체 가중치로 점수를 만든다. `PreferenceVectorService`를 import하지 않는다.

### 두 스코어링이 이미 갈라져 있다

| | 탐색 (`SIGNAL_TOPIC_WEIGHTS`) | 드립 캐시 (`SIGNAL_ACTION_WEIGHTS`) |
|---|---|---|
| 완청 | 3 | 1 |
| 재청취 | 3 | 1 |
| 담기 | 2 | 0.5 |
| 담기 해제 | −1 | −0.6 |
| 삭제 | −1 | −0.6 |
| 감쇠 | 30일 **선형** | 14일 **지수(반감기)** |

**같은 신호를 두 규칙으로 해석하고 있다.** 한쪽을 고쳐도 다른 쪽은 그대로라, 앞으로도 각자 흘러간다.

부수적으로 매 피드 조회가 신호 200건 + 주제 조인을 더 읽는다 — 캐시를 도입한 이유가 이것이었다.

## 결정이 필요한 것 (착수 전)

**바꾸면 사용자가 보는 추천 순서가 실제로 달라진다.** 성능만 얻는 변경이 아니므로, 무엇을 기준으로 통일할지 먼저 정해야 한다.

1. **가중치·감쇠를 어느 쪽에 맞출 것인가.** 캐시(드립) 쪽으로 통일하는 것이 문서 문언에 맞지만, 탐색의 값이 화면을 보며 조정된 것이라면 그쪽이 실측에 가까울 수 있다. 두 값의 유래를 아는 사람이 정해야 한다.
2. **캐시 신선도를 받아들일 것인가.** 캐시는 드립 배치가 하루 한 번 갱신한다. 방금 담은 콘텐츠가 **다음 배치 전까지 피드 랭킹에 반영되지 않는다.** `domain.md` 7.2는 이를 의도한 설계로 적지만, 탐색은 "방금 한 행동이 바로 보이는" 화면이라 체감이 다를 수 있다.
3. **캐시가 없는 사용자의 경로.** 가입 직후·첫 배치 이전에는 `user_preference_vectors` 행이 없다. 콜드스타트 분기(`isColdStart`)로 흡수되는지, 별도 폴백이 필요한지 확인이 필요하다.

## 요청 내용 (결정 후)

- 탐색 관심사 섹션 랭킹이 `user_preference_vectors.topic_weights`를 읽게 한다. 매 요청 `findRecentSignals` + 주제 조인을 제거한다.
- 통일된 가중치·감쇠를 **한 곳**에만 둔다. `SIGNAL_TOPIC_WEIGHTS`와 `SIGNAL_ACTION_WEIGHTS` 중 하나는 사라져야 한다 — 남겨 두면 이 티켓이 다시 열린다.
- `MAX_RECENT_SIGNAL_COUNT` · `SIGNAL_RECENCY_WINDOW_DAYS`가 다른 곳에서 쓰이지 않으면 함께 정리한다.

## 완료 조건

- Given 탐색 피드 조회 / When 쿼리를 센다 / Then `user_signals`를 읽지 않는다
- Given 같은 사용자 / When 탐색 랭킹과 드립 스코어링의 주제 가중치를 비교한다 / Then 같은 값에서 나온다
- Given 가중치 상수 / When 저장소를 검색한다 / Then 신호→주제 가중치 표가 한 곳에만 있다
- Given 가입 직후 사용자(캐시 행 없음) / When 피드를 연다 / Then 500이 아니라 콜드스타트 규칙대로 그려진다

## 처리 기록 (2026-09-10 — 캐시 기준으로 통일해 반영)

| 항목 | 값 |
|---|---|
| 발행 날짜 | 2026-09-08 |
| 반영 날짜 | 2026-09-10 |

**결정 1 — 캐시(드립) 쪽으로 통일했다.** 탐색의 `SIGNAL_TOPIC_WEIGHTS`를 삭제하고
`drip.constant.ts`의 `SIGNAL_ACTION_WEIGHTS`(완청 1 · 재청취 1 · 담기 0.5 ·
해제 −0.6 · 삭제 −0.6, 14일 반감기 지수 감쇠) 하나만 남겼다. 신호→가중치 환산은
`PreferenceVectorService` 한 곳에서만 일어난다.

**부수 효과 — `skip`이 랭킹에서 빠진다.** 탐색 표에만 `SKIP: -2`가 남아 있었는데
`drip-scheduling.md` 4.3은 "스킵 신호는 제거됐다(확정 2026-08-10)"고 적는다.
탐색이 폐기된 신호를 계속 쓰고 있던 것이라, 통일이 곧 문서와의 정합이다.

**결정 2 — 캐시 신선도를 받아들인다.** `domain.md` 7.2가 의도한 설계로 적은 대로
피드는 배치 결과를 읽기만 한다. 방금 담은 콘텐츠는 다음 배치부터 랭킹에 반영된다.

**결정 3 — 콜드스타트 판정도 캐시에서 읽는다.** 종전의 실시간 `countSignals()`를
캐시 행의 `signal_count`로 대체했다. 완료 조건 ①("`user_signals`를 읽지 않는다")이
실시간 카운트와 양립하지 않기도 하지만, 더 큰 이유는 **판정과 가중치가 같은
스냅샷에서 나와야** "콜드스타트는 벗어났는데 가중치는 비어 있는" 중간 상태가 생기지
않기 때문이다. 대가는 콜드스타트 탈출이 최대 배치 한 주기만큼 늦어지는 것이다.
`COLD_START_COMPLETE_SIGNAL_COUNT`(탐색 사본)도 삭제하고 드립의
`COLD_START_COMPLETE_THRESHOLD`를 쓴다 — 같은 캐시를 읽으면서 기준만 사본을 두면
같은 갈라짐이 다시 생긴다.

**결정 3의 폴백 — 별도로 두지 않았다.** 캐시 행이 없는 사용자는 `signalCount`를
0으로 읽어 콜드스타트 분기로 흡수된다. 가입 직후·첫 배치 이전이 정확히 콜드스타트
상태이므로 새 경로를 만들 이유가 없다.

### 완료 조건 확인 (실 DB·실서버 대조)

- ✅ 피드 3회 호출 동안 `pg_stat_user_tables`의 `user_signals` 스캔 증가 **0**
- ✅ 탐색 랭킹과 드립 스코어링이 같은 `user_preference_vectors.topic_weights`에서 나온다
- ✅ 신호→주제 가중치 표는 `drip.constant.ts` 한 곳뿐이다
- ✅ 캐시 행이 없는 사용자는 500이 아니라 콜드스타트 순서(인기·신규·관심사)로 그려진다

캐시 값만 바꿔 가며 피드를 실제로 호출한 결과 — `signal_count=2`는 콜드스타트 순서를
유지하고, `=5`에서 생산성 가중과 커뮤니케이션 가중이 **서로 다른 3건**을 앞에 세웠으며,
음수 가중치는 해당 주제를 뒤로 내렸다.

`MAX_RECENT_SIGNAL_COUNT` · `SIGNAL_RECENCY_WINDOW_DAYS`도 함께 삭제했다.
`PlaybackService.findRecentSignals`는 편성 배치가 계속 쓰므로 남긴다.
