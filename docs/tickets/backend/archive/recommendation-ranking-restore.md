|---|---|
| 대상 | `content_stats` 집계 배치(미구현) · `onboarding.orchestrator.ts` 랜덤 폴백 · `content.repository.ts` `findCandidates` 정렬 |
| 요청 파트 | 백엔드 |
| 발행 날짜 | 2026-09-09 |
| 발견 시점 | 2026-09-08 백엔드 전수 점검 — 세 건이 서로 맞물려 있어 하나로 묶는다 |
| 근거 문서 | `backend/domain.md` 5.4 · `features/drip-scheduling.md` 4.2·4.4·4.8 · `features/onboarding.md` 7 · `features/README.md` 결정 12 |

## 왜 하나로 묶는가

셋이 같은 뿌리에서 나온다. **`content_stats`를 채우는 배치가 없다.**

```
집계 배치 없음
  → 모든 play_count = 0
      → ① 인기도 축이 상수 → 랭킹에 기여하지 않음
      → ② 표본 30건 미만 → 폐기된 랜덤 폴백이 항상 발동
      → ③ 탐험 풀 정렬(play_count DESC)이 무의미 → 사실상 published_at 순
```

②를 코드로 지우기 전에 ①을 고치면 **②는 저절로 사라진다**(표본이 30건을 넘는 순간). 그래서 순서가 중요하다.

## ① `content_stats` 집계 배치가 없다

`domain.md` 5.4는 갱신 주기까지 정한다.

> **갱신 주기** — `week` 매주 월요일 04:00 / `month` 매달 1일 04:00 / `all` 위 배치와 함께 갱신 … 집계 배치는 `playback` 모듈이 실행한다.

그런데 `ContentStatRepository`의 쓰기 메서드를 부르는 곳은 **`seed-mock-onboarding.ts` 하나뿐이다.** 운영 코드에는 없다.

**영향 범위**

| 쓰는 곳 | 지금 |
|---|---|
| 탐색 인기 섹션·구간 토글 | 전부 0 → 사실상 `published_at DESC` |
| 탐색 주제 필터 목록 | 랭킹 1순위가 상수 → 같음 |
| 검색 동점 해소 | 동작하지 않음 |
| 드립 인기도 축 | 가중치 0.25, **콜드스타트 0.45** — 신규 사용자 추천의 절반 가까이가 무의미 |

**요청** — `domain.md` 5.4대로 재집계 upsert 배치를 만든다. "증분이 아니라 **재집계 upsert**"이고 "배치가 두 번 돌아도 결과가 같아야 한다". 04시 경계는 `service-date.util`을 쓴다. `replay_count` 컬럼은 2026-09-09에 추가돼 있다.

## ② 폐기된 랜덤 폴백이 모든 사용자에게 발동한다

`onboarding.orchestrator.ts`의 "표본 30건 미만 → 랜덤 3건 + 섹션 제목 교체 + 시드 고정" 분기다. `features/README.md` 결정 12가 **폐기**했다.

> **변경(2026-08-06): 랜덤 배치 폐기.** … 섹션 제목·시드 고정 규칙도 함께 폐기.

`onboarding.md` 91행도 같다 — "표본이 부족해도 **선정 기준을 바꾸지 않는다**".

①이 고쳐지지 않는 한 표본은 항상 0이므로, **지금 모든 신규 사용자가 온보딩 3단계에서 이 폐기된 경로를 본다.**

**요청** — 분기를 제거한다. `isMonthlySampleSufficient`와 `MONTHLY_POPULAR_SAMPLE_THRESHOLD`는 각각 호출부가 하나뿐이라 함께 죽는다.

## ③ 탐험 슬롯이 저노출과 반대로 뽑는다

`findCandidates`가 항상 `play_count DESC … LIMIT 300`(`SCORING_POOL_LIMIT`)으로 끝난다. 그 풀을 탐험 스코어러가 `lowExposure: 0.5`로 받는다.

`drip-scheduling.md` 4.8-2는 이렇게 정한다.

> **저노출·신규 우선**: 전 사용자 기준 편성 이력이 적거나 `published_at`이 최근인 콘텐츠에 가점 — **이 슬롯의 존재 이유다.**

**가장 많이 재생된 300개** 안에서 저노출을 고르고 있다. 카탈로그가 300개를 넘는 순간 저노출 콘텐츠는 풀에 들어올 수조차 없다 — 4.8이 깨려던 콘텐츠 콜드스타트 고리가 그대로 남는다.

**요청** — 탐험 슬롯에 전용 풀 조회를 준다(`published_at DESC` 또는 노출 오름차순).

## 진행 순서 (제안)

1. **점수 근거 로깅부터** — `ScoredCandidate`에 축별 점수를 실어 배치 로그에 남긴다. 지금은 "왜 이게 갔나"에 답할 수단이 없고, ①의 효과를 확인할 방법도 없다
2. ③ (독립적이고 작다)
3. ① — 이때 ②가 저절로 안 타게 된다
4. ② 코드 제거

## 완료 조건

- Given 배치 실행 후 / When `content_stats`를 조회한다 / Then `all` · `week` · `month` 구간 행이 있고 두 번 돌려도 값이 같다
- Given 재생이 30건 넘은 상태 / When 온보딩 3단계를 연다 / Then 랜덤 3건이 아니라 인기 기준으로 선정된다
- Given 카탈로그가 300건을 넘는다 / When 탐험 슬롯 후보를 본다 / Then 저노출 콘텐츠가 풀에 들어온다
- Given 편성 배치 로그 / When 한 사용자의 편성을 본다 / Then 축별 점수로 선정 이유를 되짚을 수 있다

## 처리 기록 (반영 날짜: 2026-09-09)

**셋 다 반영했고, 제안한 순서를 그대로 따랐다.**

### 0 · 점수 근거 로깅 (선행)

`ScoreBreakdown`을 `ScoredCandidate`에 실어, 편성된 콘텐츠마다 **축별·항목별 점수**를 배치 로그에 남긴다.

- `null`은 **입력이 없어 축에서 빠졌다**는 뜻이고 0과 다르다(4.2 재정규화)
- 사용자당 편성 편수(2~3편)만 남는다 — 후보 300건 전체를 남기지 않는다
- 탐험 슬롯도 같은 형태로 남기되, **쓰지 않는 축은 `null`로** 드러낸다

이게 없어서 ①②③ 셋 다 코드를 읽기 전까지 아무도 몰랐다. **입력이 죽어 있어도 점수는 나오기 때문이다.**

### ③ 탐험 풀 정렬

`ContentCandidateQuery.lowExposureFirst`를 두고 탐험 슬롯만 `play_count ASC`로 자른다. 종전에는 **가장 많이 재생된 300건 안에서 저노출을 고르고** 있었다.

### ① `content_stats` 집계 배치

`playback` 모듈에 신설했다(5.4 — "집계 배치는 playback 모듈이 실행한다").

- **재집계 upsert 한 문장.** 콘텐츠를 순회하지 않는다 — 그 사이 들어온 재생이 구간에 반쯤 섞인다
- **`is_final = true` 행은 건드리지 않는다**(`WHERE content_stats.is_final = false`)
- 끝난 구간(직전 주·월)은 확정해 잠그고, 진행 중 구간과 `all`은 잠그지 않는다
- 04시 경계를 **SQL에서도 같은 규칙으로** 환산한다 — 두 곳이 갈리면 집계와 판정이 어긋난다
- **매일 04:00에 돈다.** 문서는 주/월을 나눠 적었으나, 그 하루만 도는 잡이 실패하면 다음 주·다음 달까지 값이 빈다. 재집계라 몇 번 돌아도 같다
- 드립 편성(05:00)보다 **먼저** 돈다 — 편성의 인기도 축이 이 값을 읽는다

### ② 랜덤 폴백 제거

`isMonthlySampleSufficient` 분기를 걷어냈다. 순위가 비어 있으면 기존 정렬이 원래 후보 순서를 유지하므로, 인기 데이터가 쌓이기 전에도 **같은 기준**으로 뽑는다.

함께 죽은 것: `isMonthlySampleSufficient` · `MONTHLY_POPULAR_SAMPLE_THRESHOLD` · `shuffleWithSeed`(`seeded-random.util` 삭제).

**`RecommendationSectionType.TOPIC_DISCOVERY`는 enum에 남겼다** — 계약 필드라(`onboarding-api.md` 4.5) 서버가 더 이상 내보내지 않을 뿐이다. 제거는 계약 변경이므로 `changes/`로 분리한다.

### 부수로 고친 것

`npm run seed:mock`이 **깨져 있었다.** 2026-09-08에 `contents.partner_id`에 FK를 붙였는데, seed가 존재하지 않는 파트너를 가리키고 있었다 — **그 제약이 잡아낸 첫 사례다.** seed가 파트너 행을 먼저 만들도록 고쳤다.

### 남은 것

- **추천 결과가 실제로 바뀌었다.** 인기도 축이 살아나고 온보딩 3단계가 랜덤이 아니게 됐다. 데이터가 쌓인 뒤 로그로 확인할 것
- `TOPIC_DISCOVERY` enum·카피 정리는 `changes/` 소관
