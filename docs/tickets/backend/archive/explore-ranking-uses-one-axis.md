| 발견 시점 | 2026-09-10 탐색 랭킹을 선호도 캐시로 통일하면서(#302) — 통일 자체는 끝났고, 읽는 축이 하나뿐이라는 것이 그때 드러났다 |

## 문제

`user_preference_vectors`에는 축이 여섯 개 들어 있다.

| 축 | 편성 배치(`DripScoringService`) | 탐색(`rankByTopicWeights`) |
|---|---|---|
| 주제 가중치 | 사용 | **사용** |
| 취향 임베딩 (`taste_embedding`) | 사용 | 미사용 |
| 저자 가중치 | 사용 | 미사용 |
| 키워드 가중치 | 사용 | 미사용 |
| 형식 가중치 | 사용 | 미사용 |
| 길이 취향 (`duration_pref`) | 사용 | 미사용 |

탐색의 콘텐츠 점수는 **그 콘텐츠가 가진 주제들의 가중치 합**이다. 결과가 이렇다.

- **같은 주제를 가진 콘텐츠끼리는 점수가 같다.** 커뮤니케이션 콘텐츠 9건은 전부 동점이고, 정렬이 안정 정렬이라 **후보 풀에 들어온 순서(인기·신선도) 그대로** 나간다.
- 그래서 점수표가 흔들 수 있는 것은 **"어느 주제 뭉치가 먼저 오냐"** 뿐이다.
- 관심 주제는 2~3개이고 주제 간 가중치 차이가 벌어져 있으면 그마저도 잘 안 뒤집힌다.

**체감**: 사용자가 커리어 콘텐츠를 열 편 몰아 들어도 탐색 화면의 순서가 거의 그대로다.

### 이 티켓이 다루지 않는 것

**신선도 문제가 아니다.** 캐시는 편성 배치가 하루 한 번 갱신하는데(`domain.md` 7.2가 의도한 설계), **갱신 주기를 줄여도 위 문제는 그대로다** — 주제 단위 점수는 아무리 자주 갱신해도 같은 주제 안의 순서를 바꾸지 못한다. 반응성을 올리는 레버는 주기가 아니라 축이다.

## 요청 내용

**취향 임베딩 축을 먼저 넣는다.** 콘텐츠 한 건마다 코사인 유사도가 달라 **같은 주제 안에서도 순서가 갈리는 유일한 축**이다. 나머지(저자·키워드·형식·길이)는 그다음이다.

- `ExploreOrchestrator`가 이미 `UserPreferenceWeights` 객체 전체를 손에 쥐고 있다(#302에서 그렇게 됐다). **배관을 새로 깔 필요가 없고 읽는 필드를 늘리는 일이다.**
- 후보의 임베딩이 필요하다 — `ContentService.findScorableEmbeddings`가 이미 있다(편성 배치가 쓴다).
- 축 결합 가중치와 재정규화 규칙은 `drip-scheduling.md` 4.2가 이미 정한다(`AXIS_WEIGHT_EMBEDDING` 0.3 등). **탐색이 자기 값을 새로 만들지 않는다** — 같은 규칙의 구현이 두 벌이 되는 것이 #302가 고친 문제였다.
- `taste_embedding`이 null인 사용자(긍정 신호 콘텐츠에 임베딩이 하나도 없음)는 4.2의 재정규화로 그 축이 빠진다.

## 착수 전 판단할 것

1. **탐색이 편성 스코어링을 그대로 재사용할 것인가, 축만 빌려올 것인가.** 편성은 MMR 다양성 감점·노출 피로·시리즈 순서까지 본다. 탐색에 그대로 가져오면 "발견" 화면의 성격이 바뀔 수 있다.
2. **후보 풀도 함께 볼 것인가.** 지금 후보는 인기·신선도 상위 60건이라, **풀 밖에 있는 콘텐츠는 취향이 아무리 맞아도 올라오지 못한다.** 축을 늘려도 이 한계는 남는다(`EXPLORE_RANKING_POOL_SIZE` 주석에 이미 적혀 있다).
3. **비용** — 후보 60건의 임베딩 조회가 피드 조회마다 추가된다. #302에서 줄인 조회량을 다시 쓰는 셈이므로 실측이 필요하다.

## 완료 조건

- Given 같은 주제의 콘텐츠 여러 건 / When 사용자가 그중 일부와 비슷한 편을 완청한다 / Then **같은 주제 안에서도** 비슷한 편이 앞으로 온다
- Given 축 결합 가중치 / When 저장소를 검색한다 / Then 값이 `drip.constant.ts` 한 곳에만 있다
- Given `taste_embedding`이 null인 사용자 / When 피드를 연다 / Then 임베딩 축이 빠진 채 나머지 축으로 정상 정렬된다
- Given 콜드스타트 사용자 / When 피드를 연다 / Then 종전과 같이 인기·신선도 순으로 그려진다

## 처리 기록 (반영 날짜: 2026-09-11)

**"축만 빌려오기"로 확정하고 여섯 축을 한 번에 넣었다** — 임베딩 축만 먼저 넣는 안은 "나중에 나머지 축을
또 손대야 하는" 임시 설정이라 채택하지 않았다(사용자 결정 2026-09-11).

- `DripScoringService.rankByPersonalFit(candidates, preference, now)` 신설 — 4.2의 ① 임베딩 축 + ② 신호 선호
  축(주제·저자·키워드·형식·길이)을 편성과 **같은 상수·같은 함수**(`AXIS_WEIGHT_*`, `weightedMean`)로 결합한다.
  ③ 메타 축(인기·신선도·시리즈·노출 피로·다양성)은 "무엇을 적립할까"의 규칙이라 탐색에는 넣지 않는다 —
  후보 풀이 이미 인기·신선도 순이고 그 순서가 tie-break다. 근거 없는 후보는 중립값(0.5)으로 두어 정보가
  없다는 이유로 밀리지 않게 한다.
- `ExploreOrchestrator.findInterestContents`가 이 함수를 쓴다. 후보 임베딩은 편성과 같은
  `findScorableEmbeddings`(60건 1회 조회). `explore.ranking.ts`(주제 가중치 전용)와 그 스펙은 삭제 —
  같은 규칙의 구현이 두 벌이던 상태를 없앴다.
- 착수 전 판단 3항목: ① 편성 스코어링 통째 재사용 아님(취향 축만) ② 후보 풀 60건은 그대로(별건 —
  `EXPLORE_RANKING_POOL_SIZE` 주석에 한계 명시) ③ 비용은 피드당 임베딩 조회 1회 — 콘텐츠 수백 편에서 재실측.
- 검증: 단위 4건(rankByPersonalFit) + 탐색 오케스트레이터 2건(같은 주제 안 임베딩 순서 / 임베딩 없으면
  종전과 동일). 콜드스타트 사용자는 종전대로 인기·신선도 순(기존 테스트 유지). `taste_embedding`이 null이면
  임베딩 축이 재정규화로 빠진다.
- 완료 조건 4개 충족. 문서 변경 없음 — `explore.md` 4.1 "UserInterest + 소비 신호 기반 랭킹", `domain.md` 7.2
  "탐색 피드 랭킹도 이 캐시를 읽는다"와 정합하며 축 구성은 서버 소유다.
