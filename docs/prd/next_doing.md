# PRD 다음 단계 가이드

PRD는 "무엇을·왜"를 정의한 문서입니다. 지금부터는 이걸 "어떻게 구현할지" 화면·기능 단위로 뜯어내야 합니다.

## 1. 다음 단계, 이 순서로

1. **PRD에 남은 애매한 부분부터 확정** (P0/P1 구분, 탈퇴 시 데이터 처리 등) — 안 정하고 넘어가면 스펙 쓰다가 자꾸 PRD로 되돌아옵니다.
2. **제일 어려운 부분(콘텐츠 파이프라인: 대본생성→QA→발행) 설계를 화면보다 먼저** — 이 서비스에서 유일하게 검증 안 된 영역이라 밑그림이 없으면 화면 스펙이 계속 흔들립니다.
3. **화면별로 기능 명세서 작성** (아래 2번 형식)
4. **인앱결제는 지금 바로 별도로 시작** — 스토어 심사·테스트 계정 준비가 항상 예상보다 오래 걸립니다.
5. 명세 다 안 끝나도 다 나온 화면부터 바로 개발 시작 — 3명이니 병렬로 가는 게 속도입니다.

## 2. 기능 명세서, 이 8가지만 채우면 됩니다

| # | 항목 | 한 줄 설명 |
|---|---|---|
| 1 | 목적 & 연결 | 어느 PRD 기능(FR)과 연결되는지 |
| 2 | 진입 조건 | 언제 이 기능이 시작되는지 |
| 3 | 입력값 | 뭘 받는지, 필수/선택 |
| 4 | 처리 로직 | 조건에 따라 어떻게 분기하는지 (제일 빠뜨리기 쉬움) |
| 5 | 화면 상태 | 성공/실패/로딩/에러 화면이 각각 어떻게 보이는지 |
| 6 | 데이터 모델 | 뭘 저장/변경하는지 |
| 7 | 예외 상황 | 애매한 경계 케이스 |
| 8 | 완료 조건 | "이렇게 동작하면 완성" 문장 (Given-When-Then) |

## 3. 예시: 페이월 기능 명세서 (PRD FR-29, FR-30 기준)

**1. 목적 & 연결**
무료 사용자를 유료로 전환한다. PRD FR-29 / FR-30 / 사용자흐름 5.4와 연결.

**2. 진입 조건**
무료 사용자가 오늘 3번째 콘텐츠 재생을 시도할 때. (재생 카운트는 04시 기준으로 초기화 — PRD 9.1)

**3. 입력값**
- user_id, 현재 tier
- 오늘 재생한 콘텐츠 수(daily_play_count)
- 지금 재생하려는 콘텐츠 id

**4. 처리 로직**
- `tier == 무료` AND `daily_play_count >= 2` → 재생 차단, 페이월 바텀시트 노출
- 그 외 → 정상 재생
- 라이브러리에 "담기"만 하는 행위는 카운트에 포함 안 함 (PRD 5.4에 이미 명시)

**5. 화면 상태**
- 무료·카운트<2: 재생 버튼 → 즉시 재생
- 무료·카운트≥2·3번째 시도: 페이월 바텀시트(제한 안내 + 3티어 요금제 비교 + 결제 버튼)
- 바텀시트 "닫기": 원래 화면으로 복귀, 재생 안 됨
- 결제 진행 중: 로딩
- 결제 완료: 바텀시트 닫힘 + tier 즉시 갱신 + 원래 누르려던 콘텐츠 자동 재생

**6. 데이터 모델**
`User { tier, daily_play_count, count_reset_at }`, `Subscription { tier, started_at, expires_at }`

**7. 예외 상황**
- 04시 리셋 경계에 딱 걸쳐서 재생을 시도하는 경우
- 결제 진행 중 앱을 백그라운드로 보냈다가 다시 켠 경우
- 결제 버튼을 빠르게 두 번 눌러 중복 결제 요청이 생기는 경우

**8. 완료 조건**
- Given 무료 사용자가 오늘 2편을 재생 완료했다 / When 3번째 콘텐츠를 재생 시도한다 / Then 페이월이 뜨고 재생은 시작되지 않는다
- Given 페이월이 뜬 상태 / When 결제를 완료한다 / Then tier가 바로 바뀌고 원래 시도했던 콘텐츠가 재생된다
- Given 무료 사용자가 오늘 이미 2편을 재생했다 / When 콘텐츠를 "담기"만 한다 / Then 페이월 없이 정상적으로 담긴다

막상 채워보면 PRD에 없던 질문이 튀어나옵니다. "재생 카운트는 재생 버튼을 누른 시점에 올라가나, 완청 시점에 올라가나?" 같은 것들이요. 기능 명세서를 쓰는 이유가 여기 있습니다. PRD 단계에선 안 보이던 결정 포인트를 미리 찾아내는 겁니다.
