## 1. 현재 구조와 실측 한계

운영은 **EC2 t4g.small 한 대**(vCPU 2 · RAM 2GB)에 docker compose 로 `caddy` · `api` · `postgres` 가 함께 뜬다. 오디오·썸네일은 S3 + CloudFront 가 나르므로 이 인스턴스를 지나지 않는다.

부하 테스트에서 확인된 청취 여정의 상한이다(개발계는 운영과 같은 사양·구성).

| 동시 청취자 | 초당 요청 | p95 | API CPU (1코어 = 100%) |
|---|---|---|---|
| 200 | 85 | 42ms | 50% |
| 300 | 124 | 63ms | 75% |
| **350** | 146 | 176ms | **100% (포화)** |
| 450 | 157 | 693ms | — |
| 500 | 150~172 | 1.3~2.1s | 105% |

- **상한은 동시 350명 / 초당 150~170요청**이고, 안전 구간은 **동시 300명**이다.
- **병목은 DB가 아니라 API 프로세스 CPU다.** Node 가 단일 스레드라 한 프로세스가 1코어를 넘겨 쓰지 못한다. 두 번째 vCPU 는 Postgres 가 0.5% 만 쓰고 사실상 놀고 있다.
- 무너지는 방식은 오류가 아니라 **지연**이다. 500명에서도 실패율은 0이고 응답만 느려진다.

**클러스터링을 켜면 여기까지 간다**(2026-09-22 실측 — 워커 2개, 같은 t4g.small).

| | 단일 프로세스 | 워커 2개 |
|---|---|---|
| 포화 시작 | 동시 **350**명 | 동시 **450~500**명 |
| 처리량(포화 시) | 초당 150~170요청 | 초당 **185~210**요청(파생 추정) |
| API 컨테이너 CPU 상한 | 100%(1코어) | **123%** |
| **호스트 CPU** | 약 50~60% | **98.6%** |
| 실패율 | 0% | 0% |

**병목이 옮겨갔다.** 종전에는 "Node 가 단일 스레드라 1코어를 못 넘는다"였고, 지금은 **"이 인스턴스에 vCPU 가 2개뿐이다"** 다. API 가 1.23코어를 가져가고 나머지 0.77코어를 Postgres·Caddy·도커·에이전트가 나눠 쓰는 사이 호스트가 98.6% 로 꽉 찼다.

**그래서 클러스터링 단독의 이득은 1.3~1.4배지 2배가 아니다.** 2배를 기대하려면 코어가 늘어야 한다 — 그때는 종전과 달리 승급이 실제로 효과를 낸다(단일 프로세스에서는 코어를 늘려도 Node 가 하나만 썼다).

> ⚠️ **"동시 130명"은 잘못 읽힌 수치다.** 2026-09-11 보고서의 "초당 130~150요청"은 **초당 요청 수**이지 동시 사용자가 아니다. 같은 보고서에서 동시 200명이 초당 133요청이었다. 용량 계산에서 이 둘을 섞으면 여유가 두 배 이상 다르게 나온다.

## 2. 지금 로드밸런서를 달지 않는 이유

**첫째, 용량이 남는다.** 2026-09-20 실측으로 부하 평균 0.17, CPU 유휴 100%다. 400만원을 한 달 반에 집행할 때 발생하는 설치 수를 감안해도, 12~14분짜리 에피소드를 **같은 순간에** 듣는 사람이 300명에 닿으려면 지금 예산의 몇 배가 필요하다.

**둘째, 지금 붙이면 반쪽짜리다.** Postgres 가 애플리케이션과 같은 인스턴스에 있다. 앱 서버를 여러 대로 늘려도 **DB 가 있는 그 한 대가 여전히 단일 장애점**이다. 제대로 이중화하려면 RDS 분리가 선행이고, 그러면 ALB 비용에 RDS 비용까지 얹혀 월 고정비가 크게 는다.

**셋째, 먼저 쓸 카드가 남아 있다.** 클러스터링(0단계)과 인스턴스 승급(1단계)이 앞에 있고 둘 다 당일에 끝난다. 로드밸런서는 그 둘을 쓰고도 모자랄 때다.

캠페인 기간의 실제 위험은 처리량이 아니라 **가용성**이다. 한 대가 죽거나 배포가 잘못되면 광고비를 태우는 중에 서비스가 멈춘다. 다만 그 해법은 로드밸런서 단독이 아니라 DB 분리를 포함한 이중화이고(4장 2단계), 캠페인 규모가 그 비용을 정당화하는지는 별도 판단이다.

## 3. 세 가지 방법과 선택

Node 가 1코어만 쓰는 제약을 푸는 방법은 셋이다.

| 방법 | 어떻게 | 추가 비용 | 작업량 | 지금 적합한가 |
|---|---|---|---|---|
| **Node 클러스터링** | 마스터가 워커를 코어 수만큼 띄우고 **한 포트를 공유**한다. 요청 분산은 런타임이 한다 | **없음** | **env 한 줄**(선행 작업은 2026-09-20 코드에 반영 완료 — 5장) | **채택 — 기본값으로 켠다**(4장 0단계). 단독 이득은 1.3~1.4배다 |
| 한 EC2 안에 여러 컨테이너 | 같은 이미지를 여러 개 띄우고 Caddy 가 분배한다 | 없음 | 하루 | 효과는 같은데 설정이 더 는다 |
| ALB + 다중 EC2 | 인스턴스를 늘리고 앞에 ALB 를 둔다 | ALB + RDS 월 고정비 | 며칠 | DB 분리 전에는 이중화가 안 된다 |

**클러스터링을 고른 이유**는 세 가지다.

1. **비용이 0이다.** 이미 있는 두 번째 코어를 쓸 뿐이다. 메모리도 문제없다 — API 컨테이너가 125MB 를 쓰는데 가용 메모리가 723MB 다(6장).
2. **분배 장치가 필요 없다.** 컨테이너를 늘리는 방법은 Caddy 에 업스트림을 더하고 헬스체크·배포 순서를 새로 설계해야 하지만, 클러스터링은 런타임이 소켓을 공유해 알아서 나눈다. 인프라 구성이 그대로다.
3. **되돌리기 쉽다.** 워커 수를 1로 두면 종전 동작이다. 캠페인 중에 문제가 보이면 즉시 되돌릴 수 있다.

컨테이너 방식이 나은 경우도 있다. 워커 하나가 죽어도 나머지가 살아야 하고 **개별 재시작·무중단 롤아웃**이 필요할 때다. 다만 그 이득은 인스턴스가 여러 대가 될 때 의미가 커지므로, 그때는 어차피 2단계(ALB)로 간다.

## 4. 단계별 전환 기준

**0단계는 신호를 기다리지 않는다.** 클러스터링은 **기본값으로 켜고 시작한다**(결정 2026-09-22). 그 위부터는 신호를 보고 올린다. 표의 상한은 **전부 실측**이다(4 vCPU 만 추정).

| 단계 | 신호 | 조치 | 상한 | 소요 |
|---|---|---|---|---|
| **0 (기본)** | **없음 — 처음부터 켠다** | `CLUSTER_WORKERS=2` | 동시 **450~500**명 · 초당 190~210요청 | 10분 |
| 1 | **호스트 CPU 70% 가 10분 이상 지속** (≈ 동시 350명) | **vCPU 4개로 승급** + `CLUSTER_WORKERS=3` | 동시 900~1,000명대(추정) | 1시간 |
| 2 | 1단계로도 모자라거나, 단일 장애점을 없애야 할 때 | **RDS 분리 → ALB + EC2 2대** | 수평 확장 | 며칠 |

**왜 클러스터링을 신호 없이 먼저 켜는가.** 종전에는 "컨테이너 CPU 60% 를 보고 켠다"였는데 2026-09-22 에 바꿨다.

- **공짜다.** 이미 있는 두 번째 코어를 쓸 뿐이고 인스턴스 비용이 늘지 않는다.
- **되돌리기가 env 한 줄이다.** 문제가 보이면 `CLUSTER_WORKERS` 를 지우고 재기동하면 종전 동작이다.
- **급할 때 처음 켜는 것이 가장 나쁘다.** 트래픽이 몰리는 중에 첫 적용을 하면 확인할 것(스케줄러 중복·메모리·커넥션)을 그 자리에서 보게 된다. 평온할 때 켜 두면 그 확인이 이미 끝나 있다.

**1단계 신호가 호스트 CPU 인 이유.** 단일 프로세스일 때는 컨테이너 CPU 100% 가 곧 한계였지만, **클러스터에서는 컨테이너가 123% 에서 멈추고 호스트가 먼저 찬다**(1장). 그래서 기본값이 클러스터인 지금은 **컨테이너 CPU 를 지표로 쓸 수 없다.** 호스트 CPU 70% 는 실측 포화(98.6%)까지 여유를 두고 잡은 값이다.

- **4 vCPU 승급은 인스턴스 비용이 약 8배**가 된다(t4g 계열에서 4코어는 xlarge). 근거 없이 미리 올릴 값이 아니라 신호를 보고 간다.
- 다만 **종전과 달리 승급이 실제로 효과를 낸다** — 단일 프로세스에서는 코어를 늘려도 Node 가 하나만 썼다. 클러스터가 기본이 되면서 승급이 의미를 갖는다.
- CPU 경보는 이미 걸려 있다. **호스트 CPU 기준으로 임계치를 맞춰 둔다.**

### 4-1. 설치 수로 환산하면

**판정은 CPU 로 한다.** 아래는 "언제쯤 그 신호가 올지" 가늠하기 위한 참고이지 기준이 아니다. 가정이 여럿 겹쳐 실제와 쉽게 어긋난다.

환산 사슬은 이렇다. 에피소드 한 편이 12~14분이고, 하루 청취가 저녁 두세 시간에 몰리며, 한 사람이 하루 한 편을 듣는다고 본다.

```
동시 청취자 = DAU × 1인 하루 청취시간 × 피크 집중률 ÷ 피크 시간
            = DAU × 13분 × 0.7 ÷ 180분  ≈  DAU ÷ 20
```

여기에 설치 대비 DAU 를 20% 로 잡으면 **누적 설치 ≈ 동시 청취자 × 100** 이다.

| 단계 | 동시 청취자 | 필요 DAU | 누적 설치(대략) |
|---|---|---|---|
| 0단계(클러스터링 — 기본) | ~500 | ~10,000 | **5만 건** |
| 1단계(4 vCPU) | ~1,000 | ~20,000 | **10만 건** |

- **설치 대비 DAU 20% 는 낙관적인 값이다.** 10% 면 위 설치 수가 두 배가 된다. 즉 **5만~10만 건 사이 어딘가에서 1단계 신호가 온다.**
- 한 달 반 400만원 캠페인으로는 이 구간에 닿기 어렵다. **0단계(클러스터링)만으로 캠페인 기간을 넘긴다.**
- 이 환산은 "듣는 사용자"만 센다. 둘러보기만 하는 트래픽은 요청이 가볍고 재생 트랜잭션이 없어 더 많이 받을 수 있다.

**통근 서비스 가정으로 다시 계산하면 여유가 절반이다**(2026-09-23). 위 사슬은 저녁 3시간에 70% 집중이라는 여가 앱 가정이다. 이어의 타깃은 통근 사용자(PRD 3.1)라 청취가 **아침 8~9시 한 시간에 40~50%** 몰린다고 봐야 한다. 저녁 퇴근 피크는 집·운동·이동이 섞여 아침보다 퍼지므로 아침이 기준이다.

```
동시 청취자 = DAU × 13분 × 0.4~0.5 ÷ 60분  ≈  DAU ÷ 9~12   →  DAU ÷ 10 으로 잡는다
```

설치 대비 DAU 는 광고 유입이 오가닉보다 잔존이 낮아 **10% 를 기본, 5% 를 보수**로 본다(업계 D30 잔존 3~5%·DAU/MAU 20~25% 기준. 20% 는 낙관치).

| 운영 구성 | 안전 상한(동시 청취) | 필요 DAU | 설치 10% 가정 | 설치 5% 가정 |
|---|---|---|---|---|
| 단일 프로세스(2026-09-23 현재) | 300명 | **3,000** | **3만** | 6만 |
| 0단계 클러스터 워커 2개 | ~450명 | **4,500** | **4.5만** | 9만 |
| 1단계 4 vCPU(추정) | ~900명 | 9,000 | 9만 | 18만 |

- 기억할 숫자는 **"DAU 3,000 이면 아침 8시대에 단일 프로세스가 포화"** 다. 클러스터링을 켜 두면 4,500.
- **동기화된 시작이 진짜 위험이다.** 동시 청취는 퍼지지만 재생 시작은 8:00~8:20 에 몰린다. 그래도 DAU 3,000 이면 분당 60건(초당 1건)이라 초당 150요청 상한에는 사소하다. 문제가 되는 것은 **푸시**다 — `notification.md` 미결의 "07:30 통근 직전 고정 발송"을 채택하면 DAU 전원이 같은 1분 안에 앱을 열어 스플래시·목록 조회·재생 시작이 한꺼번에 튄다(DAU 3,000 × 탭률 30% × 3~4요청 ÷ 60초 ≈ 초당 45~60요청, DAU 1만이면 상한 초과). 고정 시각으로 바꾼다면 **발송을 10~15분에 걸쳐 흩뿌리는 조건**이 붙어야 한다. 지금의 05:00 편성 직후 발송은 부하 관점에서는 안전하다.
- **가입 몰림은 청취와 다른 경로다.** 광고 노출 직후 설치 → 스플래시·소셜 로그인·온보딩 저장·첫 드립 편성이 몇 분 안에 몰린다. 첫 드립 편성은 사용자마다 후보 풀을 재조회하는 구조라(`tickets/backend/pending/drip-batch-shared-pool-loading.md`) 청취 350명보다 먼저 CPU 를 칠 수 있다고 봤으나, **실측(4-2)으로는 분당 600명까지 여유** — 청취보다 훨씬 위에 있다.

### 4-2. 가입 몰림 실측 (2026-09-23 · 개발계 · 온보딩 여정)

광고 직후 "설치 → 온보딩 → 첫 드립 편성"이 몰리는 경로를 **분당 가입 수**로 계단식 올려 쟀다(`backend/load-test/results/2026-09-23-dev-onboarding/REPORT.md`). 여정은 상태·주제·관심사·커리어·추천·완료·첫 드립 폴링(앱과 같은 1초 간격·15초 상한)이다.

| 구성(현재 코드 `85c41aa`) | 지연 없이 받는 분당 가입 | 포화 시작 | 실패 |
|---|---|---|---|
| 단일 프로세스(운영 현재) | **~600명** | 900명(API 1코어) | 0 — 분당 1,600명까지 5xx·429 없음 |
| 클러스터 워커 2 | **~900명** | 900~1,200명(호스트 2코어) | 0 |

- **가입 경로는 캠페인 병목이 아니다.** 분당 600명 = 시간당 3.6만 설치다. 그 위로도 무너지는 방식은 지연이다 — 완료 요청 p95 가 10초대로 늘고 첫 드립 대기가 15초 상한을 넘겨 앱이 "콘텐츠를 준비하고 있어요" 배너로 진행하지만, 편성은 몇 초 뒤 전부 `completed` 된다(`queued`·`failed` 0건).
- **클러스터 이득은 여기서도 1.3~1.4배**(청취 램프와 같음). 900명부터 Postgres 와 두 코어를 나눠 쓰며 호스트가 찬다.
- **온보딩 경로가 2026-09-15 빌드보다 약 1.5~1.8배 무거워졌다.** 같은 분당 600명에서 API CPU 50% → 70~93%, 완료 요청 p95 2.7s → 13.4s(포화 구간). 무거워진 지점은 `POST /onboarding/complete`(첫 드립 편성)·`GET /onboarding/recommendations`. 원인은 프로파일링으로 가린다 — BE 티켓 감(Low). 09-15 빌드 측정은 재생성 실수로 옛 이미지가 떠 있던 덕에 얻은 비교값이다(runbook 4장 `API_IMAGE` 주의).

## 5. 클러스터링 — 선행 작업은 끝났다

백엔드 전체를 훑어 다중 워커에서 깨지는 지점을 찾고, **고칠 수 있는 것은 2026-09-20 에 코드로 미리 반영했다.**
그래서 이제 켜는 일은 **환경변수 한 줄**이다.

```bash
# 개발계 → 운영 .env.prod 에 추가하고 재배포
CLUSTER_WORKERS=2
```

값이 없거나 `1` 이면 **종전과 완전히 같이** 단일 프로세스로 뜬다. 되돌리기도 이 줄을 지우면 끝이다.

### 5.1 스케줄러 11개 — 중복 실행 위험 없음

DB 선점이나 멱등한 문장으로 이미 보호돼 있어 **데이터가 망가지는 것은 하나도 없다.**

| 판정 | 개수 | 해당 |
|---|---|---|
| **안전** (선점·락·멱등 DELETE) | 8 | 편성 배치(`run_date` 유니크 선점) · 세션/멱등키/이메일인증/첫드립 정리(같은 조건 DELETE) · 콘텐츠 만료(상태 조건부 UPDATE) · 주제 노출(행 잠금 후 판정) · 첫드립 재시도(`FOR UPDATE SKIP LOCKED`) |
| **낭비만** (중복 작업이나 결과 동일) | 3 | 콘텐츠 통계 집계(증분이 아니라 재집계 UPSERT) · 보존 정리(뒤쪽이 0건 삭제 후 조기 종료) · 푸시 영수증(대기 목록이 프로세스 메모리라 보낸 워커만 조회) |

그럼에도 **스케줄러는 담당 워커 하나에서만 등록한다**(5.2 A). 낭비를 줄이고, 앞으로 추가될 스케줄러가 이 검토를 거치지 않아도 안전하도록.

### 5.2 미리 반영한 것 (2026-09-20)

갈라지는 지점을 `backend/src/common/cluster.util.ts` 한 곳에 모았다. **워커가 1개면 아래 값은 전부 종전과 같다.**

| # | 문제였던 것 | 반영한 내용 | 상태 |
|---|---|---|---|
| **A** | 스케줄러가 워커마다 등록돼 편성 배치가 워커 수만큼 돈다 | `ScheduleModule.forRoot()` 를 **담당 프로세스에서만** 등록한다. 담당 표시는 primary 가 fork 할 때 env 로 준다 — **워커 id 로 고르면** 그 워커가 죽고 다시 뜰 때 id 가 새로 매겨져 아무도 담당이 아니게 된다 | ✅ |
| **B** | 자원 감시가 `@nestjs/schedule` 밖의 자체 `setInterval` 이라 게이팅을 빠져나가 Slack 알림이 워커 수만큼 간다 | **표본은 모든 워커가 쌓고 Slack 발송만** 담당 프로세스가 한다. 표본을 막지 않는 이유는 어드민 "서버 상태" 그래프가 어느 워커의 응답이든 그려져야 하기 때문이고, 값 자체는 호스트 전체 수치라 어느 쪽이든 유효하다 | ✅ |
| **C** | 레이트 리밋이 인메모리라 실효 한도가 워커 수만큼 느슨해진다 | 한도를 **워커 수로 나눈다**(`perWorker`). 워커 2개면 전역 300→150 · 인증 20→10 · 이메일 5→3 · 오디오 30→15. 하한이 있어 0이 되지 않는다 | ✅ |
| **D** | docker 가 PID 1 에만 SIGTERM 을 보내 워커의 종료 훅이 돌지 않는다 | primary 가 받아 **워커에 전달하고 전원 종료를 기다린 뒤** 끝낸다. 워커가 비정상 종료하면 다시 띄우고, 담당 워커였으면 담당 표시도 함께 넘긴다 | ✅ |
| **E** | DB 커넥션 풀이 워커마다 생겨 합이 `max_connections` 를 넘길 수 있다 | 풀도 워커 수로 나눠 **합을 10으로 유지**한다(하한 2) | ✅ |
| F | 워커당 메모리 | 워커 1개당 약 125MB, 가용 723MB(6장). 워커 2개는 여유지만 **실측은 켤 때 한다** | 실측 대기 |

**그 밖은 손댈 것이 없다고 확인했다.** 멱등성 모듈은 DB 기반이고, 포트 바인딩은 `app.listen` 하나뿐이며, 마이그레이션은 `docker-entrypoint.sh` 가 워커 기동 **전에** 한 번만 돌린다(이 순서를 바꾸면 워커 수만큼 동시에 마이그레이션이 돈다). SSE·WebSocket·인메모리 큐·파일 락은 없고, 나머지 인메모리 값(JWKS 캐시 등)은 워커별로 갈라져도 판정이 같다.

### 5.3 개발계 실측 (2026-09-22)

개발계(운영과 같은 t4g.small)에서 `CLUSTER_WORKERS=2` 로 켜고 계단식 램프(100명씩 600명까지)를 돌렸다.
계정 600개를 시드해 쓰고 **전량 삭제해 잔여 0건**을 확인했으며, 개발계는 단일 프로세스로 되돌렸다.

| 항목 | 단일 프로세스 | 워커 2개 | 판정 |
|---|---|---|---|
| 포화 시작 | 동시 350명 | 동시 450~500명 | **1.3~1.4배** |
| API 컨테이너 CPU | 100% | 123% | 두 코어를 다 쓰지는 못한다 |
| 호스트 CPU | 50~60% | **98.6%** | **인스턴스가 꽉 찬다** |
| API 메모리 | 84MB | 230MB (워커당 +115MB) | 여유 807MB — 문제없음 |
| DB 커넥션 | — | 11 / 상한 100 | 여유 |
| 스케줄러 등록 | 1회 | **1회** | 게이팅 정상 |
| 실패율·체크 | — | 0% · 45,389건 전부 통과 | 깨진 것 없음 |

**확인된 것**

- **5.2 의 조치가 실서버에서 의도대로 동작한다.** 워커가 둘인데 스케줄러는 한 번만 등록됐다 — 편성 배치가 두 번 돌지 않는다.
- 메모리·DB 커넥션은 걱정거리가 아니었다(F·E 해소).
- **기대했던 2배는 나오지 않는다.** vCPU 2개를 Postgres 와 나눠 쓰기 때문이다. 이 사실이 4장 2단계의 신호를 호스트 CPU 로 잡은 근거다.

**되돌리기**: `.env.prod` 에서 `CLUSTER_WORKERS` 줄을 지우고 컨테이너를 재생성하면 끝이다. 실측 후 개발계는 그렇게 되돌렸다.

### 5.4 운영 적용 — 순서가 있다

**레이트 리밋 수정(PR #586)이 운영에 먼저 나가야 한다.** 그 전에 켜면 이메일 인증이 분당 5회가 아니라 3회에서 막히고, 화면은 "1시간에 5번까지"라고 안내하는 상태가 된다(`rate-limit.constant.ts` 주석). 2026-09-22 에 이 순서를 어길 뻔해 적용 직전에 멈췄다.

1. `dev → main` 릴리즈로 레이트 리밋 수정을 운영에 반영한다.
2. 운영 `.env.prod` 에 `CLUSTER_WORKERS=2` 를 넣고 api 컨테이너를 재생성한다(재기동 중 15~30초 502).
3. 확인: `ScheduleModule dependencies initialized` **1회** · `Nest application successfully started` **2회** · `docker stats` 메모리 · `GET /admin/system-stats` 의 DB 커넥션.
4. CPU 경보 임계치를 **호스트 CPU 70%**(4장 1단계)에 맞춘다.

## 6. 메모리 — 50%의 정체

"아무것도 안 해도 메모리가 50%"라는 관찰의 원인이다. **애플리케이션이 아니라 도커 계층이다.**

2026-09-20 실측(사용 중 913MB 기준).

| 구분 | 메모리 | 비중 |
|---|---|---|
| 도커 계층 (dockerd 395 · containerd 37 · shim 3개 47) | 479MB | 52% |
| 애플리케이션 (node 125 · postgres 57 · caddy 29) | 211MB | 23% |
| 관측·운영 에이전트 (journald 76 · CloudWatch 59 · SSM 14) | 149MB | 16% |
| systemd 등 나머지 | 약 26MB | 3% |

**가장 큰 덩어리는 dockerd 하나(395~406MB)이고, 원인은 서버에서 직접 돌린 빌드의 잔재다.** (2026-09-23 정정 — 종전에는 `awslogs` 로그 드라이버 버퍼로 적었으나 틀렸다. 아래 근거.)

2026-09-23 운영·개발계 동시 실측(둘 다 t4g.small · 1841MB · 같은 컨테이너 3개 · 같은 로그 드라이버 구성):

| 항목 | 운영 | 개발계 | 차이 |
|---|---|---|---|
| `free` used | 897MB (48.7%) | 687MB (37.3%) | +210 |
| **MemAvailable** | **738MB (40%)** | 948MB (51%) | −210 |
| dockerd RSS | **406MB** | 108MB | **+298** |
| ㄴ 그중 BuildKit `contenthash` 캐시(힙 프로파일) | **224MB** | 18MB | +206 |
| ㄴ 그중 awslogs | 1.1MB | 2.1MB | ≈0 |
| node / postgres / caddy | 126 / 65 / 30 | 141 / 53 / 32 | ≈ |
| 스왑 | 없음 | 2GB(29MB 사용) | |
| 빌드 캐시(`docker system df`) | 265건 · 2.3GB · dangling 이미지 37개 | 20건 · 270MB | |

- **dockerd 힙(`/debug/pprof/heap`) 살아있는 245MB 중 224MB가 BuildKit 의 `contenthash`·radix·digest 계열**이다 — `docker compose up --build` 가 레이어별 파일 트리 체크섬을 LRU(20개)로 메모리에 들고 있는 것. 2026-08-31~09-16 사이 운영 서버에서 빌드를 15~20회 돌린 흔적(`docker builder du` 레코드 265건)이 그대로 남아 있다. 09-16 부터는 ECR pull(`push.sh` 의 `--no-build` 경로)이라 **새로 쌓이지는 않지만, 이미 찬 것은 비워지지 않는다.**
- **awslogs 는 원인이 아니다.** 드라이버 구성이 두 서버 동일하고(api·caddy `awslogs`, postgres `json-file`), 개발계가 로그를 10~16배 더 보내는데도 힙에서 awslogs 가 차지하는 양은 1~2MB다. 종전 문단이 권한 "`json-file` 로 전환" 은 효과가 없으니 **하지 않는다.**
- LRU 는 20개에서 멈추므로 시간에 비례해 자라지 않는다 — 2주간 49~50% 에서 평평했던 관측과 맞는다. **누수가 아니라 고수위**다.

**걱정할 상황은 아니다.** `free` 의 "used"(= CloudWatch `mem_used_percent`) 가 아니라 **MemAvailable 738MB(40%)** 가 실제 여유이고, 메모리 압박(PSI full)은 23일 누적 62초로 없다. 다만 **운영에는 스왑이 없어서** 여유가 바닥나면 완충 없이 OOM killer 로 간다 — 클러스터 워커를 더 띄우거나(워커당 약 125MB) 트래픽이 크게 늘 때 이 숫자를 본다.

**되돌리는 방법은 dockerd 재시작뿐이다** — 약 300MB 가 돌아와 개발계 수준(≈110MB)이 된다. `docker builder prune` 은 디스크만 지우고 이 메모리 LRU 는 비우지 않는다. 재시작의 대가: `LiveRestoreEnabled=false` 라 **api·caddy·postgres 세 컨테이너가 모두 내려갔다 올라온다**(수십 초, postgres 재기동). 트래픽 낮은 시간에, 04시 서비스 날짜 경계는 피해서, 재시작 뒤 `docker ps` 3개 healthy 를 확인한다.

**실행 완료 — 2026-09-23 16:45 KST**(팀원 상황 확인 뒤). 실측:

| | 재시작 전 | 재시작 후 |
|---|---|---|
| dockerd RSS | 415MB(23일 가동) | **100MB** (3분 뒤 103MB, 안정) |
| MemAvailable | 733MB (40%) | **1,094MB (59%)** — `mem_used_percent` 50% → 30% |
| 다운타임 | — | `systemctl restart` 6초, **health 200 복귀 +10초** |
| 컨테이너 | — | 3개 `unless-stopped` 로 자동 복귀, restarts=0, api healthy |

재시작 뒤 확인한 것: `/health` 200(24ms), 인증 가드 401, DB 연결(api→pg 2), 크론 3개 그대로, CloudWatch `/ear/api` 부팅 로그 유입·error 0건. caddy 에 `connection refused` 1건은 그 10초 창에서 서버 안에서 돌린 health 폴링이다. 재시작 뒤 dockerd 가 100MB 인 것으로 **디스크의 빌드 캐시는 시작 시 메모리로 올라오지 않는다**는 것도 확인됐다 — 다시 오르는 경우는 서버 빌드를 또 돌릴 때뿐이다.

```bash
sudo systemctl restart docker && sleep 20 && docker ps --format '{{.Names}}\t{{.Status}}'
```

**재발 방지.** 운영에서 다시 서버 빌드를 돌리면 같은 고수위가 재현된다. `backend/deploy/push.sh` 의 `API_IMAGE` 없는 분기(`up -d --build`)와 `deploy/aws/README.md` 의 `--build` 예시가 아직 남아 있다 — 운영은 **항상 `API_IMAGE=<ECR 태그>` 로만** 띄우는 것으로 스크립트·문서를 정리해야 한다(BE 파트 티켓 감).

별개로 **디스크에 3.8GB 가 회수 가능했다**(빌드 캐시 2.3GB · 미사용 이미지 1.5GB). **2026-09-23 17:10 KST 정리 완료** — 무중단(컨테이너·볼륨 무관), `builder prune` 2.87GB/34초 + `image prune` 1.47GB/14초, `/` **9.1G → 4.1G(46% → 21%)**. 이미지는 실행 중인 3개(813MB)만 남았다. 정리 직후 `/health` 20회 p50 22ms·p95 25ms(정리 전과 동일), idle 96%, 5xx 0건.

- **롤백 경로가 하나로 줄었다.** 서버에 남은 옛 SHA 이미지가 없으므로 롤백은 runbook 4장대로 **ECR 에서 이전 SHA 를 pull** 하는 방법뿐이다(수십 초 추가).

```bash
docker builder prune -af && docker image prune -af
```

## 7. CPU 버스트 크레딧 — 확인 완료, 문제 없음

t4g 는 버스터블이라 크레딧이 소진되면 기준 성능으로 묶인다. 트래픽이 몇 시간 이어질 때 **용량 문제처럼 보이는 크레딧 문제**가 날 수 있어 확인했다(2026-09-20).

| 항목 | 값 |
|---|---|
| 크레딧 사양 | **`unlimited`** — 소진돼도 스로틀되지 않고 초과분이 과금된다 |
| 크레딧 잔고 | 2주 내내 **576(상한)** 에 붙어 있음 |
| 최저 잔고 | 572.04 — 2026-09-11 운영 부하 테스트 |
| 초과 크레딧 사용·과금 | **0** |

40분간 CPU 를 90% 까지 밀어붙인 부하 테스트가 소모한 크레딧이 576 중 약 4다. t4g.small 의 기준선은 두 코어 합쳐 40% 인데 Node 가 한 코어를 다 써도 인스턴스 전체로는 50% 안팎이라 소모가 완만하다. **부하 테스트 수치는 크레딧 여유분에 기댄 값이 아니라 그대로 믿어도 되는 실측치다.**

## 8. 미결

- 4 vCPU 승급 시의 실측 상한 — 4장 **1단계**의 "동시 900~1,000명대"는 코어 수에 비례한다는 가정의 **추정치다.** 실제로 승급할 때 같은 램프로 다시 잰다.
- 레이트 리밋 Redis 저장소 도입 여부 — **인스턴스를 여러 대로 늘릴 때는 나누기로 안 되고 Redis 가 필요하다**(4장 **2단계**). 그때 `backend/architecture.md` 9.6 표도 함께 고친다.
- DB 분리(RDS) 시점과 비용 — 4장 **2단계**로 가야 할 때 별도 판단.
