# 확장 계획 — 언제 무엇을 바꾸는가

| 항목 | 값 |
|---|---|
| 작성 | 2026-09-20 |
| 배경 | 한 달 반 400만원 마케팅 집행을 앞두고 "초반 급증 구간을 지금 구조로 버티는가"를 판단하기 위해 정리했다 |
| 결론 | **지금은 아무것도 바꾸지 않는다.** 실측 상한(동시 350명) 대비 여유가 크고, 로드밸런서는 DB 분리 없이는 반쪽짜리다. 필요해지는 시점을 **신호로 정의**해 두고(4장) 그때 클러스터링부터 켠다 |
| 근거 | 부하 테스트 2회(`backend/load-test/results/2026-09-11`·`2026-09-16-dev`) · 2026-09-20 운영 서버 실측(메모리·CPU 크레딧) |
| 관련 | [`architecture.md`](architecture.md)(구조·비용) · [`inventory.md`](inventory.md)(인스턴스 실체) · [`runbook.md`](runbook.md)(배포 절차) |

## 1. 현재 구조와 실측 한계

운영은 **EC2 t4g.small 한 대**(vCPU 2 · RAM 2GB)에 docker compose 로 `caddy` · `api` · `postgres` 가 함께 뜬다. 오디오·썸네일은 S3 + CloudFront 가 나르므로 이 인스턴스를 지나지 않는다.

부하 테스트에서 확인된 청취 여정의 상한이다(개발계는 운영과 같은 사양·구성).

| 동시 청취자 | 초당 요청 | p95 | API CPU (1코어 = 100%) |
|---|---|---|---|
| 200 | 85 | 42ms | 50% |
| 300 | 124 | 63ms | 75% |
| **350** | 146 | 176ms | **100% (포화)** |
| 450 | 157 | 693ms | — |
| 500 | 150~172 | 1.3~2.1s | 105% |

- **상한은 동시 350명 / 초당 150~170요청**이고, 안전 구간은 **동시 300명**이다.
- **병목은 DB가 아니라 API 프로세스 CPU다.** Node 가 단일 스레드라 한 프로세스가 1코어를 넘겨 쓰지 못한다. 두 번째 vCPU 는 Postgres 가 0.5% 만 쓰고 사실상 놀고 있다.
- 무너지는 방식은 오류가 아니라 **지연**이다. 500명에서도 실패율은 0이고 응답만 느려진다.

> ⚠️ **"동시 130명"은 잘못 읽힌 수치다.** 2026-09-11 보고서의 "초당 130~150요청"은 **초당 요청 수**이지 동시 사용자가 아니다. 같은 보고서에서 동시 200명이 초당 133요청이었다. 용량 계산에서 이 둘을 섞으면 여유가 두 배 이상 다르게 나온다.

## 2. 지금 로드밸런서를 달지 않는 이유

**첫째, 용량이 남는다.** 2026-09-20 실측으로 부하 평균 0.17, CPU 유휴 100%다. 400만원을 한 달 반에 집행할 때 발생하는 설치 수를 감안해도, 12~14분짜리 에피소드를 **같은 순간에** 듣는 사람이 300명에 닿으려면 지금 예산의 몇 배가 필요하다.

**둘째, 지금 붙이면 반쪽짜리다.** Postgres 가 애플리케이션과 같은 인스턴스에 있다. 앱 서버를 여러 대로 늘려도 **DB 가 있는 그 한 대가 여전히 단일 장애점**이다. 제대로 이중화하려면 RDS 분리가 선행이고, 그러면 ALB 비용에 RDS 비용까지 얹혀 월 고정비가 크게 는다.

**셋째, 미리 해둘 이유가 없다.** 클러스터링도 인스턴스 승급도 **당일에 끝나는 작업**이다. 리드타임이 없으므로 신호를 보고 움직이면 된다.

캠페인 기간의 실제 위험은 처리량이 아니라 **가용성**이다. 한 대가 죽거나 배포가 잘못되면 광고비를 태우는 중에 서비스가 멈춘다. 다만 그 해법은 로드밸런서 단독이 아니라 DB 분리를 포함한 이중화이고(4장 3단계), 캠페인 규모가 그 비용을 정당화하는지는 별도 판단이다.

## 3. 세 가지 방법과 선택

Node 가 1코어만 쓰는 제약을 푸는 방법은 셋이다.

| 방법 | 어떻게 | 추가 비용 | 작업량 | 지금 적합한가 |
|---|---|---|---|---|
| **Node 클러스터링** | 마스터가 워커를 코어 수만큼 띄우고 **한 포트를 공유**한다. 요청 분산은 런타임이 한다 | **없음** | 약 2~3시간 (선행 작업 포함 — 5장) | **이것을 택한다** |
| 한 EC2 안에 여러 컨테이너 | 같은 이미지를 여러 개 띄우고 Caddy 가 분배한다 | 없음 | 하루 | 효과는 같은데 설정이 더 는다 |
| ALB + 다중 EC2 | 인스턴스를 늘리고 앞에 ALB 를 둔다 | ALB + RDS 월 고정비 | 며칠 | DB 분리 전에는 이중화가 안 된다 |

**클러스터링을 고른 이유**는 세 가지다.

1. **비용이 0이다.** 이미 있는 두 번째 코어를 쓸 뿐이다. 메모리도 문제없다 — API 컨테이너가 125MB 를 쓰는데 가용 메모리가 723MB 다(6장).
2. **분배 장치가 필요 없다.** 컨테이너를 늘리는 방법은 Caddy 에 업스트림을 더하고 헬스체크·배포 순서를 새로 설계해야 하지만, 클러스터링은 런타임이 소켓을 공유해 알아서 나눈다. 인프라 구성이 그대로다.
3. **되돌리기 쉽다.** 워커 수를 1로 두면 종전 동작이다. 캠페인 중에 문제가 보이면 즉시 되돌릴 수 있다.

컨테이너 방식이 나은 경우도 있다. 워커 하나가 죽어도 나머지가 살아야 하고 **개별 재시작·무중단 롤아웃**이 필요할 때다. 다만 그 이득은 인스턴스가 여러 대가 될 때 의미가 커지므로, 그때는 어차피 3단계(ALB)로 간다.

## 4. 단계별 전환 기준

**숫자가 아니라 신호로 정한다.** 아래 신호가 보이면 그 단계를 실행한다.

| 단계 | 신호 | 조치 | 상한 변화 | 소요 |
|---|---|---|---|---|
| 0 (현재) | — | 그대로 둔다 | 동시 350명 | — |
| 1 | **API 컨테이너 CPU 60% 가 10분 이상 지속** (≈ 동시 250명) | **Node 클러스터링**, 워커 2개 | 동시 약 600명 | 약 2~3시간 (5장) |
| 2 | 클러스터 상태에서 CPU 70% 지속 (≈ 동시 500명) | **vCPU 4개로 승급** + 워커 3개 | 동시 1,000명대 | 1시간 |
| 3 | 2단계로도 모자라거나, 단일 장애점을 없애야 할 때 | **RDS 분리 → ALB + EC2 2대** | 수평 확장 | 며칠 |

- **1단계 신호를 60%로 잡은 이유**: 실측에서 75% 가 동시 300명이고 100% 가 포화(350명)다. 60%는 동시 250명쯤으로, 포화까지 대응할 시간이 충분히 남는 지점이다.
- **2단계에서 4 vCPU 승급을 미루는 이유**: t4g 계열에서 4코어를 가지려면 xlarge 로 가야 하고 인스턴스 비용이 **약 8배**가 된다. 근거 없이 미리 낼 돈이 아니다.
- CPU 경보는 이미 걸려 있다. 1단계 신호를 그 경보로 받는다.

## 5. 클러스터링 선행 작업 — 사전 조사 결과 (2026-09-20)

급할 때 헤매지 않도록 **백엔드 전체를 미리 훑어** 다중 워커에서 깨지는 지점을 찾아 뒀다. 아래 지적은 코드에서 직접 확인한 것이다.

**결론: 데이터가 망가지는 급의 위험은 없다. 다만 그대로 켜면 안 되고, 네 가지를 먼저 막아야 한다.** 실작업 약 2~3시간이다.

### 5.1 스케줄러 11개 — 전부 안전하거나 낭비뿐

중복 실행이 데이터를 오염시키는 것은 하나도 없다. DB 선점이나 멱등한 문장으로 이미 보호돼 있다.

| 판정 | 개수 | 해당 |
|---|---|---|
| **안전** (선점·락·멱등 DELETE) | 8 | 편성 배치(`run_date` 유니크 선점) · 세션/멱등키/이메일인증/첫드립 정리(같은 조건 DELETE) · 콘텐츠 만료(상태 조건부 UPDATE) · 주제 노출(행 잠금 후 판정) · 첫드립 재시도(`FOR UPDATE SKIP LOCKED`) |
| **낭비만** (중복 작업이나 결과 동일) | 3 | 콘텐츠 통계 집계(증분이 아니라 재집계 UPSERT) · 보존 정리(뒤쪽이 0건 삭제 후 조기 종료 → 남은 분량이 다음 날로) · 푸시 영수증(대기 목록이 프로세스 메모리라 보낸 워커만 조회) |

> 첫드립 재시도는 **푸시를 보내지 않는다.** 발송 경로는 편성 배치 한 곳뿐이라 중복 발송 위험이 없다.

### 5.2 막아야 할 것

| # | 항목 | 증상 | 조치 | 소요 |
|---|---|---|---|---|
| **A** | **자원 감시가 `@nestjs/schedule` 밖에 있다** — `resource-alert.service.ts:147` 의 자체 `setInterval` | 워커마다 독립적으로 호스트 CPU 를 읽고 각자 Slack 에 보낸다. **임계 초과 시 같은 알림이 워커 수만큼** 온다. 해제 알림도 마찬가지 | `onModuleInit` 에서 담당 워커가 아니면 타이머를 걸지 않는다. **스케줄러 게이팅으로는 안 꺼진다** | 20분 |
| **B** | 자원 이력 링 버퍼가 갈라진다 — 같은 파일의 6시간치 샘플 | 어드민 "서버 상태" 그래프가 **새로고침할 때마다 달라진다**(요청이 워커에 나뉘므로) | 샘플링은 전 워커에서 살려 두고 Slack 발송만 막으면 값 자체는 유효하다(호스트 전체 수치라서). 그래프가 흔들리는 것만 감수 | 0분 (A와 동시) |
| **C** | **레이트 리밋이 인메모리** — `app.module.ts` 의 `ThrottlerModule.forRoot` 가 저장소 미지정 | 실효 한도가 **설정값 × 워커 수**가 된다. 전역 300/분은 여유가 있어 괜찮지만, **인증 20/분·이메일 발송 5/분은 방어가 목적인 숫자**라 2배가 되면 의미가 절반이다 | 급할 때는 인증 20 → 10, 이메일 5 → 3 으로 내린다. Redis 저장소는 클러스터를 상시 유지하기로 정한 뒤 별도 티켓 | 10분 |
| **D** | **SIGTERM 이 워커에 전달되지 않는다** | docker 는 PID 1(클러스터 primary)에만 보낸다. 포워딩하지 않으면 워커의 종료 훅이 안 돌고 10초 뒤 강제 종료된다. 커넥션 미정리·배치 절단이 **배포할 때마다 조용히** 일어난다 | primary 에서 받아 워커에 전달하고 전원 종료를 기다린 뒤 exit | 30분 |
| E | DB 커넥션 풀이 워커 수만큼 — `DB_POOL_SIZE = 10` | 워커 2개면 20, Postgres 기본 `max_connections` 100 이라 여유. **워커 4개 이상이면 조정 필요** | N=2 면 그대로 두고 배포 후 `GET /admin/system-stats` 로 실측 | 10분 |
| F | 워커당 RSS 만큼 메모리 증가 | 워커 1개당 약 125MB. 가용 723MB 라 2개는 여유(6장) | 개발계에서 실측 | 30분 |

**그 밖은 안전하다고 확인됐다.** 멱등성 모듈은 DB 기반이고, 포트 바인딩은 `app.listen` 하나뿐이라 코드 변경이 필요 없으며, 마이그레이션은 컨테이너 진입점이 워커 기동 **전에** 한 번만 돌린다. SSE·WebSocket·인메모리 큐·파일 락은 없다. 나머지 인메모리 값(JWKS 캐시 등)은 워커별로 갈라져도 판정이 같다.

### 5.3 켜는 절차

워커 수는 **2개**다(vCPU 2). 그 이상은 이 인스턴스에서 의미가 없다.

1. **자원 감시 게이팅** (20분) — A·B 를 같은 판정 기준으로 함께 처리한다.
2. **스케줄러 게이팅** (20분) — `ScheduleModule.forRoot()` 를 담당 워커에서만 등록한다. `SchedulerRegistry` 를 주입하는 코드가 **0건**이라 모듈을 빼도 DI 가 깨지지 않는다. **1번과 같은 워커**에 몰아야 푸시 발송과 영수증 대기 목록이 같은 프로세스에 남는다.
3. **클러스터 부트스트랩 + 종료 전달** (30분) — `src/cluster.ts` 를 새로 만든다. `main.ts` 는 `bootstrap` 을 내보내게만 바꾸고 내용은 손대지 않는다.
4. **Dockerfile 의 `CMD`** 를 새 진입점으로 (10분) — **`docker-entrypoint.sh` 는 건드리지 않는다.** 마이그레이션이 한 번만 도는 현 구조가 유지돼야 한다. compose 는 수정 불필요.
5. **레이트 리밋 스톱갭** (10분) — C. `changes/pending/` 에 사유를 남긴다.
6. **개발계 실측** (30분) — 메모리 합계, DB 커넥션 수, 스케줄러 로그가 한 워커에서만 나오는지, 종료 시 워커가 정상 종료되는지.
7. **부하 재측정** (20분) — 상한이 실제로 올랐는지 확인한다. **오르지 않으면 병목이 API CPU 가 아니라는 뜻**이므로 클러스터를 되돌리고 다른 축을 본다.

### 5.4 먼저 처리할 세 가지

1. **자원 감시의 자체 타이머**(A) — 유일하게 `@nestjs/schedule` 밖에 있어서 "스케줄러를 한 워커에만"이라는 조치를 빠져나간다. Slack 도배와 그래프 분열의 원인이 이 파일 하나다.
2. **SIGTERM 미전달**(D) — 배포마다 조용히 일어나고 증상이 "가끔 커넥션이 남는다"라서 **원인 추적이 가장 어렵다.** 2026-09-09 감사에서 한 번 고친 문제가 클러스터에서 되살아나는 퇴행이다.
3. **레이트 리밋**(C) — 위 둘과 달리 **보안 경계가 느슨해지는** 유일한 항목이다. 10분이면 되니 미룰 이유가 없다.

## 6. 메모리 — 50%의 정체

"아무것도 안 해도 메모리가 50%"라는 관찰의 원인이다. **애플리케이션이 아니라 도커 계층이다.**

2026-09-20 실측(사용 중 913MB 기준).

| 구분 | 메모리 | 비중 |
|---|---|---|
| 도커 계층 (dockerd 395 · containerd 37 · shim 3개 47) | 479MB | 52% |
| 애플리케이션 (node 125 · postgres 57 · caddy 29) | 211MB | 23% |
| 관측·운영 에이전트 (journald 76 · CloudWatch 59 · SSM 14) | 149MB | 16% |
| systemd 등 나머지 | 약 26MB | 3% |

**가장 큰 덩어리는 dockerd 하나로 395MB이고, 원인은 로그 드라이버다.** API 와 Caddy 가 `awslogs` 드라이버를 쓰는데, 이 드라이버는 컨테이너가 아니라 **dockerd 프로세스 안에서** 로그를 버퍼에 담아 CloudWatch Logs 로 배치 전송한다. Caddy 는 요청마다 JSON 한 줄을 찍어 양이 꾸준하다. 여기에 Go 런타임이 한 번 확보한 메모리를 OS 에 잘 돌려주지 않는 성질이 겹쳤다. (Postgres 는 `json-file` + 로테이션이라 이 경로가 아니다.)

**누수가 아니라 고점 유지다.** 2주간 평균 49~50% 에서 평평하고, 배포·부하 테스트 때 60~67% 로 잠깐 올랐다 돌아온다. dockerd 의 395MB 는 쌓인 데이터가 아니라 **지금까지 겪은 최대 버퍼 필요량의 흔적**이다. 그래서 **dockerd 를 재시작하면 떨어졌다가 며칠~몇 주에 걸쳐 비슷한 자리로 다시 올라온다.** 컨테이너가 같이 내려가는 대가에 비해 얻는 것이 임시 여유뿐이라 권하지 않는다.

**그리고 걱정할 상황이 아니다.** `free` 의 "used" 가 아니라 **MemAvailable 723MB(39%)** 가 실제 여유다. 클러스터 워커를 하나 더 띄워도 약 125MB 가 더 들 뿐이다.

영구적으로 낮추려면 **API·Caddy 의 로그 드라이버를 `awslogs` → `json-file`(로테이션)로 바꾸고, 이미 설치된 CloudWatch 에이전트가 그 파일을 읽어 보내게** 하면 된다. 버퍼링이 dockerd 밖으로 나간다. 지금은 여유가 있으므로 4장 2단계 이후의 후보로 둔다.

별개로 **디스크에 3.8GB 가 회수 가능하다**(빌드 캐시 2.3GB · 미사용 이미지 1.5GB). 20GB 중 44% 사용이라 급하지 않다.

```bash
docker builder prune -af && docker image prune -af
```

## 7. CPU 버스트 크레딧 — 확인 완료, 문제 없음

t4g 는 버스터블이라 크레딧이 소진되면 기준 성능으로 묶인다. 트래픽이 몇 시간 이어질 때 **용량 문제처럼 보이는 크레딧 문제**가 날 수 있어 확인했다(2026-09-20).

| 항목 | 값 |
|---|---|
| 크레딧 사양 | **`unlimited`** — 소진돼도 스로틀되지 않고 초과분이 과금된다 |
| 크레딧 잔고 | 2주 내내 **576(상한)** 에 붙어 있음 |
| 최저 잔고 | 572.04 — 2026-09-11 운영 부하 테스트 |
| 초과 크레딧 사용·과금 | **0** |

40분간 CPU 를 90% 까지 밀어붙인 부하 테스트가 소모한 크레딧이 576 중 약 4다. t4g.small 의 기준선은 두 코어 합쳐 40% 인데 Node 가 한 코어를 다 써도 인스턴스 전체로는 50% 안팎이라 소모가 완만하다. **부하 테스트 수치는 크레딧 여유분에 기댄 값이 아니라 그대로 믿어도 되는 실측치다.**
