# 장애 대응 플레이북 — 증상으로 찾고, 코드로 기록한다

> **찾는 키는 증상이다. 코드는 꼬리표다.** 새벽에 코드 번호를 기억하는 사람은 없다.
> 2장의 증상 색인이나 3장의 경보 역색인에서 들어와, 코드는 사후에 티켓·회고에 적는 용도로 쓴다.
>
> | 이 문서 | 다루는 것 |
> |---|---|
> | **`incident-playbook.md`**(여기) | **무엇이 잘못됐는지 판정하고 무엇을 할지 고르는 것** |
> | [`runbook.md`](runbook.md) | 손으로 하는 절차의 원본 — 복원·교체·배포 명령은 거기 있고 여기서는 가리킨다 |
> | [`architecture.md`](architecture.md) · [`inventory.md`](inventory.md) | 구조와 실제 리소스 목록 |
> | [`scaling.md`](scaling.md) | 느린 것이 장애가 아니라 한계일 때 |

**전제** — 운영은 EC2 한 대(`api.earcast.co.kr`)에 api·caddy·postgres 세 컨테이너, AI 서버 EC2 한 대(`admin.earcast.co.kr`)에 웹·워커·ai-server다. 이중화가 없으므로 **대부분의 A급은 "한 대를 되살리는 일"이다.**

## 0. 처음 3분 — 어디까지 죽었는지부터 가른다

순서를 지킨다. 아래로 갈수록 범위가 좁아지고, 위에서 걸리면 아래는 볼 필요가 없다.

```bash
# 1) 밖에서 살아 있나 — 200 이면 A 급이 아니다
curl -s -o /dev/null -w '%{http_code}\n' https://api.earcast.co.kr/api/v1/health

# 2) 무엇이 이상하다고 말하고 있나 — 전부 OK 여야 정상
aws --profile isb cloudwatch describe-alarms --alarm-name-prefix ear-prod \
  --query 'MetricAlarms[].[AlarmName,StateValue]' --output table

# 3) 서버에 들어가 컨테이너 셋이 다 떠 있나
ssh -i ~/.ssh/ear-prod-isb.pem ec2-user@ec2-43-203-57-240.ap-northeast-2.compute.amazonaws.com
docker ps        # ear-prod-api-1 · ear-prod-caddy-1 · ear-prod-postgres-1
df -h            # 디스크 (20GB)
```

| 1번 결과 | 뜻 | 가라 |
|---|---|---|
| 응답 없음·타임아웃 | 전면 불가 | **A001** |
| `503` | 떠 있는데 의존이 죽음(대개 DB) | **A003** |
| `502`·`504` | caddy 는 살고 api 가 죽음 | **A004** |
| `200` | 서비스는 산다 — 부분 장애다 | **2장 증상 색인** |

**SSH 가 안 되면 그것부터다.** 공인 IP 가 바뀌었을 가능성이 가장 높다(유동 IP). `curl -s https://checkip.amazonaws.com` 으로 지금 IP 를 확인하고 `ear-prod-sg` 22번에 없으면 추가한다 — 서버 장애가 아니다.

## 1. 코드 체계

**범주는 영향 범위이고, 범위가 심각도를 정한다.** 외울 필요 없이 "누가 얼마나 못 쓰나"만 보면 나온다.

| 코드 | 범위 | 뜻 | 마감 | 티켓 중요도 |
|---|---|---|---|---|
| **A** | 서비스 전면 불가 | 앱이 아예 안 된다 | **즉시** | Highest |
| **B** | 일부 기능 저하 | 앱은 되는데 어떤 동작이 안 된다 | 오늘 안 | High |
| **C** | 백그라운드·배치 | 사용자는 모르지만 쌓이고 있다 | 오늘~3일 | High~Medium |
| **D** | 데이터 무결성 | **값이 틀렸다** — 조용해서 더 위험하다 | **즉시** | Highest |
| **E** | 외부 의존 | 우리 밖이 원인이다 | 사안별 | 사안별 |

**D 가 A 와 같은 마감인 이유.** 서비스가 멈추면 누구나 알지만 값이 틀린 것은 아무도 모른 채 흘러간다. 시간이 갈수록 되돌리기 어려워지므로 **발견 즉시** 잡는다.

**E 는 원인의 위치이지 범위가 아니다.** 겉으로는 B 나 C 로 보이고 원인이 밖일 때 E 를 함께 적는다(예: 소셜 로그인 불가 = `B004 / E003`). 대응이 "기다린다"로 갈릴 수 있어 구분한다.

**번호는 발견 순서다.** 빈 번호를 메우지 않고, 없어진 항목의 번호는 재사용하지 않는다 — 과거 회고의 `C002` 가 다른 것을 가리키게 되면 기록이 거짓이 된다.

## 4. A — 서비스 전면 불가 (즉시)

### A001
**API 가 응답하지 않는다** — 헬스 타임아웃, 앱 전 화면 실패.

확인
```bash
curl -s -o /dev/null -w '%{http_code}\n' https://api.earcast.co.kr/api/v1/health   # 무응답
ssh -i ~/.ssh/ear-prod-isb.pem ec2-user@ec2-43-203-57-240.ap-northeast-2.compute.amazonaws.com
docker ps && df -h && free -m
```

조치
1. SSH 가 안 되면 → **A002**(인스턴스 자체 문제). 내 IP 문제와 헷갈리지 않게 0장을 먼저 본다.
2. 컨테이너가 내려가 있으면 `cd /opt/ear/backend && docker compose -f docker-compose.prod.yml --env-file .env.prod up -d`
3. api 만 재시작을 반복하면 → **A004**
4. 디스크가 100% 면 → **A005**
5. 무엇도 아니면 [runbook.md](runbook.md) 5.4 **서버 교체**(스냅샷 복구 10분)

### A002
**인스턴스가 죽었다** — `ear-prod-ec2-status-check` ALARM. 하드웨어·하이퍼바이저 문제거나 커널이 멈춘 것이다.

조치 — 재부팅(`aws ec2 reboot-instances`)으로 안 살아나면 곧장 [runbook.md](runbook.md) **5.4 A안**. 루트 볼륨 스냅샷이 매일 04:40 KST 7일치 있으므로 **10분이면 돌아온다.** Elastic IP 를 옮기면 DNS 변경이 필요 없다.

### A003
**헬스가 `503 degraded`** — 프로세스는 살아 있고 DB 를 못 잡는다.

확인
```bash
docker ps | grep postgres
docker logs ear-prod-postgres-1 --tail 50
docker exec ear-prod-postgres-1 pg_isready
df -h    # postgres 는 디스크가 차면 쓰기를 멈춘다
```

조치 — 컨테이너가 내려갔으면 올린다. 디스크가 원인이면 **A005** 를 먼저 푼다. 데이터 파일이 깨졌으면 **D002**.

### A004
**배포 직후 안 뜬다 / 502** — caddy 는 살고 api 가 기동에 실패한다.

확인
```bash
cd /opt/ear/backend
docker compose -f docker-compose.prod.yml --env-file .env.prod logs api --tail 100
```

흔한 원인 세 가지 — **env 검증 실패**(빠진 변수 이름이 로그에 그대로 찍힌다) · **마이그레이션 실패**(→ **D003**) · **CRLF**([runbook.md](runbook.md) 4장 함정 1).

조치 — 원인이 10분 안에 안 잡히면 **되돌린다.** 직전 이미지 태그로 롤백하는 절차가 [runbook.md](runbook.md) 4장에 있다. 고치는 것보다 되돌리는 것이 빠르고, 되돌린 뒤에 고친다.

### A005
**디스크가 찼다** — `ear-prod-disk-high`(80%). 방치하면 postgres 쓰기 실패로 A 급이 된다.

```bash
df -h && du -sh /var/lib/docker/* | sort -h | tail
docker system prune -f          # 대개 쌓인 이미지·빌드 캐시다
docker logs ear-prod-api-1 --tail 1 >/dev/null   # 로그 드라이버 확인용
```

**근본 원인이 도커 계층인 경우가 많다** — 자세한 내역은 [scaling.md](scaling.md) 6장. 정리 후에도 금방 다시 차면 볼륨 확장(gp3 는 무중단 확장 가능)을 검토한다.

## 5. B — 일부 기능 저하 (오늘 안)

### B001
**재생이 403** — 서명 불일치. 서버의 `CLOUDFRONT_*` env 와 실제 CloudFront 키페어가 어긋났다. [runbook.md](runbook.md) 5.2.

### B002
**재생이 404** — 키 매핑이 없다. 전파를 10초 기다려 보고, 그래도면 키 존재를 확인한다. [runbook.md](runbook.md) 5.2.

### B003
**썸네일이 깨지거나 느리다** — 403 이면 CloudFront `thumb/*` behavior 누락([runbook.md](runbook.md) 1.2 함정). 느린 것이면 장애가 아니라 원본 크기 문제다(서버가 768px WebP 로 재인코딩한다 — 구형 PNG 가 남아 있으면 `reprocess-thumbnails` 대상).

### B004
**소셜 로그인이 안 된다** — 대개 우리 밖이다(→ **E003**). 먼저 어느 제공자인지 가른다. 카카오만이면 네이티브 앱 키가 패키지와 묶여 있어 **빌드 종류가 바뀌면 실패**한다 — 프리뷰 앱에서만 난다면 서버 장애가 아니다.

### B005
**정상 사용자가 429 를 받는다** — 한도 자체가 잘못됐거나 키가 잘못됐다.

- 클러스터 워커 수로 한도를 나누면 **정책 수치가 줄어든다.** 인증·메일 한도는 나누지 않는 것이 규칙이고 `rate-limit.constant.spec.ts` 가 못 박고 있다.
- 로그인·가입·토큰 갱신은 **IP 기준**이라 같은 공유기 뒤 사용자가 서로의 한도를 깎는다(KAN-88). 도달 조건과 시점은 그 티켓에 적혀 있다.
- **1분 뒤 자동으로 풀린다** — 영구 차단이 아니다.

### B006
**특정 API 가 500 을 반복한다** — Slack 에 ERROR 묶음이 온다(AI 서버 워커가 5분마다 CloudWatch `/ear/api` 를 읽어 보낸다).

```bash
aws --profile isb logs tail /ear/api --since 30m --filter-pattern ERROR
```
관리자 콘솔의 **백엔드 로그** 화면에서도 같은 것을 본다. 한 엔드포인트에 몰리면 배포 회귀를 의심하고 **A004 의 되돌리기 판단**을 그대로 적용한다.

### B007
**푸시가 안 간다** — 기기 토큰이 없으면 보낼 대상이 없다. 개발계·프리뷰 빌드는 토큰 형식이 다르다(`ExponentPushToken[...]`). 규칙은 `features/notification.md`.

## 6. C — 백그라운드·배치 (오늘~3일)

### C001
**크론이 안 돌았다** — `ear-prod-cron-{backup,ebs-snapshot,content-export}-missing`. 25시간 동안 성공 지표가 없다는 뜻이다.

```bash
aws --profile isb s3 ls s3://earcast-backup-prod/pg/ | tail -5      # 덤프가 매일 쌓이는가
aws --profile isb ec2 describe-snapshots --owner-ids 639177726357 \
  --filters Name=tag:Source,Values=ear-daily --query 'length(Snapshots)'   # 7 안팎
sudo tail -50 /var/log/ear-content-sync.log
crontab -l && sudo systemctl status crond
```

**새로 만든 알람은 첫 1시간에 오탐이 한 번 날 수 있다**([runbook.md](runbook.md) 6장). 다음 성공 뒤 OK 가 오면 정상이고, 그래도 ALARM 이면 진짜 미실행이다. `INSUFFICIENT_DATA` 는 크론이 지표를 못 찍는 것(권한·네트워크)이지 크론 실패가 아니다 — 원인이 다르다.

**백업 미실행은 C 지만 오래 두면 D 가 된다.** 복구 지점이 사라지고 있다는 뜻이므로 사흘을 넘기지 않는다.

### C002
**감시자가 죽었다** — `ear-prod-cron-log-watch-missing`(30분). **이 상태에서는 500 에러가 나도 Slack 에 오지 않는다. 눈이 먼 것이다.**

AI 서버의 워커가 멈춘 것이므로 거기서 본다. 워커가 서면 콘텐츠 생산도 같이 멈추므로 **C005 를 함께 확인한다.**

### C003
**드립이 안 왔다 / 두 번 왔다** — 편성 배치 문제.

**두 번 온 경우를 먼저 의심할 곳은 클러스터링이다.** 워커가 여럿일 때 스케줄러가 한 번만 등록되어야 하고, 그 게이팅이 `cluster.util.ts` 에 있다. 기동 로그에서 `ScheduleModule dependencies initialized` 가 **1회**인지 본다([scaling.md](scaling.md) 5.1·5.3).

```bash
docker logs ear-prod-api-1 2>&1 | grep -c "ScheduleModule dependencies initialized"   # 1
docker logs ear-prod-api-1 2>&1 | grep -c "Nest application successfully started"     # 워커 수
```
규칙은 `features/drip-scheduling.md`.

### C004
**통계가 안 갱신된다** — 집계 배치 정지. 값이 **틀린** 것이면 C 가 아니라 **D001** 이다.

`content_stats` 의 `all` 은 원천 재집계가 아니라 `month` 행의 합이다(KAN-57). **배치가 한 달 넘게 멈추면 그 달 행이 영영 생기지 않아 영구 오차가 된다** — 그래서 "빠진 달 감지" 경고가 있다. 경고가 보이면 D001 로 넘긴다.

### C005
**콘텐츠 생산이 멈췄다** — AI 서버 워커·큐 문제. 사용자에게 당장 보이지 않지만 발행이 마른다. `pipeline/` 의 규칙을 따르고, 워커가 죽은 것이면 **C002 와 같은 원인**일 수 있다.

### C006
**개발계에 콘텐츠가 안 들어온다** — 운영→개발계 동기화(04:10·04:30 KST, 재빌드 05:30)가 실패. 운영에는 영향이 없다. 과거에 크론 권한 문제로 멈춘 적이 있다.

## 7. D — 데이터 무결성 (즉시)

> **D 는 조용하다.** 경보가 울리지 않으므로 대개 사람이 눈으로 발견한다. 발견한 사람이 곧 탐지 장치다.

### D001
**집계 값이 틀렸다** — 완청률·재생수가 실제와 다르다.

먼저 **틀린 범위를 고정한다**(어느 기간·어느 콘텐츠). 고치기 전에 현재 값을 남긴다 — 덮어쓰면 무엇이 틀렸는지 증명할 수 없게 된다.

`week`·`month` 는 원천에서 다시 세면 복구되지만 **`all` 은 `month` 행의 합이라 빠진 달이 있으면 그 달은 영영 안 메워진다.** 원천 보존이 180일인 계열(`user_signals`·`source_link_clicks`)은 지난 것을 다시 셀 수 없다. 규칙은 `backend/domain.md` 5.4·12.1.

### D002
**DB 를 되돌려야 한다** — 절차는 [runbook.md](runbook.md) 5.3.

**세 가지를 틀리지 않는다.**
1. `psql` 에 **`ON_ERROR_STOP=1` 을 반드시 준다.** 없으면 에러를 지나치고 exit 0 을 내어 **복원된 것처럼 보이는 반쪽짜리 DB** 가 남는다.
2. 덤프는 **서버에서 직접 받을 수 없다**(인스턴스 롤에 `s3:GetObject` 가 없어 403). 노트북으로 받아 올린다.
3. 새 서버라면 **마이그레이션을 돌리지 않은 빈 DB** 에 넣는다. 덤프에 스키마가 다 들어 있어 먼저 마이그레이션하면 전부 충돌한다.

복원 뒤 **테이블 수·주요 행 수를 덤프 시점과 대조**하고, 차이가 설명되지 않으면 복구를 끝내지 않는다.

### D003
**마이그레이션이 실패했다** — 배포는 진입점이 마이그레이션을 먼저 돌리고 api 를 띄운다. 실패하면 기동이 멈춘다(→ **A004**).

**중간까지 적용된 상태가 가장 위험하다.** 스키마가 코드와 어긋난 채 뜨면 런타임에 조용히 깨진다. 실패 로그에서 **어디까지 갔는지** 확인하고, 되돌릴 수 없는 변경(컬럼 삭제 등)이면 **D002** 로 간다.

### D004
**스크립트가 잘못된 데이터를 대량으로 썼다** — 일회성 스크립트 사고.

**개발계는 운영과 같은 S3 버킷·CloudFront 를 쓴다.** 저장소 키를 지우는 스크립트를 개발계에서 그냥 돌리면 **운영 DB 가 가리키는 파일이 지워진다.** 개발계에서는 `--dry-run` 만 돌린다.

사고가 났으면 **더 쓰지 말고 멈춘다.** 범위를 센 뒤 D002 의 시점 복원과 부분 재생성 중 무엇이 싼지 고른다.

### D005
**백업이 복원되지 않는다** — 가장 나쁜 발견이고, **리허설에서 나와야 하는 발견이다.**

리허설은 운영에 손대지 않고 임시 컨테이너(`pgvector/pgvector:pg16`)에 복원해 대조하는 방식이다. 기록이 [runbook.md](runbook.md) 5.3 에 두 건(2026-09-12·09-20) 있다. 복원이 깨지면 그 시점부터 **복구 지점이 없는 상태**이므로 A 급으로 다룬다.

## 8. E — 외부 의존 (사안별)

> E 의 대응은 대개 **기다린다 + 막힌 것을 알린다**이다. 고칠 수 없는 것을 고치려다 시간을 쓰지 않는다. **우리 쪽 설정 문제인지부터 가른다** — 그건 E 가 아니라 우리 잘못이다.

### E001
**OpenAI** — 임베딩·메타 판정·썸네일 생성. 멈추면 콘텐츠 생산이 선다(C005). 사용자 영향은 없다.

**키 문제와 장애를 가른다.** 401 이면 우리 키 문제다. AI 서버 `/health` 는 provider·model 만 보여 주고 **키 유효성은 검사하지 않는다** — `/health` 가 `openai` 라고 해서 키가 살아 있다는 뜻이 아니다(2026-09-22 실제로 겪었다). 실제 호출로 확인한다.

### E002
**ElevenLabs(TTS)** — 오디오 생성이 선다. 발행 대기만 늘고 서비스 영향은 없다.

### E003
**애플·구글** — 영수증 검증(구독)·소셜 로그인. **사용자에게 직접 보이는 유일한 E 다.**

영수증 검증 실패는 구독 상태 판정에 영향을 주므로, 장애가 길면 판정을 보수적으로(기존 권한 유지) 둘지 결정해야 한다 — 규칙은 `features/subscription.md`.

### E004
**AWS** — CloudFront·S3·EC2. 재생이 전면 실패하면 B001·B002 로 보이지만 원인이 다르다. Service Health Dashboard 를 확인하고, 우리가 할 수 있는 것이 없으면 **상태를 알리고 기다린다.**

### E005
**알림 경로 자체가 죽었다** — Slack 웹훅·SNS 구독·UptimeRobot.

**이건 침묵으로 나타나서 가장 늦게 발견된다.** 감시가 감시를 덮는 구조([runbook.md](runbook.md) 4-1)의 마지막 구멍이라, 주 1회 점검이 유일한 탐지 수단이다. 조용한 날이 이어지면 **정상이라고 가정하지 말고 한 번 확인한다.**

### E006
**배포가 안 나간다** — GitHub Actions·ECR. 서비스는 계속 돌고 **배포만 막힌다.** 급하면 [runbook.md](runbook.md) 4.1 수동 배포로 우회하되, 우회 배포는 태그·이력이 남지 않으므로 뒤에 정리한다.

## 9. 사후 — 기록해야 끝난다

**불을 끈 것과 끝낸 것은 다르다.** 아래를 하지 않으면 같은 장애가 같은 방식으로 다시 온다.

1. **코드를 붙여 티켓을 낸다** — `docs/tickets/<파트>/pending/`. 제목에 코드를 적는다(예: `[BE] C003 — 드립 배치가 두 번 돌았다`). 중요도는 1장의 표를 따른다.
2. **탐지 시간을 적는다.** 언제 났고 언제 알았는지. **둘의 차이가 감시의 성능**이고, 그 차이가 크면 경보를 하나 더 다는 것이 티켓보다 중요하다.
3. **플레이북에 없던 장애였다면 항목을 추가한다.** 이 문서가 자라는 유일한 경로다.
4. **문서가 틀렸으면** `docs/changes/pending/` 에 적는다. 장애 중에 틀린 명령을 발견하는 것이 가장 흔하다.
5. **주간 회고(`docs/retrospective/`)에 코드로 집계한다** — "이번 주 A 0건 · C 2건" 처럼. 범주별로 세어야 **어디에 손을 대야 하는지**가 보인다. 번호를 만든 값어치가 여기서 나온다.

**하지 않는 것** — 장애 중에 원인을 완전히 규명하려 들지 않는다. 먼저 되살리고, 규명은 기록을 남긴 뒤에 한다.
