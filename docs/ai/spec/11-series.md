# spec/11 — 시리즈 제작 (기획 시리즈)

> 상위: [PIPELINE.md](../PIPELINE.md) · 경로: [spec/02](02-sweep.md) 6장 B-②(주제 기획) → [spec/03](03-backlog.md)(게이트 1) → [spec/04](04-script.md)(대본) → [spec/05](05-qa.md) → [spec/07](07-publish.md)(발행)
> **상태: 설계 확정 · 구현 대기** (2026-10-09, KAN-136). 시리즈 시스템 도입이 정해지면(선행 KAN-128 — 범위 확정, 편성·표시는 BE KAN-134·FE) 이 문서대로 구현한다.
> **그 전에는 시리즈 필드를 실어 발행하지 않는다** — 서버 드립은 이미 `series_id`로 편성 순서를 바꾸고(`drip-scheduling.md` 4.2-3), 상세 화면은 "N부작 중 M화"를 그린다(`content-detail.md` 4.3-1).

## 1. 정의와 범위 (2026-10-09 박수헌 결정)

- **기획 시리즈만 시리즈다.** 처음부터 N편으로 기획한 주제 묶음으로, 편 사이에 순서가 있고 앞 편이 뒤 편의 바탕이 된다. 예: "키워드로 빠르게 배우는 CS 지식" 16편, 자격증·시험(PIPELINE.md 1장 — "시리즈가 기본").
- **군집 분할은 시리즈가 아니다.** 분할 반환([spec/03](03-backlog.md) 5.1)으로 나눈 편은 지금처럼 독립 편이다. 드립은 1화를 완청하지 않은 사용자에게 2화 이후를 넣지 않으므로, 순서가 꼭 필요한 것만 묶어야 추천 폭이 덜 줄어든다.
- **편은 각자 완결된 정규 에피소드다.** 13분 하한, 자기 축·소스(3건 하한 + 뼈대 1군)·claims, 독립 QA·비평·게이트 2를 갖는다. 시리즈는 편을 묶는 **설계안**과 편 사이 **연결(회상·예고)** 만 더한다.
- **"소스 우선"의 예외 경로는 B-②를 그대로 쓴다.** 주제(편 범위)를 사람이 정하고 편마다 소스를 찾아 후보를 세운다. 불변 원칙 1(근거 없는 주제 없음)은 편 단위로 지킨다.
- **시리즈는 관리자가 시작한다**(2026-10-09 박수헌). 입구는 콘솔 **[주제 기획]** 화면의 "단일 편 / 시리즈" 선택이다 — 사람이 주제를 주는 경로라는 점이 B-②와 같다.
  - 군집화가 시리즈를 제안하지 않는다(군집 분할은 시리즈가 아니다). 반응 좋은 단일 편을 1화로 이어 가는 경로도 두지 않는다.
  - AI가 시리즈 주제 후보를 제안하는 경로는 시리즈를 몇 개 운영해 본 뒤 더한다(11장 #7).

## 2. 흐름

```
[기획]  [주제 기획] › 시리즈 ── 관리자가 주제·범위를 주면 AI 가 편 목록 초안 → 사람 수정 → ★게이트 S 승인 (편수 확정)
   ↓
[후보]  편마다 B-② 주제 기획 ── 편 범위로 소스 검색 → 후보 N개 (series_id · series_no)
   ↓   ★게이트 1 — 편마다 (자동 승인 규칙 v1 + 형제 편 소스 겹침 예외)
[제작]  편마다 설계 → 작성 ── 시리즈 블록·연결 재료 주입. k화 설계는 k-1화 설계 뒤
   ↓   L0 시리즈 검사 · QA(연결 재료는 claims 행)
[음성·출고] TTS → 썸네일 → 패키지 — 일반 편과 같다
   ↓   ★게이트 2 — 편마다 검수 (발행은 시리즈 단위)
[발행]  전 편 검수 뒤 [시리즈 발행] — 서버에 시리즈 생성 → 1화부터 순서대로 업로드, 시리즈 필드를 싣는다
```

## 3. 시리즈 설계안 — 게이트 S

- **입력** (콘솔 [주제 기획] › "시리즈" 선택 — 단일 편 입력칸에 더해 범위·편수 칸이 열린다): 중분류 · 시리즈 주제(이름안) · 다룰 범위 설명 · 편수(선택) · 메모(시험 범위 등).
  저작권 자료는 범위 체크리스트로만 쓴다 — 문장·예시·목차 순서를 옮기지 않는다(CS 시리즈 선례, 2026-10-03).
- **산출물** (`series.plan`):
  - 시리즈 이름 · 한 줄 소개(인트로 시리즈 줄의 재료)
  - 편 목록 — 번호 · 제목(주제 이름형, 장면형 금지) · 범위(다룰 개념) · 앞 편에서 이어받는 것 · **이 편에서만 자세히 다룰 것**(형제 편의 겹침 금지 목록이 된다) · 예상 분량
- **규칙**: 같은 개념은 한 편에서만 자세히 다룬다. 앞 편이 뒤 편의 바탕이 되게 순서를 잡는다. 범위가 얇아 13분이 안 되는 편은 이웃 편과 합친다(CS 선례 22 → 16편).
- **실행**: 워커 작업 `series_plan` — 단발 호출, 도구 없음. 사람이 콘솔에서 고친 뒤 [승인]한다.
- **승인 = 편수 확정.** `total_episodes`는 업로드 뒤 바꿀 수 없다(`admin-api.md` 4.10). 편을 늘리거나 줄이는 것은 첫 편 발행 전까지만 한다.
- **승인 뒤 설계안 변경**(첫 발행 전까지): 편을 고치거나 합치거나 빼면 **그 편의 앞 편(예고)·뒤 편(회상)을 다시 작성한다** — 예고는 다음 화 제목을, 회상은 앞 편 구성안을 대본에 박아 넣었기 때문이다. 설계(구성안)는 그대로 두고 작성 단계만 다시 돌리며, TTS까지 끝난 편이면 음원도 다시 만든다.
- **중단**: [시리즈 중단](발행 전만) — 남은 후보는 반려하고, 이미 만든 편은 보관만 한다. 회상·예고가 들어 있어 단일 편으로 발행하지 않는다. `series.status = cancelled`.

## 4. 편 후보 — 게이트 1

- 승인하면 워커가 편마다 B-② 작업을 건다. payload `{ mode: "B2", mid_topic, topic: 편 제목, hint, series_id, series_no }`.
  `hint` = 시리즈 이름·한 줄 소개 + 이 편 범위 + 형제 편 범위(이 편에서 다루지 않을 것).
- 후보 행에 `series_id`·`series_no`를 단다. 그 뒤(성립 판정·[보강]·승인)는 B-②와 같다.
- **자동 승인 예외**: 소스 겹침 경고(`dedup_note`)가 **같은 시리즈 형제 편끼리**면 막지 않는다. 같은 문단을 두 편이 쓰는 것은 설계 단계의 문단 제외가 이미 막는다([spec/04](04-script.md) 2.1).
- 한 편이 성립하지 않으면 사람이 [보강]하거나 설계안을 고친다(그 편 범위를 바꾸거나 이웃 편과 합침 — 첫 편 발행 전).
- **분할 반환을 적용하지 않는다.** 시리즈 편이 26분을 넘으면 설계안을 고쳐 편을 나눈다(첫 편 발행 전).

## 5. 대본 — spec/04 확장

### 5.1 시리즈 블록

- 설계·작성 프롬프트에 시리즈 블록을 넣는다. 규칙은 **별도 자산 `skills/draft/series.md`** 에 둔다 — guidelines를 고치지 않으므로 일반 편 생산은 바뀌지 않는다. 시리즈 편에만 주입한다.
- 블록 내용: 시리즈 이름 · 이 편 번호/총 편수 · 이 편 범위 · 겹침 금지 목록(형제 편이 자세히 다룰 것) · 연결 재료(5.3).
- 설계 단계는 겹침 금지 목록의 개념을 구간으로 잡지 않는다. 언급이 필요하면 한 줄로 부르고 넘어간다.

### 5.2 인트로·회상·예고 (템플릿 tpl-series)

| 자리 | 규칙 | 템플릿 (settings `templates`) |
|---|---|---|
| 인트로 대주제 줄 | 대분류 줄 대신 시리즈 줄 | `series_intro_line` — 예: "{한 줄 소개} 시리즈, {시리즈 이름}의 {N번째} 시간입니다." (CS 선례) |
| 회상 (2화부터) | 도입의 첫 **해설 턴** 앞 1~2문장. 앞 편 요지만, 연결 재료 안에서 | 없음 (자유 문장) |
| 예고 (마지막 화 제외) | 클로징 인사 턴 안 고정 슬롯. 다음 화 제목은 설계안에서 **워커가 채운다** | `series_next` — 예: "다음 시간에는 {다음 화 제목}을 이야기합니다." |
| 맺음 (마지막 화) | 예고 자리에 시리즈 맺음 한 문장 | `series_finale` |

- 회상을 해설 턴에 두는 이유: 앞 편 내용도 사실 주장이다 — 사실 주장은 해설 담당만 한다(4장 금지 규칙 1).
- 예고를 고정 슬롯으로 두는 이유: 다음 화 제목을 기계로 채우면 예고가 실제 다음 화와 어긋날 수 없다.
- 마무리 구조(진행 클로징 도입 → 해설 정리 → 진행 클로징 인사)는 일반 편과 같다. CS 16편은 정리 턴 없이 한 턴으로 끝낸 수동 제작 예외다.

### 5.3 연결 재료 — `episodes/<id>/series-links.json`

- `prev`(2화부터): 앞 편 제목 + 앞 편 구성안의 축 · 구간 질문. 구성안은 2단계 작성이 그대로 실행하는 계약이다(spec/04 2.1).
- `next`(마지막 화 제외): 다음 편 제목(설계안).
- 회상에는 연결 재료 밖의 내용을 쓰지 않는다. 연결 재료는 **claims 표에 출처 `시리즈` 행으로 넣는다** — QA는 기존대로 claims 대조만 한다.
  다른 편의 대본·리포트는 QA에 들어가지 않는다(QA 독립성, `pipeline/CLAUDE.md` 3장).
- **순서 제약**: k화 draft는 k-1화의 `outline.md`가 있을 때만 집는다. 설계만 순차이고 작성·QA·TTS는 병렬로 돈다.

## 6. 검증

- **L0** (기계, `twoStageViolations` 확장): 인트로에 시리즈 줄이 있다 · 2화부터 도입 첫 해설 턴에 회상 문장이 있다 · 마지막 화가 아니면 클로징 인사에 `series_next`가 다음 화 제목 그대로 있다 · 마지막 화는 `series_finale`이 있다.
- **QA**: 새 항목은 없다. 회상 문장은 `시리즈` 출처 claims 행에 대조된다.
- **L1 지시 준수**: 겹침 금지 목록의 개념을 자세히 풀지 않았는가.
- 비평은 편 단위로 바뀌지 않는다.

## 7. 발행 — spec/07 확장 (발행 방식 확정 2026-10-09, 박수헌)

- **전 편이 준비된 뒤 한꺼번에 발행한다.** 탐색의 시리즈 목록이 처음부터 다 차 있고, 드립이 1화를 완청한 사용자에게 바로 2화를 넣을 수 있다.
  한 편이 늦으면 전체가 기다린다 — 그 편을 고치거나 설계안을 고친다(첫 발행 전이라 편수를 바꿀 수 있다).
- **검수는 편마다, 발행은 시리즈 단위다.** 대본·청취·추천 메타 검수(게이트 2)는 일반 편처럼 편마다 한다. 시리즈 편에는 개별 [발행]이 없다.
  전 편이 `packaged`이고 검수 확인·추천 메타가 갖춰지면 시리즈 화면의 **[시리즈 발행]** 이 열린다.
- **[시리즈 발행]**:
  1. 서버에 시리즈를 만든다(KAN-134 채택 시 `POST /admin/series`). 발행하지 않을 시리즈가 서버에 남지 않게 설계안 승인 때가 아니라 이 시점에 만든다.
  2. 1화부터 순서대로 업로드한다. 브라우저가 편마다 보낸다(구형 전체 재발행과 같은 방식).
  3. 도중에 실패하면 멈춘다. 다시 누르면 이미 올린 편은 건너뛰고 이어서 올린다.
- **업로드 payload**(`admin-api.md` 4.6): `series_id` · `episode_no` = `series_no` · `total_episodes` = 설계안 편수.
  - 지금 계약이면 파이프라인이 uuid를 만들어 보낸다. 서버는 uuid 형식과 "편 번호 ≤ 총 편수"만 검사하므로 총 편수 일치·번호 중복 없음은 파이프라인이 지킨다.
  - KAN-134가 채택되면 1에서 받은 id를 보내고, 업로드는 `series_id`·`episode_no`만 싣는다.
- **제목**: `{시리즈 이름} {N} - {편 제목}`, 번호는 0 없이. 앱이 시리즈 이름을 따로 보여 줘도 콘텐츠 제목에 그대로 둔다(2026-10-09 박수헌 — CS 선례: 시리즈 이름 "키워드로 빠르게 배우는 CS 지식", 콘텐츠 제목 "키워드로 빠르게 배우는 CS 지식 N - {주제}").
- **발행 뒤 문제가 생긴 편은 회수하지 않고 고쳐서 재발행한다.** 콘텐츠 ID가 유지된다(오디오가 바뀌면 `content_version`이 올라 재생 위치가 초기화된다 — `admin-api.md` 4.10).
  중간 화를 빼면 순서가 깨지므로 회수는 **[시리즈 회수]** 로 전 편을 한꺼번에만 한다.
- **패키지**: `upload-meta.json`에 시리즈 필드를 싣는다.
- 썸네일·TTS·추천 메타는 편 단위로, 일반 편과 같다(`metadata-pipeline.md` — "편 단위로 각각 실행"). **시리즈 표지는 1화 썸네일이다**(2026-10-09 결정) — 따로 만들지 않는다.
- **에피소드 ID**는 접두어 `S`를 쓴다(CS 선례 — 박수헌 정의 "시리즈 접두어"). 번호 규칙은 `T`와 같다.

## 8. 데이터 — 파이프라인 Supabase (마이그레이션 1건)

- **`series`**: `id uuid pk` · `name` · `mid_topic` · `intro_line` · `scope_note` · `plan jsonb`(편 목록) · `total_episodes int` ·
  `status`(`planning` · `approved` · `published` · `withdrawn` · `cancelled`) · `approved_by` · `approved_at` ·
  `published_series_id uuid`(제품 `series_id` — 지금 계약이면 `id`와 같은 값, KAN-134 채택 시 서버가 준 값) · `published_at` · `created_at` · `updated_at`.
- **`backlog`**: `series_id uuid null references series(id)` · `series_no int null` · `unique (series_id, series_no)`.
- 편의 진행 상태는 편(backlog)이 갖는다. `series.status`는 설계·승인과 시리즈 단위 발행·회수만 나타낸다.

## 9. 콘솔

- **시작은 [주제 기획] 화면**(스윕·군집화 › 주제 기획): "단일 편 / 시리즈" 선택. 시리즈를 고르면 범위·편수 칸이 열리고, 제출하면 `series_plan` 작업이 걸려 시리즈 화면으로 넘어간다.
- **시리즈 화면 `/series`**: 목록 · 설계안 편집 · [승인] · 편별 진행 상태(후보 → 초안 → QA → 발행 준비 → 검수) · [시리즈 발행] · [시리즈 회수].
- 백로그·에피소드·발행 화면에 "시리즈 이름 k/N" 배지를 단다.
