# spec/07 — 패키지·게이트 2·발행

> 상위: [PIPELINE.md](../PIPELINE.md) · 앞: [spec/05 QA](05-qa.md) · TTS: [spec/06](06-audio.md)은 게이트 2 통과 후
> 실행 주체: 패키지 = AI, 검수·발행 = **사람** · 상태: `qa_passed` → `packaged` → `published`
> 원칙: **게이트 2 없이 발행되는 경로는 없다** (불변 원칙 6). 자동 QA는 사람 검수를 대체하지 않는다.

## 1. 이 단계의 역할

QA를 통과한 에피소드를 발행 가능한 형태로 묶고(패키지), 사람이 최종 검수하고(게이트 2),
음성 합성([spec/06](06-audio.md))을 거쳐 업로드·발행을 기록한다.

순서: `qa_passed` → **패키지** → **게이트 2 (대본 검수)** → TTS·청취 확인(spec/06) → **업로드 → `published`**

## 2. 패키지 (AI)

발행에 필요한 메타데이터를 `upload-meta.json`으로 산출하고 상태를 `packaged`(사람 검수 대기)로 전환한다.

| 필드 | 내용 |
|---|---|
| 제목 · 설명 | 발행용 (클릭베이트 금지 — 백로그 제목안 기준, 검수에서 확정) |
| 대분류 · 중분류 | `topics` 참조 |
| 분량 | 예상 재생 시간 |
| 참고 자료 | 소스 목록 (발행처·제목·URL) — 사용자 노출 표기 규격은 미결 (PIPELINE.md 7장 #16) |
| 해설·진행 | 윤아\|이음 배정 |
| 산출물 경로 | 대본·claims·오디오(합성 후 추가)의 S3 경로 |

## 3. 게이트 2 — 사람 최종 검수

발행물에 대한 최종 책임의 지점이다. 검수 대상은 **대본과 메타**이며 (오디오 청취 확인은 spec/06 8장),
체크리스트로 수행한다:

| # | 확인 | 방법 |
|---|---|---|
| 1 | 사실·출처 — claims 표본 확인 (뼈대 소스 주장 중심) | claims ↔ 발췌 대조 |
| 2 | 소스 적법 — 전 소스의 계층 판정 완료, 차단 도메인 없음, 뼈대 1군 | backlog 소스 묶음 ↔ domains |
| 3 | 시그니처 템플릿(tpl-v1) — 골격 변형 없이 포함 | 대본 확인 |
| 4 | 낭독 규격·화자 규칙 — QA가 통과시킨 결과의 표본 확인 | 대본 확인 |
| 5 | 제목·설명 확정 — 내용과 일치, 과장 없음 | upload-meta 확인 |
| 6 | 타깃 적합 — 발행할 가치의 최종 판단 | 검수자 판단 |

- **누검출 기록**: 검수에서 잡은 결함이 QA 검사 범위(spec/05 3장)에 속하는 것이었다면
  "QA 누검출"로 기록한다 — QA 신뢰도 실측(spec/05 7장 4단계)의 데이터가 된다.
- 결함 발견 시: 경미(표기 수준)는 수정 후 재확인, 사실·근거 결함은 `review_required`로 되돌려
  QA 경로를 다시 밟는다. 검수자가 대본을 직접 고쳐 통과시키는 경우에도 수정 내역을 기록한다.
- 통과는 검수자·시각 기록과 함께 남긴다. 도구: 현재 테이블 에디터 + 체크리스트, 이후 웹 UI.

### 3.1 검수의 단계적 자동화 계획

체크리스트 항목은 성격이 셋으로 갈린다: **결정적 검사**(2·3 — 코드화 가능), **QA와 중복되는
검증**(1·4 — 자동화의 관건은 QA 신뢰도), **책임 판단**(5·6 — 자동화 대상이 아니라 정책 결정).
따라서 자동화는 "사람 제거"가 아니라 **검수 강도의 점진 축소**로 설계한다.

| 단계 | 내용 | 전환 조건 |
|---|---|---|
| **0 — 현재** | 전수 검수 — 6항목 전부 사람이 확인 | — |
| **1 — 항목 축소** | 2(소스 적법)·3(시그니처 템플릿)을 코드 게이트로 이전. QA 코드화(spec/05 7장 2단계) 완료 시 4는 중복 검사로 소멸. 사람은 1·5·6만 | 코드 게이트 구현 (원칙 충돌 없음) |
| **2 — 표본 검수** | **리스크 등급**(전 소스 1군 여부 · 주제 민감도 · QA 재생성 이력 · 시의성 — 전부 DB에서 산출)을 도입해, 저위험 에피소드는 1번을 표본 확인으로 축소. 고위험은 전수 유지 | QA 누검출률이 합의 임계 이하로 안정 (미결 #15) |
| **3 — 저위험 무검수** | 저위험 등급에 한해 검수 생략. 고위험·신규 유형은 전수 유지 | **책임 정책의 변경** — 팀 합의 + 불변 원칙 6 개정 필수. TTS 청취 확인(spec/06 8장)의 처리도 같은 논의에 포함 |

- 항목 6(발행 가치·책임)은 어느 단계에서도 "자동 판정"되지 않는다 — 3단계의 무검수는 판정의
  자동화가 아니라 "저위험 발행물은 사후 책임 체계로 관리한다"는 정책 선택이다.
- 발행 후 결함 처리 경로(5장)는 무검수 비율이 올라갈수록 중요해진다 — 3단계 전환 전에
  수정 재발행·내림 절차의 소요 시간을 실측해 둔다.

## 4. 업로드·발행 (사람)

- 게이트 2 통과 → TTS·청취 확인(spec/06) → 관리자 업로드. **업로드는 즉시 발행**이므로
  업로드 행위 자체를 게이트 2 이후로만 둔다.
- 업로드 완료 후 사람이 상태를 `published`로 전환하고, 제품 측 콘텐츠 식별 정보를
  `published_content_ref`에 수기 기록한다 (제품 DB 자동 연동 없음 — 미결 #13).

## 5. 발행 후

- 발행 기록(backlog의 `published` 행 + 소스 묶음)이 **이후 중복 대조의 원천**이다 (spec/03 4장).
- 발행 후 결함(오정보 등) 발견 시: 사람이 판단해 수정 재발행 또는 내림 처리하고,
  경위를 `note`와 `runs`에 기록한다. 수정 재발행은 게이트 2를 다시 거친다.
- 집계: 발행 편수 · 편당 소요 시간(승인→발행) · 게이트 2 반려율 — `runs`와 상태 전환 시각에서 산출한다.

## 6. 완료 조건

- Given `qa_passed`가 아닌 에피소드 / When 패키지를 시도한다 / Then 시작되지 않는다
- Given `packaged` 에피소드 / When 게이트 2(검수 기록) 없이 업로드를 시도한다 / Then 발행되지 않는다 (규약 — 검수 기록 없는 published 전환 금지)
- Given 검수에서 QA 검사 범위의 결함 발견 / When 기록한다 / Then "QA 누검출"로 표시되어 신뢰도 집계에 잡힌다
- Given 검수에서 사실·근거 결함 발견 / When 처리한다 / Then `review_required`로 되돌아가 QA 경로를 다시 밟는다
- Given 업로드 완료 / When 행을 확인한다 / Then `published` 상태와 `published_content_ref`·검수자 기록이 남아 있다
- Given 새 후보의 중복 대조 / When `published` 행과 대조한다 / Then 발행된 주제·소스 이력이 조회된다
