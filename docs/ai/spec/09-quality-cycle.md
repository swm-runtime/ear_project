# spec/09 — 대본 품질 개선 사이클

> 상위: [PIPELINE.md](../PIPELINE.md) · 대상 단계: [spec/04 대본](04-script.md) · 관련: [spec/05 QA](05-qa.md)
> 성격: 정규 파이프라인 단계가 아니라 **개선 루프**다 — 파일럿·운영과 병행하며 대본 프롬프트를 다듬는다.
> 전제: 파인튜닝 없이, 통제 가능한 수단(프롬프트·규칙·예시)으로 최대 품질을 뽑는다.

## 1. 3요소와 역할 분담

| 요소 | 역할 | 한계 |
|---|---|---|
| **예시 대본** | 톤·리듬·"느낌"의 전달 — 규칙으로 정의할 수 없는 것을 보여준다 | 소수(2~3개)만 유효. 같은 주제로만 고르면 과적합 |
| **규칙** | 하드 제약 — 반드시 지켜야/피해야 하는 것 | 늘수록 준수율이 떨어지고, 부정 규칙("~하지 마라")은 역효과 가능 |
| **피드백** | 위 둘을 만들어내는 **원료** | 쌓기만 하면 아무것도 개선되지 않는다 — 승격(4장)이 있어야 한다 |

우선순위: **예시 > 규칙**. 부정 규칙 열 개보다 잘 쓴 예시 하나가 세다. 규칙 승격을 검토할 때
항상 "예시로 보여줄 수 있는가"를 먼저 묻는다.

## 2. 사이클 (2026-08-28 개정 — 비평가 선행)

```
① 생성      후보 1건 → 15분 본편 대본 (prompt_version = vN)
② 비평      독립 컨텍스트의 AI 비평가가 루브릭으로 선행 채점 → 비평 리포트 (7장)
③ 판정      사람이 리포트의 플래그마다 **동의/비동의**를 찍고, 놓친 지적을 보완 (3장 규약)
              — 대본 전체 정독·서술형 피드백은 선택 사항이 된다
④ 분류      AI가 판정 결과(동의된 플래그 + 사람 추가 지적)를 세 갈래로 분류해 개정안 제시:
              (a) 일회성 — 이 대본만 수정
              (b) 규칙 승격 — 반복될 문제 → 규칙 개정안
              (c) 예시 승격 — 잘 나온 부분 → 예시 후보
⑤ 개정      사람이 승인한 것만 반영 → vN+1 (변경 이력 기록. 한 사이클에 한 묶음만 — 5장)
⑥ 재생성    같은 후보로 vN+1 생성 → 전판과 비교 (소스가 같으므로 프롬프트 차이만 보인다)
              ├─ 개선 확인 → 다음 후보로 진행 (그 대본은 예시 후보)
              └─ 미흡 → ②로
```

- **통제 비교가 이 사이클의 핵심 장치다** — 같은 후보(같은 소스 묶음)를 두 버전으로 생성하면
  순수하게 프롬프트 효과만 격리된다. 버전 간 비교는 반드시 같은 후보로 한다.
- 사이클의 평가는 QA(사실 무결성)와 별개다 — QA를 통과한 대본들 사이의 품질을 다루는 루프다.
  QA 실패는 이 사이클이 아니라 spec/05의 재생성 경로로 처리한다.

## 3. 피드백 규약 (2026-08-28 개정 — 판정 중심)

사람의 기본 역할은 **판정**이다 — 피드백을 백지에서 쓰는 게 아니라, 비평 리포트에 반응한다.

- 위치: `episodes/{id}/critic-report-{버전}.md` — 플래그마다 `동의 / 비동의 / 부분동의` 판정란.
  비동의·부분동의에는 한 줄 사유를 남기면 좋다 (비평가 교정의 원료).
- **놓친 지적 보완**: 리포트에 없는데 걸리는 부분이 있으면 자유 형식으로 추가한다 —
  이것이 비평가의 검출 누락(재현율) 측정 원료다.
- **좋았던 점도 판정 대상** — 비평가는 잘된 턴도 ⭐로 표시하며, 사람의 ⭐ 동의가
  예시 승격(c)의 원료가 된다.
- 서술형 정밀 피드백(구 `feedback.md` 방식)과 **직접 고친 완성본은 여전히 최고의 피드백**이다 —
  여력이 있을 때 선택적으로. 수정본은 곧바로 골드 스탠다드 예시 후보가 된다.
- 유형 태그(분류 정확도용): `사실` `톤` `리듬` `구성` `페르소나` `규격`

## 4. 승격 규약

**규칙 승격 (b)**

- 기준: 같은 유형의 지적이 **2회 이상 반복**되거나, 1회여도 심각(사실 왜곡 유발·페르소나 파괴)할 때.
- 부정 규칙보다 긍정 예시로 — "장황한 해설 금지"보다 간결한 해설 턴 예시가 낫다.
- 규칙 총량을 경계한다: 승격 시마다 기존 규칙과의 중복·충돌을 확인하고, **분기마다 1회 통합·삭제
  점검**을 한다. 지켜지지 않는 규칙은 늘리지 말고 예시로 전환한다.
- 승격된 규칙이 [spec/04](04-script.md)의 규격 변경에 해당하면(금지 규칙·구조 등) 명세 개정으로
  처리한다 — 프롬프트와 명세가 어긋난 채 두지 않는다.

**예시 승격 (c)**

- 예시 세트: **2~3개 유지, 서로 다른 중분류**로 (한 주제 스타일 과적합 방지).
- 자격: claims까지 완비되고 사람 수정을 거친 완성본만 — 예시도 전 규격을 준수해야 한다
  (규격 위반이 있는 예시는 그 위반을 가르친다).
- 교체: 더 나은 예시가 나오면 낡은 것을 빼고 넣는다 — 세트 크기를 늘리지 않는다.

## 5. 프롬프트 자산·버전 관리

- 자산 위치 (스킬 저장소 — 정식 구축 시 `skills/draft/`):
  - 대본 생성 프롬프트 본문 (spec/04 규격의 이식)
  - `examples/` — 예시 대본 세트
  - `CHANGELOG.md` — 버전별 변경 내용·근거(어느 피드백에서 왔는지)·날짜
- 버전 규칙: 개정마다 `prompt_version`을 올린다 (v1, v2, …). **한 사이클에 한 묶음만 변경**한다 —
  규칙 대량 추가와 예시 교체를 동시에 하면 효과 귀속이 안 된다.
- 모든 생성은 `runs`에 `prompt_version`(과 `model`)을 기록한다 — 피드백이 어느 버전에 대한 것인지
  항상 추적 가능해야 한다.

## 6. 측정·수렴 판단

- **정성 축** (피드백·비교의 관점 — 점수화 강제하지 않음): 몰입(듣고 싶은가) · 자연스러움(대화
  리듬) · 정보 밀도(15분의 가치) · 페르소나 일치 · 구성(전개의 설득력).
- **정량 보조 지표** (`runs` 집계, 버전별): QA 통과율 · 재생성률 · 게이트 2 반려율 · 피드백 건수 추이
  · **비평가-사람 일치율** (7장).
- **수렴 판단**: 연속 수 편에서 피드백이 경미(일회성 (a)뿐)하면 해당 버전을 **안정 버전으로 선언**하고
  사이클을 상시 루프(편당 피드백은 계속, 개정은 모아서)로 전환한다.
- 안정 버전 이후의 대규모 개정(페르소나·구조 변경)은 새 사이클로 시작한다.

## 7. 비평가 (선행 검수기) — 2026-08-28 신설

품질 기준의 언어화를 AI가 대신하고, 사람은 판정한다. **매 판정 기록이 검수 자동화의
기준 데이터가 된다** — 게이트 1(spec/03 6.1)·QA(spec/05 7장)와 같은 "보조 → 실측 → 위임" 패턴.

### 실행 규칙

- **독립 실행**: 생성과 분리된 새 컨텍스트에서 실행한다 (spec/05 QA와 같은 원리).
  단 QA와는 **별개의 실행**이다 — QA는 사실 무결성(claims 대조), 비평가는 스타일·품질.
- **입력 제한 4종만**: 대본 + 루브릭([skills/critic/rubric.md](../skills/critic/rubric.md)) +
  guidelines + 골드 예시. 소스 원문·피드백 이력·생성 맥락·전판 대본은 반입 금지 —
  선입견 없이 대본 그 자체를 본다.
- **산출**: 비평 리포트 (`critic-report-{버전}.md`) — 루브릭 항목별 판정 + 턴별 플래그(❌)·
  칭찬(⭐) + 각각에 사람 판정란. 형식은 루브릭 문서의 리포트 규격을 따른다.

### 일치율 측정과 자동화 로드맵

판정이 끝날 때마다 기록한다: 플래그 수 / 사람 동의 수 (→ 정밀도) / 사람 추가 지적 수 (→ 검출 누락).

```
1단계 (현재)   비평가는 보조 — 사람이 전 플래그를 판정. 일치율 축적
2단계          일치율이 안정 임계값(팀 합의)을 넘으면 → 동의 생략 가능: 비동의만 표기
3단계          표본 검수 전환 — 비평가가 "경계선" 판정한 대본 + 무작위 표본만 사람이 판정.
               전환은 사람 결정 (검출 누락률 실측 근거 필요 — QA 로드맵과 동일 논리)
```

비평가의 판정 근거(루브릭)는 guidelines와 함께 버전 관리한다 — 규칙이 승격되면 루브릭에도
검사 항목이 추가돼야 한다 (어긋난 채 두지 않는다).

## 8. 완료 조건

- Given 생성된 대본 / When runs를 확인한다 / Then 어느 prompt_version·model로 생성됐는지 추적된다
- Given 피드백 접수 / When 분류한다 / Then (a)일회성/(b)규칙/(c)예시로 나뉘고, (b)·(c)는 사람 승인 후에만 반영된다
- Given 프롬프트 개정 / When CHANGELOG를 확인한다 / Then 변경 내용과 근거 피드백이 기록되어 있다
- Given 버전 비교 / When 수행한다 / Then 같은 후보(같은 소스 묶음)의 두 버전 생성물로 비교한다
- Given 예시 세트 / When 검사한다 / Then 2~3개, 서로 다른 중분류, 전 규격 준수 상태다
- Given 같은 유형의 지적 2회 반복 / When 사이클을 돈다 / Then 규칙(또는 예시) 승격안이 제시된다
- Given 비평가 실행 / When 입력을 검사한다 / Then 대본·루브릭·guidelines·골드 예시 4종뿐이고 생성 컨텍스트와 분리돼 있다
- Given 판정 완료된 리포트 / When runs를 집계한다 / Then 플래그 수·동의 수·추가 지적 수가 기록돼 일치율을 계산할 수 있다
- Given 규칙 승격 / When 루브릭을 확인한다 / Then 해당 규칙의 검사 항목이 루브릭에 존재한다
