# spec/09 — 대본 품질 개선 사이클 · 평가 체계 (v2)

> 상위: [PIPELINE.md](../PIPELINE.md) · 대상 단계: [spec/04 대본](04-script.md) · 관련: [spec/05 QA](05-qa.md) · 비평 루브릭: [skills/critic/rubric-v2.md](../skills/critic/rubric-v2.md)(초안) / [rubric.md](../skills/critic/rubric.md)(운영 중 v1.3)
> 성격: 정규 파이프라인 단계가 아니라 **개선 루프**이자, 그 루프가 기대는 **평가 체계의 정의**다.
> 전제: 파인튜닝 없이, 통제 가능한 수단(프롬프트·규칙·예시)으로 최대 품질을 뽑는다. 파인튜닝은 이 루프가 쌓는 수정 기록을 데이터로 쓸 때 시작한다.

> **v2 (2026-09-01, 박수헌 승인 방향 "구조는 갈아엎고 원자는 남긴다")** — 근거: 멘토링(08-31) + 논문 5편 대조 연구 노트
> (PodBench ACL'26 · PodEval · BinEval ICML'26 WS · Reliability without Validity · CoreaSpeech NeurIPS'25).
> **남긴 것**: QA 대조표(소스 발췌 기준 원자 검증) · 독립 실행 · 심은 오류 프로브 · 규칙 상한 · 사람 게이트 2개 · 3요소(1장) · 통제 비교(2장) · 직접 수정(3.1).
> **갈아엎은 것**: 평가를 **하한/상한 두 층**으로 분리(6장) · **4층 실행 구조 L0~L3**(6.2) · 5축 1~5점 → **100점 배점 + 앵커**(critic-v2) ·
> 단순 일치율 → **κ·재현성·편향 + 고정 회귀 세트**(7장) · 사람 판정 전수 → **회귀 세트 상수**(8장) · 규칙 개정 시 **연동 갱신 절차**(4.3).
> v1(2026-08-28)의 사이클·규약은 아래에 흡수됐고, 구 7장 "일치율 측정과 자동화 로드맵"은 7·8장으로 대체됐다.

## 1. 3요소와 역할 분담

| 요소 | 역할 | 한계 |
|---|---|---|
| **예시 대본** | 톤·리듬·"느낌"의 전달 — 규칙으로 정의할 수 없는 것을 보여준다 | 소수(2~3개)만 유효. 같은 주제로만 고르면 과적합. **표면 문구가 복제된다**(7편 중 6편 실측) — 루브릭 G1이 감시 |
| **규칙** | 하드 제약 — 반드시 지켜야/피해야 하는 것 | 늘수록 준수율이 떨어지고, 부정 규칙은 역효과 가능. **상한 20개, one-in-one-out** (BinEval: 교훈이 쌓이면 프롬프트가 서로 충돌해 성능이 되레 떨어진다 — 1~2회차에 이득이 다 나온다) |
| **피드백** | 위 둘을 만들어내는 **원료** | 쌓기만 하면 아무것도 개선되지 않는다 — 승격(4장)이 있어야 한다. v2에서 목적지가 셋으로 갈린다(4.2) |

우선순위: **예시 > 규칙**. 규칙 승격을 검토할 때 항상 "예시로 보여줄 수 있는가"를 먼저 묻는다.

## 2. 사이클

```
① 생성      후보 1건 → 15분 본편 대본 (prompt_version = vN)
② 검사      L0 기계 검사 → L1 지시 준수 → L2 QA·비평 → L3 이해도 프로브  (6.2 — 앞 층 실패 시 뒷 층 미실행)
③ 판정      사람이 비평 리포트에 반응한다 (3장):
              플래그마다 동의/부분동의/비동의 · 하위 항목마다 사람 점수 + 한 줄 사유(→ 앵커 원료) · 문장은 직접 수정
④ 분류      AI가 판정 결과를 세 갈래로 분류해 개정안 제시:
              (a) 일회성 — 이 대본만 수정
              (b) 규칙 승격 — 반복될 문제 → 생성 규칙 개정안
              (c) 예시 승격 — 잘 나온 부분 → 예시 후보
              + (d) 평가자 교정 — 판정자가 놓쳤거나 오판한 유형 → 루브릭·앵커 개정안 (v2 신설)
⑤ 개정      사람이 승인한 것만 반영 → vN+1. **연동 갱신(4.3)까지가 한 묶음**이다
⑥ 재생성    같은 후보로 vN+1 생성 → 전판과 비교 (소스가 같으므로 프롬프트 차이만 보인다)
              ├─ 개선 확인 → 다음 후보로 (그 대본은 예시 후보)
              └─ 미흡 → ②로
```

- **통제 비교가 핵심 장치다** — 버전 간 비교는 반드시 같은 후보(같은 소스 묶음)로 한다.
- 이 사이클은 **상한(품질 점수)**을 다루는 루프다. 하한(QA·프로브·지시 준수) 실패는 spec/05의 재생성 경로로 처리하고 여기로 오지 않는다.

## 3. 피드백 규약 — 판정 중심

사람의 기본 역할은 **판정**이다 — 백지에서 쓰는 게 아니라 비평 리포트에 반응한다. 판정은 대본을 고치는 일이 아니라 **검수를 검수하는 데이터를 쌓는 일**이다(7장).

- 플래그 판정: `episodes.critic_verdicts` — 플래그마다 `동의 / 부분동의 / 비동의`. 비동의·부분동의 사유는 선택.
- **점수 판정 (v2 신설)**: 하위 항목마다 사람 점수 + 한 줄 사유. 사유는 "왜 이 구간인가"를 대본 자구로 — 이것이 그대로 루브릭의 **앵커 예시**가 된다(critic-v2 3장). 사유 없는 점수는 앵커가 못 되므로 점수만 찍는 것은 허용하되 앵커 집계에서 제외한다.
- 놓친 지적: 리포트에 없는데 걸리는 문장은 **직접 수정**한다(3.1). 서술형 추가 지적란은 폐지.
- ⭐ 판정: 비평가의 ⭐에 동의/비동의 — 예시 승격 (c)의 원료.
- 유형 태그(분류 정확도용): `사실` `톤` `리듬` `구성` `페르소나` `규격`

### 3.1 사람 피드백의 형태 — 서술이 아니라 직접 수정 (2026-08-31, 박수헌 제안)

| 무엇 | 어디에 | 왜 |
|---|---|---|
| 문장 고쳐 쓰기 | 웹 UI 대본 탭의 턴 인라인 편집 → `script.md` 갱신 + `episodes.human_edits`에 수정 전/후 누적 | 서술은 뉘앙스를 못 담고 수정본은 담는다. 수정 전/후 쌍은 골드 원료이자 파인튜닝 데이터셋(spec/08 3장 ③) |
| 플래그·점수 판정 | `episodes.critic_verdicts` | **평가자 정밀도·타당도 측정**이 목적 — 7장 승격 조건의 근거 |

- 비평 리포트 파일은 AI 스냅샷 그대로 보존한다 — 사람이 리포트 본문을 고치지 않는다(검수 스냅샷 규정).
- 사이클 종결 시 AI가 `human_edits` 묶음에서 규칙 후보를 역추론해 제안하고, 사람은 승인/기각만 한다.
- **사람 수정 후에는 재QA를 돌린다** — 사람 수정도 발췌 밖 주장·중복 인용을 만들 수 있다. 콜드오픈 원본 턴을 고치면 자구 일치가 깨지므로 UI가 경고한다.

## 4. 승격 규약

### 4.1 규칙 승격 (b)

- 기준: 같은 유형의 지적이 **2회 이상 반복**되거나, 1회여도 심각(사실 왜곡 유발·페르소나 파괴)할 때. **반복 여부는 회귀 세트가 20편이 된 뒤에야 셀 수 있다** — 그 전의 승격은 "심각" 사유로만.
- 부정 규칙보다 긍정 예시로. 규칙 총량 상한 **20개**, 넣으면 하나 뺀다. 지켜지지 않는 규칙은 예시로 전환한다.
- **코드로 검사할 수 있는 규칙은 생성 규칙으로 승격하지 않고 L0 검사로 승격한다** — 프롬프트를 늘리지 않고 잡을 수 있으면 그쪽이 싸고 확실하다.
- spec/04 규격 변경에 해당하면 명세 개정으로 처리한다.

### 4.2 피드백의 세 목적지 (v2)

| 판정에서 나온 것 | 어디로 | 효과 |
|---|---|---|
| 반복되는 동의 플래그 | **생성 규칙·예시** (guidelines) | 검수가 아니라 생성에서 결함이 사라진다 (분량 문제 해결이 실제 사례) |
| 비동의 플래그 · 사람이 직접 고쳤는데 플래그가 없던 문장 | **루브릭·앵커** (critic-vN) | 평가자가 사람에게 가까워진다 → 7장 조건 충족 → 사람 개입 축소 |
| 직접 수정한 문장 쌍 | **파인튜닝 데이터셋** (spec/08) | 규칙 상한·예시 표면 복제를 규칙 없이 푸는 길 |

### 4.3 연동 갱신 절차 (v2 신설 — C28 사고의 수리)

guidelines·템플릿·규격이 개정되면 **같은 묶음 안에서** 다음을 갱신하고, 회귀 세트를 재실행한 뒤에야 개정이 끝난다:

```
개정 대상            → 반드시 같이 갱신
guidelines 규칙     → 루브릭 검사 항목 · 골드 예시(위반 문장 정리) · L1 체크리스트 규격(spec/04)
템플릿(tpl-vN)      → QA 항목 5 · 루브릭 C군 · 골드 자리표기
미결 해소           → 그 미결로 "보류"된 QA·루브릭 규칙 해제
평가 프롬프트/루브릭 → 회귀 세트 재실행(7.4) → CHANGELOG
```

근거: full-v5.1(08-31) 개정 때 루브릭 C2·C4와 QA 항목 5 보류가 갱신되지 않아, tpl-v1 규격에 맞는 C28 마무리를 QA는 보류로 넘기고 비평은 위반으로 오판했다. "루브릭도 함께 개정한다"는 문장은 있었지만 절차가 아니어서 지켜지지 않았다.

### 4.4 예시 승격 (c)

- 예시 세트: **2~3개, 서로 다른 중분류**. 자격: claims 완비 + 사람 수정을 거친 완성본 + 전 규격 준수.
- 교체: 더 나은 예시가 나오면 낡은 것을 빼고 넣는다.
- **골드는 프롬프트에 반입되고, 레퍼런스(제3자 전사본)는 절대 반입하지 않는다.** 레퍼런스는 6.3의 수치 앵커로만 쓴다.

## 5. 프롬프트 자산·버전 관리

- 자산: `skills/draft/`(guidelines · examples · CHANGELOG) · `skills/qa/prompt.md` · `skills/critic/rubric*.md` · `settings.templates`.
- 버전 규칙: 개정마다 `prompt_version`을 올린다. **한 사이클에 한 묶음만** — 단, 4.3의 연동 갱신은 한 묶음으로 친다.
- 모든 실행은 `runs`에 `prompt_version`·`model`·`executed_by`를 기록한다. 평가 실행은 **평가자 버전**(qa-vN · critic-vN · 판정 모델)도 기록한다 — 7장 재검증의 단위다.

## 6. 평가의 구조 (v2 신설)

### 6.1 두 층 — 하한과 상한

| 층 | 무엇 | 형태 | 검사 | 근거 |
|---|---|---|---|---|
| **하한** | 사실 무결 · 규격/지시 준수 · 이해 전달 | **통과/실패** — 점수 없음, 순위에 쓰지 않음 | QA 대조표(spec/05) · L1 체크리스트 · L3 이해도 프로브 | 소스 발췌·규격 문서에 근거 → 취향 무관, 모델·프롬프트가 바뀌어도 의미 유지 |
| **상한** | 콘텐츠 퀄리티 — 깊이·구성·자연스러움·몰입·페르소나 | **100점 배점 점수** — 비교·추세·레퍼런스 대비 | 비평(critic-v2) | 우리가 실제로 **개선하는 대상**. 비교 가능성이 절대 조건 |

- 평가 목적은 "이해시켰는가"만이 아니다(박수헌, 09-01). 이해만 시키는 대본은 요약문이다. 하한은 넘어야 할 선, 상한이 올려야 할 점수다.
- 하한 지표(이해 전달률 등)를 순위나 개선 목표로 쓰기 시작하면 대본이 설명문 쪽으로 끌려간다 — **게이트로만 쓴다.**
- 하한 실패 대본에 상한 점수를 준 판정자는 취향이 다른 게 아니라 **틀린 것**이다 — 회귀 세트에서 잡는다.

### 6.2 4층 실행 구조

싼 것부터. 앞 층에서 떨어지면 뒷 층을 돌리지 않고 재생성 연쇄(spec/05 4장)로 보낸다.

| 층 | 무엇 | 실행 | 비용 | 산출 |
|---|---|---|---|---|
| **L0 기계 검사** | 분량(규칙 글자수 · 실측 환산 상수) · 턴 길이 분포·CV · 짧은 턴 비율 · 어미 분포 · 반복 n어절 · 날짜 표기 횟수 · 낭독 규격(구 D5) · 시점 고정 표현(구 D4) · 대본 형식 계약 · 어휘 다양성(MATTR, Distinct-2) · 정보 밀도(Info-Dens) | 코드, draft 직후 자동 | 0 | 지표 행(DB) + 하드 위반 목록. **관리도**: 지표별 이동 평균·분산, 최근 N편 2σ 이탈 시 알람(7.6) |
| **L1 지시 준수** | 백로그 항목(주제·각도·소스 범위·도입 형태) + spec/04 규격(구조·역할·분량·템플릿)에서 **체크리스트를 매번 생성**, 항목별 대본 인용 근거 + `0 / 0.5 / 1`, 집계 0~100. 분량은 엄격(±5%) | AI, 짧음 | 낮음 | 체크리스트 + 점수. 규격 문서에서 매번 생성하므로 **낡은 규칙이 남을 자리가 없다** |
| **L2 사실·품질** | QA 대조표(spec/05, 그대로) · 비평(critic-v2: 판단 플래그 + 100점) | AI, 독립 실행 | 높음 | qa-report · critic-report |
| **L3 이해도 프로브** | 게이트1 직후 **대본을 보기 전에** 소스 발췌로 질문 6~8개 생성 → **대본만** 받은 새 컨텍스트가 답변 → 발췌 기준 채점. 오답 3유형: 대본에 없음(→생성) · 있으나 모호(→규칙) · 틀리게 전달(→QA 누락) | AI, 중간 | 중간 | 이해 전달률 + 오답 유형. **통과/실패로만** |
| **사람 게이트 2** | 앞 4층 통과분만. 판정(3장) + 발행 결정 | 사람 | — | verdicts · human_edits |

- L0 항목은 비평가에게 **주지 않는다**(독립성) — 대신 루브릭에서 제거해 비평가가 그 항목을 플래그하지 않게 한다(critic-v2 2.2).
- 검수 순서 규정 유지: draft → QA(통과까지) → 비평은 **QA 통과본**에 → L3.
- L1이 잡는 것 = "요청한 대로 만들었는가". PodBench의 핵심 실증은 **지시 준수 95점과 내용 60점이 공존한다**는 것 — 두 점수를 절대 합치지 않는다.

### 6.3 레퍼런스 앵커

- `references/`의 제3자 전사본에 L0 지표를 돌려 **사람이 만든 팟캐스트의 대역**을 얻는다(PodEval Real-Pod 방식). 텍스트는 프롬프트에 반입하지 않고 **수치만** 비교한다.
- 방향 주의: 실제 팟캐스트는 **어휘 다양성이 낮고 정보 밀도가 높다**(군말·쉬운 단어). 어휘 다양성을 올리는 쪽으로 튜닝하면 사람에게서 멀어진다.
- 저품질 앵커(일부러 망친 대본)도 회귀 세트에 둔다 — 판정자가 나쁜 것을 나쁘다고 하는지, 점수 압축(전부 후하게)이 없는지 보는 유일한 방법.

## 7. 평가자 검증 — 회귀 세트와 승격 조건 (v2, 구 7장 대체)

"완전 자동화가 가능한가"의 답: **가능하되, 조건은 둘**이다 — ① 평가자를 믿을 수 있는가, ② 생성이 안정적인가. 둘 다 고정된 회귀 세트로 잰다. 사람 비용은 에피소드 수가 아니라 **회귀 세트 크기에 비례하는 상수**가 된다.

### 7.1 회귀 세트

| 구성 | 수 | 역할 | 갱신 |
|---|---|---|---|
| 판정 완료 대본 (새 배점·사유 포함) | **20편** | 타당도(사람 대비) | 루브릭 개정 시 재라벨. 분기마다 최신 2편 교체 |
| 심은 오류본 | **8편** | 누검출 하한 | 오류 유형 갱신 시 |
| 저품질 앵커 | 2편 | 점수 압축 검출 | — |
| 레퍼런스 대역 | L0 수치 | 상한 참조 | 전사본 추가 시 |

- 시작: 판정 대기 8편(T260828-001 ~ T260831-002)을 **critic-v2 배점으로** 판정해 첫 8편을 만든다. 구 5축으로 판정하지 않는다 — 버려질 루브릭에 사람 시간을 쓰지 않는다.
- 세트는 `episodes.regression = true`로 표시하고, 판정 라벨은 `critic_verdicts`에 평가자 버전과 함께 남긴다.

### 7.2 지표 정의

단위는 **턴**이다. 사람 정답 = (동의된 플래그가 있는 턴) ∪ (사람이 직접 수정한 턴). 판정자 출력 = 플래그가 있는 턴.

| 지표 | 계산 | 왜 |
|---|---|---|
| **플래그 타당도 κ** | 턴 단위 판정자/사람 이진 라벨의 Cohen's κ | 단순 일치율은 κ를 33~41%p 부풀린다(P4). "85% 일치"가 실제 κ≈0.48 |
| **재현율 proxy** | 편당 사람 직접 수정 턴 중 플래그가 없던 턴 수 | 정밀도만 보면 안 잡는 판정자가 통과한다 |
| **점수 타당도** | 축별 Spearman ρ(판정자 vs 사람) · 평균 절대 오차(100점 기준) | 순서와 크기 둘 다 |
| **재현성** | 같은 대본 3회(온도 0): 플래그 집합 Jaccard · 축별 점수 편차 | 흔들리는 판정자는 추세를 못 본다 |
| **편향** | ① 입력 순서 교체(골드 2종 순서·루브릭 군 순서)에서 플래그 Jaccard ② 점수–글자수 상관 | P4의 "일관성–편향 역설": 재현성이 높을수록 편향을 반드시 같이 본다 |
| **누검출** | 심은 오류 검출 수 / 심은 수 | 하드 게이트 |
| **압축** | 저품질 앵커의 점수가 세트 중앙값보다 명백히 낮은가 | 전부 후하게 주는 판정자 검출 |

### 7.3 단계와 승격 조건

숫자는 **제안값**이다(2026-09-01). 8편 판정 후 첫 측정에서 조정한다.

| 단계 | 사람의 판정 | 넘어가는 조건 (전부 만족) |
|---|---|---|
| **1단계** 전수 판정 (현재) | 전편 — 플래그 판정 + 점수·사유 | → 2단계: 회귀 세트 20+8편 확보 · **κ ≥ 0.6** · 재현율 proxy **≤ 1턴/편** · 축별 **ρ ≥ 0.6** · MAE **≤ 10점** · 누검출 **8/8** |
| **2단계** 불일치만 | 판정자 **2개**(교차 모델)를 병렬 실행, **어긋난 항목만** 사람 | → 3단계: 1단계 조건 유지 · 재현성 Jaccard **≥ 0.9**·점수 편차 **≤ 5** · 순서 편향 Jaccard **≥ 0.9**·길이 상관 **\|r\| < 0.2** · 압축 없음 · **생성 안정**(7.5) |
| **3단계** 표본 + 자동 발행 | 편당 10~20% 표본 + 알람 대응 + 월 1회 세트 리뷰 | 유지 조건 = 3단계 진입 조건. 어느 하나 미달 시 한 단계 후퇴 |

- 2단계의 "불일치만"은 BinEval의 교차 모델 방식이다 — 어긋난 항목이 정확히 규칙이 애매한 지점이라 **판정 시간 대비 규칙 개선 수율이 가장 높다**. 규칙 승격(4.1)은 이 단계에서 가장 잘 된다.
- 어느 단계에서도 **사람 게이트 2개는 유지**한다. 줄이는 것은 검수의 양이지 결정권이 아니다.

### 7.4 재검증 트리거

아래 중 하나가 일어나면 회귀 세트를 **전부 재실행**한다(사람은 결과 확인만). 조건 미달이면 후퇴.

- 판정 모델 변경(버전 업 포함) · 평가 프롬프트/루브릭 개정 · 생성 프롬프트 대개정(대본 성격이 바뀌므로)
- **4주 경과** — 호스팅 모델은 알리지 않고 바뀐다
- **미결 해소** — 연동 규칙 갱신(4.3) 포함

### 7.5 생성 안정 (수렴 판단 — 구 6장 대체)

직전 **10편** 기준: 하한(QA·L1·L3) 사람 개입 없이 **10/10 통과** · 상한 점수 평균 **≥ 목표치** · 표준편차 **≤ 8** · L0 관리도 알람 **0**.
목표치는 사람이 정한다 — 제안 **70/100**, 앵커가 잡히면 조정. 충족 시 그 버전을 **안정 버전**으로 선언한다.

### 7.6 관리도 (3단계 상시 모니터링 — 사람 없이)

L0 지표는 매 편 자동 계산되므로 **추세가 보인다**. 지표별 이동 평균·분산을 기록하고 최근 N편 기준 2σ 이탈 시 사람을 부른다.
실증: 소스 5~7건 표준 도입 후 **날짜 낭독이 0→7회로 단조 증가**, **짧은 턴 비율이 21%→3.7%로 하락**했는데 비평가는 다섯 편 뒤에야 잡았다. 관리도였다면 두 번째 편에서 알람이다.

## 8. 사람의 자리

| | 1단계 전수 | 2단계 불일치만 | 3단계 표본·자동 발행 |
|---|---|---|---|
| 게이트 1 주제 승인 | 사람 | 사람 | 사람 (편집 결정, 유지) |
| 비평 판정 | 전편 | 어긋난 항목만 | 10~20% 표본 |
| 게이트 2 발행 | 사람 | 사람 | 하한 통과 + 알람 없음 → 자동, 표본만 사람 |
| **기준 정의** 배점·앵커·규칙 승격·미결 | 사람 | 사람 | 사람 — **최종적으로 남는 자리** |
| 회귀 세트 재실행 | — | 트리거 시 결과 확인 | 트리거 시 결과 확인 |
| 알람 대응 | — | — | 관리도 이탈·프로브 실패·판정자 불일치 급증 |
| 편당 사람 시간(추정) | ~30분 | ~10분 | ~3분 + 월 1회 세트 리뷰 |

사람이 하는 일이 **검수에서 기준 정의로 옮겨간다.** 판정의 목적은 대본을 고치는 것이 아니라 판정자가 옳았는지를 기록하는 것이고, 그 기록이 7장의 재료다.

## 9. 완료 조건

- Given 생성된 대본 / When runs를 확인한다 / Then prompt_version·model·평가자 버전(qa-vN·critic-vN·판정 모델)이 추적된다
- Given draft 완료 / When L0가 실행된다 / Then 지표 행이 DB에 적재되고 하드 위반은 재생성 연쇄로, 관리도 이탈은 알람으로 간다
- Given L1 실행 / When 체크리스트를 확인한다 / Then 백로그 항목과 spec/04 규격에서 그때 생성된 것이고 항목마다 대본 인용 근거가 있다
- Given 비평 실행 / When 입력을 검사한다 / Then 대본·루브릭·guidelines·골드 4종뿐이며 L0 결과·생성 컨텍스트는 없다
- Given 비평 리포트 / When 점수를 확인한다 / Then 하위 항목별 점수 + 대본 인용 근거가 있고 합계는 100점 배점을 따른다
- Given 사람 판정 / When 저장된다 / Then 플래그 판정·하위 항목 사람 점수·사유가 평가자 버전과 함께 critic_verdicts에 남는다
- Given 하한 지표(이해 전달률 등) / When 대시보드를 본다 / Then 통과/실패로만 표시되고 순위·평균에 쓰이지 않는다
- Given guidelines·템플릿 개정 / When 개정을 닫는다 / Then 루브릭·골드·QA 프롬프트·L1 규격이 같은 묶음에서 갱신됐고 회귀 세트가 재실행됐다
- Given 회귀 세트 / When 재실행한다 / Then 7.2의 지표가 전부 계산되고 7.3 조건 대비 충족/미달이 표시된다
- Given 단계 전환 / When 결정한다 / Then 7.3 조건 전부 충족이 확인된 기록이 있고, 전환은 사람이 한다
- Given 같은 유형의 동의 플래그 2회 반복(회귀 세트 20편 이상) / When 사이클을 돈다 / Then 규칙(또는 예시·L0 검사) 승격안이 제시된다
