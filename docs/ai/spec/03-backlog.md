# spec/03 — 군집화·백로그·게이트 1

> 상위: [PIPELINE.md](../PIPELINE.md) · 앞: [spec/02 스윕](02-sweep.md) · 뒤: [spec/04 대본](04-script.md)
> 저장: `backlog` 테이블 · 실행 주체: 군집화 = AI, 승인 = **사람**
> 원칙: **후보는 실소스 군집에서 태어난다.** 근거 없는 주제 제안은 없다 (불변 원칙 1).

## 1. 이 단계의 역할

`sources`에 쌓인 메타데이터에서 **"자료 여러 건이 하나의 이야기로 묶이는" 군집**을 찾아
에피소드 후보로 만들어 `backlog`에 적재하고, 사람의 승인(게이트 1)을 받는 단계다.

게이트 1이 있으므로 이 단계는 "주제 선정의 자동화"가 아니라 **"후보 준비의 자동화"** 다 —
사람의 결정권은 그대로 두고, 결정에 드는 준비 비용만 줄인다.

## 2. 군집화 기준

- **성립 조건**: 서로 다른 소스 여러 건이 하나의 주제·서사로 묶이고, 한 편 분량의 에피소드를
  만들 충분한 내용이 있다고 판단될 것.
- **군집의 축은 주제(개념·원리·질문)다** (2026-08-28 원칙) — 하나의 사건·발표·출시를 축으로
  묶지 않는다. 이어는 소식을 전하는 서비스가 아니다. 사건성 소스는 주제를 뒷받침하는 사례
  재료로만 군집에 포함한다. (후보 제목이 "○○ 사건의 전말"형이면 축이 잘못 잡힌 것)
- **소스 수**: 하한 3건 (불변 원칙 5). **상한은 없다** — 충분한 내용이 있으면 그 이상도 된다.
- **뼈대 소스**: 군집마다 주 근거가 될 소스 1건을 지정한다. 뼈대는 1군(`allow_open`)만 가능하다.
- **소스 부족 시**: 이야기는 성립하는데 3건 미만이면 모드 B-①(주제 탐색 보강 — [spec/02](02-sweep.md) 6장)을
  호출한다. 보강해도 미달이면 후보를 만들지 않는다.
- **주제 자격**: 중분류가 `topics.ai_generation = true`인 것만 후보가 될 수 있다.
  경계가 애매한 군집(예: 기술 주제가 커리어 서사로 흐르는 경우)은 버리지 않고 `held`로 적재해 사람 판단을 요청한다.
- **타깃 적합성**: 자기계발을 원하는 2030 직장인(편도 30분 통근 상황)이 들을 이유가 있는가를
  후보마다 서술한다 — 게이트 1에서 사람이 "만들 가치"를 판단할 재료다.

**군집화 판단의 한계 명시**: 군집화는 메타데이터(제목·요약)만 보고 수행된다. 따라서 대본 단계에서
원문을 정독하면 군집 판단이 뒤집힐 수 있으며, 그 경우 후보를 반려하고 사유를 기록한다 —
이는 오류가 아니라 깔때기 구조([spec/02](02-sweep.md) 1장)의 예정된 비용이다.
(세부 품질 기준은 사례 축적 후 구체화 — PIPELINE.md 7장 #4)

## 3. 후보의 구성 (backlog 행)

| 컬럼 | 내용 | 규칙 |
|---|---|---|
| `id` | 후보 식별자 (`C01` 형식) | |
| `mid_topic` | 중분류 | `topics.mid` 참조 |
| `title` | 제목안 | 클릭베이트 금지 |
| `summary` | 한 줄 요지 | 이 군집이 왜 하나의 이야기인가 |
| `target_fit` | 타깃 적합성 | 2장의 기준 서술 |
| `angle` | 구성 각도(안) | 에피소드 전개 방향 제안 — 대본 단계의 참고 입력 |
| `sources` (jsonb) | 소스 묶음 | url·title·publisher·published·계층·`backbone`(뼈대 여부). 3건 이상, 뼈대 1건 |
| `dedup_note` | 중복 대조 결과 | 4장. **대조하지 못했으면 그 사실을 명시** — "대조한 척" 금지 |
| `status` | 상태 | 5장 |

소스 발행일 범위가 시의성 판단의 재료가 되므로, `sources` 안의 `published`는 비워두지 않는다
(스윕이 못 얻은 경우 null 허용 — 단 게이트 1에서 감안).

## 4. 중복 대조

후보를 적재하기 전에 AI가 수행하고 결과를 `dedup_note`에 기록한다. 전부 DB 쿼리다.

| 대조 대상 | 방법 |
|---|---|
| 기존 백로그와 주제 중복 | `backlog`에서 유사 주제 검색 (제목·요지) |
| 이미 발행된 에피소드와 중복 | `backlog.status = published` 행과 대조 |
| 소스 재사용 | 소스 묶음의 URL이 다른 후보·발행 에피소드에서 이미 쓰였는지 (`backlog.sources` 검색) |

- 소스 재사용 자체는 금지가 아니다 — 같은 소스가 다른 각도의 에피소드에 쓰일 수 있다.
  중복 대조의 목적은 **같은 이야기를 두 번 만드는 것**의 방지이며, 판단 재료를 게이트 1에 제공하는 것이다.

## 5. 상태 전이

```
proposed ─승인→ approved ─집기→ claimed → drafted → qa_passed → packaged ─업로드→ published
   │               │                            │
   └ rejected      └ expired          qa_failed ─(3회)→ review_required → qa_passed | rejected
   └ held (사람 판단 보류)
```

| 전이 | 전환 주체 | 기록 |
|---|---|---|
| → `proposed` | AI (군집화 적재) | runs `phase=cluster` |
| `proposed` → `approved` | **사람만** (게이트 1) | `approved_by` · `approved_at` — 사람만 기입 |
| `proposed` → `rejected` | 사람 | 사유를 `dedup_note` 또는 `note`에 |
| → `held` | AI(경계 판단 요청) 또는 사람 | 보류 사유 명시. 해소도 사람만 |
| `approved` → `claimed` | 제작 실행 시작 시 (AI/사람) | `claimed_by` · `claimed_at` — 동시 작업 충돌 방지. 이미 claimed면 집을 수 없다 |
| `claimed` → `drafted` 이후 | [spec/04](04-script.md)~[07](07-publish.md) | 각 단계 명세를 따른다 |
| `approved` → `expired` | 사람 (소스 신선도 상실 등) | 처리 주기는 미결 (PIPELINE.md 7장 #13) |
| `claimed` → 분할 반환 | AI 제안 → **사람 재승인** | 5.1 참조 |

### 5.1 분할 반환 — 대본 단계에서 군집이 한 편보다 클 때

대본 단계의 분량 판정([spec/04](04-script.md))이 "이 군집은 한 편(15분)에 완결되지 않는다"고
판정하면, **대본을 쓰지 않고 백로그로 반환**한다:

1. 원 후보: `rejected` 처리 + 사유 기록 ("분할 재적재 → C-xx-1, C-xx-2")
2. 분할된 후보들을 신규 `proposed`로 적재 — **각 편이 독립적으로 소스 3건 하한 + 뼈대 1군을 충족**해야 하며,
   각 편이 독립적으로 완결되어야 한다 (완결성 우선 — 분량을 맞추려 이야기를 중간에 자르지 않는다)
3. 게이트 1 **재승인** — 승인받은 "주제+소스 묶음"이 바뀌었으므로. 소스는 이미 검증됐으니 확인은 가볍다

대본 단계가 임의로 여러 편을 만드는 것은 금지다 — 게이트 1이 승인한 것은 "이 소스 묶음으로 한 편"이며,
승인 없이 발행물이 늘어나는 경로를 두지 않는다.

- 상태의 단일 진실 원천은 DB다. 사용자 앱에는 이 상태가 일절 노출되지 않는다.

## 6. 게이트 1 — 주제 승인

- **판단 대상은 "주제+소스 묶음"이다** — 제목이 그럴듯한가가 아니라, **이 근거면 만들 가치가 있는가**.
  후보에 소스가 내장되어 있으므로 "승인했는데 소스가 없더라"는 원리상 발생하지 않는다.
- 승인 시 확인할 것: 소스의 질(뼈대가 1군인가, 계층 판정이 완료됐는가) · 타깃 적합성 ·
  중복 대조 결과 · 소스 발행일 범위(시의성).
- 도구: 현재는 Supabase 테이블 에디터 (행의 `status`·`approved_by`·`approved_at` 편집), 이후 웹 UI (spec/08).
- 승인은 대본 생성의 유일한 입구다 — `approved`가 아닌 후보로 대본을 시작할 수 없다.

### 6.1 승인 과정의 단계적 자동화 계획

게이트 1의 자동화는 "사람을 빼는 것"이 아니라 **사람이 보는 양을 줄이는 것**부터 시작한다.
각 단계는 이전 단계의 실측 데이터가 조건을 충족할 때만 전환하며, 전환은 팀 결정이다.

| 단계 | 내용 | 사람의 일 | 전환 조건 |
|---|---|---|---|
| **0 — 현재** | 사람이 전체 후보를 검토·승인 | 후보 전량 검토 | — |
| **1 — 사전 심사** | 형식 요건을 **결정적 코드 게이트**로 자동 검증: 소스 3건 이상 · 뼈대 1군 · 전 소스 계층 판정 완료 · 중복 대조 수행됨 · `ai_generation=true`. 미달 후보는 `proposed`로 올라오지 못하고 자동 반려(사유 기록). 통과 후보에는 AI가 우선순위 점수(타깃 적합성·소스 질·신선도)를 부여 | 형식 통과 후보를 **점수순으로** 검토 — "만들 가치" 판단만 남음 | 파일럿 수 편 경험 후 즉시 도입 가능 (원칙 충돌 없음 — 승인 자체는 여전히 사람) |
| **2 — 조건부 자동 승인** | 엄격 조건(예: 전 소스 1군 + 중복 없음 + 신선도 충족 + AI 점수 임계 이상)을 충족하는 후보만 자동 승인(`approved_by = "auto:규칙버전"`). 나머지는 사람 검토 유지 | 경계 후보만 검토 + 자동 승인 결과의 표본 감사 | **AI 추천과 사람 결정의 일치율 실측**(1단계에서 축적)이 합의된 임계를 넘을 것 + **불변 원칙 6의 개정** (팀 합의 필수) |

- 1단계까지는 불변 원칙과 충돌하지 않는다 — 자동화되는 것은 "형식 검증과 우선순위"이고 승인은 사람이 한다.
- 2단계는 원칙 개정 사항이다. 판단 근거가 될 일치율 데이터는 1단계 운영 중 `runs`와 승인 기록에서 자동으로 쌓인다
  (AI 점수 상위 후보를 사람이 실제로 승인했는가). 임계값·전환 여부는 미결 (PIPELINE.md 7장 #14).
- 어느 단계에서도 게이트 2(발행 전 검수)는 영향받지 않는다.

## 7. 실행·기록

- 인터페이스: `/cluster <중분류>` — 스윕 완료 후 실행. 현재는 사람 트리거.
- `runs` 기록: `phase=cluster`, `result`(도출 후보 수·보류 수·보강 호출 여부), `prompt_version`, `executed_by`.

## 8. 완료 조건

- Given 스윕이 완료된 중분류 / When 군집화를 실행한다 / Then 실소스 3건 이상+뼈대 1건이 지정된 후보들이 `proposed`로 적재되고, 각 후보에 중복 대조 결과가 명시된다
- Given 이야기는 성립하나 소스가 2건인 군집 / When 군집화가 처리한다 / Then 모드 B-① 보강을 호출하고, 그래도 미달이면 후보를 만들지 않는다
- Given `ai_generation = false`인 중분류의 군집 / When 후보를 구성한다 / Then 적재되지 않거나, 경계 애매 시 `held`로 적재된다
- Given `proposed` 후보 / When 사람이 승인하지 않았다 / Then 대본 생성을 시작할 수 없다
- Given `approved` 후보 하나를 두 실행이 동시에 집으려 한다 / When 두 번째가 시도한다 / Then 이미 `claimed`임이 확인되어 집을 수 없다
- Given 게이트 1 승인 / When 행을 확인한다 / Then `approved_by`·`approved_at`이 기록되어 있다
- Given 대본 단계에서 원문 정독 결과 군집이 성립하지 않는다 / When 반려한다 / Then 사유가 기록되고 상태가 되돌아간다 (spec/04)
- Given 분량 판정이 "한 편에 완결 불가"로 판정한다 / When 분할 반환한다 / Then 대본이 생성되지 않고, 분할 후보들이 각각 3건 하한·뼈대 1군을 충족한 `proposed`로 적재되며, 재승인 전에는 제작이 시작되지 않는다
