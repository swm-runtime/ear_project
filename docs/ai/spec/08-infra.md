# spec/08 — 인프라·실행기·자동화 로드맵

> 상위: [PIPELINE.md](../PIPELINE.md) · 스키마 원본: [pipeline/supabase/schema.sql](../../../pipeline/supabase/schema.sql)
> 원칙: **인프라는 상태·데이터 관리까지, 실행은 스킬(절차)이, 결정은 사람이.** 절차(스킬)·상태(DB)·산출물(S3)을
> 분리해 각각 독립적으로 교체 가능하게 유지한다 — 이 분리가 API 이행과 로컬 전환의 전제다.

## 1. 데이터 계층 — Supabase (가동 중)

**접근·키 규약**

- 사람: Supabase 조직에 **각자 계정**으로 초대 — 승인·판정 기록의 신원. 테이블 에디터가 현재의 관리 UI.
- 에이전트: secret key 1개 공유 + 모든 쓰기에 `executed_by` 기록. 키는 환경변수로만 관리, 저장소 커밋 금지.
- RLS: 전 테이블 활성 + 정책 없음(기본 차단). publishable 키는 아무것도 못 읽는다.
  웹 UI 구축 시(4장) 팀 계정용 정책을 추가한다.
- DB 행에는 파일을 넣지 않는다 — **행에는 항상 S3 경로만** (덩치 큰 산출물은 전부 2장).
- 제품 인프라(EC2·제품 S3·CloudFront)와 완전 분리. **같은 AWS 계정(ISB)을 쓰되 리소스를 섞지 않는다** — 2장.

**저장 배치 기준** (2026-09-01 확정 — 새 데이터가 생기면 이 세 줄로 판정한다)

1. **행으로 조회·갱신·판정하는 것** — 상태·관계·누가 언제·화면에서 고치는 짧은 텍스트 → **Supabase**
2. **파일 정체성을 가진 산출물·증적·바이너리·큰 것** → **파이프라인 S3**(2장). DB에는 **키만**
3. **서비스가 서빙하는 것** → **제품 S3**. 진입은 관리자 업로드 한 곳(spec/07 4장) — 파이프라인은 제품 버킷에 쓰지 않는다

| 데이터 | 저장소 | 비고 |
|---|---|---|
| 상태 테이블 전부 + 사람 판정(`human_edits`·`critic_verdicts`·승인/판정 스탬프) | Supabase | |
| **프롬프트 자산**(guidelines·골드·QA 프롬프트·루브릭 — spec/10 3.2의 7개) | **Supabase `prompt_assets`** | 작고(자산당 10~20KB), 버전·active 포인터·웹 편집·diff·감사가 필요 → 행의 성질. `settings.templates` 선례의 확장. git `docs/ai/skills/`는 export 스냅샷 |
| spec/03·04·05 등 명세 문서 | git (`docs/ai/`) | 본문이 사실상 고정. 워커는 체크아웃에서 읽고 `runs`에 커밋 SHA를 남긴다. spec 안에서 자주 바뀌는 표·참조는 자산으로 승격(spec/09 4.1) |
| `episodes/{id}/` 대본·claims·발췌·QA/비평 리포트·`upload-meta.json`·`audio/` | 파이프라인 S3 | `script.md`를 DB에 두지 않는 이유: 편당 100~150KB·리포트 회차 추기로 연 100MB+ → "Supabase 비용 0" 원칙 위반, TTS·패키지·업로드가 파일을 소비, `claude -p`가 읽으려면 어차피 파일로 내려놓아야 함 |
| `sweeps/` 스윕 원본 · `datasets/` 학습 데이터 export(5장) | 파이프라인 S3 | 조회는 `sources` 테이블이 담당 |
| 발행 `dist.mp3`·썸네일 | 제품 S3 | 게이트 2 후 관리자 업로드로만 |

## 2. 저장 계층 — S3 (파이프라인 전용 버킷 · 생성 스크립트 준비됨, 산출물 이관은 spec/10 M4)

비공개 버킷 1개로 시작한다. 구조:

```
s3://<버킷>/
  episodes/{에피소드 번호}/
    script.md · claims.md · sources.md(발췌) · qa-report.md · upload-meta.json · feedback.md
    audio/ master.wav · dist.mp3 · timestamps.json(턴별 합성 시)
  sweeps/{날짜}.json          ← 스윕 원본 아카이브
  datasets/{export 날짜}/      ← 파인튜닝 데이터셋 export (5장 · 미결 #21)
```

**에피소드 번호 규칙**: `{프리픽스}{YYMMDD}-{순번 3자리}` — 예: `T260820-001`.

- 프리픽스: `T` = 테스트·파일럿 제작분. 정식 발행 제작분의 프리픽스는 추후 확정 (제안: `E`).
- 날짜: 제작 착수일(집기 시점). 순번: 그날 착수 순서.
- 디렉토리명에 주제를 넣지 않는다 — 주제·백로그 연결은 `runs.backlog_id`와 폴더 내 문서 메타로 추적한다.
- 로컬 `episodes/` 디렉토리도 같은 규칙을 쓴다 (S3 이관 시 경로 구조 유지).

- **전체 비공개**가 기본값이다. 특히 `sources.md`(발췌)는 재배포 금지 증적(spec/01 5장)이므로
  공개 설정 실수가 곧 사고다 — 버킷 공개 차단(Block Public Access)을 켠 채 유지한다.
- **버킷은 파이프라인 전용으로 따로 둔다** (2026-09-01 확정 — 제품 `earcast-audio-prod`와 분리). 이유: 발췌를 서빙 경로 옆에 두지 않는다 · 워커·웹에 주는 권한을 이 버킷으로 한정한다 · 버저닝·수명주기 정책이 제품 버킷과 다르다. 규격: 비공개 · Block Public Access · 버저닝 ON · SSE-S3 · TLS 강제 · `sweeps/` 180일 만료 · 이전 버전 90일 정리 · IAM 정책은 `episodes/*`·`sweeps/*`·`datasets/*`의 Get/Put/List만(삭제 없음, 제품 버킷 권한 없음). **계정은 제품과 같은 ISB 계정**(리소스만 추가 — 임대 만료 시 이관 목록에 포함). **AWS 자격증명은 AI 서버 EC2의 인스턴스 역할 한 곳에만** — 로컬 워커는 웹의 서명 URL 라우트로 S3를 쓰고, IAM 사용자·액세스 키는 만들지 않는다. 생성은 [`pipeline/deploy/aws/setup-pipeline-bucket.sh`](../../../pipeline/deploy/aws/setup-pipeline-bucket.sh)(멱등) — 상세 [`pipeline/deploy/aws/README.md`](../../../pipeline/deploy/aws/README.md). M6에서 인스턴스 역할 `ear-ai-ec2`에 정책을 붙인다.
- 구축 시 이관: 로컬 `episodes/`·`sources/sweeps/`를 업로드하고 `runs.artifacts`의 `local:` 경로를 교체한다.
- 제품과의 접점은 하나뿐: 발행 확정된 배포본(mp3)을 제품 서빙 버킷(CloudFront+S3)으로 **복사**하는
  단방향 경로. 파이프라인 버킷을 제품이 직접 읽지 않는다.

## 3. 실행 계층 로드맵

> **채택된 운영 계획** (2026-08-27, 박수헌 결정 · API 전환의 팀 합의 항목은 미결 #12 유지):
> ① 고도화 단계 = 에이전트 구독 (사이클 반복, 프롬프트 자산 축적) →
> ② 대량 생성 단계 = API 워커 (자산 그대로 승계, 자동화) →
> ③ 파인튜닝 완료 후 = API의 생성 역할을 로컬 모델로 전환 (5장의 설계를 따름, TTS는 별도 트랙).
> 사이클의 골드 대본·피드백 아카이브는 ③의 파인튜닝 데이터셋 원료로 보존한다.

| 단계 | 실행기 | 트리거 | 가능해지는 것 |
|---|---|---|---|
| **0 — 현재** | 파이프라인 워커의 `claude-cli` 실행기 — 팀원 Mac에서 `claude -p`(구독, **API 키 없음**). spec/10 | 웹 UI의 승인·요청 → `jobs` 큐 — 방아쇠는 사람, 연쇄는 워커 | 반자동 — draft→QA→비평 자동 연쇄까지 (M1 검증 2026-08-31). AI 작업은 로컬 워커가 떠 있어야 진행 |
| **1 — API 워커** | 같은 워커의 **API 실행기**(`EXECUTOR=api`, API 키) — EC2 상주 (draft 1편 ≈ 30분이라 Lambda 15분 상한 부적합). 형태 확정(2026-09-01): Claude API 직접 호출 + 워커 소유 루프 — 3.1·spec/10 3.1. 켜는 시점은 미결 #12(G1). **스킬 파일 그대로 승계** | 0과 동일 (`jobs` 큐) — 로컬 워커 없이 서버가 AI 작업을 집는다 | 사람 Mac 의존 제거 · "선택 즉시 생성"이 서버에서 성립 · QA 독립성은 호출 단위 새 컨텍스트로 유지 |
| **2 — 스케줄 배치** | 1단계 워커 + 스케줄러(cron) | 시간 (정기 스윕·군집화) | 사람 개입 없는 정기 수집 |

- 1단계 전환은 팀 합의 사항이다 (API 비용 계정 + 구 A-6 재론 — 미결 #12).
- 각 단계 자동화 로드맵과의 의존 관계:

| 자동화 로드맵 | 전제 실행 계층 |
|---|---|
| 게이트 1 사전 심사 (spec/03 6.1 1단계) | 0에서도 가능 (군집화 스킬에 내장) |
| QA 자동 연쇄 (spec/05 7장 1단계) | **1 필요** |
| 정기 스윕 (spec/02 6장 모드 A 배치) | **2 필요** |
| 검수 항목 축소 (spec/07 3.1 1단계) | 0에서도 가능 (코드 게이트) |

- 스킬은 저장소에 커밋해 버전 관리하고(`prompt_version`), 사람과의 확인이 필요한 지점은
  자동 실행에서 상태 전환(`review_required` 등)으로 치환되도록 작성한다.

### 3.1 실행기 전환 계획 — 구독 → API → 파인튜닝 로컬 모델 (2026-09-01 확정)

관통 원칙: **모델을 바꿔도 바뀌는 층은 워커의 `executors/` 하나여야 한다.** 그래서 1단계(API)를 만들 때부터 2단계(로컬)를 겨냥해 "모델에게 도구를 주지 않고, 워커가 재료를 다 준비해 한 번에 주고, JSON으로 받는" 형태로 간다 — 로컬 모델 전환이 엔드포인트 교체로 끝나는 조건이다.

| | 0. 현재 | 1. API 실행기 | 2. 파인튜닝 로컬 모델 |
|---|---|---|---|
| 대본 생성 위치 | 팀원 Mac `claude -p`(구독) | AI 서버 EC2의 워커, `EXECUTOR=api` | 별도 GPU 서빙 엔드포인트(vLLM 등, OpenAI 호환) + 같은 워커 |
| 모델이 하는 일 | 파일 읽기·WebFetch·파일 쓰기·python 검사까지 에이전트 | 재료는 워커가 준비 → 모델은 **긴 입력 → JSON 출력** 1회 | 동일 (입력·출력 계약 그대로) |
| QA·비평 | 같은 구독 모델 | API 모델 | **당분간 API 모델 유지** — 파인튜닝은 문체·구성을 배우지 근거 검증은 못 배운다 |
| 전환 게이트 | — | **G1**: 미결 #12 비용 합의 + 회귀 세트(spec/09 7.1)에서 0단계와 동등 | **G2**: 데이터셋 하한 + 회귀 세트에서 API 대비 문체 축 우세·QA 통과율 유지 + 서빙 비용 수용 (미결 #22) |
| 되돌리기 | — | env 플래그. Mac 워커는 남긴다 | 단계별 플래그(`EXECUTOR_DRAFT=local`, `EXECUTOR_QA=api`) |

**1단계 — API 실행기** (형태 확정: Claude API 직접 호출, 워커가 루프 소유 — spec/10 3.1)

| 단계 | 워커가 준비 | 모델 호출 | 워커가 처리 |
|---|---|---|---|
| draft | 소스 원문 fetch·본문 추출(코드 — 풀 도메인 허용 목록 집행) + guidelines·골드·spec/04를 고정 접두(캐싱) | 1회 — 구조화 출력 `{sources_md, claims_md, script_md, …}` | L0 기계 검사(spec/09) → S3 |
| qa | 대본·claims·발췌 inline | 1회 — 판정 JSON + 리포트. 새 요청 = 독립성 자동 | 리포트 S3, 재생성 연쇄 |
| critic | 루브릭·guidelines·대본·골드 2 inline | 1회 — 점수·플래그 JSON | 동일 |
| cluster | (이미 단일 호출) | 그대로 | 그대로 |

- 지금 `claude -p`가 하던 WebFetch·파일 쓰기·python 검사가 전부 **워커 코드로 이동**한다 — 1단계 작업량의 본체이자 2단계를 공짜로 만드는 투자.
- 인터페이스: `packages/pipeline`의 산출을 프롬프트 문자열에서 **`PromptBundle {system 블록들(캐싱 단위), user, 출력 스키마}`**로 바꾸고, `claude-cli` 실행기는 파일 경로+텍스트로, `api` 실행기는 messages로 렌더링한다. 같은 번들을 두 실행기에 넣어 비교하는 것이 8장 "스킬 승계 검증"의 실체다.
- 위치·크기: AI 서버 EC2 워커 `CAPABILITIES=ai,io EXECUTOR=api`. I/O 대기 작업이라 t4g.small로 충분, 동시성은 작업 수로. 서버리스(Lambda)는 draft 30분급이라 부적합.
- G1 비용 자료는 0단계에서 쌓인다 — `claude -p`의 정가 환산 비용·토큰을 `runs`에 남기면(0009) 월 API 비용이 추정이 아니라 집계로 나온다.

**2단계 — 파인튜닝 로컬 모델** (5장)

- 끼우는 자리: 1단계 실행기의 클라이언트만 OpenAI 호환 엔드포인트로 바꾼 `local` 실행기. 출력 스키마는 서빙 쪽 guided JSON으로 강제. 서빙은 **AI 서버 EC2가 아닌 별도 GPU 엔드포인트** — AI 서버는 오케스트레이션·IO·경량 추론만.
- 투입 순서: **draft부터** 로컬(파인튜닝 대상 = 문체·구성), QA·비평은 API 모델 유지. 비평 이관은 사람 판정 κ 확보 후 별도 게이트.
- 데이터셋: 입력 = 발췌·후보 정보·자산 버전 / 목표 = **사람 판정·수정을 거친 최종 대본** / 라벨 = QA 판정·비평 점수·사람 플래그 판정 — 지금 파이프라인이 매 편 만드는 것 그대로라 export 스크립트 하나(`datasets/`). G2 하한: 승인 대본 **150~300편**(제안, 미결 #22).
- 임베딩(ai-server, `text-embedding-3-small`)의 로컬 전환은 차원 변경 = `content_embeddings` 전량 재생성이라 별도 결정.

**0단계에서 심어두는 것** — ① `runs`에 비용·토큰·워커 커밋 SHA(0009) ② `episodes.asset_versions` 고정(spec/10 3.2) ③ S3 `datasets/` 접두사(2장) ④ 회귀 세트를 지금부터 고정(spec/09 7.1) ⑤ 사람 판정은 빠짐없이 DB에(이미 그렇게 함).

## 5. 로컬 모델 전환 설계 (LLM·TTS)

전환을 지금 결정하지 않되, **나중에 결정할 수 있는 구조**를 유지한다.

1. **호출 추상화** — 실행 계층 1에서 LLM 호출부를 얇은 인터페이스로 감싼다. 로컬 서빙(vLLM 등)은
   호환 API를 제공하므로, 호출부가 얇으면 전환은 엔드포인트 교체다. 그래서 1단계 API 실행기를 Agent SDK
   하네스가 아니라 **직접 호출 + 워커 소유 루프**로 만든다(3.1) — 로컬 전환 시 이행 작업이 없다.
2. **산출물 계약이 이식성의 근간** — 대본·claims·상태 전이 스키마는 모델 무관 계약이다.
   모델을 바꿔도 파이프라인의 나머지는 영향받지 않는다.
3. **전환 판단은 데이터로** — `runs.model`에 실행 모델을 기록한다. QA 통과율·재생성률·게이트 2
   반려율을 모델별로 비교해, "후보 모델이 기준 모델 대비 합의된 격차 이내"를 전환 조건으로 삼는다.
4. **투입 순서 (2026-09-01 개정)** — 원안(QA → 군집화 → 대본)은 범용 로컬 모델을 전제했다. 파인튜닝 모델은 대본의
   문체·구성을 배운 모델이므로 **draft부터** 투입하고, 근거 검증(QA)·판정(비평)은 API 모델에 남긴다. 각 단계 전환은
   회귀 세트(spec/09 7장)에서 3의 지표로 판정한다(G2 — 3.1, 미결 #22).
5. **TTS는 별도 트랙, 그리고 보이스 종속성이 핵심 리스크** — TTS는 편수 비례 비용이라 로컬 실익이
   LLM보다 먼저 온다. 단 ElevenLabs 보이스 ID는 플랫폼 자산이라 **이관 불가** — 엔진 교체 = 강제
   리브랜딩이다. 완화 경로는 자체 보이스 확보(성우 녹음 기반)이며, 보이스 확정(미결 #8) 시 함께
   결정한다. 오디오 태그(`[curious]` 등)도 엔진 종속 문법이므로 교체 시 변환이 필요하다.
6. **데이터셋과 적법성** — 목표 데이터(우리 대본·사람 수정)는 문제없다. 제3자 발췌(`sources.md`)를 학습 *입력 컨텍스트*로
   쓰는 범위는 미결 #21(법률 검토 #1과 함께). 전사본(`references/*.txt`)은 어떤 형태로도 학습에 넣지 않는다. export는
   `datasets/`(2장), 규모 하한과 게이트는 3.1.

**실익 평가 (설계 시점 판단)**: 월 100편 규모에서 LLM은 API가 로컬 GPU 서버보다 저렴할 가능성이
높다 — LLM 로컬화의 실익은 비용보다 데이터 통제·종속성 회피다. 비용 실익이 먼저 오는 쪽은 TTS이며,
로드맵상 로컬 검증의 우선순위도 TTS가 앞이다. G2에는 "1단계 월 API 비용(`runs` 집계) vs GPU 서빙 비용" 비교를 숫자로 넣는다.

## 8. 완료 조건

- Given 팀원 A가 후보를 적재한다 / When B가 조회한다 / Then 동기화 작업 없이 같은 목록이 보인다
- Given 에이전트의 모든 쓰기 / When `runs`·상태 전환을 확인한다 / Then `executed_by`와 (실행 계층 1부터) `model`이 기록되어 있다
- Given S3의 발췌 파일 / When 접근 권한을 확인한다 / Then 팀 계정·에이전트 외에는 접근 불가하다 (공개 차단 활성)
- Given 실행 계층 1 / When 사람이 UI에서 승인한다 / Then 별도 조작 없이 생성이 시작되고, QA까지 자동 연쇄된다
- Given 같은 스킬 버전의 두 실행 / When 실행 계층 0과 1에서 각각 수행한다 / Then 같은 절차·같은 산출물 규격을 따른다 (스킬 승계 검증)
- Given 후보 모델의 시험 투입 / When `runs`를 집계한다 / Then 모델별 QA 통과율·재생성률 비교가 나온다
- Given 규칙 자산이 웹에서 활성화된다 / When 어느 워커가 다음 작업을 집는다 / Then 체크아웃 상태와 무관하게 같은 active 번들을 읽고 `runs.prompt_version`에 그 버전이 기록된다
- Given 실행기 전환 후보(API·로컬) / When 회귀 세트를 같은 번들로 두 실행기에서 돌린다 / Then QA 통과율·비평 점수·κ·비용 비교표가 나오고 G1/G2 판정이 가능하다
