# spec/05 — QA

> 상위: [PIPELINE.md](../PIPELINE.md) · 앞: [spec/04 대본](04-script.md) · 뒤: [spec/06 오디오](06-audio.md) · [spec/07 발행](07-publish.md)
> 실행 주체: AI (**독립 실행**) · 입력: `drafted` 에피소드 · 상태: `drafted` → `qa_passed` | `review_required`
> 원칙: QA는 **사실 무결성 검증**이다 — "대본이 소스가 말한 것만, 소스가 말한 만큼만 말하는가."

## 1. 목적 — 하는 것과 하지 않는 것

| QA가 하는 것 | QA가 하지 않는 것 |
|---|---|
| 환각 금지 원칙의 집행 — 대본의 모든 사실 주장을 소스와 대조 | "만들 가치가 있는가" — 게이트 1의 몫 |
| 규격 준수 검사 (시그니처·금칙·길이·화자 규칙) | 재미·구성·완성도 평가 — 게이트 2(사람)의 몫 |
| 게이트 2 앞의 자동 필터 + 재생성 루프 | **사람 검수의 대체** — 게이트 2는 유지된다 |

취향 판단을 섞지 않는다 — 판정이 기계적이어야 재생성 루프가 수렴한다.

## 2. 입력 — 세 가지뿐

1. 소스 발췌 (`sources.md`)
2. 대본 (`script.md`)
3. claims 대조표 (`claims.md`)

**대본 작성 중의 판단·맥락은 전달하지 않는다.** 작성 컨텍스트가 자기 글을 검사하면 같은 맹점을
공유한다(자기가 만든 환각을 자기가 정당화). 입력 3종 외의 정보가 없는 것이 독립성의 정의다.

## 3. 검사 항목

| # | 항목 | 검사 내용 | 판정 방식 |
|---|---|---|---|
| 1 | 사실 일치 | 대본의 주장이 발췌 내용과 일치하는가 | LLM 대조 |
| 2 | 미근거 | 발췌에 없는 수치·인용·고유명사·결론이 추가됐는가 (환각) | LLM 대조 |
| 3 | 왜곡 | 주장 강도가 소스보다 세졌는가 ("~일 수 있다" → "~이다") | LLM 대조 |
| 4 | 누락 | 필수 맥락이 빠져 오해를 만드는가 | LLM 대조 |
| 5 | 시그니처 템플릿 | tpl-v1 골격(인트로·마무리)이 변형 없이 포함되고 {슬롯}만 채워졌는가 · 두 {주제 한 줄 요약}이 같은 말인가 · 마무리 뒤 추가 클로징 턴 없음. 고지 문구는 대본에 넣지 않으므로 검사하지 않는다 | **코드 검사 가능** (qa-v1.2에서 판정 활성) |
| 6 | 금칙 | 낭독 규격 위반 — 영문 표기·표·URL·시점 고정 표현·숫자 표기 | **코드 검사 가능** |
| 7 | 길이 | 분량 기준(15분 환산) 충족 | **코드 검사 가능** |
| 8 | 화자 — 사실 주장 위치 | 수치·인용·고유명사·인과 주장이 해설 턴에만 있는가 | LLM + 부분 코드 |
| 9 | 화자 — 리액션 강도 | 진행 턴의 리액션이 주장 강도를 올리지 않는가 | LLM 대조 |
| 10 | 화자 — 정합 | 턴 라벨·역할 배정(`topics.explainer`)·페르소나 말투가 규격과 맞는가 | LLM + 부분 코드 |

- 1~4번이 핵심(사실 무결성)이고, claims 대조표가 그 검증의 지도다 — claims에 매핑되지 않은
  사실 주장이 대본에 있으면 그 자체로 실패(2번)다.
- "판정 방식" 열은 자동화 로드맵(7장)의 분류 기준이다 — 코드로 가능한 검사는 코드로 옮긴다.

## 4. 판정·재생성

```
QA 실행 → 전 항목 통과 → qa_passed
        → 실패 → 실패 항목·사유·위치를 피드백으로 재생성 (spec/04) → 재QA
                   └ 최대 3회. 3회 실패 → review_required (사람 이관 — 자동 통과 경로 없음)
```

- 모든 시도는 `attempt`(1~3)로 구분해 기록한다 — 통과율·재생성률 집계의 원천.
- 실패 사유는 구체로 쓴다 ("E3 턴의 '107분'이 발췌에 없음") — 다음 생성의 입력이 되기 때문이다.
- `review_required`에서 사람이 수정하면 재QA를 거쳐 `qa_passed`로, 포기하면 `rejected`로.

## 5. 독립 실행 규약

- QA는 대본을 만든 실행과 **다른 실행**에서 수행한다.
  - 현재(스킬): 새 세션 또는 독립 컨텍스트의 서브에이전트로 `/qa <후보 id>` 실행.
  - API 이행 후: 작성 호출과 QA 호출이 물리적으로 다른 API 요청이므로 독립성이 **구조적으로 보장**된다.
- QA 실행은 입력 3종을 저장소(S3)에서 직접 읽는다 — 작성 실행이 건네주는 방식을 쓰지 않는다
  (건네주는 구조는 작성 쪽이 유리한 맥락을 끼워 넣을 통로가 된다).
- **재QA도 매번 새 컨텍스트다** — 실패 피드백은 작성 쪽으로만 흐르고, 재생성본을 검사하는 QA는
  이전 회차 판정을 기억하지 않는 새 실행으로 수행한다.
- 컨텍스트 분리 후에도 남는 편향은 동일 모델 사용(자기 선호)이다. QA가 취향 평가가 아니라
  발췌 대조이므로 영향은 제한적이나, 보강 옵션은 7장 3단계(교차 모델 판정)에 둔다.

## 6. 실행·기록

- 인터페이스: `/qa <후보 id>`. 현재는 사람 트리거.
- `runs` 기록: `phase=qa`, `attempt`, `result`(통과/실패 + 실패 항목 요약), `prompt_version`,
  `artifacts`(QA 리포트 경로), `executed_by`.
- 집계 지표: QA 통과율 · 재생성 발생률 · 항목별 실패 분포 — `prompt_version`별 비교로
  대본 프롬프트 개선의 근거가 된다.

## 7. 전체 자동화 로드맵

QA는 판정 주체가 이미 AI이므로, 자동화의 대상은 **트리거·판정 방식·신뢰도**다.
게이트 1 자동화([spec/03](03-backlog.md) 6.1)와 달리 불변 원칙과 충돌하지 않는다 — 단계 전환은 기술 검증만으로 가능하다.

| 단계 | 내용 | 전환 조건 |
|---|---|---|
| **0 — 현재** | 사람이 `/qa` 트리거, LLM이 전 항목 판정. **품질 사이클 기간에는 테스트 생성본 포함 매 생성마다 실행** — QA 자체의 검출력 실측을 함께 시작한다 (7.1) | — |
| **1 — 자동 연쇄** | `drafted` 전환 시 QA가 자동 실행 (API 워커의 draft→qa 연쇄). 재생성 루프도 자동 | API 실행기 도입 (spec/08) |
| **2 — 결정적 검사의 코드화** | 3장에서 "코드 검사 가능"으로 표시된 항목(5·6·7, 8·10 일부)을 LLM 판정에서 **코드 게이트**로 이전 — 재현 가능·비용 0·오탐 없음. LLM은 사실 대조(1~4, 9)에 집중 | 템플릿 확정(미결 #7)·분량 확정(미결 #6) 후 순차 이전 |
| **3 — 판정 신뢰도 강화** | 사실 대조를 항목별 독립 판정으로 분리하고, 경계 판정은 복수 실행 후 불일치 시 `review_required`로 — "애매하면 사람에게"를 판정 구조에 내장. 자기 선호 편향 보강이 필요하면 **작성과 다른 모델을 판정에 교차 투입** | 2단계 안정화 + 판정 비용 실측 |
| **4 — 검출률 실측** | 게이트 2에서 사람이 잡은 결함 중 QA가 놓친 것(누검출)을 기록·집계하는 절차를 검수 체크리스트에 추가 (spec/07). 이 데이터가 QA 신뢰도의 실측치다 | 3단계와 병행 |

- 4단계의 검출률 데이터는 **게이트 2 축소(무검수 비율 상향) 논의의 전제 조건**이다. 단 그 논의 자체는
  QA 자동화가 아니라 게이트 2의 결정이며, 별도의 팀 합의를 거친다 (누검출률 목표치 합의 — PIPELINE.md 7장 #15).
- 어느 단계에서도 `review_required`의 사람 이관 경로는 제거하지 않는다.

### 7.1 QA 자체 검증 — 심은 오류 프로브 (2026-08-28 신설)

QA의 검출력 역시 처음부터 좋다는 보장이 없다 — 대본과 마찬가지로 **실행하고 실측하는 루프**가
필요하다. 자연 발생 오류를 게이트 2 대조로 기다리는 방식(4단계)만으로는 데이터가 느리게 쌓인다
(잘 쓴 대본일수록 오류 발생률이 낮아, QA가 잘하는지 확인할 재료 자체가 안 생긴다). 그래서
검출률을 직접 측정하는 프로브를 병행한다.

- **방법**: 완성 대본의 사본에 유형별 오류를 의도적으로 심는다 — 수치 변형(항목 1) ·
  미근거 주장 추가(2) · 강도 상승(3) · 오귀속(1) · 진행 턴 사실 주장(8) · 리액션 강도(9) ·
  시점 고정 표현(6). 정답지는 별도 보관하고 **QA 실행에는 반입하지 않는다** (블라인드 —
  파일 경로에서도 프로브임이 드러나지 않게 한다).
- **측정**: 검출률 = 잡은 오류 / 심은 오류 · 오탐 = 심지 않은 부분에 대한 지적.
  검사 항목 유형별로 집계해 QA의 강한 검사와 약한 검사를 식별한다 — 약한 유형이
  QA 프롬프트 개선의 우선순위다 (대본 사이클과 같은 개선 루프를 QA 프롬프트에도 돈다).
- **기록**: `runs`에 `phase=qa`, result에 프로브 여부와 검출률 표기. 사이클 기간에는
  QA 프롬프트 버전마다 1회 이상 실행한다.
- **안전**: 프로브 대본 원본은 저장소 밖(작업용 임시 경로)에 두고, 저장소에는 정답지와
  결과 리포트만 남긴다 — 프로브 대본이 발행 경로에 들어갈 가능성을 구조적으로 차단한다.
- 프로브(합성 검출률)와 게이트 2 대조(자연 누검출률, 4단계)를 합쳐 미결 #15의 실측 데이터가 된다.

## 8. 완료 조건

- Given `drafted` 에피소드 / When QA를 실행한다 / Then 작성 실행과 분리된 컨텍스트에서 입력 3종만으로 판정된다
- Given claims에 매핑되지 않은 사실 주장이 대본에 있다 / When 검사한다 / Then 미근거(2번)로 실패한다
- Given 진행 턴에 수치·고유명사가 있다 / When 검사한다 / Then 화자 규칙(8번) 위반으로 실패한다
- Given QA 실패 / When 재생성한다 / Then 실패 항목·사유·위치가 다음 생성의 입력으로 전달되고 attempt가 증가한다
- Given 3회 실패 / When 한도에 도달한다 / Then `review_required`로 전환되고 자동 통과되지 않는다
- Given 한 달치 실행 기록 / When 집계한다 / Then `prompt_version`별 통과율·재생성률·항목별 실패 분포가 나온다
