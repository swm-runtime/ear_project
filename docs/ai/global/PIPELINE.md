# ear 글로벌 콘텐츠 파이프라인 — 종합 명세 (초안)

> 작성: 2026-10-14 · 상태: **초안** — 10장의 미결 중 선행 결정(G0)이 끝나야 구축에 들어간다. 확정: #1 분리 단위 · #2 주제 체계 · #3 배제 범위 · #6 로마자 표기 · #8 발행 경로 · #12 일본어판(1단계 범위 밖) · #14 API 제공자(OpenAI)(2026-10-14). G0에 남은 것은 #4 페르소나(사용자 결정 대기).
> 이 문서는 한국판 [PIPELINE.md](../PIPELINE.md)와 **분리된 독립 명세**다. 한국판 명세·자산·DB를 바꾸지 않는다.
> 한국판 단계 명세(spec/01~09)에서 가져온 규칙은 **2026-10-14 시점의 내용을 승계**한 것이다. 이후 한국판이 바뀌어도 자동으로 따라가지 않는다 — 따라갈지는 건마다 이 문서에서 정한다.

**표기**: 각 규칙 끝에 출처를 붙인다 — `승계`(한국판 그대로) · `개정`(한국판을 바꿔서) · `신설`(글로벌판에만) · `제안`(결정 대기, 10장에 미결로 등록).

## 1. 개요

**동남아·일본의 영어 사용 청취자**에게 **K-컬처를 해설하는 영어 2인 대화 팟캐스트**를 만드는 파이프라인이다.

### 1.1 한국판에서 분리하는 이유

주제(자기계발 → K-컬처)·청취자(국내 2030 직장인 → 해외 영어 청취자)·언어(한국어 → 영어)가 모두 다르다. 한국판의 규칙 자산(주제 체계·소스 풀·페르소나·guidelines·루브릭·골드·음차 사전)은 어느 것도 그대로 쓸 수 없고, 섞이면 서로의 회귀를 깨뜨린다. 반면 **단계 구조·불변 원칙·실행 기계**는 주제와 무관하므로 재사용한다. 무엇을 공유하고 무엇을 가르는지는 4장.

### 1.2 핵심 성격

- **주제 우선(기획형)** `개정` — 한국판은 소스에서 주제가 도출된다(소스 우선). 글로벌판은 **사람이 주제를 기획하고 AI가 근거를 찾는다.** 소스 풀을 먼저 채우고 RSS를 돌리는 단계(한국판 모드 A 스윕·군집화)가 없다. 단, **근거가 성립하지 않는 주제는 후보가 되지 못한다** — 순서만 뒤집혔고 "근거 없는 에피소드 없음"은 그대로다.
- **사람이 결정, AI가 준비** `승계` — 주제 기획·게이트 1 승인·도메인 판정·게이트 2 발행은 사람만 한다. 단 **대본 판정(플래그·점수·직접 수정)은 에이전트가 맡는다** `개정` (2026-10-16) — 팀에 영어 대본의 질을 판단할 사람이 없다. 발행 버튼은 에이전트가 발행 가능으로 판정한 편에만 열린다(6.10).
- **공유 상태** `승계` — 후보·진행 상태는 운영 DB에 있고 팀 전체가 같은 것을 본다. 단 **한국판과 다른 DB**다(4장).

### 1.3 표준 포맷

- 편당 **하한 5분 필수 · 평균 목표 없음 · 상한 없음** `개정` (2026-10-17 — 한국판과 달리 출퇴근길 같은 청취 상황을 가정하지 않는다. 한국판은 하한 13분·평균 15분). 길이는 재료가 정한다. 분할 제안은 재료가 20분 이상일 때만.
- 영어 2인 대화체. 1인 낭독은 채택하지 않는다 `승계`.

## 2. 주제 체계 — K-컬처

진실 원천은 글로벌 인스턴스의 `topics` 테이블이다 `승계`.

**주제 8개 · 1단계 확정** (2026-10-14). 8개 아래 중분류를 두지 않는다 — 사용자가 고르는 관심 주제도 이 8개다. 초기 콘텐츠가 적을 때 주제를 잘게 나누면 빈 주제가 늘어난다. 콘텐츠가 쌓이면 그때 나눈다. 주제별 주의 사항도 확정(2026-10-14).

- **파이프라인 `topics` 저장** (2026-10-14) — 1단계라 행마다 `major` = `mid` = 주제 이름, `explainer`는 비운다(해설 고정, 6.4). 대분류 단위로 붙는 설정(인트로 한 줄·썸네일 띠 색)이 주제마다 하나가 된다. slug는 `note`에 `slug k-pop` 형식으로 적어 둔다(파이프라인 표에 slug 칸이 없다). 콘솔 주제 화면은 글로벌판에서 대분류 칸을 숨긴다.
- `slug`는 제품 GLOBAL 주제 행의 안정 키다(`spec/api/global-api.md` 4.5 — 앱의 주제 이미지 매핑 키). 영어 이름을 소문자·하이픈으로 바꾼 값으로 **확정**(2026-10-14) — BE 적재는 KAN-189. 제품 `parent_category`는 1단계라 비워 둔다(NULL 허용).
- **겹치는 주제는 두 개를 붙인다** `확정` (2026-10-14) — 한 편에 주제 **최대 2개**. 첫째가 **대표 주제**이고, 하나만 붙는 칸(인트로의 주제 한 줄 · 썸네일 띠 색)은 대표 주제를 따른다. 예: "명절 음식은 왜 기름진가" = K-Food(대표) + Korean Culture. 두 주제의 관심 사용자 모두에게 추천 후보가 된다 — 제품 `content_topics`는 이미 다대다다(`backend/domain.md` 5.2).
  - 파이프라인 백로그는 주제 칸이 하나(`mid_topic`)라 **보조 주제 칸을 추가한다**(G2, 공유 코드의 마이그레이션 — NULL 허용이라 한국판 행에는 영향 없음). 컬럼 이름·형식은 구현 시 `schema.sql`에서 정한다.
  - 두 번째 주제는 "그 주제 관심 사용자가 들어도 납득할 만큼 축이 걸쳐 있는가"로만 붙인다. 소재가 스치는 정도로 붙이지 않는다 — 추천이 넓어지는 대신 주제 필터의 신뢰가 떨어진다.
- **노출(`is_visible`)은 사람이 켠다** — 콘텐츠가 있는 주제만 `승계`.
- 체계 변경 시 함께 갱신할 것: 템플릿의 주제 한 줄(한국판 `templates.major_lines`에 해당 — 글로벌판은 주제마다 한 줄), 썸네일 주제 색, 제품 측 GLOBAL 주제 행(`topics.market = global` · `slug` — BE가 적재, `spec/api/global-api.md` 4.5).

### 2.1 배제 주제 `확정` (2026-10-14)

한국판 `일` 대분류 AI 배제처럼, 아래는 기획 단계에서 받지 않는다.

| 배제 | 이유 |
|---|---|
| 실존 연예인·공인의 사생활·열애·논란·사건·소송 | 명예훼손·퍼블리시티권, 루머성 소스 의존, 환각 금지 원칙과 정면 충돌 |
| 진행 중인 정치 현안·남북 군사 현안 | 시의성 노후화, 해외 청취자 대상 정치적 리스크 |
| 특정 기획사·브랜드의 홍보성 주제 | 광고성 콘텐츠로 오인 |

- 실존 인물은 **공적 활동의 확인 가능한 사실**로만 언급할 수 있다(예: 데뷔 연도, 공식 수상). 주제의 축이 한 사람이 되는 기획은 받지 않는다.

## 3. 전체 흐름

```
[기획]  주제 기획 ───── 사람: 주제 1~2개 + 주제(제목안) + 메모        ← 유일한 입구 (주제 풀·RSS 스윕 없음)
   ↓
[탐색]  소스 탐색 ───── AI(서버 API): 웹 검색으로 소스 발견 (메타데이터만, 검색 8회 상한)
   ↓
[구성]  후보 구성 ───── AI: 군집화 v2 "주제 고정·축은 소스에서" → 축·역할표·다양성 판정
   ↓      성립 → proposed · 미달 → held + gaps (보강 1회)
[판정]  도메인 판정 ─── 사람: 후보 소스의 candidate 도메인 판정 (AI 증거 수집 보조)
   ↓  ★게이트 1 — 사람 승인 (자동 승인 없음 · 판정 대기 도메인 0이어야 승인 가능)
[제작]  설계(원문 정독) → 작성 ── 2단계 초안
   ↓
[검증]  L0 기계 검사(영어판) → QA(사실) → 비평(영어 루브릭) — 앞 층 실패 시 재생성 (최대 3회)
   ↓
[판정]  에이전트 판정 ── 원어민 편집 · 한국어·사실 검토 → 필수 수정 반영 (6.10)
   ↓
[음성]  TTS → 썸네일 ── 영어 보이스 + 한국어 고유명사 발음 사전
   ↓
[출고]  패키지 ───────── 업로드 메타 산출
   ↓  ★게이트 2 — 사람 최종 검수
[발행]  업로드·기록 ──── 같은 제품 서버에 market=global 로 발행 (global-api 4.9)
```

**상태 전이** `승계` — 한국판과 같은 `backlog.status` 머신을 쓴다.

```
proposed ─승인→ approved ─집기→ claimed → drafted → qa_passed → packaged ─업로드→ published
   │               │                            │
   └ rejected      └ expired          qa_failed ─(3회)→ review_required → qa_passed | rejected
   └ held (기획 검색 진행 중 · 빈 역할 · 사람 판단 보류)
```

## 4. 분리 설계 — 무엇을 가르고 무엇을 공유하는가

### 4.1 완전히 분리하는 것 `신설`

| 대상 | 글로벌판 |
|---|---|
| 운영 DB | **별도 Supabase 프로젝트** — `topics`·`domains`·`sources`·`backlog`·`episodes`·`runs`·`jobs`·`settings`·`prompt_assets` 전부 별개. 한국판 DB에 글로벌 행을 넣지 않는다 |
| 산출물 저장소 | **별도 S3 버킷**(이름 미정) — 대본·발췌·claims·오디오·썸네일 |
| 규칙 자산 | `prompt_assets` 8종 전부 새로 작성 — guidelines · 골드 3 · QA 프롬프트 · 루브릭 v1/v2 · 발음 사전 (+ 썸네일 프롬프트·장면 규칙) |
| 워커 프롬프트에 들어가는 명세 장 | `docs/ai/global/spec/` 에 별도 파일 (한국판 spec/03 군집화 기준 · spec/04 3~6장 · spec/05 3장에 해당하는 것). 영어로 쓴다(4.5) |
| 템플릿·설정 | `settings.templates`(인트로·클로징·주제 한 줄) · 보이스 · 자동화 스위치 |
| 주제 체계·소스 풀 | 2장 · 6.2 |

### 4.2 공유하는 것 `확정` (2026-10-14) — 코드는 하나, 인스턴스가 둘

**`pipeline/` 코드(웹·워커·packages)를 공유하고, 언어 종속 부분만 `PIPELINE_LOCALE`(`ko` 기본 · `en`)로 교체한다.** 같은 코드로 두 인스턴스(한국판·글로벌판)를 띄우며, 각 인스턴스는 자기 DB·버킷·자산만 본다.

- 이유: 큐·연쇄·장애 복구·S3 동기화·자산 버전 고정 같은 실행 기계는 주제와 무관하다. 코드를 포크하면 워커 버그 수정·연쇄 개선을 두 번씩 해야 하고, 3인 팀에서는 한쪽이 반드시 뒤처진다.
- 채택하지 않은 대안: 코드 포크(`pipeline-global/` 복제). 한국판에 영향을 주지 않는 독립성은 가장 높지만 위 비용이 있다. 글로벌판이 구조 자체를 크게 달리하게 되면 다시 검토한다.
- 공유의 대가: 공유 코드를 고칠 때 한국판이 깨지지 않는지 확인해야 한다 — 4.3의 "한국판 무변경" 조건과 11장 완료 조건이 그 검증이다.
- 함께 쓰는 외부 자원: AI 모델·API 실행기 코드 · ElevenLabs 계정 · 썸네일 이미지 모델 · `ai-server` 임베딩 API(호출만 공유, 벡터 저장은 발행처 몫). 실행 위치는 4.4.

### 4.4 실행 위치 — 서버 워커 + API 실행기만 `신설` (2026-10-14 결정)

글로벌판은 **노트북 워커(claude-cli 실행기, 팀원 구독)를 두지 않는다.** 주제 기획의 검색을 포함한 모든 AI 단계(탐색·후보 구성·설계·작성·축 심사·QA·비평·장면·추천 메타)를 **서버 워커가 API 실행기로** 처리한다.

- 한국판은 주제 기획(B-②)과 보강(B-①)이 검색 도구를 써야 해서 노트북 claude-cli 워커만 집을 수 있다. 서버의 OpenAI 실행기는 도구가 필요한 작업을 거절한다(한국판 spec/10 2장). 그래서 **API 실행기에 웹 검색을 붙이는 것이 G2의 구현 항목이다.**
  - **제공자는 OpenAI** `확정` (2026-10-14) — 한국판 서버 워커와 같은 OpenAI 실행기에 OpenAI의 웹 검색 도구를 붙인다(단발 호출 + 검색 도구). 단계별 모델은 한국판 서버 기본값(`gpt-6.1-sol`)에서 시작한다. 편당 비용 상한은 10장 #14.
  - 검색 결과는 **코드가 거른다** — 차단·보류 도메인, robots 불허, 이미 판정된 배제 도메인을 결과에서 빼고 남은 것만 적재한다. 제공자에 도메인 제외 옵션이 있으면 함께 쓰되, 그것만 믿지 않는다.
  - 검색 8회 상한은 실행기가 호출 단위로 센다. 검색 요약 텍스트를 산출물 근거로 쓰지 않는다는 규칙(6.1)은 그대로다 — 실행기는 링크·제목·스니펫만 결과 스키마로 받는다.
- 서버 워커 설정은 `CAPABILITIES=ai,io`, 실행기는 API다. 큐를 두고 경쟁할 노트북 워커가 없으므로 한국판의 "켜는 동안 노트북 워커를 끈다" 제약도 없다.
- **QA 독립성**은 API에서 구조적으로 보장된다 — 작성 호출과 QA 호출은 물리적으로 다른 요청이다(한국판 spec/05 5장).
- **비용**은 구독이 아니라 API 과금이다. `runs`에 단계별 사용량×단가를 남기고(한국판 OpenAI 실행기 계측 방식 승계), 편당 비용 상한을 정한다(10장 #14).

### 4.5 규칙 자산의 언어 — 영어 대본 기준 `신설` (2026-10-14 결정)

**대본 작성 규칙·검수 기준은 전부 영어 대본을 기준으로 새로 쓴다.** 한국판 규칙을 번역하는 것이 아니라, 영어 대화체 팟캐스트의 기준으로 다시 세운다.

- **한국판에서 가져오는 것은 동작뿐이다** `확정` (2026-10-14) — 단계 구조·큐·연쇄·게이트·저장·실행기(4.2)만 공유한다. 대본·QA·비평의 **규칙 내용과 프롬프트 지시문은 승계하지 않고 영어판 규칙 설계에서 처음부터 정한다.** 6.4~6.6에 `승계`로 적힌 규칙(금지 규칙 1~6, QA 항목 1~10, 비평 구조 등)은 그 설계의 출발 후보일 뿐 구속하지 않는다. 한국판 프롬프트 빌더를 번역해 쓰지 않는다(4.3 "프롬프트 빌더").

| 자산 | 기준 | 작성 언어 |
|---|---|---|
| guidelines (대본 작성 규칙) · 골드 3 · 템플릿 | 영어 대화체 대본 | 영어 |
| `docs/ai/global/spec/` 프롬프트용 명세 장 (군집화 기준 · 대본 규격 · QA 항목) | 〃 | 영어 |
| QA 프롬프트 · 비평 루브릭 v1/v2 | 영어 대본을 판정하는 기준 | 영어 |
| L0 기계 검사 규칙 | 영어 문체·형식 (4.3) | 코드 |
| 발음 사전 · 썸네일 프롬프트·장면 규칙 | 영어 TTS · 영어 제목 | 영어 |
| 게이트 2 체크리스트 · 에이전트 판정 지시문(`docs/ai/global/judge/`) · 판정 화면 | 영어 대본을 검수하는 기준 | 지시문은 영어, 판정 사유·요약 리포트·화면 문구는 한국어(팀이 읽는다) |
| 이 문서(명세 인덱스) | — | 한국어(팀 문서 규칙) |

- 모델이 읽는 자산을 영어로 쓰는 이유: 규칙 문장과 출력 언어가 같아야 표현 규칙(어조·금칙어·시점 표현 목록)을 예시 그대로 대조할 수 있고, 규칙 문구가 대본으로 새는 사고(한국판 "규칙 용어 누출")를 언어 차이로 놓치지 않는다.
- 한국판의 규칙 자산 작성 원칙(모델이 읽는 글 — 단문·기능 서술, 근거는 CHANGELOG에만)은 그대로 따른다(7장).

## 5. 불변 원칙

한국판 7개를 기준으로 고친다. 단계 명세가 바뀌어도 유지되는 상위 규칙이다.

1. **주제 우선, 근거 필수** `개정` — 주제는 사람이 기획하지만, 후보는 실소스로 성립해야 생긴다. 근거가 모이지 않는 기획은 `held`에서 멈추고 대본으로 가지 않는다. (6.1·6.3)
2. **적법한 소스만, 판정 후 승인** `개정` — 탐색은 풀 밖에서도 하지만 차단·보류 도메인·robots 불허·페이월·로그인 뒤는 배제한다. 풀 밖에서 온 도메인은 `candidate`로 등록되고, **후보의 모든 소스 도메인이 사람 판정을 마쳐야 게이트 1을 통과할 수 있다.** (6.2·6.3)
3. **탐색은 메타데이터만, 원문은 승인 후 건당** `승계` (6.1·6.4)
4. **환각 금지 + claims 대조** `승계` — 국문 소스를 영어로 옮기는 과정의 의미 변형도 환각으로 본다. (6.4·6.5)
5. **소스 3건 하한** `승계` — 미만이면 대본을 쓰지 않는다. 단일 소스를 뼈대로 삼지 않는다.
6. **게이트 두 개 모두 사람** `개정` — 한국판은 게이트 1을 조건부 자동화했지만, 글로벌판은 소스가 풀 밖에서 오므로 자동 승인을 두지 않는다. 승인자·시각을 기록한다. 검수 없는 발행 경로는 없다. 게이트 2의 대본 검수는 에이전트 판정이 하고, 사람은 그 판정을 통과한 편만 발행한다(6.10).
7. **QA 독립 실행** `승계`
8. **실존 인물 보호** `신설` (2026-10-14) — 실존 인물의 사생활·논란·미확인 사안을 다루지 않고, 썸네일에 실존 인물의 얼굴을 그리지 않는다. (2.1·6.8)
9. **음원·가사·영상 대사를 쓰지 않는다** `신설` — 오디오에 음악을 넣지 않고, 가사·대사를 낭독하지 않는다. K-pop·드라마를 다루는 편도 말로만 해설한다.

## 6. 단계별 규칙

### 6.1 주제 기획·소스 탐색 — 한국판 spec/02 B-② 기반

**입력** (사람, 콘솔 주제 기획 화면) `승계`

| 칸 | 내용 |
|---|---|
| 주제 | 2장의 8개 중 1~2개 — 첫째가 대표 주제. 기획 시점의 선택은 잠정이고, 후보 구성(6.3)이 축을 세운 뒤 보조 주제를 더하거나 뺄 수 있다(대표 주제는 사람이 정한 그대로) |
| 주제(제목안) | 에피소드가 답할 질문 또는 주장 — "X란 무엇인가"형이 아니라 축이 보이는 문장을 권장 |
| 메모(hint) | 각도·꼭 다룰 것·피할 것·참고 링크 |

- **일괄 기획 입력** `제안` — 주제 풀이 없으므로 처리량은 기획 입력량이 정한다. 주제 여러 건을 한 번에 넣는 입력(목록 붙여 넣기 → 건마다 작업 생성)을 둔다.
- 배제 주제(2.1)는 입력 단계에서 거부하고 사유를 보인다.

**처리** `승계` — 한국판 B-②와 같다.

1. 후보 행을 먼저 `held`("🔎 기획 검색 진행 중")로 만든다.
2. 주제로 웹 검색해 소스를 모은다 — **검색 8회 상한**, 가져오는 것은 링크·제목·스니펫뿐. 검색 엔진의 요약은 어떤 산출물의 근거로도 쓰지 않는다.
3. 차단·보류 도메인·robots 불허·유료 DB는 뺀다. 풀 밖 도메인은 `candidate` 행을 만들고 소스도 적재한다.
4. 군집화 v2를 "주제 고정·축은 소스에서" 모드로 이 후보 하나에 돌린다(6.3) → 성립 `proposed` / 미달 `held` + `gaps`.
5. `held` 후보는 사람이 [보강]을 눌러 B-① 보강 1회를 걸 수 있다.

- 실행기: **서버 워커의 API 실행기**가 웹 검색 도구로 수행한다 `개정` — 한국판은 노트북 claude-cli 워커만 집는다. 구현·필터 규칙은 4.4.
- **소스 언어** `제안` — 영문·국문 소스 모두 허용한다. K-컬처의 1차 자료(공공기관·사전·유산 기록)는 국문이 많다. 국문 소스의 처리는 6.4·6.5(10장 #5).
- 중복 대조(기존 후보·발행분·소스 재사용)는 글로벌 DB 안에서만 한다 `승계`. 한국판 발행분과는 대조하지 않는다 — 언어·청취자가 달라 같은 이야기의 반복이 아니다.

### 6.2 소스·도메인 판정 — 한국판 spec/01 기반

- **계층 정의**(`allow_open` 1군 · `allow_support` 2군 · `blocked` · `hold` · `candidate`)와 **판정 체크리스트 ①~④**(라이선스 · 발행 주체 · 약관 금지 조항 · 접근 구조) `승계`.
- **판정은 사람만** — `tier`·`decided_by`·`decided_at`은 AI가 기입하지 않는다. AI는 증거 수집(robots·약관 링크·라이선스 표기 — 한국판 `domain_check`)까지 `승계`.

### 6.10 에이전트 판정 — 한국판 사람 판정(spec/09 3.1) 대체 `신설` (2026-10-16 결정)

- **판정을 에이전트가 맡는다.** 판정 화면의 입력(비평 플래그 동의·부분동의·비동의 · ⭐ · 12항목 점수 · 자유 지적)과 대본 직접 수정을 에이전트가 한다. 도메인 판정(6.2)·게이트 1(6.3)·발행 버튼은 그대로 사람이다.
- **검토자 둘** — ① **원어민 편집자**: 듣기 경험·영어 구어·두 역할의 말버릇·장면과 소리 ② **한국어·사실 검토자**: 발췌·claims 원문 대조, 한국어 뜻·로마자·존댓말 같은 언어·문화 맥락, 6.4 표기·2.1 배제·원칙 8·9. 지시문은 `docs/ai/global/judge/`.
- **모델** — 대본·QA·비평과 다른 계열(Claude)을 쓴다. 같은 모델이 자기 글을 후하게 보는 편향(한국판 비평이 사람보다 5점 안팎 후했다)을 피한다.
- **작성자 눈가림** (2026-10-17) — 검토자는 대본이 AI로 만들어졌다는 것도, 제작 과정(규칙·구성안·QA·비평)도 모른다. 편집자는 대본과 점수표만, 한국어·사실 검토자는 대본·취재 노트(claims)·발췌·발음 목록·편집 방침(2.1·원칙 8·9·6.4)만 받는다. 비평 플래그·⭐ 대조와 규칙 대조는 판정 세션이 판정 뒤에 하고, 점수·발행 가능 판단을 바꾸지 않는다.
- **근거 없는 지적은 무효** — 지적마다 턴 번호와 대본 인용을 붙이고, 사실 지적은 발췌 또는 취재 노트 인용을 함께 붙인다.
- **기록** — `episodes.critic_verdicts`에 사람 판정과 같은 형식으로 쓰고 `judged_by: agent:<모델 id>`와 `agent` 블록(`publishable` · `must_fix[]` · 요약 리포트 키)을 덧붙인다. 직접 수정은 `human_edits`에 `by: agent:<모델 id>`로 남긴다. 편마다 한국어 요약 리포트(`agent-verdict.md`)를 에피소드 산출물 옆에 둔다.
- **필수 수정** — `must_fix`는 대본 수정으로 반영하고, 한국어·사실 검토자가 수정본을 다시 대조해 `fixed`로 넘긴다. 반영 뒤 L0를 다시 돌린다.
- **발행과의 관계** — `publishable: true`이고 `must_fix`가 전부 `fixed`인 편만 발행 준비·패키지를 시작할 수 있다. 콘솔 버튼과 서버 액션이 함께 막는다. 한국판 인스턴스는 이 조건을 보지 않는다.
- **실행 위치** — 파일럿은 Claude Code 세션의 서브에이전트로 돌리고 결과를 글로벌 DB·버킷에 쓴다. 정상 운영(7장) 전에 워커 단계로 옮긴다(10장 #15).
- **규칙 승격** `승계` — 에이전트 판정을 원천으로 한국판과 같은 승격 절차(판정 묶음 → guidelines·루브릭·QA·L0)를 밟는다. 승격 PR 승인은 사람이다.
- **보정** — 원어민 검토자가 생기면 같은 편을 사람과 에이전트가 함께 판정해 편향을 잰다. 그 전까지 둘은 `judged_by`로 가른다.

### 6.11 시리즈 — 한국판 spec/11 기반 `신설` (2026-10-17 결정)

- **한국판과 같은 구조로 도입한다** `승계` (박수헌 2026-10-17 — "글로벌에도 시리즈 도입"). 기획 시리즈만 시리즈이고, 관리자가 [주제 기획] › 시리즈로 시작한다. 설계안 → 게이트 S(편수 확정) → 편마다 B-② 후보·게이트 1 → 편마다 대본(회상·예고) → 편마다 검수 → [시리즈 발행]으로 한꺼번에. 규칙 원본은 [한국판 spec/11](../spec/11-series.md)이고, 여기에는 다른 점만 적는다.
- **편수 상한 없음** `승계` — 편수는 관리자가 정한다.
- **편 분량** `개정` — 편은 글로벌 정규 편이라 하한 5분(1.3)을 따른다. 시리즈 편은 분할 제안(20분)을 쓰지 않고, 길면 설계안에서 편을 나눈다.
- **출연진** `신설` — 한 시리즈의 모든 편은 같은 2인조가 맡는다. 팀은 대표 주제로 고르므로(6.7) 편 후보가 시리즈의 대표 주제(`series.mid_topic`)를 그대로 쓰면 저절로 같다.
- **영어 자산** `개정` — 시리즈 블록·인트로 시리즈 줄·회상·예고 템플릿은 영어판을 따로 둔다(4.5). 한국판 자산을 번역해 쓰지 않는다.
- **에피소드 ID** `개정` — 글로벌판은 시리즈 편도 `G` 접두사를 쓴다. 접두사는 인스턴스를 가르는 표지다(4.3). 시리즈 소속은 `backlog.series_id`·`series_no`가 나타낸다.
- **판정·발행** `개정` — 편마다 에이전트 판정(6.10)을 받는다. [시리즈 발행]은 전 편이 발행 조건(`publishable: true`, `must_fix` 전부 `fixed`)을 채운 뒤에만 열린다. 서버 시리즈 생성 API는 BE KAN-134(한국판 계약)를 글로벌 서버에도 같은 모양으로 둔다 — 글로벌 발행(6.9, KAN-204) 뒤에 붙는다.
- **데이터** — 마이그레이션 0029(`series` 테이블 · `backlog.series_id`·`series_no` · `series_plan` 작업)를 한국판과 함께 글로벌 DB에 적용했다(2026-10-17).

| API 키 | 서버 env에만 둔다(한국판 `env.prod` 방식). 코드·env 예시에 넣지 않는다 `승계` |
| WORK_ROOT | 레포 밖, 인스턴스별로 다른 경로 `승계` |
| 알림 | Slack `#dev-ai` 공유, 큐 비움 요약 메시지 머리에 `[GLOBAL]` 표시 `제안` |
| 비용 계측 | `runs` 계측 구조 `승계`, 한국판과 합산하지 않는다 |
