# [문서] 회수 동기화 응답에 서버 상한과 이어받기 커서를 둔다

| 항목 | 값 |
|---|---|
| 대상 문서 | `docs/spec/api/player-api.md` 4.6 |
| 요청 파트 | 백엔드 |
| 발행 날짜 | 2026-09-08 |
| 반영 날짜 | 2026-09-08 (같은 날 반영) |
| 발견 시점 | 2026-09-08 백엔드 성능 점검 — 클라이언트가 정하는 `since`에 상한이 없었다 |
| 심각도 | 중 — 인증된 사용자 누구나 전 구간 스캔을 걸 수 있었다 |

## 문제

4.6은 **"회수가 드물어 목록은 짧고, 페이지네이션을 두지 않는다"** 로 적고 구현도 그랬다. 그런데 `since`는 **클라이언트가 보내는 값**이다.

`?since=1970-01-01T00:00:00Z` 한 번이면 회수된 콘텐츠 전부가 상한 없이 내려온다. `architecture.md` 9.3은 **"목록 조회는 `limit` 상한을 서버가 강제한다"** 로 정하는데 이 라우트만 예외였다.

"드물다"는 지금의 데이터 상태이지 계약이 아니다. 파트너가 늘고 회수가 쌓이면 같은 요청이 그대로 무거워진다.

## 수정 내용

- **한 응답의 상한을 200건으로 두고 서버가 강제한다.**
- **응답에 `next_since`를 추가한다.** 상한에 걸려 잘렸으면 마지막 항목의 `withdrawn_at`, 아니면 `null`이다. 클라이언트는 `null`이 나올 때까지 그 값을 `since`로 다시 호출한다.
- "페이지네이션을 두지 않는다" 문장을 걷어낸다.

**`has_next` 불리언 대신 커서를 내려주는 이유** — 이 엔드포인트의 페이징 키가 이미 `since`다. 별도 커서 형식을 만들면 클라이언트가 두 가지 이어받기 방식을 갖게 된다.

**클라이언트가 `next_since`를 무시해도 화면은 깨지지 않는다.** 다음 정기 동기화가 같은 지점에서 이어받으므로, 회수분 제거가 한 주기 늦어질 뿐이다. 그래서 필수 대응이 아니라 선택적 최적화로 둘 수 있다.

## 완료 조건

- Given `player-api.md` 4.6 / When 응답 예시를 본다 / Then `next_since`가 있고 의미가 적혀 있다
- Given 같은 절 / When 상한 규칙을 찾는다 / Then 서버가 강제하는 건수와 이어받는 방법이 적혀 있다
- Given `since`를 아주 과거로 보낸다 / When 응답을 본다 / Then 상한만큼만 내려오고 `next_since`가 채워진다
