## 어긋난 지점

`explore-api.md` 4.3 서버 처리는 이렇게 적혀 있다.

> 2. `library_items` upsert
>    - **살아 있는 행이 있으면**: **아무것도 바꾸지 않고** 현재 상태를 반환 → 200
> 3. `reason = user_save`면 `user_signals`에 `action = 'save'` 적재

**2번에는 "아무것도 바꾸지 않는다"가 있는데 3번에는 조건이 없다.** 그래서 이미 담긴 콘텐츠에 담기가 다시 들어오면 라이브러리는 그대로인데 신호만 한 건 더 쌓인다.

실제 동작을 로컬에서 확인했다 — 같은 콘텐츠에 담기를 두 번 호출한 결과다.

```
library_items : 1행 (added_at 그대로 — 정상)
user_signals  : save, save        ← 상태는 안 바뀌었는데 신호는 2건
```

`library_items`는 `uq_library_items_user_id_content_id`가 중복을 막지만(`domain.md` 6.1), **`user_signals`는 append-only 이력 테이블이라 중복을 막는 제약이 없다**(`domain.md` 6.4).

## 왜 문제인가

`user_signals`는 **추천 스코어링 입력 전용**이다(`domain.md` 6.4 — A-7). `drip-scheduling.md` 4.3의 신호 해석표가 `save`를 "긍정(완청보다 약하게)"으로 읽고 주제 가중치를 올리므로, 신호가 3건 쌓이면 사용자가 한 번 담았을 뿐인 콘텐츠의 주제가 **완청 2건보다 무거워진다.**

탐색 화면만의 문제가 아니다. 같은 테이블을 드립 편성도 읽으므로(`drip-scheduling.md` 4.3) 편성 결과까지 흔들린다.

**사용자의 오조작으로 생기는 일은 아니다.** 더보기 시트는 이미 담긴 행에 [담기] 대신 [라이브러리에서 제거]를 띄우므로(`explore-uiux.md` 4.4) 같은 담기를 두 번 누를 수 없다. 실제 발생 경로는 **오프라인 큐 재전송**이다(`common-error-handling.md` 4.5).

## 같은 문제를 이미 두 곳에서 막고 있다

이 조건만 빠져 있어서 **세 규칙이 비대칭**이 됐다.

| 상황 | 문서 | 신호 | 근거 문장 |
|---|---|---|---|
| 이미 삭제된 항목을 또 삭제 | `library-api.md` 4.6 | 적재 안 함 | "그때마다 `delete` 신호를 다시 쌓으면 추천 스코어가 왜곡된다" |
| 담긴 적 없는 콘텐츠를 해제 | `explore-api.md` 4.4 | 적재 안 함 | "없던 담기의 해제로 제외·신호가 쌓이면 안 된다" |
| **이미 담긴 콘텐츠를 또 담기** | `explore-api.md` 4.3 | **적재함** | *(조건 없음)* |

앞의 두 개가 같은 이유로 이미 막혀 있으므로, 이 요청은 새 원칙을 세우는 것이 아니라 **빠진 한 줄을 맞추는 것**이다.

## 제안 문구

### `explore-api.md` 4.3 — 서버 처리 3번 교체

**현재**

> 3. `reason = user_save`면 `user_signals`에 `action = 'save'` 적재(`explore.md` 4.3 확정 — FR-15, `domain.md` 6.4)

**제안**

> 3. `reason = user_save`이고 **2번에서 라이브러리 상태가 실제로 바뀐 경우에만** `user_signals`에 `action = 'save'` 적재(`explore.md` 4.3 확정 — FR-15, `domain.md` 6.4). 즉 **행을 새로 만들었거나 삭제된 행을 되살렸을 때**이며, 살아 있는 행을 그대로 둔 경우에는 적재하지 않는다.
>   - **`user_signals`에는 중복을 막는 제약이 없다**(`domain.md` 6.4 — append-only 이력). 라이브러리는 그대로인데 신호만 쌓이면 그 주제의 가중치가 부풀려지고, 같은 테이블을 읽는 드립 편성까지 흔들린다(`drip-scheduling.md` 4.3).
>   - 사용자가 화면에서 같은 담기를 두 번 누를 수는 없다(시트가 [라이브러리에서 제거]로 바뀐다 — `explore-uiux.md` 4.4). 실제 경로는 **오프라인 큐 재전송**이다(`common-error-handling.md` 4.5).
>   - **삭제분 재담기에는 신호를 남긴다.** 행을 새로 만들지 않아 응답은 200이지만, 사용자의 진짜 담기 조작이다.
>   - 라이브러리 삭제(`library-api.md` 4.6)·담기 해제(4.4)가 같은 이유로 이미 no-op 신호를 막고 있다.

### 세 갈래 정리 (4.3 서버 처리 2번 표에 "신호" 열 추가 제안)

| 상태 | 처리 | 응답 | `user_signals` |
|---|---|---|---|
| 행 없음 | `source = save`로 생성 | 201 | **적재** |
| 살아 있는 행 | 아무것도 바꾸지 않는다 | 200 | **적재하지 않음** |
| 삭제된 행 | 되살리고 `added_at`을 새로 찍는다 | 200 | **적재** |

## 클라이언트 계약 변경 여부

**없다.** 요청·응답 필드가 하나도 바뀌지 않고 상태 코드(201/200)도 그대로다. 서버 내부의 신호 적재 조건만 달라진다.
