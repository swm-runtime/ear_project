## 수정 1 — `POST /auth/sign-up`은 멱등 캐시를 쓰지 않는다

### 왜

응답에 **`refresh_token` 원문**이 실려 있다. 멱등 캐시에 넣으면 `idempotency_keys.response_body`에 **30일짜리 자격증명이 평문으로** 저장된다. `sessions`가 해시만 두는 이유(`domain.md` 3.3)를 이 한 테이블이 무력화한다.

그러면서 **중복 방지에 보태는 것이 없다.**

| 재시도 형태 | 무엇이 막는가 |
|---|---|
| 순차 재시도 | 서버가 `provider + provider_user_id`로 기존 계정을 찾아 그대로 돌려준다 |
| 동시 요청 | `uq_users_provider_provider_user_id`. 서버가 유니크 위반을 흡수한다(`architecture.md` 8.4) |

게다가 클라이언트는 **호출마다 새 멱등키를 만든다.** 사용자가 다시 누른 재시도는 애초에 캐시를 타지도 않았다.

### 무엇을 바꿨나

- **3장 표** — 2번 행(`/auth/sign-up`)의 멱등키 ★ 표시 해제
- **4.2** — "`Idempotency-Key` 필수" → "받지만 응답을 캐시하지 않는다". 헤더를 계속 받는 이유(클라이언트 5xx 자동 재시도 조건)와, 재시도가 새 세션을 받게 된다는 차이를 명시

### 남는 차이

재시도는 **저장된 첫 응답이 아니라 새로 발급된 토큰**을 받는다. 같은 계정이므로 클라이언트 동작에는 영향이 없다(토큰 값을 시도 간에 비교하는 코드가 없다).

## 수정 2 — `EMAIL_ALREADY_REGISTERED`의 판정 기준

### 왜

`auth.md` 4.4는 **"인증이 끝난 이메일은 앱에서 변경할 수 없다"**(확정 2026-09-07, 재확인 2026-09-08)로 정하고, "새 주소로 코드 인증을 통과하면 변경 허용"하는 안을 **검토 후 기각**했다.

그런데 4.8의 정의가 **"같은 주소"** 로 좁혀져 있어, 다른 주소를 보내면 서버가 코드를 보내고 인증 성공 시 덮어썼다 — **기각된 그 동작이 그대로 열려 있었다.** 잠금은 화면에만 있었고, 화면이 진입점을 감추는 것은 안내이지 판정이 아니다.

이 값은 **탈퇴 후 거래기록 보존의 식별자**다(`domain.md` 11.3). 임의로 바뀌면 보존 대상 주소가 거래 시점의 주소와 달라진다.

### 무엇을 바꿨나

- **4.8 에러 표** — "인증까지 끝난 **같은 주소**" → "**계정에 인증까지 끝난 주소가 이미 있다.** 보낸 주소가 그 값이든 다른 값이든 같다"
- **4.8 설명** — 판정 기준이 `is_email_verified`이지 보낸 주소가 아님을 불릿으로 추가. 미인증 주소는 종전대로 보낸다(그 경로를 막으면 결제로 나아갈 방법이 사라진다)

**새 에러 코드를 만들지 않았다.** 코드를 추가하면 `error-code.enum.ts` → 9장 표 → api 문서 5장을 함께 고쳐야 하는데(`architecture.md` 7.5), 409의 의미가 이미 "계정 상태와 충돌한다"라 넓히는 편이 맞다. 클라이언트도 이미 처리하는 코드다.

## 완료 조건

- Given `auth-api.md` 3장 표 / When `/auth/sign-up` 행을 본다 / Then 멱등키 ★가 없다
- Given 4.2 / When 요청 규약을 읽는다 / Then 헤더를 받되 캐시하지 않는다는 것과 그 이유가 적혀 있다
- Given 4.8 / When `EMAIL_ALREADY_REGISTERED` 정의를 읽는다 / Then 판정 기준이 보낸 주소가 아니라 계정의 인증 여부임이 적혀 있다
