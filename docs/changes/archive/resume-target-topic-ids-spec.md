## 바꾸는 규칙

4.3 응답의 `content` 는 목록 응답 4.1 의 `content` 와 **같은 모양이어야 한다.** 4.1 에는 `topic_ids` 가 이미 있는데 4.3 에만 없어서, 같은 콘텐츠 카드가 **어느 경로로 그려졌는가에 따라** 카테고리 줄이 있고 없고가 갈렸다.

개정: **4.3 응답 예시에 `"topic_ids": ["uuid", "uuid"]` 를 넣고, 주제가 없을 때의 값을 명시한다.**

```diff
   "content": {
     "id": "uuid",
     "title": "번아웃 없이 오래 일하는 법",
     "duration_sec": 620,
     "thumbnail_url": "https://...",
-    "content_version": 1
+    "content_version": 1,
+    "topic_ids": ["uuid", "uuid"]
   },
```

선정 규칙 아래 설명 목록에 한 줄을 덧붙였다 — **주제가 없으면 `null` 이 아니라 `[]`** 라는 것. 이걸 적지 않으면 클라이언트가 `null` 분기를 만들게 되고, 서버가 빈 배열을 주는 것과 어긋난다.

## 왜 계약 문서를 고쳤는가

`spec/api/` 는 백엔드의 수정 범위 밖이지만, **이 변경의 완료 조건 자체가 문서에 있다**(KAN-91 세 번째 조건). 필드를 내려보내면서 계약서에 적지 않으면 그 시점부터 문서가 거짓이 되므로, 코드와 같은 PR 에서 함께 반영하고 여기에 기록을 남긴다.

## 함께 확인한 것

**서버 조회는 손대지 않았다.** `getResumeTarget` 은 목록과 같은 `toItemViews` 를 거치므로 `topicIds` 가 이미 채워져 있었고(주제가 없으면 `[]`), 응답 DTO 만 그 필드를 빼고 있었다. 그래서 "목록 응답과 같은 배열"이라는 완료 조건은 **같은 함수를 쓴다는 구조로** 보장되지 추가 쿼리로 맞추는 것이 아니다.

## 완료 조건

- Given `library-api.md` 4.3 / When 응답 예시를 읽는다 / Then `content.topic_ids` 가 있다
- Given 같은 절 / When 설명을 읽는다 / Then 주제가 없을 때 `[]` 라는 것이 적혀 있다
