# architecture.md 9.1 — refresh 재사용 탐지에 짧은 유예창을 둘지 (제안, 2단계)

| 항목 | 값 |
|---|---|
| 대상 문서 | `docs/backend/architecture.md` 9.1 |
| 발행 날짜 | 2026-09-09 |
| 발견 시점 | 백엔드 전수 감사 — 실서버에서 정상 클라이언트의 동시 갱신이 전 세션 무효화를 두 번 일으켰다(앱·어드민 웹) |
| 요청 파트 | 백엔드 |

## 현행과 1단계 조치(코드 선반영 2026-09-09)

9.1: "이미 쓰인 토큰이 재사용되면 해당 사용자의 세션 전체를 무효화한다" — 코드는 이를 그대로 구현하나
회전 자체가 비원자(조회→revoke→발급)여서 **완전 동시 요청은 둘 다 통과하고(탐지 우회), 근소 직렬 요청은
정상 사용자를 강제 로그아웃**시켰다. 1단계로 revoke를 조건부 UPDATE(`WHERE revoked_at IS NULL`)의
affected 판정으로 바꿔 원자화했다 — 문서 개정 없이 규칙을 정확히 구현한 것이다.

## 제안 (2단계 — 결정 필요)

업계 표준(Auth0 "reuse interval" 등)처럼 **직전 토큰을 회전 후 짧은 창(예: 10초) 안에 1회 재사용하면
같은 신규 토큰 쌍을 돌려주고 탐지로 보지 않는다.** 그 창을 넘긴 재사용만 탈취로 판정한다.

- 얻는 것: 응답 유실 후 재시도·멀티탭 같은 정상 경합이 로그아웃으로 번지지 않는다.
- 보안 비용: 탈취범이 정확히 그 10초 안에 재사용해야만 세션을 얻고, 그 경우에도 정상 사용자와 같은
  토큰을 공유해 다음 회전에서 충돌이 드러난다 — 미미하다.
- 구현: `sessions`에 회전 시각·후속 세션 참조가 필요(스키마 변경 → domain.md 3.3 동반).

**권장: 채택하되 급하지 않다** — 1단계 원자화 + FE single-flight(`splash-gate-session-restore` 요청 3)로
실측된 두 사례는 이미 닫힌다. 스키마 변경이 필요하니 다음 인증 관련 작업 때 묶는다.

## 완료 조건

- Given `architecture.md` 9.1 / When 재사용 탐지 규칙을 읽는다 / Then 유예창 채택 여부와(채택 시) 창 길이가 적혀 있다

## 처리 기록 (반영 날짜: 2026-09-10)

`architecture.md` 9.1에 **두 가지를 함께** 적었다 — 완료 조건이 "채택 여부가 적혀 있다"이므로 결론을 남기는 것이 반영이다.

1. **1단계(원자화)를 규칙으로 명시했다.** 코드는 2026-09-09에 이미 바뀌었지만 문서에는 없었다. 조회 → 무효화 → 발급을 나눠 하면 **완전 동시 요청 둘이 모두 통과해 탐지를 우회하고, 근소 직렬 요청은 정상 사용자를 강제 로그아웃**시킨다는 것과, 실서버에서 두 사례가 다 발생했다는 사실을 근거로 적었다.

2. **유예창은 두지 않는다 — 다만 폐기가 아니라 보류다.** 권장이 "채택하되 급하지 않다"였는데, 문서에 "채택"만 적고 구현하지 않으면 **문서와 코드가 어긋난 채로 남는다.** 그래서 현재 상태(미도입)를 규칙으로 적고, **도입 조건**("정상 경합이 다시 로그아웃으로 번지는 것이 관측되면")과 **동반 비용**(`sessions` 스키마 변경 → domain.md 3.3)을 함께 남겼다.

지금 도입하지 않는 근거는 요청서 그대로다 — 원자화 + FE single-flight로 실측된 두 사례가 이미 닫힌다.
