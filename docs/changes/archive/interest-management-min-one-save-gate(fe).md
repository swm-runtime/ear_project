## 왜 기록하는가

문서가 이 지점에서 스스로 갈라져 있다.

- **4.2**: "마지막 1개까지 해제 시도 → **저장 자체를 막는다.** '관심 주제는 1개 이상 선택해야 해요'"
- **5장 화면 상태 표**: "마지막 1개 해제 시도 → **해당 칩 해제 불가** + 토스트"
- **8장 완료 조건**: "Given 관심 주제가 1개뿐인 사용자 / When 그 주제를 해제하려 한다 / Then **해제되지 않고** 최소 1개 안내가 노출된다"

와이어프레임 검토(2026-08-09)에서 **저장 차단(4.2 쪽)으로 결정**했다.

- 현재 선택을 **전부 해제하고 새로 고르는 동선**을 탭 차단이 막는다 — 1개 보유 사용자가 주제를
  바꾸려면 "새것 먼저 선택 → 기존 해제" 순서를 강요받는데, 그 순서를 알 방법이 화면에 없다.
- 온보딩 1단계(O1)가 이미 같은 패턴이다 — 0개면 [다음] 비활성 + "관심 주제를 1개 이상
  선택해주세요". 두 화면이 같은 목록·같은 상한을 쓰면서 최소 개수의 처리만 다르면 학습이 갈린다.
- 규칙 자체는 불변이다 — 드립 편성이 최소 1개 주제를 전제하므로 **0개 저장은 성립하지 않고**,
  서버의 최소 1개 검증도 그대로다. 바뀌는 것은 판정 지점(탭 → 저장)뿐이다.

## 기록할 내용 (반영 완료 2026-08-09)

1. **5장 화면 상태 표** — "마지막 1개 해제 시도 | 해당 칩 해제 불가 + 토스트 …" 행을
   **"전부 해제(0개) | 0개 상태 허용. [저장] 비활성 + 하단 사유 문구 '관심 주제를 1개 이상
   선택해주세요'(온보딩 O1과 같은 패턴·같은 문구)"** 로 교체한다.
2. **8장 완료 조건** — "Given 관심 주제가 1개뿐인 사용자 / When 그 주제를 해제하려 한다 /
   Then 해제되지 않고…" 를 **"Then 해제되어 0개 상태가 되고, [저장]이 비활성이며 최소 1개
   사유 문구가 노출된다"** 로 교체한다.
3. 4.2는 이미 "저장 자체를 막는다"라 수정이 없다 — 문구가 토스트가 아니라 상시 사유 문구로
   노출된다는 점만 표현을 맞춘다.

## 완료 조건

- Given 이 요청이 통합 과정에서 반영된다 / When `interest-management.md` 5장·8장을 읽는다 /
  Then 마지막 1개 해제가 허용되고 0개 상태에서 [저장]이 비활성이라는 서술로 통일되어 있으며
  "칩 해제 불가" 서술이 남아 있지 않다
- Given 반영 후 / When 4.2·5장·8장을 대조한다 / Then 최소 1개 제약의 판정 지점이 세 곳 모두
  "저장"으로 일치한다
