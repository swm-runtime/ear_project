## 문제

4.3은 "반영 주기: 편성 배치 시점에 최신 신호를 읽어 계산한다 … 탐색 피드 랭킹(4.7)도 같은 캐시를 읽는다"로 적고, 4.1은 "미청취 재고가 5편 이상이면 **그날 적립을 건너뛴다**"로 적는다. 두 규칙의 관계 — 적립을 건너뛴 사용자의 캐시도 재계산하는가 — 를 어느 문서도 명시하지 않았다.

구현은 재고·플랜 스킵 판정 **뒤에** 재계산을 두고 있어, 재고가 늘 5편 이상인 사용자는 캐시가 영영 만들어지지 않았다. 탐색 피드는 그 캐시로 콜드스타트 여부(`signal_count < 3`)와 관심사 섹션 순서를 정하므로, `save` 신호를 가장 많이 만드는 사용자가 정확히 그 신호의 혜택을 받지 못했다. `tickets/backend/archive/explore-ranking-reads-preference-cache.md`가 받아들인 대가("반영이 최대 배치 한 주기 늦어진다")가 이 사용자에게는 무기한이 됐다.

## 수정 내용

코드(2026-09-15 반영): `DripBatchOrchestrator.scheduleForUser`에서 재계산을 관심 주제 0 판정 직후, 재고·플랜 스킵 판정 **앞**으로 옮겼다. 편성 결과(적립 여부·편수)는 변하지 않고 스킵 사용자당 6쿼리가 늘어난다.

문서에 다음을 명시한다.

- `drip-scheduling.md` 4.3 반영 주기 항목에 한 줄 추가: **"재고(4.1)·플랜 편수로 그날 적립을 건너뛴 사용자도 캐시는 재계산한다 — 스킵은 적립 규칙이지 신호 집계 규칙이 아니다."**
- `domain.md` 7.2 `user_preference_vectors` 갱신 주기에 같은 문장을 덧붙인다.

## 완료 조건

- Given `drip-scheduling.md` 4.3 / When 반영 주기를 읽는다 / Then 적립 스킵 사용자도 재계산 대상이라는 문장이 있다
- Given 미청취 재고 5편 이상인 사용자 / When 일일 배치가 돈다 / Then `library_items`는 늘지 않고 `user_preference_vectors`는 그날 갱신된다 (`drip-batch.orchestrator.spec.ts` "미청취 재고로 적립을 건너뛴 사용자도 취향 캐시는 재계산한다")

## 처리 기록 (반영 날짜: 2026-09-15)

`drip-scheduling.md` 4.3 반영 주기 항목과 `domain.md` 7.2 갱신 주기 항목에 "스킵 사용자도 재계산" 문장을 넣었다. 코드는 PR #349(`DripBatchOrchestrator.scheduleForUser`)로 dev에 반영돼 있다.
