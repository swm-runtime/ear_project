# [문서] 대시보드 응답시간을 산점도(로그 축)로 적는다

| 항목 | 값 |
|---|---|
| 대상 문서 | `features/backend-monitoring.md` 대시보드 행(48행) |
| 요청 파트 | 문서(pipeline 구현은 `feat(ai)/request-scatter`에서 선반영) |
| 발행 날짜 | 2026-09-08 (2026-09-09 전면 개정 — 표현을 선 그래프에서 산점도로 바꿨다) |
| 발견 시점 | "같은 시각인데 3시간과 6시간의 값이 다르다"를 파고들다가, 표현 자체가 이 트래픽에 맞지 않는다고 판단 |
| 심각도 | 중 — 문서가 없으면 로그 축을 선형으로 오독한다 |

## 왜 필요한가

문서는 대시보드를 "버킷별 요청 수(오류 적층)·응답시간 p50/p95"로 적는다. 그런데 **p50/p95
선 그래프가 이 트래픽에서는 성립하지 않는다.**

운영 실측(2026-09-09 `admin.earcast.co.kr`): **6시간 창에 요청 39건.** 칸당 표본이 한두 건이고,
표본 2건의 "p95"는 통계가 아니라 그냥 그 칸의 최댓값이다.

게다가 **백분위는 합칠 수 없다.** 10분 칸의 p95는 5분 칸 두 개 p95의 평균도 최댓값도 아니다.
그래서 범위 버튼으로 칸 폭이 바뀌면 같은 시각의 값이 통째로 달라졌다 — 실측에서 09:20 구간이
3시간 뷰(5분 칸·표본 2건) p50 16ms, 6시간 뷰(10분 칸·표본 17건) p50 304ms 였다. 축도 그 값들에
끌려 30분 뷰 305ms ↔ 3시간 뷰 96ms 로 흔들렸다.

요청 수 막대(합계)나 자원 선 그래프(순시값)에 같은 문제가 없는 이유가 이것이다 — 합계와
순시값은 구간을 바꿔도 의미가 보존되지만 백분위는 그렇지 않다.

## 수정 내용

대시보드 행의 "응답시간 p50/p95"를 다음으로 바꾼다.

| 항목 | 규칙 |
|---|---|
| 표현 | **요청 1건 = 점 1개인 산점도.** 버킷도 백분위도 쓰지 않는다 |
| 점 색 | 정상 = 브랜드색 · **4xx/5xx = 빨강** |
| y축 | **로그 축**(1·10·100·1,000ms). 응답시간은 배수로 읽는 지표이고, 지금 데이터는 10ms 대와 300ms 대로 갈려 선형 축에서는 빠른 쪽이 바닥에 뭉갠다 |
| 호버 | 가장 가까운 요청 하나 — 시각·소요·**메서드와 경로**·status. 느린 요청이 어느 엔드포인트였는지가 바로 보인다 |
| 백분위 | 차트가 아니라 카드 부제에 **창 전체 기준** p50·p95·최대를 적는다. 창 전체는 쪼개지 않으므로 합산 문제가 없다 |
| 요청 수 막대 | 그대로 둔다 — 합계라 구간을 바꿔도 보존된다 |

앞선 판(▲ 축 상한 초과 표식, 고립된 칸의 점, 버킷 p95 기반 y축 상한)은 **폐기한다.** 산점도는
축 상한을 추정하지 않고 칸을 쓰지 않으므로 그 표식들이 가리킬 대상이 없다.

## 언제 다시 바꾸는가

트래픽이 칸당 수십 건 규모로 늘면 점이 뭉개진다. 그때는 **히스토그램 버킷**(개수는 합칠 수
있다) 기반의 백분위나 히트맵으로 간다. AWS에서는 CloudWatch Logs Insights의
`stats pct(duration_ms, 95) by bin(5m)`가 첫 단계이고, 그다음이 EMF·메트릭 필터로 로그를
메트릭으로 내보내는 것이다.

## 완료 조건

- Given `features/backend-monitoring.md` / When 대시보드 행을 읽는다 / Then 응답시간이 산점도이고 요청 1건이 점 1개라고 적혀 있다
- Given 같은 문서 / When y축을 찾는다 / Then **로그 축**임과 그 이유가 적혀 있다
- Given 같은 문서 / When 백분위를 찾는다 / Then 차트가 아니라 창 전체 기준 요약값이라고 적혀 있고, 버킷 백분위를 쓰지 않는 이유(합칠 수 없다)가 적혀 있다
- Given 같은 문서 / When ▲·고립점 표식을 찾는다 / Then 그런 표식이 없다(폐기됨)

## 처리 기록 (반영 날짜: 2026-09-09)

`features/backend-monitoring.md` 대시보드 행에 전부 반영했다 — 산점도(요청 1건=점 1개, 오류
빨강), 로그 축과 그 이유, 백분위는 카드 부제의 창 전체 요약(버킷 백분위를 못 쓰는 이유 포함),
트래픽 증가 시 히스토그램/히트맵 전환 시점까지. ▲·고립점 표식 서술은 애초에 문서에 없어
지울 것이 없었다.
