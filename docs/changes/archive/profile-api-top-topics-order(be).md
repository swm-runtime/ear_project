## 어긋난 지점

같은 데이터(`user_interests`)를 읽는 두 계약이 다른 정렬을 지시하고 있었다.

| 계약 | 지시한 정렬 | 구현 |
|---|---|---|
| `explore-api.md` 4.2-2 (주제 칩) | **`created_at` 오름차순 — 선택한 순서** | 선택 순서 ✅ |
| `profile-api.md` 4.1 (`top_topics`) | **`topics.display_order`** | 선택 순서 ❌ |

**화면끼리는 어긋나지 않았다.** 탐색 칩과 프로필 대표 주제가 실서버에서 둘 다 `심리학 · 커리어 · 재테크`(선택 순서)로 같았다. 어긋난 것은 **프로필 구현과 프로필 명세** 사이, 그리고 **두 명세** 사이다.

## 왜 고쳐야 했나 — 지금이 아니라 다음이 문제다

개정 전 문장은 이랬다.

> 관심사 관리 목록과 같은 정렬(**현행** `topics.display_order`)을 그대로 쓰며

"현행"이 가리키는 **관심사 관리 화면은 아직 없고 API 명세도 없다.** 만들어지지 않은 화면의 정렬을 추측해 적어둔 문장이었다.

그대로 두면 예약된 문제가 된다 — 관심사 관리를 만드는 사람이 이 문장을 근거로 `display_order`를 택하고, 그 순간 **관심사 관리만 다른 순서**가 되어 탐색·프로필과 어긋난다. 사용자는 같은 세 주제를 화면마다 다른 차례로 보게 된다.

## 왜 코드가 아니라 문서를 고쳤나

셋 다 문서를 고치는 쪽을 가리켰다.

1. **탐색 계약이 더 나중에, 명시적으로 확정됐다**(합의 2026-08-07 — `explore-api.md` 9장). 같은 데이터에 대한 규칙이므로 나중 합의가 앞선다
2. **구현 두 곳이 이미 선택 순서다.** 문서 한 줄을 고치면 전부 맞는데, 코드를 고치면 탐색과 어긋나게 만드는 일이 된다
3. **선택 순서가 사용자에게 자연스럽다** — 먼저 고른 주제가 앞에 온다. `display_order`는 운영자가 정한 노출 순서라 개인의 선택과 무관하다

## 함께 확인할 것

- **관심사 관리 명세를 쓸 때 이 규칙을 따른다.** 4.1에 그 문장을 함께 넣어 뒀다 — 명세를 쓰는 사람이 프로필·탐색을 각각 뒤지지 않아도 된다.
- **`user_interests.created_at`이 같은 값으로 저장되는 문제는 별개다.** 온보딩이 여러 주제를 한 번에 넣어 세 행의 `created_at`이 마이크로초까지 동일하다(2026-08-08 탐색 테스트에서 확인). 정렬 키가 유일하지 않아 순서가 보장되지 않는데, 현재는 삽입 순서로 나와 우연히 맞는다. **이 문서의 범위 밖이며, 순서가 실제로 어긋나는 사례가 나오면 그때 tie-breaker를 정한다.**
