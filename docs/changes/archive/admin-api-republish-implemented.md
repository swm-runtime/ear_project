### 2. 출처(`sources`) 교체 규칙을 4.10에 명문화한다

**구현이 계약보다 한 줄 더 막고 있다.** 4.10은 `sources`를 "넘긴 키만 바꾼다"까지만 적었는데,
그대로 두면 `ai_generated` 콘텐츠의 참고 소스를 **빈 배열로 지울 수 있다.** 업로드(4.6)는
`ai_generated`에 소스 1개 이상을 요구하므로(`admin.md` 3.1), 업로드로는 만들 수 없는 행이
재발행으로만 생긴다. 반대로 `partner`에 소스를 붙이는 것도 4.6이 허용하지 않는 조합이다.

4.10의 불릿 목록에 다음을 넣는다.

> - **`sources`를 넘길 때의 규칙은 4.6과 같다** — `origin`이 `ai_generated`면 최소 1개(빈 배열
>   400 `VALIDATION_FAILED`, `details.field = "sources"`), `partner`면 넣지 않는다(넣으면 같은 400).
>   `origin`은 재발행이 바꾸지 못하므로 **기존 행의 값**으로 판정한다.

### 3. 9장 미결에서 지울 것

없다. `partner_id` 존재 검증 등 기존 미결은 재발행에도 그대로 남는다.

## 사유

- 1은 **문서가 코드보다 늦으면 파이프라인 담당이 404를 예상하고 기다린다.** 실제로 파이프라인의
  [재발행] 버튼은 404를 "구현 대기"로 안내하는 분기를 갖고 있다(`republish-button.tsx`).
- 2는 **계약에 없는 400을 서버가 주고 있는 상태**다. 구현이 옳다고 보지만(`admin.md` 3.1의 공시
  규칙을 재발행이 우회하게 둘 수 없다), 계약에 없으면 호출부가 알 방법이 없다.

## 완료 조건

- Given `admin-api.md` / When 1장·3장·4.10을 읽는다 / Then 재발행이 구현된 라우트로 적혀 있고 "구현 대기" 문구가 없다
- Given `admin-api.md` 4.10 / When `sources` 항목을 읽는다 / Then `origin`별 최소·금지 조건과 그때의 에러 코드·`details.field`가 적혀 있다

## 처리 기록 (반영 날짜: 2026-09-07)

`admin-api.md`에 전부 반영했다.

- **1 "구현 대기" 해제** — 작성 이력·1장 범위 목록·3장 엔드포인트 표·4.10 첫 문장 네 곳. 1장 범위에 "콘텐츠 **재발행**" 항을 새로 넣었다.
- **2 `sources` 규칙 명문화** — 4.10 불릿에 `origin`별 최소·금지 조건과 `details.field = "sources"`를 적고, 5장 에러 표의 4.10 `VALIDATION_FAILED` 행에도 그 경우를 덧붙였다.
- **요청에 없던 수정 하나** — 4.10 말미의 "클라이언트 측 동작" 참고 문장이 **일어나지 않는 동작을 사실처럼 적고 있었다.** 앱은 재생 위치를 로컬에 보관하지 않아 "보관값과 비교"를 할 수 없다(FE 코드 확인 2026-09-07). 문장을 지우지 않고 경고 블록으로 실제 상태와 담당 티켓 2건을 덧붙였다 — `player.md` 7·`player-api.md`가 여전히 그 규칙의 소유자라 여기서 규칙 자체를 바꾸지 않았다.
