## 넣을 내용

### 4.6-5 중복 실행 방지 — 근거 정정
- 배치 단위: `drip_batch_runs.run_date` 유니크 선점(그대로).
- **사용자 단위: `already_placed` 스킵** — 오늘 서비스 날짜(04:00 경계)에 이미 편성분(`library_items.source IN (drip, discovery)`, **삭제분 포함**)이 있으면 건너뛴다. 종전 "`library_items` 유니크가 막는다"는 삭제한다 — 유니크는 같은 콘텐츠의 중복만 막는다.

### 4.1 스킵 사유에 한 행 추가
| 사유 | 조건 | 비고 |
|---|---|---|
| `already_placed` | 오늘 서비스 날짜에 편성분이 있음 | 중단된 배치의 재실행·사용자 재시도에서만 나온다. 취향 캐시는 재계산한다(4.3의 2026-09-15 결정과 같음). 재고 스킵보다 먼저 판정 |

### 2장 재시도 행 · 7장
- **사용자 단위 실패**: 잠깐 뒤(1초) **한 번 더** 시도한다. 두 번째도 실패하면 `failed_count`로 남기고 그날은 끝이다(하루 상한 안에서 다음 날 다시 대상이 된다). 적립 뒤에 던진 경우는 `already_placed`가 이중 적립을 막는다.
- **사용자 페이지 조회 실패**: 2초·5초 뒤 두 번 더 읽고, 그래도 실패하면 **실행 기록을 닫지 않고**(`finished_at` NULL 유지) 던진다.
- **재시작 시 재개**: 배치가 도는 중에 프로세스가 죽으면(배포·크래시) 배치 안의 코드로는 이어갈 수 없다. 편성을 돌리는 프로세스(스케줄러 워커)가 **다시 뜰 때** 오늘 날짜의 미완료 실행(`finished_at` NULL)이 있으면 나이와 무관하게 이어받는다. 정상 배포에서는 미완료 행이 없어 아무 일도 하지 않는다. 시각 기반 재실행 크론은 두지 않는다 — 재시작이 없었다면 재개할 것도 없다(결정 2026-09-26). 재개에서 이미 받은 사용자는 `already_placed`로 skipped에 집계되고, 실행 기록의 카운트는 재개 패스 기준으로 덮어쓴다.

### 8장 완료 조건
- "같은 날 두 번 실행 → 하루 적립 편수가 상한을 넘지 않는다"의 근거를 `already_placed`로 바꾼다.
- 추가: Given 05:00 배치가 도는 중 프로세스가 재시작됐다 / When 스케줄러 워커가 다시 뜬다 / Then 남은 사용자가 편성되고 먼저 받은 사용자는 또 받지 않는다.

### admin-api.md 4.16
`skip_reason` 값에 `already_placed` 추가. 미리보기도 오늘 편성분이 있으면 이 사유를 적은 채 끝까지 계산한다.

### domain.md 7.3
`finished_at` NULL = "진행 중 **또는 중단됨**". 중단된 행은 다음 재시작 때 재개되어 닫힌다. 카운트는 마지막 패스 기준.
