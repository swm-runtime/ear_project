## 왜 필요한가

`explore.md` 4.2는 주제 칩 줄을 "**사용자의 관심 주제를 앞쪽에** 배치하고 나머지 주제를
뒤에 붙인다"로 정하는데, **explore-api.md에 이 칩 목록을 내려주는 엔드포인트가 없다.**

- 피드 응답(4.1)의 `topic_group` 섹션은 일부 주제만 담겨 전체 주제 목록이 되지 못한다.
- 관심 주제가 무엇인지(정렬 기준)는 서버만 안다 — 클라이언트가 전체 주제와 관심 주제를
  따로 조회해 조립하면 정렬 규칙이 두 곳에 생긴다.

## 제안 계약

`GET /explore/topics` — 인증 필요, 파라미터 없음.

**Response 200**

```json
{
  "topics": [
    { "id": "uuid", "name": "커리어", "is_interest": true },
    { "id": "uuid", "name": "IT·테크", "is_interest": false }
  ]
}
```

- **정렬은 서버 소유다** — 관심 주제(`is_interest = true`)를 앞쪽에, 나머지를 뒤에 배치해
  내려준다(`explore.md` 4.2). 클라이언트는 순서를 재배열하지 않는다.
- 라이브러리의 주제 목록(`library-api.md` 4.2 — 담긴 콘텐츠의 주제)과 다르다. 이쪽은
  **필터로 고를 수 있는 전체 주제**다 — 담기지 않은 주제도 탐색에서는 골라볼 수 있어야 한다.
- FE 구현·mock은 이 계약으로 이미 동작한다(`frontend/src/features/explore/api/explore.dto.ts`
  TODO 주석 참조). 합의 후 이 문서를 explore-api.md에 반영하고 TODO를 지운다.

## 함께 결정할 것 (백엔드 협의 항목)

1. **소유 모듈** — 주제 원본은 `topics`(콘텐츠 도메인), 관심 여부는 `user_interests`다.
   탐색 경로(`/explore/topics`)에 둘지, 기존 주제 조회(온보딩 계열)에 `is_interest`를 얹을지.
2. **노출 조건** — 발행 콘텐츠가 0건인 주제도 칩으로 노출할지(고르면 E9 빈 결과가 된다).
   초기 콘텐츠 풀이 작아(PRD 8.1) 전부 노출하는 쪽이 단순하다고 본다.
