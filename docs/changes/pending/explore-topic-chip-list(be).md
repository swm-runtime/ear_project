# [BE] 탐색 주제 칩 목록 — 내려줄 통로가 계약에 없다

| 항목 | 값 |
|---|---|
| 대상 문서 | `docs/spec/api/explore-api.md` · `docs/features/explore.md` · `docs/spec/uiux/explore-uiux.md` |
| 위치 | `explore-api.md` 3장 엔드포인트 목록 · `explore.md` 4.2 주제 필터 · `explore-uiux.md` 4.1 |
| 요청 파트 | 백엔드 (계약·화면 문서 소유 파트에 전달) |
| 관련 작업 | 탐색 백엔드 구현 (`feat(be)/explore`) |
| 성격 | 화면 규칙은 있는데 **그 데이터를 내려줄 엔드포인트·필드가 없다** |
| 상태 | **동작 규칙은 확정(2026-08-07). API 형태만 FE와 합의 대기** — 이후 티켓을 발행해 프론트와 함께 구현한다 |

> **코드를 먼저 쓰지 않는다.** 계약에 없는 필드·경로를 백엔드가 임의로 만들면 그것이 사실상의 계약이 된다(`backend/CLAUDE.md` 6장). 이 문서가 확정되고 티켓이 발행되면 그때 구현한다.

---

## 어긋난 지점

`explore.md` 4.2가 칩 줄의 구성을 정하고 있다.

> 상단 가로 스크롤 칩. **사용자의 관심 주제를 앞쪽에 배치하고 나머지 주제를 뒤에 붙인다**

`explore-uiux.md` 4.1도 같은 규칙을 반복한다. 그런데 **그 목록을 클라이언트가 받을 방법이 없다.**

| 문서 | 현재 상태 |
|---|---|
| `explore-api.md` 3장 | 엔드포인트 5개 중 주제 목록을 주는 것이 없다 |
| `explore-api.md` 4.1 | 피드 응답은 `sections` + 잔여 표시값 3필드가 전부다. `topics` 필드가 없다 |

**피드의 `topic_group` 섹션으로 대신할 수 없다.** 그 섹션은 관심 주제마다 하나씩 생기지만 **콘텐츠가 0건인 주제는 섹션이 통째로 빠진다.** 초기 콘텐츠 풀이 작은 상황에서는(PRD 8.1) 충분히 발생하며, 그때 사용자는 자기가 고른 주제를 칩 줄에서 볼 수 없다.

**다른 화면 API도 맞지 않는다.**

| 후보 | 문제 |
|---|---|
| `GET /users/me/profile` | `interest_summary.top_topics`로 관심 주제를 주지만(상한 3개라 사실상 전부), **프로필 화면 API를 탐색이 호출**하게 되고 통계·커리어·구독까지 딸려 오는 무거운 응답이다 |
| `GET /onboarding/topics` | 전체 주제를 주지만 **온보딩 전용 경로**다 |
| `GET /users/me/library-items/topics` | **라이브러리에 실제로 담긴** 주제만 준다 |

결과적으로 주제 필터 조회(`GET /explore/contents`)는 계약에 있는데, **무엇으로 필터할지 고를 목록이 없는** 상태다.

## 확정된 동작 규칙 (2026-08-07)

### 1. 구성 — 관심 주제 앞, 나머지 뒤

`explore.md` 4.2의 기존 규칙 그대로다. 이번에 아래 두 세부 규칙이 추가로 확정됐다.

### 2. 사용자가 가진 관심 주제는 숨김 여부와 무관하게 보여준다

**`is_visible = false`인 주제라도 사용자의 활성 관심 주제이면 칩 줄에 포함한다.**

- 관리자가 나중에 주제를 내리면 그것을 이미 선택한 사용자가 생긴다. 일괄로 걸러내면 **자기가 고른 주제인데 칩이 없어 필터를 걸 수 없다.**
- `profile-api.md` 4.1이 같은 방향을 이미 정하고 있다 — "관리자가 숨긴 주제도 개수에 포함한다. 편집 화면과 같은 기준을 써야 개수가 어긋나지 않는다"
- **뒤쪽의 "나머지 주제"에는 적용되지 않는다.** 관심 주제가 아닌 숨겨진 주제는 노출하지 않는다(FR-38 — 콘텐츠 풀이 없는 주제는 애초에 고를 수 없다).

정리하면 칩 줄 = `사용자의 활성 관심 주제 전부` + `그 밖의 is_visible = true 주제`.

### 3. 관심 주제끼리는 선택한 순서

**`user_interests.created_at` 오름차순**이다. 서버가 임의의 "대표" 기준을 만들지 않는다.

- 뒤쪽의 나머지 주제는 기존 규칙대로 `topics.display_order` 오름차순이다.
- **`profile-api.md` 4.1의 관심 주제 요약(`top_topics`)은 현재 `topics.display_order` 순이다.** 두 화면의 주제 순서가 달라지는데, 목적이 다르므로(칩은 필터 조작, 카드는 요약 표시) 문제가 아니라고 본다면 그대로 두면 된다. **어긋나 보이는 것을 막으려면 프로필 쪽도 함께 정해야 한다** — 이 문서의 범위 밖이라 지적만 남긴다.

## 남은 결정 — API 형태 (FE와 합의)

| 안 | 형태 | 장점 | 단점 |
|---|---|---|---|
| **A (권고)** | `GET /explore/feed` 응답에 `topics` 필드 추가 | **왕복이 늘지 않는다.** 칩 줄은 필터를 걸어 단일 목록으로 전환해도 유지되므로(`explore.md` 4.4-1), 피드에서 한 번 받아 계속 쓰면 된다 | 피드 응답이 조금 커진다(주제는 중분류 수십 개 수준) |
| B | `GET /explore/topics` 엔드포인트 신설 | 피드 응답이 가볍다. 관심사 편집 화면과 공유할 여지가 있다 | 탐색 진입 시 왕복이 하나 는다 |

**B를 고른다면 관심사 관리 화면과 함께 설계할 값이 있다.** `interest-management.md`는 아직 API 명세가 작성되지 않았는데, 그 화면도 **전체 주제 목록**이 필요하다. 같은 엔드포인트를 쓸지, 각자 둘지 회의 때 함께 보는 편이 낫다.

**응답 모양은 어느 안이든 같다.**

```json
{
  "topics": [
    { "id": "uuid", "name": "커리어", "is_interested": true },
    { "id": "uuid", "name": "생산성", "is_interested": false }
  ]
}
```

- **서버가 정렬해 내려주고 클라이언트는 순서를 재배치하지 않는다.** 정렬 규칙이 두 곳에 생기면 어긋난다.
- `is_interested`를 함께 주는 이유는 화면이 관심 주제 칩을 시각적으로 구분할 수 있어야 하기 때문이다. 필요 없다면 빼도 되며, **순서만으로는 어디까지가 관심 주제인지 알 수 없다.**

## 서버 구현 상태

**미구현.** 다만 재료는 이미 전부 있다.

| 필요한 것 | 이미 있는 것 |
|---|---|
| `is_visible = true` 주제, `display_order` 순 | `TopicService` → `TopicRepository.findAllVisible()` |
| 사용자의 활성 관심 주제, **선택한 순서** | `UserInterestService.findAllActive()` — 이미 `created_at ASC`로 정렬되어 있어 3번 결정과 일치한다 |
| 숨김 관심 주제까지 이름을 붙이기 | `TopicService.findAllByIds()` |

`ExploreModule`이 `InterestModule`을 이미 import 하고 있어 **의존 방향도 바뀌지 않는다.** 실제 작업은 두 목록을 합쳐 정렬하는 조립 코드다.

**참고** — 노출할 주제가 하나도 없는 상태는 별도로 설계하지 않아도 된다. 그때는 피드도 비어 E8(피드 비어 있음)이 되고, `explore-uiux.md` 4.7이 그 화면에서 **주제 칩 줄을 숨기도록** 이미 정하고 있다.

## 완료 조건

- Given `explore-api.md`를 읽는다 / When 칩 줄의 데이터 출처를 찾는다 / Then 엔드포인트(또는 피드 응답 필드)와 응답 모양이 정의되어 있다
- Given `explore.md` 4.2를 읽는다 / When 칩 목록의 구성 규칙을 찾는다 / Then **숨김 여부 처리**(관심 주제는 포함, 나머지는 `is_visible = true`만)와 **정렬 기준**(관심 주제는 선택 순서, 나머지는 `display_order`)이 명시되어 있다
- Given 관리자가 사용자의 관심 주제를 숨김 처리했다 / When 그 사용자가 탐색에 진입한다 / Then 그 주제 칩이 앞쪽에 그대로 노출되고 필터를 걸 수 있다
- Given 사용자가 A → B → C 순으로 관심 주제를 골랐다 / When 칩 줄을 본다 / Then A, B, C 순으로 앞쪽에 배치되고 그 뒤로 나머지 주제가 `display_order` 순으로 붙는다
- Given 관심 주제 중 콘텐츠가 0건인 주제가 있다 / When 칩 줄을 본다 / Then 그 주제도 칩으로 노출된다(피드에 `topic_group` 섹션이 없는 것과 무관하다)
