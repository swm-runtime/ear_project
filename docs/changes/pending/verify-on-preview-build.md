# 실기기 검증은 preview 빌드로 한다 — 스토어 빌드로 하지 않는다

| 항목 | 값 |
|---|---|
| 대상 문서 | `frontend/architecture.md` 2.1 OTA 업데이트 운용 |
| 발행 날짜 | 2026-09-15 |
| 발견 시점 | FE 수정 3건을 `dev`에 머지하고 OTA 발행에 성공했는데 실기기에 하나도 닿지 않았다 |
| 결정자 | 이주호 (2026-09-15, A안) |

## 문제

문서는 채널 대응표를 정확히 적고 있다 — `dev` merge → `preview`, `main` merge → `production`.
**그런데 검증을 어느 빌드로 하는지는 어디에도 없다.**

검증 기기가 스토어 빌드(=`production` 채널)면 `dev`에 아무리 머지해도 그 기기에는 가지
않는다. 2026-09-15에 이걸로 태웠다.

- #346(탭 복원 경쟁 조건) · #347(설정 아이콘) · #352(번들 표시)를 `dev`에 머지
- 워크플로는 매번 성공했다 — **`preview` 채널로**
- 검증 기기는 구글플레이 빌드라 3시간 전 `production` 번들을 계속 돌고 있었다
- 증상은 "고쳤다는 게 안 고쳐져 있다"로 보인다. **코드를 의심하게 만든다** — 실제로 그렇게 했다

번들 식별자 표시(`1.0.0 (앞 6자리)`)가 이것을 잡아줬어야 하는데, 6자리가 **약 4.6시간을 한
값으로 뭉쳐서**(업데이트 ID가 UUIDv7 — 앞 48비트가 발행 시각 ms) 서로 다른 발행이 같은
값으로 보였다. 8자리로 늘렸다(#352).

## 결정

**실기기 검증은 `preview` 내부 빌드로 한다.** 검증이 끝난 것만 `main`을 통해 스토어 빌드로 간다.

B안(= `dev` 머지마다 `production`도 발행)은 버렸다. 검증 기기와 실사용자 기기가 같아져서
**확인 안 된 코드가 곧바로 실사용자에게 나간다.** 지금은 사용자가 적어 체감되지 않을 뿐,
검증의 의미가 사라지는 구조다.

## 반영할 내용

`frontend/architecture.md` 2.1의 채널 표 아래에 다음을 더한다.

> - **실기기 검증은 `preview` 빌드로 한다.** 스토어 빌드는 `production` 채널이라 `dev` merge가
>   닿지 않는다 — 스토어 빌드로 검증하면 **고친 것이 안 고쳐진 것처럼 보인다**(2026-09-15).
> - **검증을 부탁할 때 기대 번들 ID(8자리)를 함께 준다.** 기기에 붙었는지를 눈으로 가를 수 있어야
>   한다. 발행 로그의 `Android update ID`·`iOS update ID` 또는 `eas update:list`의 값과 대조한다.
> - `preview` 빌드도 `runtimeVersion`이 맞아야 받는다. 정책 전환 전 빌드(2026-09-06 vc=6)는
>   지문이 옛 값이라 지금 발행을 받지 못한다 — **새로 뽑는다.**
