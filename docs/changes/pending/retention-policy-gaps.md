# domain.md 12.1 — 보존 기간이 없는 무한 성장 테이블에 기간을 정의한다

| 항목 | 값 |
|---|---|
| 대상 문서 | `docs/backend/domain.md` 12.1 |
| 발행 날짜 | 2026-09-09 |
| 발견 시점 | 백엔드 전수 감사 — 탈퇴 외 삭제 경로가 없고 문서에도 기간이 없는 테이블들 |
| 요청 파트 | 백엔드 |

## 왜 필요한가

12.1은 `email_verifications`(24h)·`first_drip_jobs`(30일)·`idempotency_keys`(24h) 등 일부만 주기 보존을
정의한다. 아래 테이블은 **탈퇴 시 파기(12.3)만 있고 운영 중 보존 기간이 없어** 무기한 성장한다.
코드가 임의로 지울 수 없으므로(문서 우선 규칙) 기간을 먼저 정의해야 한다.

| 테이블 | 성장 속도 | 실제 사용 범위 | 제안 기간 |
|---|---|---|---|
| `user_signals` | 재생·담기·완청마다 1행 | 드립 스코어링은 **최근 90일**만 읽는다(`SIGNAL_LOOKBACK_DAYS`), `content_stats` 재집계는 기간 구간별 | **180일** (스코어링 창의 2배 — 재집계 소급 여유) |
| `audio_access_logs` | 서명 URL 발급마다 1행(재생 중 5분 갱신 포함) | 이상 탐지·감사 — 현재 소비 코드 없음 | **90일** |
| `source_link_clicks` | 원문 클릭마다 1행 | `content_stats` 재집계 입력 | **180일** (signals와 동일) |
| `play_records` | 사용자×콘텐츠×서비스날짜당 1행 | 한도 판정(당일)·통계 재집계·프로필 청취 시간(전체) | **정의 보류** — 프로필이 전 기간 합계를 읽어 삭제 시 표시값이 바뀐다. 비식별 집계 컬럼으로 옮긴 뒤 정하는 것이 맞다 |
| `audit_logs` | 관리자 행위마다 | 감사 — 장기 보존이 목적 | **삭제하지 않음**(명시) — 파트너 계약 분쟁 대비 |
| `notification_logs` | 발송마다 | 중복 발송 방지 | **90일** |

## 수정 내용

12.1 표에 위 6행을 추가한다(`play_records`는 "보류 — 사유"로, `audit_logs`는 "영구 — 감사"로).

## 구현 (승인 후 별도)

승인된 기간마다 `idempotency-purge.scheduler.ts` 동형 배치. `created_at` 인덱스 유무를 구현 시 확인
(`user_signals`·`audio_access_logs`는 `created_at` 단독 인덱스가 없어 삭제 쿼리도 풀스캔 — 인덱스 추가 마이그레이션 동반).

## 완료 조건

- Given `domain.md` 12.1 / When 위 6개 테이블을 찾는다 / Then 각각 보존 기간(또는 영구·보류 사유)이 적혀 있다
