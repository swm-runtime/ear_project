## 배경

`explore.md` 4.5-5는 오타 교정·초성·어간 매칭을 **지원하지 않는 것**으로 두고 "검색 쿼리 로그로 미스율을 확인한 뒤 재검토"라고 적는다. PM이 2026-10-22에 그 보류를 걷고 두 가지를 넣기로 했다.

1. **오타 → "대신 검색"(질의 교정)**. 오타는 결과를 섞는 문제가 아니라 **검색어를 고쳐 다시 검색하는 문제**다(구글 "다음에 대한 검색결과"). 키워드 결과가 0건이면 서버가 교정어 하나를 골라 그 말로 검색하고 **"‘커리어’로 대신 검색했어요 / 혹시 ‘커리오’로 검색하고 싶나요?"** 로 알린다. 뒤 문장을 누르면 교정을 끄고 원문 그대로 검색한다. 교정어는 **자모 트라이그램**으로 고른다 — 한글은 자모 하나가 틀리면 음절이 통째로 바뀌어("커리오"↔"커리어") 음절 단위로는 유사도가 안 나오고, 자모로 풀면(ㅋㅓㄹㅣㅇㅗ ↔ ㅋㅓㄹㅣㅇㅓ) 한 자모 차이가 된다.
2. **의미 유사 검색 → 하이브리드(항상)**. 매 검색을 **키워드 부분 일치 + 임베딩 코사인** 두 엔진으로 돌려 RRF로 한 목록에 합산한다. 키워드 결과가 있어도 뜻이 가까운 편("이직" → '퇴사·연봉 협상')이 같은 목록에 든다. 대본 임베딩(`content_embeddings`, text-embedding-3-small 1536)이 추천용으로 이미 있고, 질의 임베딩만 AI 서버 `POST /embeddings`로 받는다 — **백엔드가 요청 시점에 AI 서버를 처음으로 부른다**(`architecture.md` 1장 — 모델 추론은 AI 서버 안).

- **비용 인지**: 디바운스 300ms 자동 검색이라 한 번 검색에 임베딩 호출이 몇 번 나간다. 질의 임베딩을 **정규화 질의 키로 인-프로세스 캐시**(TTL ≥ 커서 수명)해 타이핑 중 같은 질의·커서 다음 페이지는 재호출하지 않고, AI 서버가 늦거나 실패하면 **그 요청은 키워드 엔진만으로** 응답한다 — 검색은 AI 서버 때문에 실패하지 않는다.
- **초성 검색(ㅋㄹㅇ)은 여전히 되지 않는다** — 자모 트라이그램이 초성열과 거의 겹치지 않는다. 범위 밖.
- 자모 생성 컬럼·GIN 인덱스는 두지 않는다(02:48 안에서 걷음). 교정어 어휘(태그·주제명·시리즈 제목·제목 토큰)는 수백 편 규모라 **질의 시 함수 호출로 전수 비교**해도 충분하다. 어휘가 수만 항목으로 커지면 `search_terms` 머티리얼라이즈드 뷰 + trgm 인덱스를 그때 본다.

## 수정 내용

### 1. `explore.md` 4.5-2 입력 — `exact` 토글

- 추가: "혹시 ‘OO’로 검색하고 싶나요?"를 탭하면 **교정을 끄고(`exact=true`) 원문 그대로** 같은 검색을 다시 한다. 그 결과는 교정 없는 하이브리드(키워드 0 + 의미 결과 → 4.5-3의 "관련 결과", 둘 다 0 → 빈 결과)다. 최근 검색어 저장 규칙은 그대로(입력 그대로 저장 — 교정어를 저장하지 않는다. 사용자가 친 말이 "다시 찾는 경로"다).

### 2. `explore.md` 4.5-3 결과 목록 — 안내 2종

- **교정됨**(`corrected_from`가 있음): 격자 위 두 줄 — **"‘커리어’로 대신 검색했어요"** / **"혹시 ‘커리오’로 검색하고 싶나요?"**(탭 가능). 격자는 교정어의 하이브리드 결과.
- **관련 결과**(`match: "related"` — 교정 없이 첫 페이지에 키워드로 맞은 편이 0, 의미 결과만): **"‘커리오’와 관련된 결과예요"** 한 줄.
- 둘이 같이 뜨는 경우는 없다 — 교정은 **교정어로 키워드 결과가 1건 이상일 때만** 적용하므로(4.5-5) 교정된 응답은 항상 `match: "keyword"`다.
- 격자·타일·⋯ 시트·커서 로딩은 그대로. 두 엔진 모두 0건이고 교정어도 없으면 종전 빈 결과(관련 주제 칩 + 인기).
- **태그 전용 검색(`#태그`)은 종전대로** 태그 정확 일치만 — 교정도 의미 엔진도 없다.

### 3. `explore.md` 4.5-5 매칭·랭킹 — 전면 개정

- **흐름**: ① 정규화(NFC·소문자·트림) → ② 하이브리드(키워드 + 의미) → ③ `exact`가 아니고 **키워드 엔진이 0건**이면 교정어 탐색 → 교정어가 있고 **교정어로 키워드 1건 이상**이면 교정어로 ②를 다시 돌려 그 결과를 낸다(`query_used` = 교정어, `corrected_from` = 원문). 아니면 ②의 원문 결과 그대로(의미 결과만 있으면 `related`).
- **키워드 엔진**: 종전 `ILIKE` 부분 일치(제목 > 태그 > 저자 > 주제명 > 설명, 시리즈 제목은 스위치 켜짐일 때)·가중 합산으로 엔진 내 순위.
- **의미 엔진**: `query_used` 임베딩(AI 서버, 같은 모델) vs `content_embeddings.embedding` 코사인 ≥ 임계값, 상위 K. `model` 현행·`content_version` 일치 행만(재발행 후 미갱신 벡터 제외 — 5.6). 임베딩 없는 콘텐츠는 이 엔진에서 빠진다.
- **합산 = RRF**: 편마다 Σ 1/(k + 엔진 내 순위). **k·임계값·K는 서버 구현이 소유**(가중 계수와 같은 원칙 — 시작 k=60·코사인 임계·K=50, 로그로 조정). 동점: 인기(직전 확정 구간) → `published_at` DESC → id. 클라이언트는 재배열하지 않는다.
- **교정어 선택**: 어휘 = 사용자 시장의 발행 콘텐츠에서 **태그 항목 · 주제명 · 시리즈 제목(스위치 켜짐) · 제목 토큰**(공백·문장부호로 나누고 끝의 조사 — 을/를/이/가/은/는/의/에/로/와/과/도 — 를 뗀 것). `word_similarity(hangul_to_jamo(원문), hangul_to_jamo(어휘)) ≥ 임계값`(시작 0.5)에서 최대값, 동점은 태그·주제명 우선(깨끗한 명사) → 빈도. 원문과 같은 말은 교정어가 아니다. 자모 분해는 **SQL 함수 `hangul_to_jamo(text)` 하나**(겹모음 ㅘ=ㅗ+ㅏ·겹받침 ㄺ=ㄹ+ㄱ, 치는 순서대로 — `search-text.util.ts`의 로그 묶음용 분해와 같은 규칙).
- **AI 서버 결손**(타임아웃 예산 초과·오류): 의미 엔진 없이 키워드만으로 응답, `engines`에 `semantic` 없음. 교정 흐름은 영향 없음.
- 종전 "지원하지 않는 것" 개정: 오타는 교정이, 동의어·주제 연관은 의미 엔진이 흡수한다. 여전히 지원하지 않는 것은 **초성 검색 · 형태소 어간 변형**. "로그로 미스율 확인 뒤 재검토"는 **임계값·k 조정의 근거**로 역할이 바뀐다.
- 성능 메모: 후보 전수 계산(ANN 없음 — 5.6의 기존 결정). 수천 편까지 전수 코사인으로 충분, 그 위로 가면 HNSW를 그때 본다.

### 4. `explore-api.md` 4.5 `GET /explore/search`

- 요청 추가: **`exact`** boolean, 선택(기본 `false`) — `true`면 교정을 하지 않는다. "혹시 ‘OO’로 검색하고 싶나요?" 탭이 보내는 값. `#` 질의에는 의미 없음(무시).
- 응답 최상위 추가:
  - **`query_used`** string — 실제 검색에 쓴 정규화 질의. 교정 없으면 입력의 정규화 값.
  - **`corrected_from`** string | null — 교정했으면 원문(정규화 값). 화면의 "혹시 ‘OO’로" 자리.
  - **`match: "keyword" | "related"`** — 첫 페이지에 키워드로 맞은 편이 하나라도 있으면 `keyword`, 없으면 `related`(`items`가 비면 `keyword`). 교정된 응답은 항상 `keyword`.
  - **`engines: ("keyword" | "semantic")[]`** — 이 응답을 만든 엔진. 진단·로그 대조용.
- `items[]`에 **`matched_by: ("keyword" | "semantic")[]`** — 어느 엔진에서 왔는가. 화면은 지금 쓰지 않는다(나중에 '관련' 꼬리표의 근거).
- **덧붙이는 필드만** — 옛 앱(1.2.x·1.3.0)은 무시하고 결과를 일반 결과처럼 그린다(교정어로 검색된 것도 모른다 — 0건보다 낫다고 보고 호환으로 둔다).
- 커서: `query_used`·`exact`·RRF 점수·id 키셋·질의 벡터 캐시 키. 다음 페이지는 같은 교정어·같은 벡터로 이어 가고, 응답마다 `query_used`·`corrected_from`을 반복한다. 캐시가 사라졌으면 재계산(미세한 순서 흔들림 감수 — 문서 명시). 발급 시점과 `query`·`topic_ids`·`exact`가 다르면 `EXPLORE_CURSOR_INVALID`.
- 랭킹 규칙·임계값·k·교정어 선택은 4.5-5가 소유하고 이 문서는 재정의하지 않는다.
- 예시 JSON에 `"query_used"`·`"corrected_from"`·`"match"`·`"engines"`·`items[].matched_by` 추가.

### 5. `explore-uiux.md` 4.5 — E7 앞에 안내 2종

- **교정 안내**(두 줄, 격자 첫 행 위): 1줄 **"‘커리어’로 대신 검색했어요"**(보조 글자색) · 2줄 **"혹시 ‘커리오’로 검색하고 싶나요?"**(링크 색, 탭 영역 44pt — 탭하면 `exact=true`로 같은 검색). en **"Showing results for “커리어”"** / **"Search instead for “커리오”?"**. 두 검색어는 입력·교정 정규화 값을 그대로 되비춘다.
- **관련 결과 안내**(한 줄): **"‘커리오’와 관련된 결과예요"** / en **"Showing related results for “커리오”"**. 보조 글자색.
- 상태 ID는 새로 두지 않는다(E2 격자 + 안내 — 빈 상태가 아니다). 접근성: 결과 도착 때 안내를 **한 번** 낭독(커서로 격자가 늘어날 때 다시 읽지 않는다). 교정 안내의 2줄은 버튼 역할·"‘커리오’로 검색" 낭독.
- 타일에 '관련' 꼬리표는 두지 않는다(범위 밖 — `matched_by`가 근거로 남아 있다).

### 6. `domain.md` 5.1 · 5.6

### 7. `domain.md` 5.7 `search_query_logs` · `admin-api.md` 4.21

- 컬럼 추가: **`query_used varchar(100)`**(교정어 또는 원문 — `query`는 종전처럼 입력 정규화 값), **`keyword_count smallint`**(첫 페이지 중 키워드로 맞은 건수), **`engines text[]`**. `result_count`는 하이브리드 첫 페이지 건수(종전 의미 "사용자가 본 건수" 유지). 묶음 덮어쓰기 때 함께 덮는다. `exact=true` 재검색은 같은 `query`의 재조회가 아니라 **새 행**(교정 거절을 세기 위해 — `query_used = query`, 직전 행이 교정 행).
- 4.21 응답: `totals.corrected`(`query_used <> query`), `totals.correction_rejected`(교정 행 직후 10분 안 같은 `query`의 `exact` 행), `totals.keyword_misses`(`keyword_count 0`), `totals.rescued`(`keyword_count 0`이고 `result_count > 0` — 의미 엔진이 살린 것), `totals.semantic_unavailable`(`engines`에 `semantic` 없음), `missed[]`·`top[]`에 `query_used`·`keyword_count`. `misses`·`miss_rate` 정의는 불변.
