# [BE] settings-api.md 4.1 — 버전 조회에 `platform`이 없어 플랫폼별 값을 고를 수 없다

| 항목 | 값 |
|---|---|
| 대상 문서 | `docs/spec/api/settings-api.md` 4.1(Request 파라미터 · `version` 설명) — 스플래시 API 명세 작성 시 그쪽도 함께 |
| 요청 파트 | 백엔드 (**결정은 FE와 함께** — 요청 파라미터가 늘어나는 계약 변경이다) |
| 관련 작업 | 설정 백엔드 구현 (`feat(be)/settings`) — 버전 판정 구현 중 발견 |
| 근거 문서 | `docs/backend/domain.md` 13.3 · `docs/features/splash.md` 6장 |
| 성격 | **문서 간 충돌.** 두 문서가 플랫폼별 값을 전제하는데 계약에 그것을 고를 입력이 없다 |
| 상태 | 대기 — **FE가 설정 화면을 시작하기 전에 정하는 것을 권한다**(아래 "왜 지금인가") |

> **지금 당장 깨지지는 않는다.** iOS·Android의 최신 버전이 같은 동안에는 드러나지 않는다. 문제는 **한쪽 스토어 심사가 늦어지는 순간**이다.

---

## 어긋난 지점

두 문서가 **플랫폼별로 값이 다르다**고 정하고 있다.

`domain.md` 13.3:

> **플랫폼(iOS/Android)별로 값을 나눠야 한다.** 스토어 심사 주기가 달라 최소 지원 버전이 동시에 올라가지 않는다.

`splash.md` 6장:

> 최소 지원 버전·최신 버전·점검 공지는 **배포 설정에서 관리**하고 서버가 조회 API로 내려준다(domain.md 13.3). **플랫폼별로 값이 다르다.**

그런데 `settings-api.md` 4.1의 요청 파라미터는 이것뿐이다.

| 필드 | 타입 | 필수 |
|---|---|---|
| app_version | string (semver) | 필수 |

**플랫폼을 받지 않으므로 서버가 어느 쪽 값과 비교해야 하는지 알 수 없다.** 구현은 계약을 따라 단일 값(`LATEST_APP_VERSION`)으로 만들었다.

## 무엇이 잘못되나

**한쪽 스토어 심사가 늦어지면 다른 쪽에 잘못된 안내가 나간다.**

Android에 1.5.0이 먼저 배포되고 iOS는 심사 대기 중이라고 하자. 배포 체크리스트대로 `LATEST_APP_VERSION`을 1.5.0으로 올리면:

| 플랫폼 | 실제 스토어 최신 | 사용자 앱 | 현재 구현의 판정 |
|---|---|---|---|
| Android | 1.5.0 | 1.4.0 | [업데이트] ✅ 맞다 |
| iOS | **1.4.0** | 1.4.0 | **[업데이트]** ❌ 받을 게 없는데 배지가 뜬다 |

설정 화면은 **안내**라 사용자가 스토어에 갔다가 돌아오는 정도로 끝난다. **스플래시는 다르다** — `min_supported_version`으로 **차단**하기 때문이다. iOS 심사가 밀린 상태에서 최소 지원을 1.5.0으로 올리면 **iOS 사용자 전원이 업데이트할 수 없는 화면에 갇힌다.** `domain.md` 13.3이 "심사 주기가 달라"를 이유로 든 것이 이 상황이다.

## 제안

### 1. `settings-api.md` 4.1 Request에 `platform` 추가

| 필드 | 타입 | 필수 | 비고 |
|---|---|---|---|
| app_version | string (semver) | 필수 | *(그대로)* |
| **platform** | **enum `ios` / `android`** | **필수** | 어느 스토어의 최신 버전과 비교할지. **값 집합은 기기 등록(`onboarding-api.md` 4.9)과 같다** |

- **선택이 아니라 필수로 둔다.** 기본값을 정하면 그 플랫폼에는 맞고 다른 쪽에는 조용히 틀린 판정이 나간다 — 틀렸다는 사실이 드러나지 않는 기본값은 두지 않는다.
- **응답은 바뀌지 않는다.** `version` 오브젝트는 `latest_version` · `min_supported_version` · `update_available` 셋 그대로이며, 서버가 플랫폼에 맞는 값을 채워 내려줄 뿐이다.

### 2. `version` 설명에 한 줄

> - `latest_version` · `min_supported_version`은 **요청한 플랫폼의 값**이다(`domain.md` 13.3 — 스토어 심사 주기가 달라 두 플랫폼의 값이 동시에 올라가지 않는다). 비교도 그 값으로 서버가 한다.

### 3. 스플래시 명세를 쓸 때 같은 규칙을 따른다

`splash.md` 6장이 이미 플랫폼별 값을 전제하고 있으므로, API 명세를 쓸 때 같은 `platform` 파라미터를 받게 한다. **강제 업데이트는 차단이라 설정보다 위험이 크다.**

## 코드 수정 범위 — 지금이면 작다

### 프론트엔드 — **수정할 게 없다**

`frontend/src/features/`에 **settings 폴더가 아직 없고**, 설정 API를 호출하는 코드가 한 줄도 없다(2026-08-09 확인 — 프로필까지 구현됨). **지금 계약을 넓히면 FE는 처음부터 그렇게 만들면 된다.**

이미 만들어져 있었더라도 몫은 작다 — React Native의 `Platform.OS`가 `'ios' | 'android'`를 그대로 주므로 쿼리 파라미터 한 줄이고, 응답 모양이 그대로라 화면 코드는 손대지 않는다.

### 백엔드

| 대상 | 바뀌는 것 |
|---|---|
| 환경 변수 | `LATEST_APP_VERSION` → `_IOS` / `_ANDROID`, 최소 지원도 동일 (2개 → 4개) |
| 요청 DTO | `platform` 필드 추가 — **`DevicePlatform` enum을 그대로 쓴다** |
| `SettingsOrchestrator.buildVersion()` | 플랫폼으로 값을 고르는 분기 |
| 테스트 | 플랫폼별 케이스 |

**값 집합을 새로 만들 필요가 없다.** `DevicePlatform`(`ios` · `android`)이 이미 있고 `device_tokens`와 기기 등록 요청(`register-device-request.dto.ts`)이 쓰고 있다 — 같은 문자열을 그대로 재사용한다.

`semver.util.ts`는 손대지 않는다. 비교 함수는 그대로고 **어느 값을 비교할지만** 달라진다.

## 왜 지금인가

| 시점 | FE | BE |
|---|---|---|
| **지금** | 없음 (화면 미개발) | env 2개 추가 · DTO 1필드 · 분기 · 테스트 |
| 설정·스플래시 배포 후 | API 호출부·mock·테스트 수정 | 위 + **배포된 차단 로직 수정** + 배포 순서 검토 |

미뤄서 얻는 것이 없고, 늘어나는 것은 위험뿐이다. **스플래시가 아직 구현 전이라는 점이 특히 크다** — 지금 정하면 처음부터 맞게 만들어진다.

## 함께 확인할 것

- **반려하면 `domain.md` 13.3과 `splash.md` 6장을 고쳐야 한다.** 단일 값으로 확정하는 결정이라면 두 문서의 "플랫폼별로 값이 다르다"를 걷어내야 계약과 스키마 문서가 같은 말을 하게 된다. **어느 쪽이든 문서 수정은 필요하다** — 지금 상태가 유일하게 어긋난 상태다.
- **점검 공지도 같은 배포 설정에 있다**(`domain.md` 13.3 `AppConfig`). 플랫폼별로 나눌지는 그 기능을 만들 때 함께 본다 — 이 요청은 버전 두 값만 다룬다.
- **웹은 범위 밖이다.** 현재 클라이언트는 앱뿐이라 `ios` · `android` 둘로 충분하다. 늘어나면 `DevicePlatform`에 값을 더한다.
