# [문서] 백엔드 모니터링의 로그 조회 상한을 "건수" 기준으로 다시 적는다

| 항목 | 값 |
|---|---|
| 대상 문서 | `features/backend-monitoring.md` 실시간 로그(44행)·요청 통계(45행)·대시보드(48행) |
| 요청 파트 | 문서(pipeline 구현은 `fix(ai)/latency-graph-to-dev`에서 선반영) |
| 발행 날짜 | 2026-09-08 (2026-09-09 개정 — 구현이 줄 기준에서 건수 기준으로 바뀌었다) |
| 발견 시점 | 대시보드 응답시간 그래프가 6시간을 골라도 오른쪽 끝 세 칸만 그려지는 원인을 찾다가 |
| 심각도 | 중 — 값이 아니라 **단위**가 오해를 만든다. 이 오해가 그래프를 못 믿게 했다 |

## 왜 필요한가

문서는 상한을 "기본 300줄(최대 1,000줄)"로 적는다. 값 자체는 맞지만, 읽는 사람은 이를
"요청 1,000건"으로 받아들인다. **줄과 요청은 1:1이 아니다.**

운영 CloudWatch 실측(2026-09-08 `admin.earcast.co.kr`, api 스트림 1,000줄):

| | 값 |
|---|---|
| 요청 1건이 차지하는 줄 | **9~11줄** — `request completed` + `Object(6) {` + 필드 6줄 + `}` |
| 1,000줄 안의 요청 | 90건 |
| 그중 헬스체크 | **54건(60%)** — 파싱 후 버려지는데 조회 예산은 다 먹었다 |
| 그래프가 실제로 쓴 것 | **36건 · 26.8분치** |

Nest ConsoleLogger는 `compact:false`가 기본이라 객체를 여러 줄로 찍고,
`backend/docker-compose.prod.yml`의 awslogs 드라이버에 `awslogs-multiline-pattern`이
없어 줄마다 별개 이벤트가 된다. `GetLogEvents`는 tail이라 상한에 걸리면 **창의 앞부분이
통째로 빠진다.** 그래서 6시간을 골라도 36칸 중 3칸만 값이 있었다.

**줄 수를 올리는 것으로는 해결되지 않는다** — `GetLogEvents` 한 번의 CloudWatch 상한이
10,000이고, 그중 60%는 헬스체크가 먹는다. 그래서 구현을 **건수 기준**으로 바꿨다.

## 수정 내용

| 대상 | 현재 | 변경 |
|---|---|---|
| 실시간 로그(44행) | `기본 300줄(최대 1,000줄)` | 그대로 둔다 — 이 화면은 원문 tail이라 줄이 맞는 단위다 |
| 요청 통계(45행) | 상한 언급 없음 | `한 번에 최대 1,500**건**을 모은다(줄이 아니다)` |
| 대시보드(48행) | 상한 언급 없음 | `요청 로그는 건수 기준으로 모은다 — 목표 1,500건을 채울 때까지 CloudWatch를 과거로 넘기고(최대 6회), 헬스체크는 건수를 세기 전에 제외한다. 못 채우면 창의 앞부분이 빠지며 [요청 수] 카드가 어디부터 그렸는지 밝힌다` |

덧붙일 배경 한 줄: **요청 1건이 9~11줄이라 "줄 수"는 표본 수의 대용이 되지 못한다.**

## 완료 조건

- Given `features/backend-monitoring.md` / When 대시보드 행을 읽는다 / Then 상한이 **건수**(1,500건)이고 헬스체크를 세기 전에 제외한다고 적혀 있다
- Given 같은 문서 / When 요청 통계 행을 읽는다 / Then 상한이 건수 단위임이 적혀 있다
- Given 같은 문서 / When 실시간 로그 행을 읽는다 / Then 줄 단위 상한이 그대로이고, 그것이 원문 tail이기 때문임을 알 수 있다
- Given 같은 문서 / When 목표 건수를 못 채웠을 때의 동작을 찾는다 / Then 창의 앞부분이 빠진다는 점과 화면 표기가 적혀 있다
