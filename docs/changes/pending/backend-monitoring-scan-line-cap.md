# [문서] 백엔드 모니터링의 로그 상한을 "줄 수"로 명시하고 값을 올린다

| 항목 | 값 |
|---|---|
| 대상 문서 | `features/backend-monitoring.md` 실시간 로그·대시보드·요청 통계 행 |
| 요청 파트 | 문서(pipeline 구현은 `fix(ai)/latency-graph-accuracy`에서 선반영) |
| 발행 날짜 | 2026-09-08 |
| 발견 시점 | 대시보드 응답시간 그래프가 6시간을 골라도 오른쪽 끄트머리에만 그려지는 원인을 찾다가 |
| 심각도 | 중 — 값이 틀린 게 아니라 **단위**가 오해를 만든다. 이 오해가 그래프를 못 믿게 했다 |

## 왜 필요한가

문서는 상한을 "기본 300줄(최대 1,000줄)"로 적는다. 값 자체는 맞지만, 읽는 사람은 이를
"요청 1,000건"으로 받아들인다. **줄과 요청은 1:1이 아니다.**

Nest ConsoleLogger는 `compact:false`가 기본이라 요청 로그 객체를 여러 줄로 찍고
(`Object(6) {` + 필드 6줄 + `}` = 8줄), `backend/docker-compose.prod.yml`의 awslogs
드라이버에는 `awslogs-multiline-pattern`이 없어 줄마다 별개 CloudWatch 이벤트가 된다.
즉 1,000줄 = **요청 약 125건**이고, 여기에 파싱 후 버려지는 `/health` 핑과 WARN/ERROR
블록이 같은 예산을 먹는다.

`GetLogEvents`는 tail(`startFromHead: false`)이라 상한에 걸리면 **창의 앞부분이 통째로
빠진다.** 그래서 6시간을 골라도 최근 몇 분만 그려졌고, 버킷당 표본이 한 자릿수가 되어
p95가 사실상 그 버킷의 최댓값이 됐다(표본 n ≤ 20이면 p95는 정의상 최댓값에 닿는다).

## 수정 내용

| 현재 | 변경 |
|---|---|
| 실시간 로그: `기본 300줄(최대 1,000줄)` | `기본 300줄(최대 10,000줄)` |
| 대시보드·요청 통계: 상한 언급 없음 | `한 번에 10,000줄을 훑는다 — **요청 건수가 아니라 줄 수**이고, 요청 1건이 8줄이라 요청 약 1,200건에 해당한다. 상한에 걸리면 창의 앞부분이 빠지며 화면이 어디부터 그렸는지 밝힌다` |

## 완료 조건

- Given `features/backend-monitoring.md` / When 실시간 로그 행의 상한을 읽는다 / Then 10,000줄이다
- Given 같은 문서 / When 대시보드·요청 통계 행을 읽는다 / Then 상한이 줄 단위임과 요청 환산값이 적혀 있다
- Given 같은 문서 / When 상한 초과 시 동작을 찾는다 / Then 창의 앞부분이 빠진다는 점과 화면 표기가 적혀 있다
