# 추천 평가 체계 — 배포 전 오프라인 평가

> 작성: 2026-09-30 (KAN-108). 소유: 백엔드. 추천 로직(`features/drip-scheduling.md` 4장)을 바꾸는 PR은 이 문서의 절차를 거친다.
> 연결 문서: `features/drip-scheduling.md`(동작 규칙) · `spec/api/admin-api.md` 4.18(스냅샷 내보내기) · `tickets/frontend/pending/recommendation-algorithm-research.md`(KAN-104 — 대안 비교는 이 문서의 지표·기준으로 한다)

## 1. 목적

추천(드립 편성·탐색 랭킹)을 고치면 **배포 전에 무엇이 좋아지고 무엇이 나빠졌는지 숫자로 남긴다.** 지금까지는 개발계에서 몇 명을 눌러 보고 "괜찮아 보인다"로 배포했다. 그러면 ① 사람이 안 본 사용자에게 무슨 일이 나는지 모르고 ② 지난번보다 나아졌는지 비교할 근거가 없고 ③ "일어나면 안 되는 일"(본 것을 다시 준다, 관심 밖 콘텐츠가 정규에 섞인다)을 우연에 맡긴다.

세 가지를 한 번에 본다:

| 질문 | 방법 | 절 |
|---|---|---|
| 일어나면 안 되는 일이 일어나는가 | **불변식** — 평가가 만든 편성 계산 전부에 대해 검사 | 5.1 |
| 전형적인 행동에 기대대로 반응하는가 | **페르소나 시뮬레이션** — 합성 사용자 7종이 N일간 받고 반응 | 3.2 · 5.2 |
| 실사용자에게 지난번보다 나은가 | **백테스트 + 편성분 지표** — 실사용자 스냅샷 위에서 기준선과 비교 | 4 · 5.3 |

## 2. 구성 — 점수식을 다시 쓰지 않는다

```
GET /admin/recommend-eval/snapshot ──▶ eval/snapshots/<env>-<날짜>.json   (익명 · 커밋 금지)
                                              │
npm run eval:recommend -- --snapshot … ───────▶ EvalWorld(인메모리 세계)
                                              │      └─ DripBatchOrchestrator.planForUser ← 제품 코드 그대로
                                              ▼
                                     eval/reports/<시각>-<sha>-<env>.json + 마크다운 요약(표준 출력)
```

- **평가기는 제품 편성기(`DripBatchOrchestrator.planForUser`)를 그대로 돌린다.** 스코어링(`DripScoringService`)·취향 계산(`PreferenceVectorService.compute`)·자동 확장(`decideAutoExpand`)·시리즈 게이트·MMR 전부가 제품 코드다. 평가기가 대신하는 것은 **SQL이 답하던 것뿐**이다 — 후보 필터·정렬(`ContentRepository.findCandidates`), 라이브러리 집계, 신호 조회. 그 쿼리를 바꾸면 `eval-world.ts`의 대응 메서드도 고쳐야 한다(각 메서드에 원본 위치를 적어 두었다). 점수식을 두 벌 유지하면 반드시 어긋나고, 어긋난 사실을 아무도 모른다 — 편성 미리보기(admin-api 4.16)가 계산기를 배치와 공유하는 것과 같은 이유다.
- 코드: `backend/src/modules/recommend-eval/` — `eval-world.ts`(세계) · `eval-runner.ts`(백테스트·지표·시뮬레이션·불변식) · `eval-personas.ts`(샘플 사용자) · `eval-metrics.ts`(지표 정의) · `eval-report.ts`(판정·마크다운) · `synthetic-catalog.ts`(합성 카탈로그) · `cli.ts` · `recommend-eval-snapshot.service.ts`(내보내기).

## 3. 입력 — 스냅샷과 샘플 사용자

### 3.1 실사용자 스냅샷

`GET /admin/recommend-eval/snapshot`(관리자, 읽기 전용 — `admin-api.md` 4.18)이 발행 콘텐츠(메타·주제·집계·임베딩)와 사용자(관심 주제·신호·라이브러리·영구 제외·토글)를 한 파일로 내려준다.

- **익명이다.** 사용자는 `u001`… 키뿐이고 이메일·닉네임·`users.id`가 없다. 그래도 행동 이력이므로 **저장소에 커밋하지 않는다** — `backend/eval/`은 gitignore다.
- 운영 스냅샷이 평가의 기준이다(실제 신호가 있는 곳은 운영뿐). 개발계 스냅샷은 콘텐츠 동기화(KAN-84)로 카탈로그는 같지만 사용자 행동이 적어 백테스트 표본이 안 된다.
- 받는 법: 어드민 웹에 로그인한 브라우저에서 `localStorage.ear_admin_tokens`의 `access_token`으로 `curl -H "Authorization: Bearer <token>" https://api.earcast.co.kr/api/v1/admin/recommend-eval/snapshot > backend/eval/snapshots/prod-2026-09-30.json`. (어드민 웹 [스냅샷 내려받기] 버튼은 후속 — 9장)

### 3.2 샘플 사용자 셋(페르소나)

추천이 **달라져야 하는** 행동을 한 가지씩 담은 합성 사용자. 주제·콘텐츠를 이름으로 박지 않고 카탈로그 구조(콘텐츠가 많은 주제 순)에서 고르므로 어떤 스냅샷 위에서도 같은 정의가 돈다. 재료가 없으면(시리즈 없음 등) 그 페르소나만 건너뛴다.

| 페르소나 | 상태 | 반응(시뮬레이션) | 검사 |
|---|---|---|---|
| `cold-start` | 관심 3개, 이력 없음 | 받은 편 전부 완청 | 첫날 정규가 목표 편수를 채운다 |
| `focused` | 관심 3개 중 하나만 5편 완청 | 그 주제만 완청, 나머지 무시 | 첫날 정규 1순위가 그 주제 |
| `negative` | 관심 2개 — 하나는 3편 완청, 하나는 받는 족족 삭제 | 같은 패턴 | 첫 3일 정규에서 지운 주제 ≤ 완청한 주제 |
| `outside-listener` | 관심 3개 + **관심 밖 주제 3편 완청** | 그 주제만 완청 | 첫날 자동 슬롯 추가 · 3일 안에 그 주제 정규 편성 · 직접 고른 주제 유지 (스위치 OFF면 "관심 주제 불변") |
| `series-follower` | 시리즈 1편 완청 | 전부 완청 | 첫날 정규에 2편 |
| `heavy` | 관심 1개, 그 주제 70% 완청 | 전부 완청 | (고갈되는 날을 리포트에 싣는 것이 목적) |
| `remover` | 주제 하나를 직접 해제한 뒤 그 주제 2편 완청 | 전부 완청 | 해제 주제가 다시 붙지 않는다 · 그 주제 콘텐츠가 탐험 편으로 오지 않는다 |

시뮬레이션은 하루 단위다: 편성 계산 → 적립(정규 `drip`·탐험 `discovery`) → 페르소나 반응(완청/무시/삭제, 신호와 라이브러리 상태에 반영) → 다음 날. 자동 확장 판정은 매일 실제로 적용한다(배치와 같은 함수 — `planForUser`의 `persistAutoExpand`).

### 3.3 합성 카탈로그

스냅샷 없이 돌리면(`--snapshot` 생략, CI) 주제 6 × 콘텐츠 14 + 3부작 시리즈의 고정 카탈로그를 쓴다(`synthetic-catalog.ts`, 시드 고정). 임베딩은 주제별 축에 잡음을 얹은 16차원 — 같은 주제끼리 가깝다는 성질만 있으면 코사인 계산이 실데이터와 같은 방향으로 움직인다. **숫자 지표의 절대값은 의미가 없다** — 불변식·페르소나 검사용이다.

## 4. 지표 정의

### 4.1 백테스트 — 실사용자 (`backtest`)

"사용자가 **스스로 고르고 완청한** 콘텐츠를, 고르기 직전 시점의 세계에서 정규 편성 순위가 몇 위에 세웠는가."

- 사례: `library_items.source ∈ {save, onboarding}`이고 `completed_at`이 있는 항목. **드립·탐험으로 받은 것은 뺀다** — 추천기가 고른 것을 추천기로 맞히는 순환이다. 사용자당 최근 5건.
- 되감기: `added_at` 직전으로 신호·라이브러리·영구 제외·발행 콘텐츠를 걷어낸다. 되감을 수 없는 것 — 콘텐츠 누적 집계(`play_count`·`complete_count`)와 관심 주제 이력(현재 값 사용). 한계로 적어 둔다.
- 값: `Hit@K`(K = 2·5·10 — 2는 하루 정규 편수) · `MRR`. 정답이 정규 후보에 없던 사례(관심 밖 주제·시리즈 게이트)는 모든 방법에서 빗나간 것으로 센다 — 그 비율이 `reachableShare`다(낮으면 후보 범위의 문제지 순위의 문제가 아니다).
- 기준선: **인기순**(같은 후보를 `play_count` 순으로) · **무작위 기대값**. 개인화가 인기순을 못 이기면 신호 축이 일을 안 하는 것이다.

### 4.2 편성분 지표 (`lists` · `simulation`)

| 지표 | 정의 | 방향 |
|---|---|---|
| 고갈률 `exhaustionRate` | 정규 편성분 < 목표 편수인 계산의 비율 | 낮게 |
| 주제 다양성 `topicDiversity` | 편성분의 서로 다른 주제 수 / 편수 (최대 1) | 참고 — 1이면 하루 편성이 전부 다른 주제 |
| 편성분 내 거리 `intraListDistance` | 편성분 쌍의 평균 (1 − 코사인) — 임베딩 있는 쌍만 | 높게 — 내용이 겹치지 않는다 |
| 신규 `freshShare` | 발행 14일 이내 콘텐츠 비율 | 참고 |
| 미노출 `zeroExposureShare` | 아무에게도 편성된 적 없는 콘텐츠 비율 — 탐험 슬롯의 존재 이유 | 참고 |
| 커버리지 `catalogCoverage` | 편성된 서로 다른 콘텐츠 수 / 발행 카탈로그 | 높게 — 같은 편만 돌지 않는다 |
| 사용자 간 겹침 `userOverlap` | 사용자 쌍의 편성분 자카드 평균 | 낮게 — 사람마다 다른 것이 간다 |
| 자동 확장 `autoExpand` | 판정 분포(`add`·`replace`·`expire`·`none`) | 참고 |

`lists`는 실사용자 전원에게 "지금 배치를 돌리면"의 편성분(각 1일), `simulation`은 페르소나 N일치다.

### 4.3 페르소나 (`personas`)

`likedTopicShare` — 정규 편성분 중 그 페르소나가 좋아하는 주제에 걸린 비율(합성 사용자의 적중률). `exhaustedOnDay` · `autoExpandOnDay` · `checks`.

## 5. 통과 기준

### 5.1 불변식 — 절대 기준 (하나라도 어기면 실패)

1. 정규 편성분은 (자동 슬롯 포함) 관심 주제 안의 콘텐츠다
2. 라이브러리에 있었거나 영구 제외된 콘텐츠를 다시 편성하지 않는다
3. 같은 날 같은 콘텐츠가 두 번 편성되지 않는다
4. 시리즈는 직전 편을 완청한 다음 편만 정규로 가고, 탐험은 1편(또는 단편)만 간다
5. 편성 편수가 플랜 편수를 넘지 않는다
6. 사용자가 직접 해제한 주제의 콘텐츠는 탐험 편으로 가지 않는다
7. 자동 확장은 직접 고른 관심 주제를 빼지 않고 자동 슬롯은 1개를 넘지 않는다

### 5.2 페르소나 검사 — 절대 기준, `soft` 예외

3.2의 검사는 실패면 평가 실패다. 단 **명세의 기대이지만 현 코드가 못 미치는 것으로 알고 있는 항목**은 `soft`로 표시해 경고로만 싣는다 — 고쳐서 통과하면 `hard`로 올린다. 현재 soft: 없음.

- 이력: `series-follower` "첫날 정규에 2편"이 첫 실행(2026-09-30)에서 실패했다 — 코드가 시리즈 연속을 메타 축 항목 하나(가중치 0.1)로만 밀어 콜드스타트에서 2편이 19위. 같은 날 선정 규칙으로 고쳤다(`drip-scheduling.md` 4.2-3 — 시리즈 연속 편은 다양성 선정에 앞서 먼저 뽑는다, `DRIP_ALGORITHM_VERSION` 2026-09-30.2) → hard.

### 5.3 지표 — 기준선 대비 (기준선이 있을 때만)

| 지표 | 실패 조건 | 비고 |
|---|---|---|
| 백테스트 `Hit@10` | 0.05 이상 하락 | 사례 20건 이상일 때만. 미만이면 참고값(경고) |
| 편성분 내 거리 | 0.05 이상 하락 | `simulation`·`lists` 각각 |
| 커버리지 | 0.05 이상 하락 | 〃 |
| 고갈률 | 0.05 이상 상승 | 〃 |
| 페르소나 `likedTopicShare` | 0.10 이상 하락 | 페르소나별 |

값은 `eval-report.ts` `PASS_CRITERIA` — **초기값**이며 표본이 쌓이면 조정한다. 좋아지는 방향은 막지 않는다. 기준선이 없으면 지표는 판정하지 않고 리포트가 곧 기준선이 된다. 경고: 사례 20건 이상인데 개인화 `Hit@10`이 인기순보다 낮으면 신호 축 점검 대상이다.

## 6. 실행

```bash
cd backend
npm run eval:recommend                                    # 합성 카탈로그 — 불변식·페르소나만
npm run eval:recommend -- --snapshot eval/snapshots/prod-2026-09-30.json \
  --baseline eval/reports/<이전 리포트>.json --strict      # 실사용자 — 기준선 비교, 실패면 종료 코드 1
```

옵션: `--days <n>`(시뮬레이션 일수, 기본 7) · `--no-auto-expand`(서버 스위치 OFF로 평가) · `--out <디렉토리>`. 리포트는 JSON(전체)과 마크다운 요약(표준 출력)이며, 요약은 PR 본문에 그대로 붙인다.

CI: `eval-runner.spec.ts`가 PR마다 합성 카탈로그 위에서 불변식·hard 검사를 돌린다(`npm test`에 포함). 실사용자 스냅샷 평가는 사람이 돌린다 — 스냅샷이 저장소 밖이기 때문이다.
